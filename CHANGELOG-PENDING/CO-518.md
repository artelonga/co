## CO-518 — wave-review fixes: WhatsApp window/template fallback, retry-safe dedup, digest window param

Fixes from the wave review of the WhatsApp Cloud API + lead-digest work, each with a
contract/integration test on the ACTUAL request/response shape (closing the
lib-vs-integration gap where both sides of a cross-process contract were unit-tested
with fakes that re-encoded the bug).

### HIGH — CO-496 24h-window / template fallback was dead code
`is_window_open` / `send_template` / `build_template_payload` had no production
caller. Both business-initiated send paths now use it:
- OTP (`link_start_handler`) and birthday greetings (`birthday::send_greetings`) call
  the new `ChannelProvider::send_business_initiated`, which on the Cloud API falls
  back to a pre-approved **template** when the recipient is outside the 24h
  customer-service window (free-form text Meta would reject).
- Template name/lang are configurable via env (`CO_WHATSAPP_OTP_TEMPLATE` /
  `CO_WHATSAPP_BIRTHDAY_TEMPLATE`, `*_LANG`, default `pt_BR`). When the window is
  closed and no template is configured, the send is refused with an actionable
  error instead of silently sending text Meta rejects.
- Tests: pure `build_business_payload` shape assertions + a real local-server
  integration test asserting the bytes on the wire are a `template` outside the
  window and `text` inside it (`WHATSAPP_GRAPH_BASE` makes the send path
  redirectable for the capture server).

### MED — wamid dedup no longer poisons Meta retries
`event_handler` recorded the wamid as seen BEFORE `enqueue_inbound`, so a SHED
(queue-full) message stayed "seen" and Meta's retry of that dropped message was
deduped away and lost. The dedup is now split into a PEEK (`wamid_is_duplicate`)
and a RECORD (`record_wamid_seen`); the record happens only after a successful
enqueue. Test models the shed→retry sequence (retry is processed, not dropped).

### LOW — birthday job reuses the shared timed client
`run_birthday_job` built an untimed `reqwest::Client::new()` (a stuck send could
hang a worker forever); it now reuses `whatsapp_cloud_routes::shared_client()` (the
process-wide 30s-timed client).

### LOW — lead-digest accepts the bot's `window` param
`DigestQuery` only read `days`, but the bot (`co_tools.telemetry_digest`) sends
`window=7d`/`30d`, so the window was silently ignored. It now accepts `window`
(`"<n>d"` or a bare integer; `days` still works and wins when both are present).
Contract test deserializes the actual `universe=acme&window=30d` query string and
asserts a 30-day window.
