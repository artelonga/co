## CO-298 — CO-284-I — `co serve --staging` mode (latency + fault injection decorators)

Adds a `--staging` flag to `co serve` that wraps each trait-backed infra plug
with simulation decorators, turning a local instance into a staging environment
that behaves like production under realistic constraints.

### What changed

**New decorators in `co-web/src/infra/staging/`:**

- `LatencyInjectedStorage` — wraps any `Storage` impl, adds `latency_ms`
  delay before every storage call (uses `std::thread::sleep`; synchronous
  trait so blocking is intentional). Same latency is also injected at the HTTP
  layer via an axum middleware so lightweight endpoints like `/api/health` are
  also measurably slower.
- `FlakyBlobStore` — wraps any `BlobStore`, fails every `ceil(1/error_rate)`th
  call with a `"staging: simulated 503"` error. Deterministic counter (no rand).
- `EvictingCache` — wraps any `Cache<K,V>`, evicts just-inserted entries at the
  configured rate to simulate memory pressure. The server's `CacheLayer` is
  also periodically evicted via a background task.
- `RetryProneWorkerExecutor` — wraps any `WorkerExecutor`, makes
  `ceil(1/error_rate)` of `enqueue` calls fail to exercise retry paths.

**CLI additions:**

- `co serve --staging` — enables all four decorators.
- `co serve --staging-latency-ms <N>` — per-call and per-request delay (default 20ms).
- `co serve --staging-error-rate <R>` — fraction of ops that fail (default 0.05).

**Opt-out per plug (env vars):**

| Env var | Disables |
|---|---|
| `CO_STAGING_LATENCY=false` | `LatencyInjectedStorage` + HTTP middleware |
| `CO_STAGING_FAULT_INJECTION=false` | `FlakyBlobStore` |
| `CO_STAGING_EVICTION=false` | `EvictingCache` / CacheLayer eviction task |
| `CO_STAGING_WORKER_FAILURE=false` | `RetryProneWorkerExecutor` |

**Documentation:** `docs/staging.md` — quick start, flag reference, per-plug
descriptions, mix-and-match examples.

### Why

Local development against a well-behaved server masks latency-sensitive code
paths and missing retry logic. Staging mode surfaces these issues before
production: if your feature works correctly under simulated 503s and 50ms
latency, it is more likely to behave correctly in production.
