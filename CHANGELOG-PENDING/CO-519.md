## CO-519 — make the flaky co-agent retry test deterministic

`co-agent`'s `test_retry_then_drop_on_persistent_5xx` passed in isolation but
intermittently failed under `cargo test --workspace` parallel load, blocking
unrelated PRs (e.g. PR #321, a co-web-only change).

The test asserted exactly 2 retry attempts but read the server-side hit count
after a `start_paused` virtual-clock dance: it spawned the flush task, then ran a
fixed `tokio::time::advance(1s)` + `yield_now()` loop to skip the retry back-offs.
Under parallel scheduling the flush task could not yet be parked on its back-off
`sleep` when the `advance()` calls fired, so the advances were lost and the count
was read before the worker had settled — a timing race, not a real defect.

### Fix

The test now AWAITS the flush worker as its completion signal instead of guessing
via timing: `agent.flush().await` returns only after `ship_batch` has exhausted
all retries (with `max_retries = 2`: one real ~200-300 ms back-off, then drop), so
the attempt count is read from a provably settled state.

Virtual time was removed: simply awaiting `flush()` under `start_paused` also fails
deterministically, because tokio auto-advances the paused clock straight to
reqwest's request timeout and cancels the POST before it reaches the mock server
(observed count = 0). Using real time keeps the single short back-off sleep real
and makes `flush().await` an honest, race-free completion barrier.

### Verify

- `cargo test -p co-agent test_retry_then_drop_on_persistent_5xx` — 5/5 green.
- `cargo test --workspace` — full parallel run clean (0 failed).
- `cargo fmt`; `cargo clippy -p co-agent -- -D warnings` — clean.
