## CO-499 — Lead-temperature digest (output B) from raw web telemetry

A read-only analytics surface that turns `telemetry_events` into a cold/warm/hot
lead digest — the "lead-temperature" output of the input→síntese→3-outputs loop.
Per-subject *temperature* (recency + frequency + dwell), *trend*
(subindo/caindo/estável, window-over-window) and the *why* (top pages, return,
language, referrer).

- New `co-web/src/platform/lead_digest.rs`: pure `compute_digest` +
  `classify_temperature`/`classify_trend` (fully unit-tested, no server), plus
  `GET /api/v1/whatsapp/telemetry/digest`.
- The endpoint self-gates via `Scoped<TelemetryRead>` (`telemetry:read`, CO-448),
  mirroring `telemetry_api`: a full JWT/session passes, a least-privilege token
  carrying `telemetry:read` passes, anything else gets 403/401.
- No new schema and no new migration — every field is projected from the existing
  `telemetry_events` table (al_vid visitor token, linked `user_id`, dwell,
  referrer/language from `properties`).

### PRIVACY INVARIANT (LGPD)
Subjects are NAMED only when there is an identified/consented user identity
(`telemetry_events.user_id`, set after the CO-490 companion-app link via
`users.whatsapp` / a logged-in session). ANONYMOUS visitors (an `al_vid` token
with no linked identity) are reported ONLY inside an aggregate bucket
`{count, temperature_mix}` and are NEVER emitted as a nominal lead. This is a
hard partition in `compute_digest` with dedicated unit tests: an anonymous-only
dataset yields ZERO named subjects; a mixed dataset names only the identified
ones (an empty-string `user_id` is treated as anonymous).

### Why
The bot brain can quote *why* a lead is warming (which pages, return, language)
without ever turning anonymous telemetry into a nominal lead. Organizing the
digest is automatic; sending/publishing stays manual — the sacred boundary is
preserved (this endpoint never dispatches a WhatsApp message).
