## CO-556 — Complete EN values + PT/EN toggle switches strings AND content

The SPA language toggle now flips **both** the chrome strings and the page
content, end to end.

- **pt/en parity**: every `data-i18n` key now resolves in both languages. Filled
  the 10 missing English values (the `ygg.*` Yggdrasil-hub keys); pt and en maps
  are now identical key sets (392/392) with zero blank values.
- **Content switch on toggle**: `setLang(lang)` updates the chrome (existing
  `data-i18n` path) and then navigates content pages to their language
  counterpart — `/sobre` ↔ `/en/sobre`, `/template/sobre` ↔ `/template/en/sobre`.
  The board SPA (and any non-content path) is never redirected, and an already-
  correct URL is a no-op (no loop). Slug list mirrors
  `pretty_urls::TEMPLATE_SLUGS`.
- **Content URL is authoritative for the chrome language**: landing on
  `/en/sobre` shows English chrome regardless of the `co_lang2` cookie (and never
  bounces between twins at startup).
- Tests: `components/__tests__/i18n.test.ts` now loads the **real** `i18n.js` and
  asserts pt/en key parity, no blank values, the toggle→counterpart navigation,
  and that the board SPA is not redirected.

### Why
UI chrome alone is not a language switch — a reader on `/sobre` who toggles to
English expects the English page, not just English buttons. This is the
client-side half of the CO-555/CO-557 i18n surface; it reuses the existing
`data-i18n` mechanism rather than inventing a parallel one.

### Fix: language toggle no longer triggers a rate-limit popup burst
Toggling the language fired a burst of network requests that tripped the server
rate limiter (429) and stacked one "rate limit" error popup per failed request.
Two compounding causes, both fixed:

- **Refetch on a pure language switch.** The `co:langchange` handler called the
  full `render()`, which re-runs network-backed view renders (`renderConteudo`
  fires 6 `getUniverseEntries`; `renderUniverseHome`, calendar/dashboard/changelog/
  workspace/scrum all fetch on entry; kanban lazy-loads agent-session footers).
  A language change must only re-render from **existing cached state**. `render()`
  and `renderContent()` now take `{ refetch = true }`; the `co:langchange` handler
  passes `refetch:false`, which skips every network-backed render and `updateScrumTab()`
  while still re-rendering the cached-state views (kanban/table/timeline) so their
  JS-built strings retranslate. `renderKanban({ refetch })` also skips its
  fire-and-forget footer load. Result: a toggle makes **zero** network calls.
- **Double-fire per click.** Each language button did `setLang(...); render()` —
  but `setLang()` already dispatches `co:langchange`, whose handler re-renders.
  So one click produced two renders, the explicit one refetching. Removed the
  redundant explicit `render()`/`_render()` from all five lang toggles (header
  pill, mobile overflow, login modal, criar modal, onboarding banner); the single
  global `co:langchange` handler is now the only re-render path.
- **Defensive de-dupe.** `showToast()` now suppresses identical toasts (same
  type+message) within a 3 s window, so any future request burst can never stack
  many identical popups.

### Fix: board Conteúdo content now follows the language toggle
The `refetch:false` fix above (correctly) skips `renderConteudo()` on a toggle to
avoid its 6-entry fan-out — but on the **Conteúdo view** that left the displayed
content body (the landing/index entry) in the old language: the chrome flipped to
EN while the content stayed PT. The `co:langchange` handler now, when on the
Conteúdo view, re-renders **only the current entry** via a **single** fetch of its
language twin (`retranslateConteudoDetail`): `index.md` ↔ `en/index.md`,
`<slug>` ↔ `en/<slug>` (the CO-555 ingest mirror path). Switching to EN fetches the
`en/` twin; switching to PT strips the `en/` prefix. If the twin doesn't exist the
current content is kept gracefully — no error popup. The re-render is transient
(it never overwrites the persisted selection key), and it issues **at most one
`/api/` entry request per toggle** — never `refreshTasks()` or the 6-entry burst,
so the no-burst / rate-limit guarantee above still holds. An already-target-language
entry triggers **zero** requests.
