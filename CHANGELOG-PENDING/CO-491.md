## CO-491 — Deterministic, versioned WhatsApp consent (served verbatim)

Wires the consent/legal copy so the bot displays it **VERBATIM** and the LLM
never phrases, paraphrases, or translates legal text. The source of truth is the
existing `co-web/seed/legal/whatsapp-consent.v1.yaml` (a LEGAL ARTIFACT); only
`{operator}` is substituted.

### co-web — consent endpoint
- New `co-web/src/integrations/whatsapp_consent.rs`: `include_str!`s the YAML,
  parses it with `serde_yaml` (already a workspace dep), and exposes
  `GET /api/v1/whatsapp/consent?operator=<name>` returning
  `{version, agreement, boundary, how_it_works,
  commands{export, erase_confirm, erase_done, forget_done}, rights}` with
  `{operator}` substituted. Deterministic and **public-readable** (it *is* the
  consent text). Operator defaults to `CO_OPERATOR_NAME` (env) or `ArteLonga`.
  Route mounted at `/api/v1` next to the lead digest (no auth layer).
- `consent_version()` exposes the document `version`
  (`whatsapp-consent/2026-06-27.v1`).
- Unit tests: the pinned version string, `{operator}` substitution with no
  placeholder leaking in any field, all keys present/non-empty, and the default
  operator fallback.

### co-web — consent version threaded into the link flow
- `link/start` and `link/verify` now include `consent_version` in their JSON
  response and `tracing::info!` it (with the `user_id`), so the agreed version is
  known/auditable end-to-end (LGPD demonstrabilidade, Art. 8º §2º). The link
  prompt shows the versioned `agreement`; the user agrees by completing the OTP
  verify.

### bot (`tools/whatsapp-bot`) — deterministic consent pre-router
- `CoTools.consent(operator=None)` calls `GET /api/v1/whatsapp/consent` and
  returns the consent document unchanged.
- `BrainRouter.handle` gains a DETERMINISTIC pre-router that runs **before** the
  model/tool loop *and* before identity gating (consent & rights are pre-link):
  a pt-BR keyword match (`match_deterministic_intent`) maps an inbound message to
  one of `consent / privacy_boundary / how_it_works / show_my_data / erase_all /
  forget_me / my_rights`; the intent → consent-key mapping
  (`DEFAULT_DETERMINISTIC_INTENTS`, overridable per tenant via the profile's
  `deterministic_intents`) selects the field (e.g. `agreement`, `boundary`,
  `commands.export`), and the VERBATIM string is returned. The model is **never**
  invoked for legal/consent copy.
- Offline tests (`tests/test_consent_router.py`): each consent intent returns the
  exact verbatim text and the orchestrator is never called; an unlinked user
  still gets the verbatim rights text (not the link prompt); a normal message
  still reaches the model loop; the profile can override the mapping.

### Why
Consent and rights copy is a legal artifact: it must be reproducible exactly as
shown (LGPD demonstrabilidade) and never "warmed up" by a model. Serving it
verbatim from a single versioned source — and recording the version at link time
— gives a stable, auditable consent surface that every tenant shares.

### Durable per-user consent persistence (DONE)
The agreed consent version is now persisted durably per user, so it survives a
restart and is queryable for an LGPD request (demonstrabilidade, Art. 8º §2º) —
not only observable via the `link/verify` response field + log line.

- **Migration `v094`** (`co-web/src/storage/migrations/v094.rs`): additive,
  guarded, idempotent — adds three `users` columns:
  - `whatsapp_consent_version` — the agreed document version string.
  - `whatsapp_consent_at` — RFC 3339 timestamp of the agreement.
  - `whatsapp_consent_sha` — sha256 (hex) of the rendered `agreement` text for
    the operator, fingerprinting the exact copy agreed to. `LATEST_VERSION` → 94.
- **Storage helpers** (`co-web/src/storage/users.rs`):
  `set_whatsapp_consent(user_id, version, at, sha)` and a test getter
  `get_whatsapp_consent(user_id) -> Option<(version, at, sha)>`.
- **Consent module** (`whatsapp_consent.rs`): `current_version()` (the parsed
  document version) and `agreement_sha(operator)` (plain sha256 hex of the
  rendered agreement; `sha2` is already a workspace dep).
- **Recorded at link time** (`whatsapp_cloud_routes.rs::link_verify_handler`):
  after a successful link (number set + token minted), the handler writes the
  consent record under the same storage lock. Operator from `CO_OPERATOR_NAME`
  (same default the consent endpoint uses). **Best-effort**: a write failure is
  logged (`tracing::warn!`) but never fails the link — the user is already linked
  CO-side and the version is still logged.
- **Tests**: `fresh_db_reaches_latest_version` passes at 94; v094 idempotent on
  rerun + columns default NULL; `set_whatsapp_consent`→`get_whatsapp_consent`
  round-trip; `agreement_sha` is deterministic, 64-hex, and operator-sensitive;
  `current_version()` matches `consent_version()`.

#### v094 cross-branch coordination note
This branch's train tip was 93, so the migration claims `max + 1 = 94`. The
sibling branch `feat/CO-488` (birthday-consent columns) **also** defines a
`mod v094`. That overlap is intentional: claiming the **same** number (rather
than skipping to a `v095` gap) makes the conflict a **loud, compile-time
duplicate-`mod v094` error at merge** — forcing a clean renumber-to-`v095` of
whichever lands second, with both additive column sets applied in order. A
`v095` gap would instead be **prod-unsafe**: if this branch merged first and the
sibling later added `v094`, the guarded `current_version < 94` check would
**silently skip** the sibling's block on DBs already at 95. Loud-at-merge beats
silent-in-prod. (Full rationale in the `v094.rs` header.)
