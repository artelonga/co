## CO-497 — self-host transport cascade + deployment-mode invariant

The WhatsApp release is now self-hostable, not Cloud-only.

- Every WhatsApp send (OTP, reply, birthday greeting) routes through one shared
  `notification_providers::whatsapp_provider_cascade()`: the official **Cloud API**
  for managed/public deploys, else **Evolution** for self-host (QR-links your own
  WhatsApp, outbound-only — no Meta app and no public webhook, survives residential
  CGNAT). The birthday job's inline cascade was refactored onto the same helper.
- Previously `link/start` (OTP) and `reply_to` were hard-locked to the Cloud API, so
  a self-hoster on Evolution couldn't complete the per-user link.
- **Self-host hardening:** `EVOLUTION_API_URL` now defaults to `http://localhost:8080`
  (was the public Evolution SaaS) so a self-hoster's WhatsApp is never silently
  routed through a third party.
- Documented the two-mode invariant (`docs/whatsapp-launch.md` → Deployment modes):
  always self-hostable (your box, your data, encrypted, no third party) **or** opt
  into managed infra where any collection is consent-gated under its own versioned
  policy. Sensitive (whatsapp/secrets) and identifying (name/CPF) data stay on the
  instance by default.

### Why
Data autonomy requires the whole stack to run on the user's own machine with zero
third-party calls — confirmed end-to-end by the CO-497 audit. The cascade keeps the
code identical across self-host and managed modes.
