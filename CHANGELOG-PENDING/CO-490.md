## CO-490 — WhatsApp per-user account link (co-web side) + security hardening

Authenticated companion-app flow that links the caller's account to a WhatsApp
number so the bot can act *as that user* on inbound messages — now with
proof-of-possession, least-privilege tokens, token rotation, one-number-per-account
uniqueness, and authenticated loopback calls to the bot brain.

### Two-step proof-of-possession link (replaces the single-shot endpoint)

- `POST /api/v1/whatsapp/link/start` (auth) `{whatsapp}` — sends a **stateless
  8-digit OTP** to the number via the official WhatsApp Cloud API
  (`CloudApiProvider`), proving the caller controls it. The code is
  `first 8 decimal digits of HMAC-SHA256(secret, "<user_id>|<digits>|<floor(unix/300)>")`
  where `secret = CO_WHATSAPP_OTP_SECRET` or, when unset, `JWT_SECRET`. Returns
  `{sent:true}` — the code is **never** returned. `503` when the Cloud API isn't
  configured (cannot prove possession).
- `POST /api/v1/whatsapp/link/verify` (auth) `{whatsapp, code}` — recomputes the
  OTP for the current **and** previous 300s bucket and compares constant-time
  (`billing::constant_time_eq`). Mismatch → `401`. On match:
  - **Uniqueness**: if the (digit-normalized) number already belongs to a
    *different* user → `409` (new `Storage::get_user_id_by_whatsapp`).
  - Sets the caller's own `users.whatsapp` (digit-normalized).
  - **Revokes** the caller's prior `whatsapp-bot` tokens before minting
    (new `Storage::delete_api_tokens_by_name`).
  - Mints a **least-privilege** token (see below).
  - Best-effort pushes `{whatsapp, token, user_id}` to the bot identity ingest.
  - Returns `{linked:true}` — the token is **never** echoed.

The OTP digit-extraction, bucket math, and current/previous-window match are pure
helpers with unit tests (right code passes; wrong/different-user/different-number
fail; previous-bucket within window passes; two buckets later expires).

### #2 Least-privilege bot token

The link path now mints via `create_api_token_with_scopes` (CO-448) instead of
the owner-tier `create_api_token`. The bot token carries **exactly** three
capabilities: `entries:read`, `entries:write`, `universes:read`. It explicitly
excludes `universes:write`, every admin surface (`gestao:read`, `funnel:read`,
`chat:read`, `chat:write`, `deployments:read`), and `agent:dispatch`. There is no
token-management capability in the vocabulary, so a leaked bot token can never
mint or revoke tokens.

### #1 In-app per-user forwarding

`POST /api/v1/bot/chat` (`bot_proxy_routes`) now forwards the authenticated
`user_id` in the JSON it posts to the brain (keeps `sender:"app"`), so the bot
acts as that user. The identity push (#3e) likewise carries `user_id` so the bot
can key identities by it.

### #5 Loopback secret on brain calls

Both `bot_proxy_routes` (→ bot `/api/chat`) and `whatsapp_cloud_routes`
`fetch_brain_reply` (→ `CO_BOT_BRAIN_URL`) now send `X-Bot-Secret =
CO_BOT_SHARED_SECRET` when set, so the bot can authenticate co-web. The header
set is built by a pure helper (`brain_auth_header`) with a unit test: present
when the secret is set, absent when unset/empty.

### Residual-findings review follow-up (R1–R4)

Closing four findings from the CO-490 per-user-access security review:

- **R1 (MEDIUM — privilege escalation, bot side).** The bot routed
  `sender=="system"` to the shared `CO_TOKEN` service identity based on the
  attacker-controllable `/api/chat` JSON alone, and `/api/chat` fails *open* when
  `CO_BOT_SHARED_SECRET` is unset. The service identity is now selectable **only**
  when the request was authenticated by a matching `X-Bot-Secret`: `main.py`
  threads an `authorized` flag (new strict `system_authorized()` — True only when
  the secret is **set** and matches) into `BrainRouter.handle`, which honors
  `sender=="system"` → service identity **only** when `authorized` is True. With
  the secret unset the service-identity path is disabled; an unauthorized "system"
  request falls through to per-user resolution and then the read-only concierge.
- **R2 (MEDIUM — uniqueness bypass, co-web).** `social::birthday::consent_handler`
  stored `users.whatsapp` un-normalized, defeating the digit-exact uniqueness
  check (`Storage::get_user_id_by_whatsapp`). It now normalizes via the **same**
  helper the link flow uses (`whatsapp_cloud_routes::validate_whatsapp`) before
  storing, so a number captured at birthday-consent matches the link-flow form.
- **R3 (MEDIUM — OTP brute force, co-web).** The stateless OTP is widened from 6
  to **8 decimal digits** (10^8 keyspace within the 5-minute window); the OTP is
  computed and verified entirely in co-web, so this is a single-place change to
  the pure helper + its unit tests.
- **R4 (LOW — accepted residual).** `POST /whatsapp/link/start` sends a WhatsApp
  message to a caller-supplied number capped only by the global write
  rate-limit; there is no per-number / per-account send cooldown, so an
  authenticated caller could enumerate `link/start` to have CO deliver verification
  messages to arbitrary numbers (bounded by the global limiter and the Cloud API
  quota). Accepted for now; a per-number/per-account cooldown is a tracked
  follow-up.

### Why

Lets a logged-in user bind their WhatsApp number to their CO identity with proof
of possession, so the bot's BrainRouter resolves an inbound sender → that user's
*scoped* token and CO's permission model scopes every read/write. A leaked bot
token, identity push, or loopback call now grants far less and is authenticated.
Implemented with **no schema migration** (another branch claims v094) — uniqueness
and rotation are app-level checks over the existing `users.whatsapp` column.

## CO-489 — tier-2 scalability hardening of the WhatsApp inbound reply path

Closes the three HIGH findings from the scalability review of the Meta-webhook
reply path. No schema migration; in-memory + env-only.

- **Shared, timed HTTP client.** `reply_to` / `fetch_brain_reply` and
  `bot_proxy_routes::chat_handler` (and `link/start`) built a fresh
  `reqwest::Client::new()` per message with **no timeout**, so a stuck brain hop
  leaked the task forever and skipped connection pooling. Replaced with ONE
  process-wide `OnceLock<reqwest::Client>` (`whatsapp_cloud_routes::shared_client`)
  built once with an explicit 30s timeout (mirrors `webhook_worker`), reused for
  the brain hop, the Cloud API send, and the `bot_proxy` chat hop.
- **Bounded reply concurrency.** `event_handler` spawned an **unbounded**
  reply task per inbound message fronting a single local model. Each spawned
  reply now acquires a permit from a process-wide
  `OnceLock<Arc<tokio::sync::Semaphore>>` before the brain hop and releases it on
  completion, capping in-flight brain hops. Size comes from
  `CO_WHATSAPP_REPLY_CONCURRENCY` (default 4; non-numeric/empty/zero → default).
  The fast-200 ack and fixed fallback reply are unchanged — over-cap tasks wait
  their turn rather than being dropped or spawned unboundedly.
- **`wamid` idempotency / dedup.** Meta is at-least-once and retries; a
  redelivery used to re-run the brain and double-send. `parse_inbound` now
  carries the message id (`InboundMsg.wamid`), and before dispatch each wamid is
  checked against a short-TTL (5 min) in-memory seen-set
  (`OnceLock<Mutex<HashMap<String, Instant>>>`, pruned opportunistically);
  already-seen wamids are skipped. The decision is a pure helper
  (`dedup_decision`) unit-tested for first-seen vs repeat-within-TTL vs expired.

`parse_inbound` stays pure and unit-tested (now also asserts the carried wamid);
new unit tests cover the dedup helper, the env-parsed concurrency default, and
that the shared client is built once.

### Why

The inbound reply path was the platform's only unbounded fan-out fronting a
single local model with no timeouts and no redelivery guard — a burst, a hung
model, or Meta's retries could leak tasks, double-reply users, and starve the
runtime. These three bounds (timeout, semaphore, dedup) make it tier-2 safe.
