## CO-496 — Tier-3 scalability hardening

Pushes the platform past the tier-2 envelope on the paths that bind under load:

- **meta.db concurrent read pool** (`storage/read_pool.rs`, `MetaReadPool` in `server/state`): the auth hot path (token lookup → owner-tier check) now reads users/ownership rows off a concurrent read pool instead of serializing the whole auth path behind the global write `Mutex<Storage>`.
- **Ingress shedding** (`integrations/whatsapp_cloud_routes.rs`): the inbound webhook replaced its unbounded `spawn`-per-message with a **bounded mpsc + fixed worker pool** — under a flood/redelivery storm it sheds (drops + logs) when the queue is full, so parked-task memory is hard-bounded by `workers + queue_capacity` (Meta already has its 200; a shed message is simply not answered).
- **Cloud API at scale** (`social/notification_providers.rs`): tracks Meta's 24-hour customer-service window (free-form text vs template fallback) per recipient and computes a polite `429`/`Retry-After` backoff so the number isn't throttled harder.
- **fd-limit raise** (`platform/fd_limit.rs`): lifts the file-descriptor soft limit at boot (more concurrent connections/pool handles).
- **v095** migration: indexes backing the read-pool hot paths.

### Why
Tier-2 (CO-489) bounded in-flight work but left unbounded parked tasks and a single
write-locked auth path. Tier-3 makes degradation graceful under real load.
