## As
Yuri operando co-auto em várias máquinas e deployments, QUERO uma visão
centralizada em tempo real — projetos, quadros, launchers ativos e consumo de
tokens — PARA priorizar onde gastar a janela de inferência (opus/fable vs
sonnet/haiku) com dados, não intuição.

## Escopo

### 1. Ingestão (API + DB)
- [ ] Migration nova: tabela `agent_sessions` (id, task_key, universe_key,
      machine, model, tokens_in, tokens_out, tokens_cache_read,
      tokens_cache_write, cost_usd NULL, started_at, ended_at, outcome,
      reported_at). Sem `.ok()` engolindo SELECT em coluna nova.
- [ ] `POST /api/v1/usage/sessions` (token auth, mesmo esquema do vault/sync):
      valida e insere; publica `DomainEvent` → `AnalyticsEvent` no
      `AnalyticsBuffer` (platform/observability.rs) — o dashboard recebe via
      broadcast existente, **sem polling**.
- [ ] `POST /api/v1/usage/heartbeat`: launcher registra sessão ativa
      `{task_key, universe_key, machine, model, started_at}` no início e push
      de progresso; TTL em memória (WorkerInfo) — sessão some do painel se o
      heartbeat parar (crash de máquina), sem precisar de DELETE.

### 2. Consulta
- [ ] `GET /api/v1/usage/summary?window=5h|day|week&by=universe|model|machine|task`
      — agregados para o dashboard e para a política de downshift (CO-427).
- [ ] `GET /api/v1/usage/active` — launchers ativos agora.

### 3. Dashboard (Gestão, admin-only)
- [ ] Painel `usage` na área Gestão: (a) launchers ativos (máquina, task,
      universo, modelo, há quanto tempo); (b) usage por universo/quadro com
      drill-down por task; (c) por modelo (quanto foi haiku/sonnet/opus/fable);
      (d) janela corrente: tokens nas últimas 5h e na semana, com barra de
      consumo. Atualização em tempo real via stream já existente do
      AnalyticsBuffer (SSE/broadcast) — nunca setInterval+fetch.
- [ ] Visão "projetos": linha por universo com quadro, tasks todo/in_progress,
      último deploy e usage acumulado — a visão centralizada da frota.

## Acceptance Criteria (gerais)
- [ ] Workers/subscribers novos não dão panic segurando `Mutex<Storage>`.
- [ ] Testes de integração das 4 rotas (tower::ServiceExt, sem porta real).
- [ ] openapi.yaml regenerado E `api-catalog.md` atualizado no mesmo PR.
- [ ] Nenhum mapeamento universo→máquina/repo hardcoded — tudo vem do DB ou
      do payload.

## Notas
- Limites exatos da assinatura (janela 5h/semana) não são expostos por API da
  Anthropic; o painel mostra **consumo observado** e marcos configuráveis
  (env/config `CO_USAGE_SOFT_LIMIT_*`), não "restante oficial".
- Backfill histórico: reaproveitar a lógica do `co-mine-claude-sessions.py`
  fica FORA deste escopo (task futura se necessário).
