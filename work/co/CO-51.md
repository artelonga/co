GIVEN the Vault REST API (CO-35) provides file CRUD and the user wants Google Drive-like local editing,
WHEN I implement `co sync` commands with proper conflict resolution,
THEN:

## Commands

```bash
co login                    # Authenticate via email code, store API token in ~/.co/token
co sync pull <universe>     # Download all entries to ~/Co/<universe>/
co sync push <universe>     # Upload changed local files
co sync watch <universe>    # Watch for local changes, auto-push (debounced 2s)
co sync status <universe>   # Show diff: new/modified/deleted local vs remote
co sync resolve <file>      # Manually resolve a conflict
```

## Sync Protocol

```
1. Read ~/.co/universes/<slug>/sync.json → { files: { path: { hash, mtime, remote_hash } } }
2. GET /api/v1/universes/:slug/vault/notes → remote file list with hashes
3. Diff:
   a. Local hash == remote hash → NO CHANGE
   b. Local hash != sync.json hash AND remote hash == sync.json hash → LOCAL CHANGED → push
   c. Local hash == sync.json hash AND remote hash != sync.json hash → REMOTE CHANGED → pull
   d. Local hash != sync.json hash AND remote hash != sync.json hash → CONFLICT
4. Execute:
   - Push: PUT /api/v1/universes/:slug/vault/notes { path, content }
   - Pull: GET /api/v1/universes/:slug/vault/read?path=... → write to local file
   - Conflict: apply strategy (see below)
5. Update sync.json with new hashes
```

## Conflict Resolution

### When two users edit the same file

**Detection:** Both local and remote hashes differ from the last known sync hash.

**Strategies (configurable in ~/.co/config.yaml):**

| Strategy | Behavior | When to use |
|----------|----------|-------------|
| `last-write-wins` (default) | Newer `modified` timestamp wins | Solo editing, low risk |
| `local-wins` | Always keep local version | Offline-first workflow |
| `remote-wins` | Always keep remote version | Read-mostly workflow |
| `manual` | Save both as `.local` and `.remote`, prompt user | Collaborative editing |
| `merge` | Line-level 3-way merge (using sync.json's base version) | Advanced users |

### Worst-case scenario: merge conflict

```
1. Alice edits content/sobre.md locally (changes paragraph 2)
2. Bob edits content/sobre.md on web (changes paragraph 5)
3. Alice runs `co sync push` → CONFLICT detected
4. Strategy = manual:
   a. Save Alice's version as content/sobre.md.local
   b. Save Bob's version as content/sobre.md.remote
   c. Save base (last sync) as content/sobre.md.base
   d. Print: "CONFLICT: content/sobre.md — resolve with `co sync resolve content/sobre.md`"
5. Alice runs `co sync resolve content/sobre.md`:
   a. Opens diff view (terminal or $EDITOR)
   b. Alice merges manually
   c. Saves resolved version → pushes to remote
   d. Cleans up .local/.remote/.base files
```

### Strategy = merge (automatic):
```
1. CONFLICT detected
2. Load base version (from sync.json snapshot or GET with old hash)
3. 3-way merge: base + local + remote → merged
4. If merge succeeds (no overlapping changes) → auto-push merged version
5. If merge fails (overlapping hunks) → fall back to `manual` strategy
```

### Idempotency guarantees

- [ ] Running `co sync pull` twice produces same result (no duplicates)
- [ ] Running `co sync push` with no local changes is a no-op
- [ ] Running `co sync push` during `co sync push` is safe (lockfile)
- [ ] Server-side: PUT with same content + hash is idempotent (no new version created)
- [ ] Crash during sync → next sync recovers (sync.json only updated after successful ops)
