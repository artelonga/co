## As

a user with CO open in another tab (or recently closed it)

## I Need

browser push notifications for new DMs, mentions, and invitations,
so I see them without the tab being focused

## So That

DMs and invitations reach me in real time without me having to keep
the tab in foreground or check email.

---

## Precondition

CO-199 must be live. This ticket adds the Push delivery channel
alongside the email channel (CO-200).

## Architecture overview

Standard W3C Web Push:

1. Service worker (`push-sw.js`) registers and subscribes to Push
   Manager with the VAPID public key.
2. Browser returns a subscription endpoint (Mozilla autopush / Apple /
   Google FCM) + p256dh + auth keys.
3. Frontend POSTs the subscription to `/api/v1/me/push-subscriptions`
   which stores it server-side.
4. When CO-199 creates a notification AND user prefs allow push AND
   it's not quiet hours, a worker sends a push payload to each of the
   user's subscription endpoints.
5. The service worker receives the push event, shows a system
   notification, and on click navigates to the relevant CO page.

## Schema

```sql
CREATE TABLE IF NOT EXISTS push_subscriptions (
    id              TEXT PRIMARY KEY,        -- pushsub_xxxxx
    user_id         TEXT NOT NULL,
    endpoint        TEXT NOT NULL UNIQUE,    -- the push service URL
    p256dh          TEXT NOT NULL,           -- public key
    auth            TEXT NOT NULL,           -- auth secret
    user_agent      TEXT,                    -- "Mozilla/5.0 ..." for diagnostics
    created_at      TEXT NOT NULL,
    last_success_at TEXT,
    failure_count   INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX IF NOT EXISTS idx_push_subscriptions_user
    ON push_subscriptions(user_id);
```

Subscriptions with `failure_count >= 5` are pruned by a daily cleanup
task (Apple/Mozilla revoke endpoints when the user uninstalls the
browser; we get 410 Gone responses).

## VAPID keys

Generated once during deployment, stored as Fly secrets:

```bash
flyctl secrets set \
    VAPID_PUBLIC_KEY="..." \
    VAPID_PRIVATE_KEY="..." \
    VAPID_SUBJECT="mailto:yuri@artelonga.com.br" \
    -a co-artelonga
```

Generate locally with the `web-push` crate or `openssl ecparam`:

```bash
openssl ecparam -genkey -name prime256v1 -noout -out vapid_private.pem
openssl ec -in vapid_private.pem -pubout -out vapid_public.pem
```

`VAPID_PUBLIC_KEY` is exposed to the frontend via `GET
/api/v1/notifications/vapid-public-key` (anonymous) so the SW can
subscribe.

## Endpoints

### `GET /api/v1/notifications/vapid-public-key` (anonymous)

Returns the base64url-encoded public key. No auth required since it's
truly public.

```jsonc
{ "key": "BLxC..." }
```

### `POST /api/v1/me/push-subscriptions` (auth)

```jsonc
// Request
{
  "endpoint": "https://updates.push.services.mozilla.com/...",
  "p256dh": "...",
  "auth": "...",
  "user_agent": "Mozilla/5.0 ..."
}
```

Upsert by `(user_id, endpoint)`. Returns 201 with the new subscription
id. Idempotent for the same endpoint.

### `DELETE /api/v1/me/push-subscriptions/:id` (auth)

Remove a specific subscription (e.g., user toggles off push on this
device).

### `GET /api/v1/me/push-subscriptions` (auth)

List the caller's current subscriptions (for the "registered devices"
UI):

```jsonc
{
  "subscriptions": [
    { "id": "pushsub_abc", "user_agent": "Chrome 142 Mac", "created_at": "..." }
  ]
}
```

## Service worker

`co-web/static/variants/a/push-sw.js`:

```js
self.addEventListener('push', (event) => {
    const payload = event.data ? event.data.json() : {};
    const title = payload.title || 'CO';
    const options = {
        body: payload.body,
        icon: '/static/icon-192.png',
        badge: '/static/badge-72.png',
        data: { url: payload.url },
        tag: payload.tag,          // e.g. "dm-room_xyz" — coalesces multiple notifs from same thread
        renotify: false,
    };
    event.waitUntil(self.registration.showNotification(title, options));
});

self.addEventListener('notificationclick', (event) => {
    event.notification.close();
    const url = event.notification.data?.url || '/';
    event.waitUntil(clients.matchAll({ type: 'window' }).then((clientList) => {
        for (const client of clientList) {
            if (client.url.endsWith(url) && 'focus' in client) return client.focus();
        }
        if (clients.openWindow) return clients.openWindow(url);
    }));
});
```

## Frontend module

`co-web/static/variants/a/modules/push.js`:

```js
export async function setupPushNotifications() {
    if (!('serviceWorker' in navigator) || !('PushManager' in window)) return;
    const reg = await navigator.serviceWorker.register('/push-sw.js');
    return reg;
}

export async function subscribeToPush() {
    const permission = await Notification.requestPermission();
    if (permission !== 'granted') return null;
    const reg = await navigator.serviceWorker.ready;
    const vapidResp = await fetch('/api/v1/notifications/vapid-public-key');
    const { key } = await vapidResp.json();
    const sub = await reg.pushManager.subscribe({
        userVisibleOnly: true,
        applicationServerKey: urlBase64ToUint8Array(key),
    });
    await apiFetch('/api/v1/me/push-subscriptions', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            endpoint: sub.endpoint,
            p256dh: btoa(...),  // sub.getKey('p256dh')
            auth: btoa(...),     // sub.getKey('auth')
            user_agent: navigator.userAgent.slice(0, 256),
        }),
    }, true);
}
```

A "Ativar notificações" button in settings calls `subscribeToPush`.
If browser doesn't support push or user declines permission, button
remains in the off state with explanatory hint.

## Push delivery worker

Background task spawned at startup, similar to CO-200's email worker:

```rust
tokio::spawn(crate::notification_push_worker::run(Arc::clone(&state)));
```

Tick every 10 seconds (push is more time-sensitive than email digests):

1. Find users with unread notifications and `push_*=1` for the event types
2. For each such user, list their push subscriptions
3. Encrypt payload with the subscription's p256dh + auth keys (use the
   `web-push` crate)
4. POST to each subscription endpoint with VAPID-signed Auth header
5. On 201/202: success — mark `delivered_push_at` on the notif
6. On 410 Gone: subscription is dead, delete it
7. On 5xx: bump `failure_count`, retry next tick; if >= 5, mark dead

## Crate

Add `web-push = "0.10"` to `co-web/Cargo.toml`. Pure-Rust, no native
deps.

## Notification payload

Keep it small — most push services cap at 4KB encrypted:

```jsonc
{
  "title": "Maria",
  "body": "te enviou uma mensagem",
  "url": "/?dm=room_dm_xyz#msg-abc",
  "tag": "dm-room_dm_xyz"
}
```

The tag value coalesces multiple notifs from the same thread, so
3 quick DMs show as one growing notification, not three separate ones.

## Out of scope

- **Native iOS / Android apps push** (APNs / FCM directly). Web Push
  is the v1 channel. Native is CO-N+.
- **Rich notifications** (images, action buttons). System notification
  with title + body is enough for v1.
- **Notification batching at the push layer** ("5 new from Maria").
  The `tag` field handles this declaratively per-thread.
- **Real-time presence in service worker** — when tab is closed.
