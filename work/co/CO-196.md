## As

a chat user (any role)

## I Need

to edit my own messages, delete my own messages, and — if I'm an
owner or admin of the universe — delete anyone's messages

## So That

- typos and embarrassing first drafts are recoverable
- spam, abuse, or accidentally-private content can be removed by space
  stewards without DB surgery
- the soft-delete tombstones from CO-193 actually get exercised

---

## Precondition

CO-193 (REST + soft-delete column) and CO-194 (WebSocket broadcast)

## REST endpoints

### `PATCH /api/v1/universes/:slug/chat/rooms/:room_slug/messages/:msg_id` (auth)

Body:
```jsonc
{ "body": "edited text" }
```

Authorization: caller must be `author_id` of the message **and** the
message must not be soft-deleted **and** the message must be within
the **edit window** (15 minutes from `created_at`).

After the edit window, edits return 403 with `edit_window_expired`.
Rationale: prevents revisionism. 15 min is enough for typo fixes,
short enough that the history is honest.

Side effects:
- `body` replaced.
- `edited_at` set to `now()`.
- WS broadcasts `message.edited` with the full updated message.

Validation: same as POST — non-empty, ≤4000 chars. 400 on violation.

### `DELETE /api/v1/universes/:slug/chat/rooms/:room_slug/messages/:msg_id` (auth)

Soft delete. Authorization:
- Caller is `author_id` → can always delete (no edit window for delete).
- Caller is `owner` or `admin` of the universe → can delete any
  message in any room of that universe.
- All other cases → 403.

Side effects:
- `deleted_at` set to `now()`.
- `body` preserved in DB for audit but **never returned to clients**
  after deletion. GET handlers + WS broadcasts substitute the
  i18n tombstone `[mensagem removida]`.
- WS broadcasts `message.deleted` with `{message_id, deleted_at}`.

Deleting an already-deleted message: 410 (gone).

## Storage helpers (extending CO-193's `storage/chat.rs`)

```rust
impl Storage {
    pub fn edit_chat_message(
        &self,
        message_id: &str,
        author_id: &str,         // caller — must match stored author_id
        new_body: &str,
        edit_window: chrono::Duration,
    ) -> Result<ChatMessageWithAuthor, EditError>;

    pub fn delete_chat_message(
        &self,
        message_id: &str,
        caller_id: &str,
        caller_can_moderate: bool, // owner/admin
    ) -> Result<DateTime<Utc>, DeleteError>;
}

pub enum EditError { NotFound, NotAuthor, AlreadyDeleted, EditWindowExpired, BodyTooLong, BodyEmpty, Db(rusqlite::Error) }
pub enum DeleteError { NotFound, NotAuthorAndNotMod, AlreadyDeleted, Db(rusqlite::Error) }
```

Map to HTTP via the existing `AppError` shape: 403 / 404 / 410 / 400.

## WebSocket events (extending CO-194's `ChatEvent` enum)

Already declared in CO-194 spec:

```jsonc
{ "type": "message.edited",  "message": { /* with edited_at populated */ } }
{ "type": "message.deleted", "message_id": "msg_xyz", "deleted_at": "..." }
```

CO-196 wires the REST PATCH and DELETE handlers to fire these events
on the room's broadcast channel, same `tx.send(...)` pattern CO-194
established for `message.created`.

## UI affordances (extending CO-195's `modules/chat.js`)

### Hover state on each message

```
┌────────────────────────────────────────┐
│ Yuri · há 5 min                         │
│   Olá pessoal!                           │
│                                          │
│                       [✏️ editar] [🗑️] │   ← on hover
└────────────────────────────────────────┘
```

Affordance visibility rules:
- ✏️ editar: visible iff `message.author.user_id === me.user_id` AND
  not deleted AND within 15 min of `created_at`. Hidden otherwise.
- 🗑️ deletar: visible iff (`author_id === me` OR `my_role ∈ {owner, admin}`)
  AND not already deleted.

### Edit flow

Clicking ✏️ swaps the body into an inline `<textarea>` pre-filled with
the current body. `Enter` submits the PATCH; `Esc` cancels.

While editing, an Enviar / Cancelar pair appears below the textarea.
On success the WS `message.edited` echo confirms and the textarea
reverts to read-only with a subtle "(editado)" tag next to the
timestamp.

### Delete flow

Clicking 🗑️ shows a confirm popover ("Apagar esta mensagem?") with
`Apagar` / `Cancelar`. On `Apagar`, fire DELETE. Optimistic UI: the
message flips to tombstone state immediately; rollback if the request
errors.

### Tombstone rendering

```
[mensagem removida]
```

Italic, 50% opacity, no avatar. Click → nothing. The original body
is gone from the client; only the timestamp + the author chip remain.

Mod-deleted vs self-deleted are visually identical for v1. (A future
ticket could add "(removida por moderação)" for transparency.)

## Acceptance — REST

- [ ] PATCH within edit window by author → 200, `edited_at` set,
      `message.edited` broadcast.
- [ ] PATCH outside edit window → 403 `edit_window_expired`.
- [ ] PATCH by non-author → 403.
- [ ] PATCH with empty body → 400.
- [ ] PATCH on deleted message → 410.
- [ ] DELETE by author → 200, `deleted_at` set, `message.deleted`
      broadcast, future GETs show tombstone.
- [ ] DELETE by owner/admin of someone else's message → 200.
- [ ] DELETE by non-author non-mod → 403.
- [ ] DELETE on already-deleted → 410.

## Acceptance — UI

- [ ] Own messages show ✏️ on hover within 15 min, hidden after.
- [ ] Owner/admin sees 🗑️ on every message; member sees 🗑️ only on
      own messages; viewer/subscriber sees no moderation affordances.
- [ ] Edit inline-textarea flow works; Enter submits, Esc cancels.
- [ ] Delete confirm popover; optimistic tombstone with rollback on
      error.
- [ ] Subtle "(editado)" tag rendered after successful edit.
- [ ] Live updates from other clients render the same way (other
      tabs see the edit/delete reflected).
- [ ] i18n strings PT + EN.

## Out of scope

- **"Removida por moderação" attribution** (vs self-delete). Audit
  table reserved for future ticket.
- **Restore deleted message** (un-delete). Soft delete is one-way for v1.
- **Reactions, pins, stars.** Different tickets.
- **Edit history** (showing past versions). Body is overwritten, no
  versioning.
- **Bulk delete** (delete all of user X's messages). Manual one-at-a-
  time for v1.
