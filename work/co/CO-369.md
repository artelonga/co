## As
A platform operator wanting to see CO's actual history as if it had been scrum-managed all along

## I Need
A one-shot script + generated documentation that walks `git log` + CHANGELOG.md + `work/co/CO-*.md` and reconstructs the past N months of CO work as bi-weekly sprints, with PBIs mapped to merged PRs, Sprint Increments mapped to release tags, and DoD checklists derived from each spec's acceptance criteria.

## So That
- We have an honest historical view of "what we built per sprint" without needing future scrum discipline to back-fill anything.
- The sprint calendar (CO-372) has past sprints to render alongside the next 4 future ones.
- The retrospective process has data — past velocity, common slippage patterns, DoD completion rates — measurable from day one.
- ArteLonga's `scrum.md` thesis becomes empirically grounded: "CO has been shipping in sprint-like cadence already; here's the evidence."

## Context

CO has been shipping continuously since v0.1 with ad-hoc release cycles (~2-5 days apart, no fixed cadence). The bi-weekly Thursday 15:00 BRT cadence (from CO-368's `_scrum.yaml`) starts going forward. This spec back-fills retrospectively.

Starting anchor: **2026-06-11 15:00 BRT** = Sprint 1's review/release moment going forward. Working backwards in 14-day windows:
- Sprint 0 (current) = 2026-05-29 → 2026-06-11
- Sprint -1 = 2026-05-15 → 2026-05-28
- ...

## Design

### Reconstruction script

New file `scripts/scrum/retro-simulate.ts` (Node + tsx, matches CO-350's stack):

```typescript
type Sprint = {
  number: number;           // negative for retrospective, positive going forward
  start_at: string;         // ISO
  end_at: string;
  release_tags: string[];   // v2.39.0, v2.38.0, etc — any that closed in this window
  pbis: Pbi[];
};

type Pbi = {
  id: string;               // CO-279, CO-211, etc
  title: string;
  status: 'done' | 'partial' | 'carried-over';
  merged_pr: number | null;
  merged_at: string | null;
  spec_file: string;        // work/co/CO-279.md
  acceptance_checks: { text: string; checked: boolean }[];
  release_tag: string | null;
};
```

Algorithm:
1. Read all `work/co/CO-*.md` → spec catalog (title, acceptance criteria parsed from `- [ ]` and `- [x]`)
2. Walk `git log --first-parent main --merges` → merge commits, extract PR numbers + dates
3. Walk `git tag --list 'v*'` → release tags + dates
4. For each merge commit, find the CO-N tag in the PR title or body
5. Bucket merges into 14-day windows ending Thursday 15:00 BRT
6. A merge in window W = a PBI delivered in Sprint(W)
7. A release tag in window W = the Sprint Increment for Sprint(W)
8. Acceptance criteria → DoD checklist; check off the boxes that were actually `[x]` in the spec at merge time (heuristic: spec's last commit before the merge)
9. Compute velocity (PBIs/sprint, story points/sprint if specs have `points:`)

### Generated outputs

```
docs/scrum/
├── retro-simulation.md           — narrative overview + cadence math
├── retro-velocity.md             — velocity chart per sprint
├── sprints/
│   ├── sprint-minus-12.md        — earliest reconstructed
│   ├── ...
│   ├── sprint-minus-1.md         — last completed
│   ├── sprint-0.md               — current (in-flight as of run date)
│   └── _index.json               — machine-readable sprint catalog
└── retro-anomalies.md            — patterns flagged (PBIs without specs, releases without merges, etc.)
```

Each `sprint-N.md` mirrors the format CO-372 will render at `/scrum/sprints/N`:

```markdown
# Sprint -1 (2026-05-22 → 2026-06-04)

**Sprint Goal**: (retrospective — inferred from PBIs)
**Release**: v2.39.0 (2026-06-04)
**Velocity**: 6 PBIs delivered

## Delivered PBIs

### CO-211 — Universe Content API v1 spec + Swagger UI
- [x] OpenAPI 3.1 spec served at /api/v1/openapi.json
- [x] Swagger UI at /api/v1/docs
- [x] All entries routes documented
- ...

### CO-280 — Universe vs sub-universe vs deployable-unit
- ...

## Carried over
- (none)
```

### Spec-extraction heuristics

- A spec is a PBI if it has frontmatter `id: N` and `type: user-story | task`
- DoD = the `## Acceptance` checklist (CO's existing convention)
- "Delivered" = spec status is `done` AND the merge commit lands in the sprint window
- "Carried over" = spec status is in_progress at sprint end (uses spec's `updated_at`)
- "Partial" = some acceptance boxes unchecked at merge

### Future sprints (going forward)

Same script can run in `--forward` mode to generate `sprint-1.md` … `sprint-N.md` (empty templates) with the predicted release date, ready for CO-372's calendar.

### Idempotency

Script is idempotent — running twice on the same state produces identical output. CI hook (optional): run nightly, commit changes if `git diff docs/scrum/sprints/` is non-empty. Defer hook to CO-369-B.
