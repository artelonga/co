## What this slice does

Extracts a `Storage` trait in `co-web/src/infra/storage.rs` and makes the existing rusqlite-backed code an implementation of it. No behavior change; foundation for every later CO-284 sub-story.

## ⚠ Reopened 2026-05-25 — e2e fixture auth regression

The first two attempts (commits `fc4979f` + `7b3fefe` on branch `feat/CO-290-co-284-a-storage-trait-abstraction-sqlit`) ship the trait correctly and pass the 682 lib tests. **But the e2e suite fails 165/317** with this dominant pattern:

```
co-web/e2e/fixtures.ts:46
const res = await apiContext.post("/api/projects", { data: project });
expect(res.status()).toBe(201);

Expected: 201
Received: 401
```

The 401 cascades into 16 test files (board-drag, board-ux, changelog-viewer, co-landing, codemirror, integration, pipeline-workflow, recursive-universe, responsive, seed-links, smoke, subtask-tree, theme-coverage, theme, uat-flow, universe).

### What this means (precise diagnosis)

The e2e fixture signs JWTs locally using some test secret, then POSTs to a spawned test server. The server validates with its own `JwtKey` loaded from env. **The two no longer match** because CO-290's `CoreState::from_storage()` constructor refactor changed when/how `JwtKey::load_or_generate()` is initialized in the test server boot path, OR the e2e fixture's JWT_SECRET env var setup happens to occur after `JwtKey` has already cached a different value.

### Required actions before re-marking done

1. **Read `co-web/e2e/fixtures.ts` end-to-end.** Find where it signs tokens — what JWT secret value does it use? Where does it set `JWT_SECRET` env var for the spawned server?

2. **Read `co-web/src/auth/mod.rs`** — find `JwtKey::load_or_generate()`. Trace which env vars it reads and at what boot point. Trace the seam where CO-290's refactor changed initialization timing.

3. **Read the e2e server-spawn code** (likely in `co-web/e2e/playwright.config.ts` or a similar bootstrap) — find where `cargo run` or the binary is launched and which env vars are set on its environment.

4. **Make the JWT secret consistent across fixture-sign + server-verify**. The fixture must sign with a value that matches what the server reads from env at boot. Two ways to fix:
   - (a) Hardcode both to the same literal (e.g. `"e2e-test-secret"`) in fixture + in the playwright config's `webServer.env`
   - (b) Have the fixture read the same env var the server uses, ensuring the test runner sets it before spawning

5. **Verify locally before pushing**:
   ```bash
   cd co-web
   BASE_URL=http://localhost:54321 npx playwright test --reporter=line
   ```
   Expected: pass count matches main's baseline (likely ~300/317). Anything significantly less = not fixed yet.

## Scope

1. New module `co-web/src/infra/mod.rs` + `co-web/src/infra/storage.rs`
2. Define trait `Storage` matching the existing storage API (read-only-first; mutating methods phased in as call sites migrate):
   - `fn get_entry(&self, universe: &str, path: &str) -> Result<Option<Entry>>`
   - `fn list_entries(&self, universe: &str, filter: EntryFilter) -> Result<Vec<Entry>>`
   - `fn put_entry(&mut self, universe: &str, entry: Entry) -> Result<()>`
   - `fn delete_entry(&mut self, universe: &str, path: &str) -> Result<()>`
   - (plus the other concrete methods used today — extract them from `storage::Storage`'s current public surface)
3. Implementation `SqliteStorage` wrapping the current `parking_lot::Mutex<rusqlite::Connection>`
4. `AppState` gains an `Arc<dyn Storage>` field; constructor accepts it
5. Migrate ~10-20 call sites from direct `state.storage.lock()...` to `state.storage_trait.put_entry(...)` patterns
