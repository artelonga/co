GIVEN CO-474 hashed the redb `AuthStore` magic-codes (Argon2id via
`auth::hash_code`/`auth::verify_code`) but the SEPARATE game-auth path persists
its own `VerifyCodeData` in `game_storage` and still stored the code in plaintext
(`entry.code != code` plaintext compare in `game_routes::verify`),
WHEN the game `login` handler generates a verification code and the `verify`
handler checks a submitted code,
THEN the value persisted in `game_storage` for `VerifyCodeData.code` is an
Argon2id hash (never the live plaintext code) and `verify` compares the submitted
code against that hash via the shared hashing helper, preserving expiry and
attempt-counting behavior.

This closes the second plaintext magic-code path flagged during CO-474. The
plaintext code is only ever materialized at generation time (to email it); it is
never stored at rest.

## Acceptance

- [ ] The game `login` handler hashes the freshly generated code with
      `auth::hash_code` (Argon2id) before placing it in `VerifyCodeData.code`;
      the plaintext code is used only to build the email body.
- [ ] The game `verify` handler compares the submitted code against the stored
      hash via `auth::verify_code` instead of `entry.code != code`.
- [ ] Expiry (`expires_at`) and attempt-counting (`attempts` / `MAX_ATTEMPTS`)
      behavior is unchanged.
- [ ] Tests prove: the stored `VerifyCodeData.code` value is NOT the plaintext
      code; the correct code verifies; a wrong code fails.
- [ ] No `game.db` / redb schema change required (the code is opaque JSON; only
      the hashing of one field changes).
