> **Done.** Extracted into `dev/co-auto/`. Workspace member, kept out of `default-members` so end-user `cargo install` of `co-cli` does not pull dev tooling. Invoked as `co-auto --task CO-XXX --space co`. Canonical execution surface for sprint tasks (see `work/co/SPRINT-V1-LAUNCH.md`).

GIVEN `co auto` is a 1257-line developer tool currently shipped as a subcommand of the user-facing `co` CLI, while end users have no use for it; and the procedural single-function design (`run(AutoConfig)`) makes it hard to swap task sources, executors, or reviewers,
WHEN we extract it into a separate `dev/co-auto` crate (NOT in `default-members`) and refactor the internals around six composable traits — `TaskSource`, `TaskSelector`, `ContextBuilder`, `Executor`, `Reviewer`, `Finalizer`,
THEN the user `co` binary stops carrying dev tooling, the auto pipeline becomes pluggable (filesystem → GitHub Issues, Claude Code → shell, …), and tests mock individual phases instead of running the whole 1257-line procedure.

## Architecture target

```
dev/co-auto/
├── Cargo.toml                         # own crate, own version
└── src/
    ├── lib.rs                         # traits + Pipeline orchestrator
    ├── main.rs                        # thin CLI (clap)
    ├── config.rs                      # AutoConfig + per-component config
    ├── task.rs                        # Task struct (was in auto.rs)
    ├── context.rs                     # Context struct (output of ContextBuilder)
    ├── tracker.rs                     # RunTracker (observability)
    ├── source/
    │   ├── mod.rs                     # trait TaskSource
    │   └── filesystem.rs              # current load_tasks/parse_task
    ├── selector/
    │   ├── mod.rs                     # trait TaskSelector
    │   └── unblocked_first.rs         # current select_next_task
    ├── context_builder/
    │   ├── mod.rs                     # trait ContextBuilder
    │   └── default.rs                 # current build_context
    ├── executor/
    │   ├── mod.rs                     # trait Executor
    │   └── claude_code.rs             # current launch_claude
    ├── reviewer/
    │   ├── mod.rs                     # trait Reviewer
    │   └── acceptance.rs              # current review_criteria
    ├── finalizer/
    │   ├── mod.rs                     # trait Finalizer
```

## Trait sketches

```rust
pub trait TaskSource: Send + Sync {
    fn list_tasks(&self) -> Result<Vec<Task>>;
}

pub trait TaskSelector: Send + Sync {
    fn pick_next<'a>(&self, tasks: &'a [Task], filter: &PickFilter) -> Option<&'a Task>;
}

pub trait ContextBuilder: Send + Sync {
    fn build(&self, task: &Task, workdir: &Path) -> Result<Context>;
}

pub trait Executor: Send + Sync {
    fn execute(&self, task: &Task, context: &Context, workdir: &Path) -> Result<ExecutionResult>;
}

pub trait Reviewer: Send + Sync {
    fn review(&self, task: &Task, result: &ExecutionResult) -> Result<ReviewVerdict>;
}

pub trait Finalizer: Send + Sync {
    fn finalize(&self, task: &Task, verdict: &ReviewVerdict, workdir: &Path) -> Result<()>;
}
```

A `Pipeline { source, selector, context_builder, executor, reviewer, finalizers }` holds boxed trait objects; `Pipeline::run(&Config) -> Result<RunReport>` wires them in order, with a `RunTracker` recording phase timings + outcomes.

## Composition gains (concrete examples)

| Today | After CO-84 |
|-------|-------------|
| Tasks come from filesystem (`*.md` in data dir) | `MultiTaskSource(vec![FilesystemTaskSource, GitHubIssuesTaskSource])` federates |
| One reviewer (acceptance criteria match) | `ChainedReviewer(vec![AcceptanceReviewer, CargoTestReviewer])` — all must pass |
| Executor is hardcoded `claude --dangerously-skip-permissions` | `ShellExecutor`, `AiderExecutor`, custom-bin executors all viable |
| `update_task_status` always to "done" | `Finalizer` chain: status update + git commit + GitHub PR + Slack notification |
| Single test per pipeline run | Mock each trait in isolation; phase tests are 10-line unit tests |

## Migration path (5 commits, each compiles + runs)

1. **Crate scaffold** — `dev/co-auto/Cargo.toml`, `lib.rs`, `main.rs` with `clap` clone of current flags. Workspace `members += ["dev/co-auto"]`, NOT in `default-members`. `co-cli` keeps its `Auto` subcommand, but it `eprintln!`s deprecation + delegates to spawned `co-auto` binary if present, else falls back to current code. **Compiles, both binaries work, no behavior change.**
2. **Move task model + git helpers** — `task.rs`, `git/{crypt, branch, workdir}.rs` are pure code-moves to the new crate. `co-cli/src/commands/auto.rs` re-exports them via `pub use co_auto::...`. **Tests pass.**
3. **Introduce traits + default impls** — define the six traits in their own modules. Wire current functions as the default `Filesystem*`, `Default*` implementations. `Pipeline::run` orchestrates. The legacy `run(AutoConfig)` becomes a thin wrapper that constructs the default `Pipeline`. **Behavior identical.**
4. **Delete auto.rs from co-cli** — remove `Commands::Auto` and `commands::auto` module. Document `co-auto` as the new binary. Users get a clean `co` binary. **Build green.**
5. **Composability tests** — three new integration tests: `MultiTaskSource` federates, `ChainedReviewer` short-circuits on failure, `ShellExecutor` runs without launching Claude. Demonstrates the trait surface works.

## Risks + mitigations

| Risk | Mitigation |
|------|-----------|
| Step 4 breaks scripts that call `co auto` | Keep a stub in `co-cli` for one release that prints "moved to `co-auto`" and execs it if found |
| 1257-line file split makes diffs hard to review | Land step 2 (pure moves) as one PR with `git log --follow`-friendly renames; subsequent steps add structure on top |
| Trait objects add dyn dispatch overhead | Pipeline runs ~once per second at most (Claude Code launch dominates); dyn dispatch is invisible. If it ever matters: switch to generics + monomorphisation |
| New crate in workspace bloats `cargo build` | `dev/co-auto` not in `default-members`; only built explicitly. CI for scaffold doesn't pay this cost |
| Git-crypt key handling tangled with workdir setup | Encapsulate in `git/crypt.rs` with a clear `KeyProvider` trait (file path vs keychain vs none) |

## Out of scope (deferred)

- TOML-based pipeline config (`co-auto.toml`)
- Concurrent multi-task runs (Pipeline is single-threaded for v1)
- Plugin loading (third-party impls of the traits) — possible later, not a v1 need
- Migration of git-crypt logic to a generic encrypted-content layer
- Co auto subcommands (`list`, `pick`, `config`) beyond the current single entry point

## Acceptance

- `cargo install --path co-cli` produces a `co` binary that has NO `auto` subcommand
- `cargo install --path dev/co-auto` produces a separate `co-auto` binary
- Running `co-auto artelonga/co --task CO-66` behaves identically to today's `co auto artelonga/co --task CO-66`
- Three new tests (`MultiTaskSource`, `ChainedReviewer`, `ShellExecutor`) pass
- `cargo build` (workspace default) does NOT compile `co-auto` — verify in CI
- All existing co-cli tests still pass
