## As

a maintainer running the QB-9 e2e (cross-repo: quilombo SvelteKit redirects to `co.artelonga.com.br/recover`) who hit four real UX gaps after CO-172 shipped

## I Need

four follow-up patches that polish the recovery flow end-to-end and harden the quilombo→CO bridge so a fresh production deploy never creates an orphaned account

## So That

(a) the `/recover` page reads coherently when bounced from quilomboaraucaria.com.br,
(b) legacy quilombo users (pre-CO-172, or post-bridge-failure) can recover via email without an admin,
(c) every new quilombo signup since 1.91.3 is guaranteed to have a matching CO account,
(d) the recovery form's "user OR email" UX (which actually requires both) is replaced with two clear fields.

## All work in this ticket lives in the `co` repo

`co.artelonga.com.br` is the auth source-of-truth. Every change here is server-side or in CO's SPA. The quilombo SvelteKit SPA is unchanged for this ticket — it already redirects to `co.artelonga.com.br/recover` per QB-9 (in `~/projects/quilomboaraucaria/`).

## What shipped, by sub-version

### 1.91.1 — `/recover` is friendlier when bounced from quilombo

- Title swap: "Entrar" → "Recuperar senha".
- Subtitle swap: "Acesse seu quadro de projetos" → "Recupere o acesso à sua conta."
- Step subtitle ("Digite seu usuário ou email") hidden when modal title already says "Recuperar senha".
- Initial implementation included return_to-aware copy ("Sua conta funciona em CO e Quilombo…"); reverted in 1.91.2 per user feedback.

**Backend** — `find_user_for_recovery` extended:

```
1. users.usuario = identifier
2. quilombo_usuarios.usuario = identifier → linked_co_user_id  ← NEW
3. verified email channel
4. phone channels (sms / whatsapp)
```

Step 2 fixes the case where a quilombo user's `users.usuario` is `NULL` because `quilombo_bridge.rs` fell back on a unique-index collision.

### 1.91.2 — lazy-bridge legacy quilombo users on recovery

User-reported gap: a quilombo user who set their email *after* signup but whose bridge silently failed (or never ran) couldn't recover via email.

**Fix:** `find_user_for_recovery` gets a step 4 (renumbered):

```
1. users.usuario
2. quilombo_usuarios.usuario → linked_co_user_id
3. verified email channel
4. quilombo_usuarios.email → run ensure_co_user_for_quilombo +  ← NEW
   link_quilombo_to_co + ensure_email_recovery_channel,
   then return the new CO user id
5. phone channels
```

Idempotent — once bridged, the verified-channel lookup catches them at step 3 on subsequent calls and the lazy step never fires.

Also: simplified the recover subtitle (dropped "Sua conta funciona…" copy per "no need to mntion sua conta funciona etc etc its okay").

### 1.91.3 — pair lookup (usuario AND email both required) + mandatory cadastro bridge

**Frontend** — recovery form refactor. Single "Usuário ou canal de recuperação" field replaced by two fields, both required:
- **Usuário** — identifies which account (CO or quilombo, lookup chain handles both).
- **Email** — confirms ownership and is where the code arrives.

Client-side mirrors the validation; both must be non-empty and email must contain `@` before POST.

**Backend** — `find_user_for_recovery_pair(identifier, email)`:
1. Resolve user via `find_user_for_recovery(identifier)`.
2. If `email` is non-empty, verify the resolved user has a verified email channel matching `email` (or `users.email` matching, as a belt-and-suspenders fallback).
3. Return `Some(user_id)` only when both checks pass.

When `email` is empty, falls back to legacy single-identifier behavior so older API consumers keep working.

`forgot-password` AND `forgot-password/verify` both use the pair so a stolen code can't be replayed against a different account.

**Hardened cadastro bridge** — `quilombo_routes::cadastro_handler` now treats `ensure_co_user_for_quilombo` + `link_quilombo_to_co` as mandatory. On failure: rolls back the freshly-created `quilombo_usuarios` row, logs at `ERROR`, returns 500 with a Portuguese retry message. Combined with the 1.91.2 lazy bridge for legacy users, every quilombo user — past or future — has a path to a working CO account.

**Boot-time integrity log** — `server.rs` runs `SELECT COUNT(*) FROM quilombo_usuarios WHERE linked_co_user_id IS NULL` after the recovery backfills and warns if any. Pre-1.91.3 legacy rows recover lazily; non-zero count after the fleet rolls = regression signal.
