GIVEN the `users.tier` column today serves two unrelated purposes — (a) a billing/quota class (anonymous/user/pro) used by CO-80 for rate limits, and (b) a global authority signal (`tier='admin'`) used by `dev_board.rs:31` and `universe_routes.rs:765` to bypass per-universe permission checks; AND the platform's correct authorization model is "every user is admin of their own universes" (CO-49 already implements this via `owner_id` and `universe_members.role`),
WHEN we remove `tier='admin'` as a write/access bypass entirely and enforce that **every privileged action is determined by per-universe membership/ownership, never by global tier**,
THEN the platform is multi-user-ready (no risk of a global-admin escalation), the `tier` field becomes billing-only with a clear definition, and the user mental model is consistent: you only get to act on universes you own or are a member of.

## The principle

> **A user has privileged access only to universes they own or are members of.** "Admin" is not a global role — it's a per-universe role on `universe_members`, and is implicit for the `owner_id` of any universe. There is no platform-wide authority granted by anything in the `users` row.

This is already true for ~90% of code paths (CO-49 deterministic access model). CO-90 closes the remaining bypasses.

## Concrete changes

### 1. Remove global-admin bypasses in handlers

| File:line | Today | After |
|-----------|-------|-------|
| `co-web/src/dev_board.rs:31` | `if claims.tier == "admin" { … }` grants access to the dev board | Replace: dev board access requires user to be a member of `co-dev` universe (universe_members table). yuri's account has the `coordenacao` or `admin` role in that universe — same effect, scoped properly. |
| `co-web/src/universe_routes.rs:765` | `user.tier == "admin"` lets any "admin tier" user configure ANY universe's git config | Remove. The `set_universe_git` route (CO-50) is being deleted in CO-64 anyway; no replacement needed. |
| Telemetry routes (`/api/v1/admin/telemetry/*`) | gated on `gestao_github_admins` env list (already universe-scoped via `dados` universe ownership in some paths) | Audit — anything still gated on `tier='admin'` becomes "must be owner of `dados` universe." |

Audit path: `grep -rn 'tier\s*==\s*"admin"\|tier\.as_deref().*"admin"' co-web/src/` should return zero matches when CO-90 is done.

### 2. Refactor `tier` to billing-only enum

```rust
// Today: tier is a free-form string with values mixing billing + auth
// Examples in DB: "anonymous", "user", "pro", "admin"

// After CO-90:
pub enum BillingTier {
    Anonymous,      // not logged in
    User,           // logged in, default
    Pro,            // paid (CO-80)
}
// "admin" no longer a valid value. Migration converts existing 'admin' rows to 'user'.
```

`BillingTier` is used exclusively by:
- CO-80 rate limiter (per-tier request budgets)
- Quota enforcement (storage cap, universe count)
- Future paid-feature gates

Never by an access check. Document this at the type's declaration site.

### 3. Update CO-85 seed to drop `tier='admin'`

`storage.rs::seed_admin_user_from_env` currently inserts/updates with `tier='admin'`. After CO-90:

```rust
// before
"INSERT INTO users (id, email, display_name, tier, password_hash, created_at) \
 VALUES (?1, ?2, 'admin', 'admin', ?3, ?4)"

// after
"INSERT INTO users (id, email, display_name, tier, password_hash, created_at) \
 VALUES (?1, ?2, ?2, 'user', ?3, ?4)"
```

The seeded user is just a regular user. Their authority over system universes (template, yggdrasil, dados, co-dev) comes from being the `owner_id` of those universes, NOT from `tier`.

### 4. Migration

```sql
-- migration vNN: drop 'admin' as a tier value
UPDATE users SET tier = 'user' WHERE tier = 'admin';
-- (no schema change to the column; the value just stops appearing)
```

For yuri's existing universes on prod: ensure he is owner_id or admin-role member of every system universe. Probably already true, but verify in the migration:

```sql
-- ensure yuri owns/is-admin of every system universe
UPDATE universes SET owner_id = (SELECT id FROM users WHERE email = ? LIMIT 1)
  WHERE key IN ('template', 'yggdrasil', 'dados', 'co-dev', 'co-experience')
    AND owner_id = 'system';
```

(If yuri's id differs between UAT and prod, the migration takes a parameter.)

### 5. UI/i18n cleanup

- Anywhere the UI shows "admin" as a user attribute (e.g., `/co/co-dev/dados` admin badge), reframe to "owner" or remove entirely
- pt-BR strings: `admin` → `proprietário` for universe context; never global
- The "tier" badge on profile pages stays (Pro tier is meaningful for billing) but admin disappears

### 6. CO-89 / co-dev universe access

Once CO-89 ships, `co-dev` becomes a universe like any other. Its access model:
- Yuri is `owner_id` (sees + writes everything)
- Other contributors get `member` or `editor` roles per `universe_members`
- Anyone else gets the same access as any private universe (404)

No special "dev board sees if you're a global admin" check. The dev board is just a view of the `co-dev` universe.

## Risks

- **UAT `dev_board.rs` access regression** — if yuri isn't already a member of `co-dev` universe, removing the tier bypass locks him out. Mitigation: migration ensures he's owner of co-dev.
- **Missed bypass elsewhere** — manual audit might miss something. Mitigation: add an integration test that attempts known privileged actions as `tier='user'` and asserts they all 403/404 unless owner-membership exists.
- **Pro tier integration with CO-80** — CO-80 spec uses `tier='pro'` for higher rate limits. CO-90 doesn't change that path; just removes `admin` from the tier enum's valid values.
