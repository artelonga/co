## As

a maintainer collaborating across branches via the proposal/merge UI shipped in 1.74.0

## I Need

three-way merge with explicit conflict markers when proposal-source and proposal-target diverge from a common ancestor

## So That

I can merge proposals safely instead of being limited to fast-forward / clean overwrite, and conflicting branches don't either silently clobber state or block forever

---

## Current state (1.76.0)

Proposals + merges (Phase 4) ship as fast-forward only — `POST /api/v1/universes/:slug/merges` accepts a proposal path and applies it on top of the target if there's no divergence. If the target moved since the proposal forked, the merge is rejected with 409 and the user has no resolution path.

The state-manifest format is body-hash aware (1.74.0), the CAS layer (1.75.0) stores every body keyed by sha256, and the `relation_index` (1.76.0) carries temporal validity — every primitive needed for a real three-way merge is in place.

## Design

### LCA detection

Each proposal records the parent state it forked from (`proposals.base_state`). For three-way merge we need:

- `base` — common ancestor state (the proposal's recorded `base_state`).
- `ours` — current head of the target branch.
- `theirs` — proposal head.

If `base == ours`, fast-forward applies (existing path). Otherwise, run three-way merge.

### Per-entry merge

For each path P that appears in any of `(base, ours, theirs)`:

| base | ours | theirs | result |
|------|------|--------|--------|
| X | X | Y | Y (theirs changed only) |
| X | Y | X | Y (ours changed only) |
| X | Y | Z (Y == Z) | Y (same change both sides) |
| X | Y | Z (Y != Z) | conflict — emit markers |
| absent | X | absent | X |
| absent | absent | X | X |
| X | deleted | X | deleted |
| X | X | deleted | deleted |
| X | deleted | Y | conflict (delete vs modify) |
| X | Y | deleted | conflict (modify vs delete) |

Body-hash equality is the comparison key — pulled directly from the manifest's 3-column format `(combined_hash, body_hash, path)`.

### Conflict marker format

When two non-equal modifications collide, write a single resolution entry to a `conflicts/` shadow directory inside the merged state with markers identical to git's:

```
<<<<<<< ours (state-id <hash-prefix>)
…body of ours…
=======
…body of theirs…
>>>>>>> theirs (state-id <hash-prefix>)
```

The user resolves via the UI by editing the body (which is then a normal vault PUT) and a `POST /api/v1/universes/:slug/merges/:merge_id/resolve` endpoint commits the merge.

### Resolve UI

Conteúdo gains a "Conflicts" panel listing files in the active merge with:
- diff3 view (base | ours | theirs)
- "use ours" / "use theirs" / "edit manually" actions
- "Mark resolved" button (verifies no conflict markers remain in body)
- "Commit merge" once all entries clean

## API additions

```
POST   /api/v1/universes/:slug/merges        # already exists — extend response
                                             # with `{ status: "conflict",
                                             # merge_id, conflicts: [path...] }`
GET    /api/v1/universes/:slug/merges/:id    # current merge state
POST   /api/v1/universes/:slug/merges/:id/resolve   # body: { path, body }
POST   /api/v1/universes/:slug/merges/:id/commit    # finalize once clean
DELETE /api/v1/universes/:slug/merges/:id    # abort
```

A new table `merge_sessions` records `(id, slug, base_state, ours_state, theirs_state, status, started_at)` and `merge_conflicts (merge_id, path, base_body_hash, ours_body_hash, theirs_body_hash, resolved INTEGER NOT NULL DEFAULT 0)`.

## Acceptance

- [ ] LCA detection picks the recorded `proposals.base_state` deterministically
- [ ] Per-entry merge handles all 9 rows of the table above
- [ ] Conflict markers match git's format byte-for-byte (so existing tooling can parse)
- [ ] Resolve API rejects bodies that still contain `<<<<<<<` / `=======` / `>>>>>>>`
- [ ] Commit endpoint creates a new state whose manifest contains every resolved path with the user's chosen body
- [ ] UI: Conflicts panel renders, diff3 view works, all three resolution actions work
- [ ] No regression — existing fast-forward path stays the same when there are no conflicts
- [ ] Tests: 12+ new test cases covering each of the 9 cases plus 3 UI flows

## Out of scope

- Recursive / cross-merge (a merge of a merge) — separate ticket if it's ever needed
- Rename detection (entry path moved on one side) — Phase 5.5
- Conflict UI in the kanban / garden views — Conteúdo only for this phase

## Estimate

~3-5 days of focused work. Sequence: LCA + per-entry diff (1d), conflict marker writing (1d), resolve/commit endpoints (1d), UI panel (1-2d), tests throughout.
