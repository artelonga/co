## As

a user who doesn't have CO open all day

## I Need

email digests of my pending notifications (chat, DMs, invitations,
mentions), delivered at the frequency I chose in preferences (instant,
hourly, daily, weekly, or never), respecting quiet hours

## So That

I learn about DMs and invitations even when I'm not logged in — the
async backbone of CO communications.

---

## Precondition

CO-199 must be live. This ticket reads from the `notifications` table
+ `notification_preferences` and ships nothing new at the storage
layer.

## Background worker

A long-running tokio task spawned at server startup:

```rust
tokio::spawn(crate::notification_email_worker::run(Arc::clone(&state)));
```

Loop: every 60 seconds, scan users with pending undelivered
notifications and fan out per-user email digests.

```rust
async fn run(state: AppState) {
    let mut interval = tokio::time::interval(Duration::from_secs(60));
    loop {
        interval.tick().await;
        if let Err(e) = tick(&state).await {
            tracing::warn!("notif email tick: {e}");
        }
    }
}

async fn tick(state: &AppState) -> anyhow::Result<()> {
    let now = Utc::now();
    let users = {
        let storage = state.storage.lock().unwrap();
        storage.list_users_with_pending_email_notifications()
    };
    for user_id in users {
        let prefs = storage.get_preferences(&user_id);
        if !should_send_now(&prefs, now) { continue; }
        let batch = storage.list_pending_email_notifications(&user_id, MAX_PER_DIGEST);
        if batch.is_empty() { continue; }
        match send_digest_email(state, &user_id, &batch).await {
            Ok(()) => storage.mark_notifications_email_delivered(&batch.iter().map(|n| n.id.clone()).collect::<Vec<_>>())?,
            Err(e) => tracing::warn!("digest send for {user_id}: {e}"),
        }
    }
    Ok(())
}
```

## Frequency policy

`should_send_now` honors `email_digest_freq`:

| Value | Behavior |
|---|---|
| `instant` | Send as soon as an unread, undelivered notification exists |
| `hourly` | Send if oldest pending notif is ≥ 55 min old |
| `daily` | Send if oldest pending notif is ≥ 23 h old (rolls roughly once/day) |
| `weekly` | Send if oldest pending notif is ≥ 6.5 days old |
| `never` | Skip user entirely |

Plus: skip if the current local hour for `prefs.quiet_hours_tz` falls
inside `[quiet_hours_start, quiet_hours_end)`. Quiet hours that span
midnight (e.g., 22:00 → 07:00) are detected as such and handled.

Plus: skip if all notif `event_type`s in the batch are toggled OFF in
prefs (`email_chat_message=0`, `email_chat_dm=0`, etc.).

## Email content

Subject (PT):
- Single notif: `"Maria te enviou uma mensagem no CO"`
- Multiple notifs: `"3 notificações no CO"`

Body template (PT, simplified):

```
Olá {display_name},

Você tem {N} notificações pendentes:

{for each notif:}
• {summary} — há {relative_time}
  {if chat or DM: short body preview}
  {link to thread / drawer / accept page}

Para alterar suas preferências de notificação ou frequência de
envio, visite:
https://co.artelonga.com.br/settings

— equipe CO
```

EN translation key-table follows the same pattern.

Each notif's link target depends on `event_type`:
- `chat.message`, `chat.mention` → `{base}/{universe_key}#chat-{room_id}-{object_id}`
- `chat.dm` → `{base}/?dm={room_id}#msg-{object_id}`
- `universe.invitation` → `{base}/invitations/{object_id}`

The drawer / inbox UIs from CO-189/CO-198 already handle these anchor
patterns; this ticket doesn't change frontend.

## Delivery via existing Resend cascade

Reuse the existing `MailProvider`:
1. Try Resend (`RESEND_API_KEY` configured).
2. Fall back to SMTP (`CO_SMTP_*`).
3. Log only as last resort.

Sender: `notificacoes@seguranca.artelonga.com.br` (new identity, falls
back to existing `senhas@seguranca.artelonga.com.br` if not configured
in Resend). Configurable via `NOTIF_FROM_EMAIL` env.

Subject and body localized per user's `users.language` if present;
default `pt`.

## Rate limit / abuse guard

- Cap one digest per user per minute (regardless of `instant` setting)
  to prevent a flood of single-event mails.
- After 5 send failures for a user, mark notifications as "delivery
  failed" (new column? or just leave undelivered + log) and stop
  retrying until next prefs update.

## Acceptance

- [ ] Background worker spawns at startup; logs `notif email worker
      active` once per boot.
- [ ] User with `email_digest_freq=instant` and 1 unread notification
      → receives email within ~60s.
- [ ] Same user with the same notification already delivered → no
      duplicate email.
- [ ] User with `email_digest_freq=daily` and notifs created 30 min
      ago → no email yet.
- [ ] Same user 24h later (and unread) → email sent.
- [ ] User with `email_digest_freq=never` → never sent.
- [ ] User in quiet hours → skipped during the quiet window, sent
      after window ends.
- [ ] User with `email_chat_message=0` and 5 chat-message notifs +
      1 DM → digest contains only the DM.
- [ ] After send, `notifications.delivered_email_at` populated.
- [ ] After send failure, retry next tick (up to 5 attempts).
- [ ] Email subject + body localized per `users.language`.
- [ ] CSS-inlined HTML email renders correctly in Gmail desktop +
      mobile + dark mode.
