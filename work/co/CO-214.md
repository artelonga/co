## As

a downstream universe runtime (quilombo's SvelteKit, future yggdrasil/artelonga
backends) holding a short-lived 60s handover JWT (CO-186) or a session cookie

## I Need

a server-to-server endpoint that exchanges the short-lived token for a
long-lived (7-day) ES256 JWT that can be carried as Bearer auth on co's
REST and WS APIs (chat, telemetry ingest, blobs, entries)

## So That

quilombo's `co-client` (and any other satellite universe) can call co's
chat/telemetry/storage APIs continuously on behalf of the user without the
60s window expiring mid-session

---

## Context

CO-185/CO-186 shipped the cross-apex SSO handover token — ES256, 60s TTL —
signed by `sign_handover_jwt_es256` in `co-web/src/auth.rs:561`. Receivers
(currently quilombo's `/auth/co-handover`) validate it via JWKS and
establish their own local session.

QB-13 Phase 1 introduced quilombo's `co-client` which uses that token to
call co's chat API (`GET /api/v1/universes/quilomboaraucaria/chat/...`).
Problem: the 60s TTL means chat works for the first minute after login
then breaks. The current quilombo workaround caches `co_token` as a
60s cookie — unusable.

**Two gaps discovered:**

1. **`require_auth` is HS256-only.** Despite ES256 being co's stated
   cross-domain JWT direction (CO-166, JWKS endpoint at
   `/.well-known/jwks.json`), `require_auth` (auth.rs:339-367) and
   `require_auth_with_token` (auth.rs:375-410) only call
   `decode::<Claims>` with `Algorithm::HS256`. `decode_claims_any`
   (auth.rs:240) does support ES256 + HS256 but is referenced only
   from its own unit tests — no middleware uses it. Result: a valid
   60s ES256 handover token presented as `Authorization: Bearer ...`
   gets a 401 from every route gated by `require_auth`, including all
   of `chat_routes.rs`.

2. **No exchange-session endpoint.** Even with #1 fixed, a 60s window
   isn't enough for a SvelteKit page that wants to keep a chat WS
   connection alive across a normal session.

Cookie-sharing can't substitute: co's cookie domain is
`.artelonga.com.br` (`config.rs:61`), quilombo is at
`quilomboaraucaria.com.br` — different apex, no overlap.

This PR addresses both, because either alone is useless: fix #1 without
#2 and chat works for 60s; fix #2 without #1 and the exchanged token
gets rejected by the routes it's meant for.

## Endpoint

```
POST /api/v1/auth/exchange-session

Auth: Bearer <handover-or-session-token>  OR  Cookie: session=...

Response 200:
  {
    "token": "<es256-jwt>",
    "expires_at": "2026-05-23T11:55:00Z"
  }

Response 401: { "error": "unauthenticated" }
```

No request body. No rate-limit dedicated (covered by the general API
rate limiter). Token includes the same claims the caller already had
(sub, email, tier) — no privilege escalation possible because the new
token only has what the old token proved.

## Security notes

- **No infinite TTL extension.** Re-exchange is allowed (the new token
  is a valid input to a future exchange) — but co does not maintain a
  session revocation list anyway. Per-request membership/role checks in
  `chat_routes.rs:157` already enforce real-time access control. If
  membership is revoked, the token becomes harmless even if not
  expired. This matches how the existing `sign_jwt_es256` flow works
  for the login endpoint.
- **No new attack surface.** The endpoint accepts only valid existing
  tokens — it cannot mint a token for an arbitrary user. The handover
  token's 60s TTL already constrains the exchange window to the
  immediate post-login moment.
- **Audit log.** Each exchange writes a `telemetry_events` row
  (`event_type='auth.exchange'`, sub) for forensic visibility.

## Implementation sketch

**Part A — widen `require_auth` to use `decode_claims_any`:**

```rust
// auth.rs:339 — replace the HS256-only decode with the dual decoder.
pub async fn require_auth(
    State(state): State<crate::server::AppState>,  // new — needed for jwt_key
    mut req: Request<Body>,
    next: Next,
) -> Result<Response, Response> {
    let token = extract_bearer_or_cookie(&req)
        .ok_or_else(|| unauthorized("Missing or malformed Authorization header"))?;

    let claims = decode_claims_any(&token, &state.jwt_key, &jwt_secret())
        .map_err(|_| unauthorized("Invalid or expired token"))?;

    req.extensions_mut().insert(UserId(claims.sub));
    Ok(next.run(req).await)
}
```

Same change for `require_auth_with_token` (line 375). Note signature
change — `require_auth` now needs `State`, mounted via
`axum::middleware::from_fn_with_state(state.clone(), require_auth)`
instead of `from_fn(require_auth)`. Audit all mount sites in
`server.rs`.

**Part B — exchange-session endpoint** in new file
`co-web/src/auth_routes.rs` (separate from `oidc_routes.rs` because
this isn't OIDC — it's a private inter-service bridge).

```rust
pub fn auth_router() -> Router<AppState> {
    Router::new().route("/v1/auth/exchange-session", post(exchange_session_handler))
}

async fn exchange_session_handler(
    State(state): State<AppState>,
    headers: HeaderMap,
) -> Result<impl IntoResponse, AppError> {
    let user_id = resolve_user_id(&state, &headers)
        .ok_or_else(|| AppError::Unauthenticated("no valid session or bearer".into()))?;

    let storage = state.storage.lock();
    let user = storage.user_by_id(&user_id)
        .ok_or_else(|| AppError::Unauthenticated("user not found".into()))?;

    let (token, expires_at) = sign_jwt_es256(
        &state.jwt_key,
        &user.id,
        &user.email,
        &user.tier,
    )?;

    Ok(Json(json!({ "token": token, "expires_at": expires_at })))
}
```

Mounted in `server.rs` next to other `/api/v1/auth/...` routes
(currently at line 204).

## Out of scope

- Token revocation list (would require a new table + migration; not
  needed for this round per Security notes above).
- Refresh-token semantics (this endpoint is the refresh mechanism).
- Rate limiting beyond the general API limiter.
