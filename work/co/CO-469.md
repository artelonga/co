GIVEN `jwt_secret_from` falls back to the hardcoded `dev-secret-change-me` when
`JWT_SECRET` is unset, and nothing stops a production deployment from booting
with it — making every session JWT forgeable by anyone who reads the source,
WHEN the server boots in a non-local/test environment, it must refuse to start
if the resolved secret is the development fallback,
THEN a misconfigured prod deploy fails closed with a clear, actionable FATAL
message instead of silently accepting forged sessions.

## Acceptance

- `ensure_jwt_secret_safe(is_local_or_test, secret)` returns `Err` for
  (prod, dev-fallback) and `Ok` for (prod, real-secret) and (local/test, any)
- `start_server_inner` panics with `FATAL (CO-469)` + remediation hint when the
  guard fails, before binding the listener
- The dev fallback is a single shared const (`DEV_JWT_SECRET_FALLBACK`) used by
  `jwt_secret_from` and `recovery_crypto` (no duplicated string literals)
- Unit tests cover all three guard cases

## Remaining auth backlog (tracked, not in this change)

- **F2 — `CO_ENV` fail-open:** `is_local_or_test()` treats empty `CO_ENV` as
  local, so a deploy with `CO_ENV` unset returns `dev_code` inline (leaks login
  codes). Make empty fail-closed (treat as prod) without breaking local-dev
  ergonomics. Behavior change — needs its own PR + e2e check.
- **F3 — vault path-traversal:** audit `write_vault_entry` path handling for
  `..`/absolute-path escapes on the `{*path}` capture.
- **F4 — legacy magic-codes at rest:** the redb `AuthStore` stores verification
  codes in plaintext; hash them (Argon2, as the CO-190 onboarding store does).
- **Auth unification:** retire the legacy redb `AuthStore`; make `/auth/login`
  a thin adapter over the SQLite onboarding store (removes the dual-store
  single-slot overwrite bug).
