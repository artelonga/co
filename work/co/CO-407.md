## GIVEN / WHEN / THEN

- GIVEN prod `/api/health` failing (non-200 or timeout) for > N consecutive
  checks, WHEN the probe detects it, THEN Yuri is notified within ~5 minutes
  (e-mail via Resend — already configured — and/or ntfy/webhook push), and a
  `health.down` event lands in atividades/`/agora` when the server returns.
- GIVEN recovery, THEN a `health.recovered` notice with downtime duration.
- The probe lives OUTSIDE the prod machine (a Fly scheduled machine,
  GitHub Actions cron, or the staging app probing prod — cheapest wins;
  GH Actions cron costs nothing and needs no new infra).
- Scope check: staging probed too, but staging alerts are digest-only.

## Acceptance

- [x] An external probe (GitHub Actions cron, no new infra) runs every ~5 min
      and curls prod `https://co.artelonga.com.br/api/health` from OUTSIDE the
      prod machine.
- [x] An outage is declared only after **N consecutive** failures (default 3,
      in-run, ~20s apart) so a single transient blip does not false-alarm.
- [x] On a down transition a `health.down` alert is emitted; Yuri is notified
      within ~5 min via Resend e-mail and/or ntfy push (channel set by repo
      secret `RESEND_API_KEY` / `NTFY_URL`), and as a GH Actions annotation +
      run summary even with no channel configured.
- [x] On recovery a `health.recovered` notice is emitted with the **downtime
      duration**, computed from cross-run state persisted via the Actions cache.
- [x] Staging (`https://staging.co.artelonga.com.br/api/health`) is probed too
      but at digest priority (warning annotation + summary only, no push).
- [x] Probe never fails the CI job (exit 0 always) so the alert channel cannot
      be muted by a red workflow; notification secrets are documented, not
      committed.

## Implementation

- `scripts/uptime-probe.sh` — dependency-light bash probe + state machine +
  notification fan-out (Resend / ntfy / annotation). N-consecutive logic and
  down/recovered transitions with duration formatting.
- `.github/workflows/uptime-probe.yml` — `*/5 * * * *` cron + `workflow_dispatch`;
  one job per target (prod = high priority, staging = digest), state persisted
  across runs via `actions/cache` (per-run key + prefix restore-keys).

## Context

2026-06-11: prod crash-looped for ~3 hours (disk-full panic) and was found
only by manually testing the site. Two prior incidents (2026-04-30 column
reads, 2026-05-12 mutex poisoning) were likewise user-discovered. Three
strikes — alerting is no longer optional.
