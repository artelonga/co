## As

a universe owner who wants to invite collaborators (and a person who was invited)

## I Need

a UI for both sides of the CO-188 invitation flow: a "Convidar pessoas" section in the universe settings panel for inviters, and a public `/invitations/:token` page that previews the invite and accepts it on click

## So That

users never have to construct API requests by hand to use invitations — point-and-click flow end-to-end.

---

## Precondition

CO-188 must be live (migration v40 applied, three REST endpoints responding). This ticket only adds frontend.

## Surfaces

### A. Inviter side — universe settings panel

Add a "Convidar pessoas" section to the existing universe settings modal (where `theme_preset` / `layout` / custom tokens already live). Visible only to owner / `universe_members` row with role in (`owner`, `admin`).

**Form:**

```html
<section class="settings-section invite-section">
  <header class="settings-section-header">
    <h3 data-i18n="invitations.title">Convidar pessoas</h3>
    <p class="form-hint" data-i18n="invitations.subtitle">Convide por email ou usuário do CO.</p>
  </header>
  <div class="form-group">
    <label for="invite-recipient" data-i18n="invitations.recipient">Email ou usuário</label>
    <input type="text" id="invite-recipient" autocomplete="off" placeholder="email@exemplo.com ou usuario">
  </div>
  <div class="form-group">
    <label for="invite-role" data-i18n="invitations.role">Permissão</label>
    <select id="invite-role">
      <option value="member" data-i18n="invitations.role_member">Membro</option>
      <option value="admin"  data-i18n="invitations.role_admin">Administrador</option>
      <option value="viewer" data-i18n="invitations.role_viewer">Apenas leitura</option>
    </select>
  </div>
  <div class="form-actions">
    <button type="button" class="btn btn-primary btn-full" id="btn-send-invite" data-i18n="invitations.send">Enviar convite</button>
  </div>
  <p id="invite-msg" class="form-hint"></p>
  <div id="invite-pending-list" class="invite-pending-list"></div>
</section>
```

**JS handler:**

- On submit: POST `/api/v1/universes/:slug/invitations` with `{email|usuario, role}`. Detect `@` to decide between `email` and `usuario` field.
- 201: toast "Convite enviado para j***@example.com" (use `sent_to` from response).
- 409: error "Esse usuário já é membro."
- 404: error "Usuário não encontrado." (only when `usuario` field used and lookup miss)
- After success, refresh the pending-list.

**Pending invitations list:**

- New endpoint reused: `GET /api/v1/universes/:slug/invitations` (CO-188 already exposed `list_invitations_for_universe` storage helper; need to wire a route — confirm in CO-188 or add here as a small extension).
- Each row: masked recipient, role, sent date, expiry, "Reenviar email" link (re-sends the same token; doesn't mint a new one).
- "Cancelar" link (revoke) — **out of scope this ticket**; the column exists on the table per CO-188 but no endpoint yet. Show greyed/disabled.

### B. Public `/invitations/:token` page

New SPA route. The CO server-side change is one line in `server.rs`:

```rust
.route("/invitations/{token}", get(serve_co_index))
```

Mirrors the `/recover` pattern (CO-176). The SPA handles everything client-side from there.

**JS bootstrap (in `modules/invitations.js`, new file):**

When `window.location.pathname` starts with `/invitations/`:

1. Extract `token` from URL.
2. `GET /api/v1/invitations/:token` — public, no auth. Receive preview.
3. Render full-page card (use the `.login-card` style for visual consistency):

```
┌────────────────────────────────────┐
│  Convite                            │
│                                     │
│  Yuri (display_name) convidou você  │
│  para o universo                    │
│  Quilombo Araucária (universe.name) │
│                                     │
│  Permissão: Membro                  │
│  Expira em: 14 maio 2026            │
│                                     │
│  [ Aceitar convite ]                │
│  Já tenho conta · Criar conta       │
└────────────────────────────────────┘
```

4. **If not logged in** (cookie absent or 401 on `/api/v1/auth/me`):
   - Show "Aceitar convite" button that bounces to `/login?return_to=/invitations/:token`.
   - After login, the recover/google flow's `?return_to=` brings them back here.
   - Login modal already has signup tab + Google button per CO-175 / CO-177.
5. **If logged in**:
   - "Aceitar" calls `POST /api/v1/invitations/:token/accept`.
   - 200: toast "Convite aceito! Carregando {universe.name}..." → redirect to `/{universe.key}` (the universe view).
   - 410: card flips to "Convite expirado" / "Convite já usado".
   - 403 (identity mismatch): "Esse convite é para outro email/usuário. Saia e entre com a conta certa."

**Edge: logged-in but identity mismatch** — common case is "I was invited as guest@example.com but logged in as yuri.fh@gmail.com". Show explicit affordance to log out + return.

### C. Recipient inbox banner (light version)

When a logged-in user has pending invitations, surface a subtle indicator:

- Sidebar header gets a "🎁 N convite(s)" link → opens a modal showing all pending.
- Each row in the modal: same "Aceitar" / "Recusar" actions calling the API directly (no token URL needed when user is already authenticated and matches `invited_user_id`).
- Inbox uses `GET /api/v1/me/invitations` — needs to be exposed (either in CO-188 or here as a small extension).

This is optional polish — invitations always reach users via the email link too. **Mark as optional in acceptance.**

## Storage / API additions (small, on top of CO-188)

If CO-188 didn't already include them, add:

- `GET /api/v1/universes/:slug/invitations` — list pending for a universe (auth + owner/admin).
- `GET /api/v1/me/invitations` — list pending for the current user, matched by `invited_user_id` OR `invited_email = users.email` (auth required).
- (Optional) `POST /api/v1/invitations/:token/resend` — re-send the email for a still-valid pending invitation.

## Acceptance

- [ ] Universe settings shows "Convidar pessoas" section for owner / admin only.
- [ ] Submitting form with email triggers POST and shows toast on 201.
- [ ] Submitting form with usuario (no `@`) routes to the `usuario` field.
- [ ] Pending list refreshes after a send.
- [ ] `/invitations/{token}` URL renders preview card without auth.
- [ ] Anonymous user clicking "Aceitar" lands on login modal with `?return_to=/invitations/{token}`.
- [ ] Logged-in user clicking "Aceitar" hits API + redirects to the universe.
- [ ] Identity mismatch is detected and surfaced clearly.
- [ ] Expired / consumed states render their own messages, not generic 404.
- [ ] Inbox-count badge in sidebar (optional — mark as bonus).
- [ ] No regression on existing `setupSettingsPanel` / `setupSecurityModal` flows.
- [ ] All new strings have PT + EN entries.
