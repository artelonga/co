## As

The operator (yuri) running CO at small scale today but planning for growth — and any future contributor who'll inherit the platform when it spans multiple machines/regions

## I Need

A **trait-abstracted infrastructure layer** that lets every backend concern (storage, workers, telemetry, cache, secrets, auth, blobs) be **swapped at config time** between:

- **Local impl** — single-process, in-memory or SQLite-backed, for `co serve` + tests
- **Production single-node impl** — current Fly setup (SQLite + tokio + local FS)
- **Production scaled impl** — Postgres/distributed-KV + queue + S3/R2 + OTLP-exported telemetry (future, when measured demand exists)

Combined with a **`co serve --staging` mode** that simulates production behavior (latency injection, fault injection, telemetry routed to local Jaeger/OTLP) so the localhost version is a **true staging environment**, not just a dev tool.

## So That

- The localhost version (CO-282) becomes a **real staging environment**: same binary, full test coverage, production-fidelity simulation
- The platform stops being inseparable from its current single-machine Fly deployment shape — clustering, multi-region, and multi-tenancy become incremental engineering work, not rewrites
- Every infrastructure concern has a documented trait and at least two implementations, so swapping a backend never blocks on a new contributor
- Telemetry, tracing, and resource monitoring scale naturally from "stderr in dev" to "OTLP to Honeycomb in prod" without touching application code
- Tests run against real instances (in-process or out-of-process) — the production code paths are exercised, not just mocked

## Context

### Where we are today

| Concern | Current implementation | Scale ceiling |
|---|---|---|
| **Storage** | `parking_lot::Mutex<rusqlite::Connection>` per universe | Single writer, single machine |
| **Workers** | tokio tasks spawned in-process (CO-223 Worker trait) | Single-process; no cross-machine work distribution |
| **Telemetry** | `tracing` crate → stderr; custom event bus (CO-220) for app events | Local only; no APM, no distributed traces |
| **Cache** | In-process `lru::LruCache` | Per-machine, lost on restart |
| **Secrets** | `std::env::var` reads in many places | Fly secrets work; no rotation, no audit |
| **Blob store** | Local FS via `UPLOAD_DIR/` | Per-machine; R2 adapter exists (CO-263) but disabled |
| **Auth** | Hardcoded JWT + Argon2id flows | Local only; no SSO, no SAML, no OAuth provider switching |
| **Rate limiting** | In-process `governor` per route | Per-machine; doesn't aggregate across instances |

Each is a fine choice **for today's scale**. None is **abstracted** behind a trait. Adding a second machine, a Postgres backend, or an OTLP exporter requires touching dozens of call sites.

### What "horizontally scalable" requires

For each concern, a clean trait + at least two implementations + a config-time selector:

1. **Storage trait** — `KvStore`, `EntityStore`, or split per-aggregate. Current SQLite impl satisfies; Postgres/CockroachDB/FoundationDB impls become possible without touching domain code.
2. **Worker executor trait** — `WorkerExecutor` with `enqueue`, `run_now`, `cancel`. Current "spawn tokio task" satisfies; future NATS/Temporal/k8s-Jobs impls plug in.
3. **Telemetry trait** — `tracing::Subscriber` already gives us this; we just need to wire an OTLP exporter conditionally.
4. **Cache trait** — `Cache<K, V>` with `get`, `put`, `invalidate`. Current LRU satisfies; future Redis/Memcached impls plug in.
5. **Secrets trait** — `SecretsProvider` with `get`, `rotate`, `audit`. Current env-var satisfies; future Vault/AWS Secrets Manager impls plug in.
6. **Blob store trait** — partially done (CO-263). Standardize: `BlobStore` with `put`, `get`, `delete`, `presign_url`. LocalFS, S3, R2 impls.
7. **Auth provider trait** — `AuthProvider` with `verify_credentials`, `issue_token`, `revoke`. Current JWT satisfies; OAuth/SAML/Magic-link impls plug in.
8. **Rate-limit trait** — `RateLimiter` with `try_acquire`. Current in-process satisfies; future Redis-backed sliding-window impl plugs in.

### What "local staging" requires

A `co serve --staging` mode that wraps each plug to simulate production:

- **Storage**: same SQLite, but optionally wraps in a "latency-injected" decorator (`SimulatedNetworkStorage`) — adds 5-50ms artificial latency to every read/write to approximate a remote DB
- **Telemetry**: routes to a local OTLP collector (`docker run jaegertracing/all-in-one` or similar) instead of stderr
- **Cache**: optionally simulates eviction pressure at the rate a production-sized cache would experience
- **Workers**: optionally injects scheduled failures (5% error rate, e.g.) to verify retry logic works
- **Blob store**: optionally simulates S3 latency + occasional 503s

All of this is **optional decorators** wrapping the same underlying impls. `--staging` flag enables them.

### What "horizontally scalable" does NOT mean today

This epic is **not** about deploying a 100-node cluster tomorrow. It's about **not painting ourselves into a corner**. The bar for shipping CO-284-X is "the trait abstraction exists and the local impl works"; the bar for "we use the scaled impl" is "we have measured a need and CO-281's right-sizing isn't enough."

In practice: most plugs will ship Phase 1 (trait + local impl), and the scaled-impl Phase 2 work happens **incrementally, only when needed**. The platform doesn't pay a horizontal-scale tax until it actually scales.

## Decision — phases, sub-stories, and what ships when

### Phase 1 — extract traits (the foundation, ~4-6 weeks split across sub-stories)

| Sub-story | Scope | Risk | Ships |
|---|---|---|---|
| **CO-284-A** | Storage trait + SQLite impl wrapped, update call sites | High (touches most of co-web) | Week 1-2 |
| **CO-284-B** | Telemetry trait — `tracing` already-there, add OTLP exporter behind feature flag | Low | Week 1 |
| **CO-284-C** | Worker executor trait — formalize CO-223's `Worker` trait, add `enqueue` separate from `tick` | Medium | Week 2 |
| **CO-284-D** | Cache trait — wrap existing LRU usage | Low | Week 2 |
| **CO-284-E** | Blob store trait — standardize on top of CO-263's adapter shape | Medium | Week 3 |
| **CO-284-F** | Secrets trait — wrap env-var reads in a thin `SecretsProvider::env()` | Low | Week 3 |
| **CO-284-G** | Auth provider trait — extract JWT flow, prepare for OAuth | Medium | Week 4 |
| **CO-284-H** | Rate-limit trait | Low | Week 4 |

Each is independent and ships its own PR. None changes runtime behavior — they're refactors.

### Phase 2 — local staging mode (~2 weeks)

| Sub-story | Scope | Ships |
|---|---|---|
| **CO-284-I** | `co serve --staging` flag wires latency-injection decorators around each plug | Week 5 |
| **CO-284-J** | OTLP exporter wired by default in staging mode; docs for running a local Jaeger via Docker | Week 5 |
| **CO-284-K** | `co::testkit::TestServer` — spawn a real `co serve` instance in tests, run assertions against it (like testcontainers) | Week 6 |

### Phase 3 — first scaled impl (deferred, only when measured)

Don't commit to which plug gets the first scaled impl until we have data showing it's needed. Likely candidates (rough order of likelihood):

1. **Blob store → R2** (CO-263 already partial; quilombo's media at scale)
2. **Telemetry → Honeycomb/Grafana Cloud** (CO-273 deployment dashboard hints at "real APM would be nicer")
3. **Cache → Redis** (only if multi-machine LRU consistency starts mattering — currently no)
4. **Storage → Postgres** (only if SQLite write-throughput hits a wall — probably years away)

### Phase 4 — multi-node coordination (much later)

This is when "horizontally scalable" goes from "could be" to "is". Genuinely hard work:

- Raft for leader election (one machine writes, others read replicas)
- Content-addressed sharding (universe X always lives on shard Y)
- Cross-shard query coordinator
- Distributed locks for migrations

**Not in scope for CO-284 — separate epic when we get there (CO-300+).** Spec'ing it here only to flag that the trait foundation we build in Phases 1-3 is what makes Phase 4 *possible* without rewriting.

## What this enables (worth being explicit)

1. **Real staging via localhost**: `co serve --staging` becomes the test bed. Visible distributed traces, simulated remote latency, fault injection — all running locally before any deploy.
2. **Single-config production environments**: deployment differs only in `co.toml` (or env vars selecting trait impls). The same binary runs dev, staging, prod, cluster.
3. **Genuine testability**: `co::testkit::TestServer` lets us write integration tests against a real `co serve` instance — no mocks, full code paths exercised. Catches bugs that in-process tests miss.
4. **Optionality on every plug**: when a scaled impl is finally needed, the engineering cost is "write one trait impl + flip a config flag", not "rewrite half the codebase".
5. **Mental model alignment**: the platform stops being "a Rust binary with SQLite" and becomes "a Rust binary with pluggable everything". Contributors stop reading the code as monolithic; they read it as composed.

## Why now

User's exact words (2026-05-24):
*"we can run all test locally before deploying, its like a full staging section with simulated environment and storage (backend) like a remote computer but local, all infrastructure plugs (eg telemetry, api tracing, resource utilization for memory an d compute etc) need to expand to horizontally scalable architectures eg multithread and cluster paralelism"*

Three convergent reasons this is the right architectural arc *now*:

1. **CO-281 makes us conscious of where work runs** (5 deployable units, embedding sidecar, etc.). The natural next question — "how do those units coordinate?" — is what CO-284 answers structurally.
2. **CO-282 (localhost) + CO-283 (canvas) move the platform toward local-first**. Without trait abstractions, "local-first" stays a UX feature; with them, it becomes an architectural property.
3. **The recent cascading CI failures** in this session (deep_link → template → clippy → JWT_SECRET — 4 layers of "fix one, surface the next") are a symptom of low cohesion. Trait abstractions force seams that make these classes of failures rarer (each plug has its own tests, isolated state).

Deferring CO-284 means every sub-system bug fix gets harder, every new infra concern gets bolted on the side, and the eventual scale-out work becomes a rewrite instead of an incremental swap.
