## As
Yuri organizing work with a 4-day-week experiment, AND viewing the Milky Way → human history → fictional epochs side-by-side at `/timeline`

## I Need
A time-rendering primitive that decouples canonical time storage (Unix ms) from rendering. A per-universe `_calendar.yaml` defines available calendar lenses; the UI lets users switch lenses at view time without touching the underlying entries.

## So That
- The IaaS principle holds for time: bounded service (lens spec) renders the brain content (entries with timestamps) — same pattern as themes for design, workspaces for layout.
- A 4-day-week org review doesn't require a schema migration — same entries, different lens.
- Cosmic / human / fictional timelines render with the same component, with different epoch + scale.
- The brain's creative time (custom calendars, fictional epochs) is liberated; the service's time (timestamps, durations) stays bounded + deterministic.

## Context

CO entries already have `event_at`, `due_at`, `scheduled_at` per CO-73 (shipped). They store as ISO 8601 strings today. This spec:
1. Migrates them to canonical Unix ms (or stores both, with ms as authoritative) **for the human-scale lenses**.
2. **Adds per-lens canonical unit declarations** — cosmic scale (~13.8 Gyr) overflows i64 ms by 47×, so cosmic lens uses its own `cosmic_year: f64` field. Each lens declares which canonical field drives its math.
3. Adds a per-universe `_calendar.yaml` defining available lenses.
4. Builds a `<co-time-grid>` SPA component that accepts `(entries, lens)` → renders.

### Per-lens canonical unit (the key correction)

Unix ms (i64) covers ±292 million years from epoch — more than enough for human / historical / fictional / Pomodoro scales. But:

| Scale | Max representable | Storage |
|---|---|---|
| Human (CE → far future) | ±292 Myr from 1970 | `event_at_ms: i64` ✓ |
| Historical (Bronze Age → now) | ±292 Myr from 1970 | `event_at_ms: i64` ✓ |
| Fictional (Shandara mythos) | ±292 Myr from any epoch | `event_at_ms: i64` ✓ OR `mythos_year: i64` |
| Cosmic (Big Bang ~13.8 Gyr ago) | **OVERFLOWS i64 ms** (~47×) | `cosmic_year_bp: f64` (years before present) |
| Quantum (Planck time → now) | Overflows in the other direction (sub-ms) | `planck_offset: f64` (defer) |

The fix: each lens declares `canonical_unit` (the field it reads). Math is per-lens. Same component, different input field.

### Use cases (unchanged)

- **4-day-week org review** — visualize a quarter's work as 91 weeks × 4 days = 364 day-slots; see whether the team's rhythm fits.
- **Cosmic + human + fictional timeline** — `/timeline` renders Milky Way events (cosmic lens, log scale, `cosmic_year_bp` field) alongside human history (Gregorian lens, linear, `event_at_ms`) alongside a fictional universe (fictional lens, linear, `mythos_year` field). The component stacks them; storage stays separated by canonical unit.
- **Pomodoro view** — 25-minute work cells with 5-minute breaks.
- **Fiscal year view** — Apr-Mar instead of Jan-Dec.
- **Lunar calendar** — for cultural content (Islamic, Chinese, Mayan).

## Design

### Canonical storage (per-lens)

Migration v66 adds **canonical numeric columns** for the human-scale lenses:

```sql
ALTER TABLE entries ADD COLUMN event_at_ms INTEGER;       -- i64 ms (Gregorian, fictional, Pomodoro)
ALTER TABLE entries ADD COLUMN due_at_ms INTEGER;
ALTER TABLE entries ADD COLUMN scheduled_at_ms INTEGER;

-- Backfill from existing ISO strings
UPDATE entries
SET event_at_ms = strftime('%s', event_at) * 1000
WHERE event_at IS NOT NULL AND event_at_ms IS NULL;
```

For lenses that exceed i64 ms range, the spec uses **lens-specific custom fields stored in frontmatter** (no schema change — `entries.frontmatter_json` is already free-form):

| Lens | Canonical field | Type | Storage |
|---|---|---|---|
| Gregorian, fictional-linear, Pomodoro, 4-day-week | `event_at_ms` | `i64` ms | `entries.event_at_ms` column |
| Cosmic | `cosmic_year_bp` | `f64` years-before-present | `entries.frontmatter_json.cosmic_year_bp` |
| Mythos (per CO-355 fictional pattern) | `mythos_year` | `i64` | `entries.frontmatter_json.mythos_year` |
| Quantum (deferred) | `planck_offset` | `f64` | (defer) |

**Why no `BIGINT` / `i128` column?** SQLite uses INTEGER as a variable-width type up to 8 bytes (i64). For cosmic scale we need f64 anyway (log math is f64-native). Storing cosmic timestamps in frontmatter keeps the schema lean — most entries don't need cosmic-scale precision.

Old ISO columns kept for backward compat (computed on read).

### Per-universe `_calendar.yaml`

```yaml
default_lens: gregorian

lenses:
  - id: gregorian
    name: Gregorian (canonical)
    epoch_ms: 0                       # Unix epoch
    scale: linear
    week_length_days: 7
    weekday_names: [Mon, Tue, Wed, Thu, Fri, Sat, Sun]
    month_length: gregorian           # special: variable per month
    timezone: America/Sao_Paulo

  - id: 4-day-week
    name: 4-day week experiment
    epoch_ms: 1735689600000            # 2025-01-01 BRT (project start)
    scale: linear
    week_length_days: 4
    weekday_names: [Um, Dois, Três, Quatro]
    display_format: "S{week}.D{day}"   # Sprint.Day

  - id: cosmic
    name: Cosmic (Big Bang → now)
    canonical_field: cosmic_year_bp     # entries' frontmatter field (f64; years before present)
    canonical_type: f64
    scale: log
    epoch: present                       # 0 = now; positive = past
    display_unit: "billion years"
    label_periods:
      - { name: "Big Bang", at: 13.8e9 }
      - { name: "Sun forms", at: 4.6e9 }
      - { name: "Earth forms", at: 4.54e9 }
      - { name: "First life", at: 3.6e9 }
      - { name: "Common Era", at: 2024 }   # ~2024 years before "now" if rendered in 4024 CE; refresh annually

  - id: fictional-mythos
    name: Shandara epoch
    epoch_ms: 0                        # arbitrary; uses internal `mythos_year` field
    scale: linear
    custom_event_field: "mythos_year"  # entry.payload.mythos_year drives position
    week_length_days: 7

  - id: pomodoro
    name: Pomodoro (work cells)
    epoch_ms: 1735689600000
    scale: linear
    cell_duration_ms: 1500000          # 25 min
    break_duration_ms: 300000          # 5 min break
    display_format: "Pom{cell}"
```

Loader: `co-web/src/time/calendar_loader.rs`. Universe without `_calendar.yaml` defaults to Gregorian (no breaking change).

### Render component

`<co-time-grid>` SPA component (vanilla JS, no framework):

```html
<co-time-grid
  universe="co"
  lens="4-day-week"
  range-from="2026-01-01T00:00:00Z"
  range-to="2026-12-31T23:59:59Z"
  group-by="entry_type"
  view-mode="grid">
</co-time-grid>
```

Modes: `grid` (calendar grid), `timeline` (horizontal bars), `scatter` (events as dots), `gantt` (with durations).

Subscribes to event bus (CO-380): live updates as entries change in the rendered range.

### Lens-switching UX

Universe header gets a lens dropdown next to the language toggle:

```
[ 🗓 Gregorian ▾ ]  [ pt-BR ▾ ]
   ├─ Gregorian (canonical)
   ├─ 4-day week experiment
   ├─ Cosmic
   ├─ Shandara epoch
   └─ Pomodoro
```

Selected lens stored in `localStorage.co_calendar_lens_<universe>`. Switching = re-render only; no API call.

### Conversion math (per-lens)

Pure functions in `co-web/src/time/conversion.rs` (mirror in `static/.../lib/co-time.js`):

```rust
/// Each lens reads its canonical_field from the entry, then maps to a LensPosition.
pub fn entry_to_lens_position(entry: &Entry, lens: &Lens) -> Option<LensPosition> {
    let raw = entry.read_canonical_field(&lens.canonical_field)?;  // f64 or i64 from column/frontmatter
    match (lens.scale, lens.canonical_type) {
        (Scale::Linear, CanonicalType::I64Ms) => {
            let ms = raw.as_i64()?;
            let offset = (ms - lens.epoch_ms.unwrap_or(0)) as f64;
            let day = (offset / 86_400_000.0).floor() as i64;
            let week_len = lens.week_length_days.unwrap_or(7) as i64;
            Some(LensPosition::Linear {
                week: day / week_len,
                day_of_week: day % week_len,
                hour: ((offset / 3_600_000.0).floor() as i64) % 24,
            })
        }
        (Scale::Log, CanonicalType::F64Years) => {
            let years_bp = raw.as_f64()?;
            // log_10 placement on a normalized axis; closer to present = right
            Some(LensPosition::Log {
                log_position: years_bp.max(1.0).log10(),
            })
        }
        _ => None,  // type/scale mismatch — render as orphan
    }
}
```

`read_canonical_field` checks the column first (for `event_at_ms` etc.) then falls back to `frontmatter_json[<field>]` (for cosmic, mythos, etc.).

Reverse: `lens_position_to_canonical` for "click on a cell to create event there" — emits the right field type for the active lens.

### Timeline at /timeline (the killer use case)

`/timeline` becomes a multi-universe time view (existing alias per CO-280):
- Renders entries from `tempo`, `universo`, `humanity` universes
- Each entry tagged with origin universe → color-coded
- Lens dropdown: switch between cosmic / human / fictional
- Cosmic lens: log scale, Big Bang → now, milky way events visible
- Human lens: linear, CE → now, with cultural overlays
- Fictional lens: arbitrary epoch (per `_calendar.yaml`'s mythos)

User can pin multiple lenses side-by-side via `?lens=cosmic,human,fictional` → renders 3 stacked rows with same time range. The Brain compares mentally.

### Privacy

CO-378 path redaction applies: private universes' entries don't appear in the rendered grid for anon viewers. Calendar lens metadata is universe-scoped — choosing a lens never reveals other universes' data.

### Telemetry (via CO-380)

- `time.lens_switched{universe, from_lens, to_lens}` per user choice
- `time.grid_rendered{universe, lens, entry_count}` per load (sampled)
- Visible in /agora live timeline
