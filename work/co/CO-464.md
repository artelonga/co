GIVEN the README advertises install paths (`curl … /install.sh | sh`, `cargo install`)
that were not all real — `/install.sh` returned 404 and there was no single
getting-started page or a recorded decision about crates.io publishing,
WHEN we serve the binary installer at the documented URL, add a getting-started
guide covering the three personas (hosted / CLI / self-host), and record the
crates.io decision in the README,
THEN the documented install experience works end-to-end and the distribution
strategy is captured, without the large refactor that a crates.io `co-cli`
library split would require.

## Acceptance

- `/install.sh` is served (not 404) from `co-web/static/install.sh`, matching the
  README one-liner `curl -fsSL https://co.artelonga.com.br/install.sh | sh`
- `docs/getting-started.md` exists and covers the three personas: hosted
  (e-mail signup → web), CLI (`co login` + `co sync`), and self-host (`co serve`)
- README records the crates.io decision: no `cargo install co-cli` (the CLI
  embeds the full `co-web` server); supported installs are `cargo install --git`
  and the one-line installer

## Out of scope (deferred)

- Slimming `co-cli` off its `co-web` path dependency to publish a crates.io
  library — large refactor, no user benefit while the working install paths exist.
- Pushing `v<x.y.z>` git tags from `release-commit.sh` so `release.yml` rebuilds
  per-target binaries (release assets stale since v3.11.0) — tracked separately.
