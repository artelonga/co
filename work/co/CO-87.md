GIVEN every read/write of a `CoFile` (CO-86) crosses the same conceptual layers — physical (disk/net) → cache (LRU) → storage (SQLite/S3/blob) → network (HTTP/sync) → privacy (encryption) → security (signing) — and today these concerns are smeared across `storage.rs`, `vault_routes.rs`, ad-hoc helpers, and inline error handling,
WHEN we expose each layer as a `Layer` trait whose input and output is a `CoFile` (or a transform thereof) and provide a composer that chains them at construction,
THEN any code path can declare its stack at call site (`Disk → Lru → Encrypted → Vault`), every layer is unit-testable in isolation, and adding a new concern (a new compression codec, a peer-to-peer transport, a hardware-key signer) is a new trait impl, not a refactor.

## Conceptual layers (bottom → top)

| Layer | Concern | Examples |
|-------|---------|----------|
| Physical | Bytes on disk or network | `FilesystemBytes`, `HttpBytes`, `S3Bytes` |
| Cache (short-term) | Avoid repeated upstream fetches | `LruCache<Key, CoFile>`, `IndexedDbCache` (browser) |
| Storage (long-term) | Indexed durable home | `SqliteStorage`, `BlobStore` (CO-81), `LiteFsStorage` |
| Network | Cross-machine transport | `VaultApiTransport`, `SyncProtocolTransport` (CO-61), `P2pTransport` |
| Privacy | Confidentiality at rest + transit | `ChaCha20Encrypted`, `RecipientSet`, `PassthroughPlain` |
| Security | Integrity + provenance | `Ed25519Signed`, `HmacSigned`, `UnverifiedTrusted` |

Layers are not strictly ordered (encryption above vs. below storage is a design choice — see § Composition rules) but they are *typed* such that composing them yields a coherent stack.

## Trait surface

```rust
/// A layer transforms a `CoFile` going one direction (read or write) and the
/// reverse on the other. Every layer is also a sink/source for the layer
/// above it. Errors propagate; failures at any layer abort the whole flow.
pub trait Layer: Send + Sync {
    type ReadInput;
    type ReadOutput;
    type WriteInput;
    type WriteOutput;
    type Error: std::error::Error + Send + Sync + 'static;

    fn read(&self, input: Self::ReadInput) -> Result<Self::ReadOutput, Self::Error>;
    fn write(&self, input: Self::WriteInput) -> Result<Self::WriteOutput, Self::Error>;
}

/// Composer: stacks two layers so the bottom's output feeds the top's input.
pub struct Stack<Bottom, Top> { bottom: Bottom, top: Top }

impl<B: Layer, T: Layer<ReadInput = B::ReadOutput, WriteOutput = B::WriteInput>>
    Stack<B, T>
{
    pub fn new(bottom: B, top: T) -> Self { Self { bottom, top } }
}

/// Marker traits for canonical layer roles. A stack that ends with a Source can
/// produce a CoFile from no input; a stack ending with a Sink writes the
/// CoFile into the void (storage / network / disk).
pub trait Source: Layer<ReadInput = ()> {}
pub trait Sink: Layer<WriteOutput = ()> {}
```

In practice we'll have layer-flavor traits (`Cache`, `Storage`, `Transport`, `Privacy`, `Security`) that constrain the input/output types more tightly. Below is the simpler "all `CoFile`" model — adequate for v1.

## Concrete layers (v1)

### Physical

```rust
pub struct FilesystemBytes { pub root: PathBuf }
impl Layer for FilesystemBytes { /* reads/writes raw bytes by relative path */ }

pub struct HttpBytes { pub base: String, pub auth: AuthBearer }
// Reads via GET, writes via PUT. Used by VaultApiTransport above.
```

### Cache

```rust
pub struct LruCache<K, V> { /* ... */ }
// In-process, non-shared. Promotion on read; eviction on write or capacity.

pub struct IndexedDbCache;
// Browser-only; populated via wasm bridge (CO-69 PWA path uses this).
```

### Storage

```rust
pub struct SqliteStorage { pub conn: Arc<Mutex<Connection>> }
// Maps (universe_key, entry_path) → CoFile bytes (in body column).

pub struct BlobStore { pub adapter: Box<dyn ObjectStorage> }
// Content-addressed (sha256) for attachments and large bodies (CO-81).
```

### Network

```rust
pub struct VaultApiTransport { pub client: reqwest::Client, pub base: String }
// Reads via GET /api/v1/universes/:slug/vault/*, writes via PUT.
// Content-negotiates: Accept: application/vnd.co+protobuf preferred.

pub struct SyncProtocolTransport { /* CO-61 op-log */ }
```

### Privacy

```rust
pub struct ChaCha20Encrypted { pub recipients: Vec<RecipientPubKey> }
// Wraps `body` field in an Encrypted oneof; encrypted_key is per-recipient.

pub struct PassthroughPlain;
// No-op; preserves the CoFile as-is.
```

### Security

```rust
pub struct Ed25519Signed { pub signer: SigningKey }
// Computes signature over canonical-encoded CoFile (without signature field
// itself) and stores in CoFile.signature.

pub struct UnverifiedTrusted;
// No-op; for local writes where signing is unnecessary.
```

## Composition rules

- **Privacy below Security** — sign the ciphertext, not the plaintext. Tampering with ciphertext invalidates the signature without revealing plaintext to the verifier.
- **Cache above Storage / Transport** — caches sit closer to the consumer than the durable backing.
- **Compression below Encryption** — compress first, encrypt the compressed bytes (compressed-then-encrypted leaks less than encrypted-then-compressed).
- **Storage and Transport are mutually exclusive at the bottom** — a stack ends in either persistent storage *or* a network transport (or both via fan-out, see § Tee).

Example reader stack (browser fetching a private encrypted file):

```rust
let pipeline = HttpBytes::new(base, token)
    .stack(VaultApiTransport::new())     // .co protobuf bytes → CoFile
    .stack(Ed25519Verifier::new(known))  // verify signature, strip sig
    .stack(ChaCha20Decryption::new(key)) // decrypt body
    .stack(LruCache::new(1000));         // memoize for reuse

let cofile = pipeline.read(("yuri-universe", "diary/2026-04-27.md"))?;
```

Example writer stack (server writing a signed encrypted file to SQLite + LiteFS):

```rust
let pipeline = SqliteStorage::new(conn)
    .stack(Ed25519Signed::new(server_key))
    .stack(ChaCha20Encrypted::new(recipient_set))
    .stack(ZstdCompressed::new(3));

pipeline.write((key, path, cofile))?;
```

## Cross-cutting helpers

### Tee (fan-out)

A `Tee<L1, L2>` writes to both layers; reads prefer L1 and fall back. Used for:
- LiteFS replication (write to primary + read replicas)
- Multi-tier storage (write to SQLite + S3 blob mirror)

### Telemetry

A `Measured<L>` wrapper records `Telemetry` (CO-86 message field) on every read/write — bytes-on-wire, latency, success/error. Composable with anything; produces metrics without changing the inner layer's signature.

### Fallible composition

Layers can fail. The composer surfaces errors as `Result<_, StackError>` where `StackError` carries `(layer_name, source_error)` for diagnostics. No silent fallbacks — fail loudly.

## Minimal CLI (informs CO-86 + CO-88)

```bash
co encode in.md -o out.co               # compose: read .md, encode CoFile, write bytes
co encrypt --recipient yuri@... in.co   # compose: decode, wrap in encrypted, encode
co sign --key ./signer.key in.co        # compose: decode, sign, encode
co sync push <universe>                 # compose: read local → http transport
co sync pull <universe>                 # compose: http transport → local
co inspect in.co                        # decode CoFile + dump telemetry/metadata
```

Each command is `Stack` of layers — no command-specific pipeline code beyond layer composition.

## Why this matters

- **One mental model** for the entire data path. New contributors learn one set of traits and they cover everything from "save a draft" to "broadcast to peers."
- **Test in isolation** — every layer has a well-defined signature. Mocks are trivial.
- **Configurable at runtime** — different deployments can wire different stacks (e.g., self-hosted instance with no encryption, multi-tenant with mandatory encryption).
- **Aligns with CO-86** — the protocol stack doesn't reinvent the file format; it composes around the existing `CoFile`.
- **Aligns with CO-77** — per-universe SQLite is just one `Storage` impl. LiteFS replication is a `Tee` configuration. Object storage is another `Storage` impl.

## Tradeoffs

- **Trait dispatch overhead** — each layer is a virtual call. Negligible at the per-file granularity (compared to disk/network); measurable in tight loops. Mitigation: monomorphize hot stacks via generics where the compose order is known statically.
- **Type complexity** — generics on `Stack<B, T>` get verbose. Wrap common stacks in type aliases.
- **Migration cost** — porting existing storage methods to the trait surface is significant work. Do it incrementally; the trait can coexist with the procedural API for one release.

## Out of scope (deferred)

- Async layer trait (current code is sync; switch to async when transport is the bottleneck — likely never for SQLite, eventually for HTTP under heavy load)
- Pluggable layers loaded at runtime from `.so`/`.wasm` (extension story is a 3.0 concern)
- Cross-language port of the trait surface (Scala/TS clients can mirror the model, not import the impl)

## Acceptance

- A 5-layer stack (Filesystem + LRU + Compressed + Encrypted + Signed) reads/writes a real `CoFile` and round-trips bit-perfect
- Replacing one layer (e.g., swap `ChaCha20Encrypted` for `PassthroughPlain`) requires zero changes elsewhere
- A unit test mocks each layer in isolation
- The pilot refactor of `put_vault_file` produces identical HTTP behavior with no integration test regressions
- Bench reports per-layer encode/decode times via CO-86 telemetry
