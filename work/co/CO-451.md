GIVEN `skills_for_task` (em `dev/co-auto/src/auto.rs`) carrega skills de
`{workspace}/skills/*.md` por um mapa label→skill **hardcoded** que só cobre
`module:spa|editor|ui → spa-conventions`, `module:deploy|infra → deploy-runbook`,
`type:test → playwright-pattern`, `module:* → rust-architecture`,

AND o playbook canônico (processo co-auto + papéis orchestrate/implement/review/
test/release) agora existe como skills nos workspaces (ex.: `ArteLonga/skills/`),
mas NÃO é carregado por co-auto porque não há mapeamento,

WHEN estendemos `skills_for_task` para:
1. **Sempre** injetar a skill core `co-auto-process.md` se existir no workspace
   (todo agente herda o loop + os 3 gates + fallback de modelo).
2. Mapear labels de papel → skill: `type:orchestrate→orchestrate`,
   `type:implement|feat|fix→implement`, `type:review→review`,
   `type:test→test` (somar a playwright-pattern), `type:release|deploy→release`.
3. Suportar um array `skills:` no frontmatter da tarefa para inclusão explícita
   (override/extra), deduplicado com os derivados de label.

THEN tarefas de qualquer space (AL, CO, …) herdam o processo canônico e a skill
do seu papel automaticamente; o orquestrador deixa de depender de injeção manual.

## Critérios de aceitação

- [ ] `co-auto-process.md` sempre injetada quando presente no workspace.
- [ ] Mapa de labels de papel implementado; dedup mantido.
- [ ] Frontmatter `skills: [..]` lido e mesclado.
- [ ] Testes de `skills_for_task`: core sempre presente, mapa de papel, `skills:` explícito, ausência graciosa.
- [ ] `cargo test` + `cargo clippy -D warnings` + `cargo fmt` limpos.
- [ ] Doc: `co/skills/` README ou runbook nota o contrato (core + papéis + `skills:`).
