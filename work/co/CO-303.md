## As

Any developer testing the platform on localhost + any user running the SPA in any environment

## I Need

The **same login flow** to complete end-to-end in every environment (local, UAT, production) without leaving the browser or grep'ing server logs. Specifically:

1. **Magic-code flow**: when `CO_ENV` is dev/test, the code is **displayed inline in the login modal** so localhost can complete login through the UI exactly like production would (via email). Same modal, same fields, same UX — just delivery mechanism differs by env.
2. **Admin password fallback**: when the server exposes `allows_uat_login()` (CO_ENV=test or uat), the login modal shows a **secondary "Admin (password)" tab** that uses the existing `uat-login` / `password-login` endpoints. Provides operator/admin access in any env via UI, not just curl.
3. **Documented admin seeding**: `CO_SEED_ADMIN_EMAIL` + `CO_SEED_ADMIN_PASSWORD_HASH` env vars work in any env to bootstrap an admin user.

## So That

- Localhost becomes a **true production-fidelity environment** for UAT testing — the exact login flow real users see, completable through the UI
- The need for a separate Fly UAT deployment evaporates (matches memory `feedback_no_uat.md`)
- E2e tests can use the **same code path** real users do (today's fixture uses the hidden uat-login backdoor — high coverage gap)
- Onboarding new contributors is one command: `CO_ENV=test cargo run --bin co-web` → open localhost → log in → ready to develop

## Context

### The gap as it stands today

Three login paths exist on the server:

| Path | UI exposed in SPA? | Gated by | User-facing |
|---|---|---|---|
| Magic code (`POST /api/auth/login` + `/verify`) | ✅ Yes (modal default) | none | **The path real users see** |
| UAT password (`POST /api/v1/auth/uat-login`) | ❌ No | `CO_ENV=uat\|test` | Hidden — only curl |
| Admin password (`POST /api/v1/auth/password-login`) | ❌ No | user has `password_hash` | Hidden — only curl |

**The defect**: the magic-code flow (the only one in the UI) **doesn't complete locally** because no mail server delivers to test addresses like `yuri@uat.local`. The code is generated, written to STDERR by `LogMailProvider`, but never reaches the user via the UI.

Effect: every dev session begins with either (a) tail server logs and grep for the code, or (b) bypass the UI entirely with curl + manually paste a session cookie into DevTools. **Neither resembles production user experience.**

### Why this matters structurally

Identity is the entry point to **every** authenticated path on the platform:

- `/api/projects/*` (board CRUD) — requires session
- `/api/v1/universes/*` (CRUD) — ownership/visibility derived from `UserId`
- `/api/v1/admin/*` — admin tier check
- WebSocket sync, chat, notifications, telemetry, agent runs — all keyed on user

A broken/divergent login means **all downstream API testing on localhost is broken or fake**. The CO-302 e2e fixture-auth fix worked around it by hardcoding the hidden uat-login path — but real users will never click that. The e2e suite has a high coverage gap on the actual login flow.

### Why the fix is small

The server already has the infrastructure:
- `LoginResponse` is JSON
- The code generator produces a 6-digit string
- The magic-code endpoint is local to one handler in `co-web/src/server/auth_handlers.rs`

Adding a `dev_code` field that's `Some(code)` when `CO_ENV` is dev/test and `None` otherwise is ~3 lines of Rust. The SPA modal adding a display banner for it is ~10 lines of JS. **High value, tiny diff.**

## Decision — three layers

### 1. Server: inline dev-code field in LoginResponse (small)

```rust
// co-web/src/server/auth_handlers.rs

#[derive(Serialize)]
struct LoginResponse {
    message: String,
    /// In CO_ENV=dev|test|uat (not prod), the generated code is returned so
    /// localhost/UAT users can complete login without an email round-trip.
    /// PRODUCTION NEVER POPULATES THIS FIELD.
    #[serde(skip_serializing_if = "Option::is_none")]
    dev_code: Option<String>,
}

pub async fn login_handler(...) -> Result<Json<LoginResponse>, AppError> {
    // ... existing code that generates `code` ...

    let dev_code = if state.core.config.is_local_or_test() {
        Some(code.clone())
    } else {
        None
    };

    Ok(Json(LoginResponse {
        message: "If registered, a code has been sent to your email".into(),
        dev_code,
    }))
}
```

Add `WebConfig::is_local_or_test()` in `co-web/src/platform/config.rs`:
```rust
pub fn is_local_or_test(&self) -> bool {
    matches!(self.co_env.as_str(), "test" | "uat" | "dev" | "local" | "")
    // Production explicitly sets CO_ENV=prod
}
```

### 2. SPA: modal shows the code inline when present (small)

In the login modal's submit handler (`co-web/static/variants/a/modules/login.js` or similar):

```js
const res = await fetch("/api/auth/login", { /* ... */ });
const body = await res.json();

if (body.dev_code) {
  // Dev/test mode — show the code inline + auto-fill
  showDevBanner(`Dev mode — code: ${body.dev_code}`);
  document.querySelector("#login-code-input").value = body.dev_code;
}
```

A small banner above the code-input field, visible only when the response carries `dev_code`. Tells the user "you're in dev mode, this code would be emailed in production". No production behavior change.

### 3. SPA: secondary "Admin (password)" tab in the login modal (medium)

The modal already has two-step form (email → code). Add a small link below the email input:

```
[ Email input               ]
[ Continue with email code  ]
                                     [ Admin sign-in (password) → ]
```

Clicking that link reveals an alternative form with email + password fields. Submits to `/api/v1/auth/uat-login` (or `password-login` depending on which endpoint is enabled). The link itself is only rendered when the server's `/api/v1/auth/login-options` endpoint says password is allowed.

New endpoint:
```rust
// co-web/src/server/auth_handlers.rs
async fn login_options(State(state): State<AppState>) -> Json<LoginOptionsResponse> {
    Json(LoginOptionsResponse {
        magic_code: true,  // always available
        password: state.core.config.allows_uat_login(),
        google: state.integrations.google_oauth.is_configured(),
    })
}
```

The modal calls this on mount and renders only the available paths.

### 4. Document admin seeding (zero code)

In `CLAUDE.md` deployment section, add:
```bash
# Seed an admin user in any environment (works in prod, uat, test):
HASH=$(printf 'mySecretPassword' | argon2 "$(openssl rand -hex 16)" -id -t 3 -m 16 -p 1 -e)
export CO_SEED_ADMIN_EMAIL=yuri@artelonga.com.br
export CO_SEED_ADMIN_PASSWORD_HASH="$HASH"
# Start the server — admin user is seeded on first boot
```

Already exists at `co-web/src/storage/users.rs:263` (`seed_uat_user`); just needs to be invoked from a non-UAT seeding path. ~10 LOC.

## Why now

User's exact words (2026-05-26): *"therefore this is not a sufficient reproduction of a production environment for uat purposes, since one of the core user experiences (logging in) isnt wired correctly. approach should work always for both environments in a scalable way, considering these credentials are they key to organizing access throughout the api chain."*

Three converging pressures:

1. **The CO-302 e2e fixture-auth fix was a band-aid** — we routed test fixtures through the hidden uat-login path. Real users never click that. Coverage on the actual login flow is currently zero from e2e.
2. **localhost-first development (CO-282) depends on this**. Without a working login UX on localhost, the "develop offline against your own SQLite" promise is broken — every dev session starts with a 5-minute setup ritual.
3. **The CO-296 AuthProvider trait** (in CO-284 epic) is the proper architectural fix but it's 1-2 weeks of work. CO-303 is a 4-6h tactical fix that unblocks localhost UAT today while preserving the path to CO-296 later.

After CO-303, every subsequent CO-N ticket benefits from a working local auth loop. Before CO-303, every contributor pays the auth-friction tax on every session.

## Strategic followup — CO-296

This ticket is **tactical**. The strategic fix lives in CO-296 (Auth provider trait, part of CO-284 epic), which would:
- Make all login paths pluggable behind a single trait
- Eliminate env-gate complexity (the trait impl is chosen at boot, not per-route)
- Make adding OAuth/Passkeys/SAML/etc. trivially additive

Once CO-296 ships, CO-303's `dev_code` field becomes a property of the `MagicCodeAuthProvider` impl — the SPA doesn't change. The path forward is consistent: CO-303 unblocks today, CO-296 architects for tomorrow.
