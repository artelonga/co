## As

a CO operator (and eventually an external auditor)

## I Need

an append-only audit log of every `K_u` unwrap event inside the privileged zone, recording `(timestamp, universe_id, job_name, job_run_id, output_aggregation_id, requester_principal)`, with tamper detection via hash chaining

## To

make "operator cannot read user content" a **detectable** property when prevention fails, not a hope; satisfy the third hardening control of §C.2 of the platform roadmap review

## Given / When / Then

GIVEN the privileged zone (CO-130) is the only place that unwraps `K_u`,
WHEN we add an audit log target that the zone writes to (write-only) and `co-web` reads from (read-only) — implemented as a separate Fly app with an append-only API,
THEN every unwrap produces one audit row, the chain of rows is verifiable via Merkle/hash-chain, and tampering with any row breaks the chain on next verification.

## Audit row shape

```json
{
  "id": "01JX7K2H6Q8N9...",
  "timestamp": "2026-05-21T14:23:11.482Z",
  "universe_id": "u_meu_portfolio",
  "job_name": "sessions_aggregated",
  "job_run_id": "run_01JX7K1Z...",
  "requester_principal": "flink-job-runner@co-privileged-zone",
  "output_aggregation_id": "events.aggregated.sessions:offset=12831",
  "prev_hash": "blake3:7f3a...",
  "self_hash": "blake3:c9d1..."  // = hash(prev_hash || canonical(this row minus self_hash))
}
```

## Acceptance

- [ ] Audit log Fly app deployed (separate from `co-privileged-zone` and from `co-web`)
- [ ] API: `POST /v1/audit` (zone-only), `GET /v1/audit?universe_id=...&since=...` (admin-only)
- [ ] Hash chain verified at write time and on every read
- [ ] One synthetic unwrap event in the zone produces one audit row
- [ ] Tamper test: directly modify one row in storage → verification fails on next read; alert fires
- [ ] Audit-log retention: 7 years (regulatory ceiling); cold storage after 90 days
- [ ] Documented procedure for serving an external auditor's read request without exposing live keys

## Out of scope

- Cryptographic timestamping by an external authority — separate ticket if regulatory pressure emerges
- Audit log on a separate cloud (defense in depth across providers) — Phase 5+ revisit
- User-facing "who looked at my data" surface — depends on operator-cannot-read being delivered first

## Risks

- **Audit log as DoS target.** Mitigation: separate Fly app with its own limits; `co-web` reads through cache
- **Chain break recovery.** Mitigation: documented break-glass procedure that rebuilds chain from snapshot, with an explicit gap row that auditors will see
