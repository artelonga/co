## As

a user editing files locally and expecting them to land on prod within seconds (Google-Drive-style)

## I Need

a continuous bidirectional sync channel that streams **deltas only** (added / modified / deleted files) in a **compact wire format** (protobuf SyncDelta + zstd compression) over a **WebSocket** so changes propagate without per-request HTTP overhead, in either direction

## To

replace the v1 stat-poll-and-REST-fan-out approach in `scripts/co-watch.py` with the canonical sync protocol — and unlock server-pushed deltas (a teammate's edit on prod hits my local within seconds)

---

## v1 (already shipped, 2026-05-03)

`scripts/co-watch.py` polls 4 admin repos every 5s, computes diffs from a local snapshot, and fans out per-file REST calls (`POST /assets`, `PUT /vault`, `DELETE /vault`). Wire format: JSON. One TLS connection reused via urllib's keep-alive. Auth: session cookie refreshed from macOS keychain on 401.

This works (touch a file → 4–8s to prod, delete → 7s) but:
- O(N) HTTP requests per tick (one per changed file)
- No server-pushed deltas (one-way)
- JSON instead of compact binary
- Polls every 5s even when nothing changed

## v2 (this ticket)

### Wire format — `core/proto/sync.proto`

```protobuf
syntax = "proto3";
package co.v1;

import "co.proto";  // CO-86's CoFile

// One delta = one logical change to one logical file.
message SyncDelta {
    string universe_key = 1;
    string entry_path   = 2;
    int64  client_ts_ns = 3;       // when the client observed the change

    enum Kind {
        UNSPECIFIED = 0;
        UPSERTED    = 1;           // new or modified
        DELETED     = 2;
        RENAMED     = 3;           // path changed; sha256 same
    }
    Kind kind = 4;

    oneof body {
        co.v1.CoFile cofile = 10;  // full content (CO-86 envelope)
        string blob_ref     = 11;  // sha256 — for content-addressed dedup
        bytes  patch        = 12;  // diff against last_known_sha256 (future)
    }

    string last_known_sha256 = 20; // for patch path
    string new_sha256        = 21;
}

// Client→server batch (uplink) and server→client batch (downlink).
message SyncBatch {
    repeated SyncDelta deltas = 1;
    string client_id          = 2;
    int64  batch_ts_ns        = 3;
    int64  resume_token       = 4; // server tells us where to resume on reconnect
}
```

### Channel: WebSocket

```
GET /api/v1/sync/ws
  Authorization: Bearer <jwt>      (or session cookie)
  X-Sync-Resume: <token>           (optional — picks up where we left off)
  Accept: application/vnd.co+protobuf+zstd
```

Frames are zstd-compressed protobuf `SyncBatch` messages.

### Compression: zstd dictionary

A small training dictionary (~32 KB) trained on a corpus of admin markdown gives ~30-50% better ratio than raw zstd on small messages. Train offline, ship as a constant in both client and server.

### Auth + recovery

- Client connects with session cookie or bearer JWT.
- Server tracks `(universe_key, last_resume_token)` per client.
- On reconnect, client sends `X-Sync-Resume: <token>` and server replays missed deltas. If the token is too old (>24h), server sends a full snapshot delta.

### Bidirectional flows

- **Uplink (client → server):** local file change → SyncDelta → batched → zstd → WS frame.
- **Downlink (server → client):** prod entry write (any source: API, another client, manual edit) → fan out via `DocRoomManager`-style room → matching clients receive SyncBatch → apply locally.

### Conflict policy

- Identical sha256 = no-op (content addressing).
- Concurrent edits to same path with different sha256 = last-write-wins by `client_ts_ns`, server keeps both ciphertexts in `assets` (CO-148 already content-addresses by sha256), exposes a conflict marker in `entries` payload that the SPA renders.
- Future: 4-way merge UI (CO-128).

## Why this is its own ticket

The v1 watcher is sufficient for one-user solo use. v2 is needed when:

- Multiple clients edit the same universe simultaneously (CRDT territory if it's the same file at the character level — yrs already handles that for live docs).
- Latency matters more (< 1s vs current 4–8s).
- Bandwidth matters (mobile / metered).
- Server wants to push (collaborator's edit, server-side scheduled changes).

## Acceptance

- A 1 KB markdown file change lands on prod in < 500 ms (vs current 4–8 s).
- A delete propagates in < 500 ms.
- 100 concurrent clients pushing 1 file/s each: server stays under 50% CPU on a single shared-cpu-1x Fly machine.
- Server-push works: `curl -X PUT /entries/foo.md` from another client → connected watcher applies the delete locally within 1 s.
- Wire bytes per delta ≤ 30% of equivalent JSON+TLS.
- Reconnect with stale resume-token replays correctly without missed deltas.

## Out of scope

- CRDT character-level merge for live docs (already in `yrs` rooms).
- Mobile clients (separate ticket; needs swift bindings to `core/`).
- Encrypted-at-transit beyond TLS (CO-86 envelope handles in-flight encryption opportunistically; full E2E with KEK gating is CO-148 follow-up).
