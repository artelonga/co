## As
A visitor to yuri.artelonga.com.br wanting to navigate the site through conversation, AND Yuri wanting Claude reserved for his own dev work (co-auto, internal CLI tooling)

## I Need
A public-facing chat endpoint backed by a non-Claude LLM (local Ollama, OpenAI, or similar) that retrieves info from CO through deterministic tool calls, never via vector search or hallucination

## So That
- Visitors get a friendly conversational interface to find published content + deployment status
- Claude credits stay reserved for Yuri's authenticated, dev-flavored work
- Costs scale predictably with visitor traffic instead of bleeding API spend

## Design

### Provider split (clean separation)

| Path | Provider | Why |
|---|---|---|
| `/chat` (yuri.artelonga.com.br, public) | **Ollama** (default) → **OpenAI** fallback | Cheap, visitor-scale; never Claude |
| Yuri's authenticated dev CLI (co-auto, internal tools) | **Claude** | Reserved for developer work; better at code |

The `AiProvider` trait from CO-328 already enables this. New constraint: `/chat` route is **hard-coded** to construct a non-Claude provider — no env-var override, no "use Claude here for testing." Misuse-resistant.

### Deterministic tool routing (no RAG)

```
Visitor: "what songs have you published?"
   ↓ LLM (Ollama) parses intent → function call
   ↓ tool: search_entries(type="song", published=true)
   ↓ deterministic CO API: GET /universes/yuri/entries?type=song
   ↓ data flows back (filtered to published-only for anon by CO-330)
   ↓ LLM formats the structured response → natural-language reply
   ↓ "I've published 12 songs. Recent ones: Grace Kelly (Mika), Virtual Insanity (Jamiroquai)..."
```

LLM never sees data it can't trace to a tool call. No vector index, no embeddings, no hallucination risk on content. Only the routing decision (which tool + args) is fuzzy.

### Tool surface

| Tool | Implementation | Notes |
|---|---|---|
| `search_entries(type?, published?, q?, after?, before?)` | wraps `GET /universes/yuri/entries` | filter args passed through |
| `get_entry(path)` | wraps `GET /universes/yuri/entries/<path>` | 404 if not visible to caller |
| `list_types()` | aggregates distinct `type` values | helps LLM choose the right filter |
| `get_recent(since?)` | `created>=since OR modified>=since` | for "what's new" queries |
| `get_deployment_status()` | new endpoint `GET /api/v1/deployments/status` | cached `flyctl status` for the 5 sister apps |

All tools execute through the **same authenticated context** as the chat request — anonymous visitors trigger the CO-330 published filter naturally. **No privilege escalation surface.**

### Provider implementations

#### 1. Ollama (default, local)
- Detect `ollama` binary at boot; warn if missing
- Default model: `qwen2.5-coder:7b` (or smaller for laptops)
- Function calling via Ollama's OpenAI-compatible API endpoint

#### 2. OpenAI fallback (configurable)
- `CO_CHAT_FALLBACK=openai` + `OPENAI_API_KEY` env var
- Falls back when Ollama unreachable or quality threshold not met
- Reserved for prod if local LLM isn't viable

#### 3. NOT Claude
- Hard-coded prevention at `/chat`: if the configured chat provider tries to construct a Claude provider, return 500 with a clear error
- Test asserts: `provider.kind() != "claude"`

### Chat endpoint

`POST /api/v1/chat/yuri` (universe scoped):
```json
{ "message": "show me daily notes from May", "session_id": "abc-..." }
```

Response: SSE stream of tokens. Each tool call surfaces as a SSE event so the UI can show "🔍 searching daily notes...". Final result is plain text.

### Chat UI

Simple widget on yuri.artelonga.com.br:
- Floating chat button bottom-right
- Click → modal with message log + input
- Conversation persists per-session (localStorage) for the visit
- Owner (Yuri logged in) sees the same UI but tools return drafts too — same code path, just different auth context

### Analytics

Every chat query logged to CO-329 `/analytics`:
- Tool used, parameters, response length, latency, provider, success/error
- Yuri can see what people are asking about (and what the LLM is getting wrong) to refine the tool set or system prompt

## Dependencies

- **CO-328** (LLM provider trait + Ollama + Claude impls) — must ship first; this PR adds the OpenAI impl and the routing constraint
- **CO-323** (subdomain routing) — needed so `/chat` lives at yuri.artelonga.com.br
- **CO-329** (analytics) — for query logging; can defer if CO-329 hasn't landed yet

## Not in scope

- Vector index / RAG / embedding search — explicitly excluded (deterministic only)
- Free-text training / fine-tuning — out of scope; use off-the-shelf models
- Multi-language UI — phase 1 PT only (matches the site's default)
- Voice / audio input — out of scope
- Long-term memory across sessions — out of scope; session-scoped chat history only

## Why now

- Closes the loop on the yuri.artelonga.com.br vision: visitors get an active discovery surface, not just static pages
- Decouples Claude usage (dev work) from visitor traffic — keeps per-query cost down + privacy clean
- Deterministic routing eliminates the biggest LLM risk (hallucination on content) without sacrificing UX
- All the auth + visibility plumbing is already done (CO-330 + CO-324 frontmatter convention)
