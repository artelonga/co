## As

a logged-in user

## I Need

a single `GET /api/v1/me/universes` endpoint that returns my universes
bucketed by relationship — owned, member, subscribed, invited,
discoverable — so the SPA sidebar can render each section semantically
(with badges, separators, "join" / "accept invite" affordances) without
making three calls and stitching the buckets client-side

## So That

invitations from CO-188/189 get a first-class place in the sidebar
inbox, public universes are discoverable inline, and the sidebar can
distinguish "you own this" from "you were invited" from "this is a
public universe you might want."

---

## Today (1.97.0)

- `GET /api/v1/universes` (auth) — returns a flat `Vec<Universe>` of
  everything `list_universes_for_user(user_id)` produces. No bucket info,
  no role, no "is this an invitation" flag.
- `GET /api/v1/universes/public` — separate call, returns the public
  catalog.
- `GET /api/v1/me/invitations` (CO-189) — separate call for pending
  invites.

The SPA sidebar at `co-web/static/variants/a/modules/sidebar.js:25`
calls `api.listUniverses()` and treats the response as one undifferentiated
list. There's no "🎁 N convites" affordance, even though CO-189 shipped
the inbox endpoint.

## New endpoint

### `GET /api/v1/me/universes` (auth required)

Response:
```jsonc
{
  "owned": [
    { "key": "yuri", "name": "Yuri", "role": "owner", "parent_key": null,
      "is_template": false, "is_public": false, "content_count": 42,
      "visibility": "private", "hidden": false }
  ],
  "member": [
    { "key": "quilomboaraucaria", "name": "Quilombo Araucária",
      "role": "admin", "parent_key": null, "is_template": false,
      "is_public": true, "content_count": 95, "visibility": "public-subscribable",
      "hidden": false }
  ],
  "subscribed": [
    // public-subscribable universes the caller has explicitly subscribed
    // to but does not own / is not a member of. Reads from the existing
    // `universe_subscriptions` table (or whatever today's subscribe path
    // populates — verify before implementing).
  ],
  "invited": [
    // CO-189: pending universe_invitations for this user.
    { "token": "<raw_token>", "universe_key": "private-team",
      "universe_name": "Private Team", "invited_by_display_name": "Yuri",
      "role_offered": "member", "expires_at": "2026-05-24T00:00:00Z" }
  ],
  "discoverable": [
    // public-subscribable universes the caller is NOT in any of the above
    // buckets. Capped at 50 most recent / most populated for UI perf.
  ],
  "counts": { "owned": 1, "member": 1, "subscribed": 0, "invited": 1, "discoverable": 12 }
}
```

Each entry has a uniform shape (see `Universe` struct) plus a `role`
field — `"owner" | "admin" | "member" | "viewer" | "subscriber" | null`.

Order within each bucket: most-recently-active first (or by name as a
fallback). Order of buckets in the response is fixed: owned → member →
subscribed → invited → discoverable.

## Storage helpers

In `co-web/src/storage/universe.rs`:

```rust
impl Storage {
    /// Returns universes the caller owns (owner_id = user_id),
    /// excluding those marked hidden=1 unless owner.
    pub fn list_owned_universes(&self, user_id: &str) -> Vec<UniverseWithRole>;

    /// Returns universes where the caller has a `universe_members` row,
    /// with `role` resolved.
    pub fn list_member_universes(&self, user_id: &str) -> Vec<UniverseWithRole>;

    /// Returns subscribed-but-not-owned-not-member universes.
    /// Reads from `universe_subscriptions` (verify table exists; if not,
    /// scope down to "future work" — the buckets owned/member/invited/
    /// discoverable are enough for v1).
    pub fn list_subscribed_universes(&self, user_id: &str) -> Vec<UniverseWithRole>;

    /// Returns public-subscribable universes the caller is NOT in
    /// owned/member/subscribed/invited buckets. Cap at `limit`.
    pub fn list_discoverable_universes(
        &self,
        user_id: &str,
        excluded: &HashSet<String>,
        limit: usize,
    ) -> Vec<UniverseWithRole>;
}
```

`UniverseWithRole` is a serde-friendly wrapper:
```rust
#[derive(Serialize)]
pub struct UniverseWithRole {
    #[serde(flatten)]
    pub universe: Universe,
    pub role: Option<String>,
}
```

## Routes wiring

In `co-web/src/server.rs` (or universe_routes.rs):

```rust
.route("/v1/me/universes", get(me_universes_handler))
```

`me_universes_handler` calls each `list_*` helper, builds the excluded
set from the union of keys it has already seen, then queries discoverable.
Re-uses the existing `list_invitations_for_me` from CO-188/189 for the
invited bucket.

## Backward compat

- `GET /api/v1/universes` keeps its current flat-list shape. Don't break
  existing API consumers.
- `GET /api/v1/universes/public` keeps its anonymous-friendly shape.
- `GET /api/v1/me/invitations` keeps its current shape (just becomes a
  subset of `/me/universes` for callers that want only invites).

## Acceptance

- [ ] `GET /api/v1/me/universes` returns 401 when unauthenticated.
- [ ] For an owner with 1 owned, 1 member, 1 invited, 0 subscribed, the
      response contains all 3 in the right buckets with correct `role`.
- [ ] `discoverable` bucket excludes universes the caller owns / is
      member of / has pending invite for / is subscribed to.
- [ ] `discoverable` is capped at 50 entries.
- [ ] `counts` matches array lengths.
- [ ] Hidden universes are excluded except from `owned` (the owner can
      always see their own hidden ones).
- [ ] Tests: 6+ covering each bucket, role resolution, hidden filter,
      discoverable exclusion, empty user, and the CO-189 `invited`
      shape (token, universe_name, invited_by_display_name).
- [ ] No regression on `GET /api/v1/universes` flat-list shape.

## Out of scope

- **Sidebar UI consumption** — that's CO-192 (depends on this).
- **Subscribe / unsubscribe endpoints** — already exist or scoped
  separately. This ticket only *reads* the subscription table.
- **Activity-based ordering** — uses created_at / name for now. A
  future ticket can sort by last-touched.
- **Pagination** — `discoverable` is capped; the others are bounded by
  user's own membership rows.
