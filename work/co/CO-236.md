## As

A CO user or developer working from the terminal (or eventually from a future Settings UI)

## I Need

A single `co auth` command suite that bundles the multi-step password recovery + token lifecycle into one cohesive UX

## So That

Resetting a password, logging in, creating an API token, listing/revoking tokens, and checking auth status don't each require remembering a separate curl invocation. The same callable surface can later be wired into a Settings UI in the SPA.

## Context

Today the password-reset flow is **four sequential curls** to `/api/v1/auth/forgot-password`, `/forgot-password/verify`, `/reset-password`, then `/password-login`. The 90-day API token (`POST /api/v1/auth/token`) is a fifth call. This is painful in the terminal, error-prone when codes are pasted across windows, and impossible to discover for non-engineers.

The endpoints already exist (CO-165 forgot-password flow, CO-35 long-lived API tokens). This task wraps them in a CLI that's safe by default (passwords prompted with hidden input, never on command line) and produces machine-readable output for scripting.

## Scope

New CLI subcommand surface under `co-cli` (existing crate):

```
co auth login [--email <email>] [--save-token]
    Interactive password login. Prompts for password (hidden input).
    With --save-token: also creates a 90-day API token named "cli-<hostname>-<date>",
    writes it to ~/.config/co/credentials (chmod 600), prints the token id.

co auth reset-password [--email <email>]
    Full forgot-password flow in one command:
      1. POST /forgot-password (sends code to verified channel)
      2. Prompt for code
      3. POST /forgot-password/verify (returns reset_token)
      4. Prompt for new password (hidden input, twice for confirmation)
      5. POST /reset-password
      6. Auto-login with new password
      7. Optionally create + save a 90-day API token

co auth change-password
    Requires existing auth (cookie or token). Prompts old/new password.

co auth status
    Prints: logged-in user, token id (if from API token), expires_at, base URL.
    Exit code: 0 if authenticated and not expired; 1 otherwise.

co auth token create [--name <name>]
    Creates a 90-day API token. Without --name, defaults to "cli-<hostname>-<YYYY-MM-DD>".
    Prints the token ONCE (cannot be retrieved later — only revoked).
    With --save: writes to ~/.config/co/credentials.

co auth token list
    GET /api/v1/auth/tokens — prints id, name, created_at, expires_at, last_used_at.

co auth token revoke <id>
    DELETE /api/v1/auth/tokens/:id — confirms before deleting.

co auth logout
    DELETE the session cookie locally; if --revoke-token, also DELETE the API token server-side.
```

## Storage of credentials

`~/.config/co/credentials` (chmod 600, owner-readable only):

```toml
[default]
base_url = "https://co.artelonga.com.br"
token = "co_<40chars>"
token_id = "tok_<id>"
user_id = "usr_<id>"
expires_at = "2026-08-17T..."

# Multiple profiles supported for power users (UAT, local, prod)
[uat]
base_url = "https://co-artelonga-uat.fly.dev"
token = "co_<uat-token>"
```

The CLI reads `[default]` unless `--profile <name>` is passed. Token file is never logged or printed except on creation.

## Server-side affordance (no API changes)

This task is **pure CLI** — all endpoints already exist. The only thing it touches server-side is a small documentation update in `co-web/seed/co/public/seguranca-criptografia.md` to reference `co auth reset-password` as the canonical user-facing flow.

## UI integration path (future, separate task)

After CO-236 ships, the SPA can mirror the same flow:
- Settings page → "Reset password" button → same 4-step modal flow
- Settings → "API tokens" → list, create, revoke
- The CLI commands and the UI buttons call the **same underlying functions** (in a future `co-client.ts` per QB-2 or a shared TS module)

That UI work becomes CO-N when prioritized; this task only delivers the CLI substrate.

## Acceptance

- `co auth login` works end-to-end against prod and UAT.
- `co auth reset-password` runs the full flow with hidden-password prompts (no plaintext in shell history).
- `co auth status` exits 0 when authenticated, 1 otherwise (script-friendly).
- `co auth token create` writes to `~/.config/co/credentials` with mode 600. Token printed only once. File permissions enforced (warn + chmod if user has it world-readable).
- `co auth token list` prints in both human and `--json` formats.
- All 9 endpoints in CO-165 + CO-35 covered by the CLI surface.
- Documented in `co-web/seed/co/public/seguranca-criptografia.md` as the canonical user-facing recovery path.
- E2E test: `co auth reset-password` against UAT replaces the existing seed-admin password; subsequent `co auth login` succeeds.

## Blast radius

Additive — new CLI subcommands under `co auth`. No server changes. Existing curl-based flows continue to work.
