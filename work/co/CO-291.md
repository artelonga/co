## What this slice does

Wires the `opentelemetry-otlp` exporter behind a `tracing` subscriber layer so the same Rust binary can emit spans to stderr (dev), local Jaeger (staging via CO-298), or Honeycomb/Grafana Cloud (prod) by flipping config.

## Scope

1. Add deps: `opentelemetry`, `opentelemetry-otlp`, `tracing-opentelemetry` (~2MB compile-time impact)
2. New module `co-web/src/infra/telemetry.rs` exposing `init_subscriber(config: TelemetryConfig)`:
   - `TelemetryConfig::Stderr` (current default behavior)
   - `TelemetryConfig::Otlp { endpoint, service_name, sampling_ratio }`
3. Wire the appropriate subscriber at server boot based on env vars (`CO_TELEMETRY_OTLP_ENDPOINT`, `CO_TELEMETRY_SERVICE_NAME`)
4. Add a span around each HTTP request (extract from `tower-http::trace::TraceLayer` if not already there)
5. Add spans around DB queries (one span per query, tagged with universe + table)
6. Docs: `docs/observability.md` covering how to:
   - Run a local Jaeger: `docker run -d -p 16686:16686 -p 4317:4317 jaegertracing/all-in-one`
   - Point co-web at it: `CO_TELEMETRY_OTLP_ENDPOINT=http://localhost:4317 cargo run -p co-web`
   - Open Jaeger UI: `http://localhost:16686`

## Acceptance

- [ ] Without OTLP env var set, behavior is identical to today (stderr logs)
- [ ] With OTLP env var pointing at a local Jaeger, spans appear in the UI within 10s of an HTTP request
- [ ] Each HTTP request produces at least one trace with parent/child spans for DB queries
- [ ] No measurable latency regression on warm requests (telemetry adds < 5% overhead)

## Not in this phase

- Setting up Honeycomb/Grafana Cloud (out of scope; ops decision when needed)
- Metrics export (only tracing/spans; metrics is a sibling subspec if wanted later)
