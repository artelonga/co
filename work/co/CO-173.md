## As

a logged-in user navigating the artelonga family of sites

## I Need

`/api/v1/auth/me` (and the SPA shell that consumes it) to return not just my user identity but the list of universes I have access to, with a metadata bag per universe — role, last-seen, profile slice, channel preferences

## So That

(a) the SPA can render a per-universe sidebar with the right state without a second roundtrip,
(b) per-universe profile fragments (quilombo's `papel`/`bio`/`telefone`, artelonga's `assinatura` tier, co's `tier`) live next to the universe entry instead of being scattered,
(c) external clients (mempalace shim, agents, mobile app) can introspect a single API call.

---

## Current state (1.89.1)

`MeResponse` in `co-web/src/models.rs:550`:
```rust
pub struct MeResponse {
    pub user_id: String,
    pub email: String,
    pub display_name: String,
    pub tier: String,
}
```

That's it. No universes list. The SPA fetches `/api/v1/universes` separately to populate the sidebar; per-universe profile fields live in disconnected places (quilombo: `quilombo_usuarios`; CO universes: `universe_members`; subscriptions: `subscriptions`).

## Design

### Extended response shape

```jsonc
{
  "user": {
    "id": "usr_abc",
    "email": "yuri@artelonga.com.br",
    "usuario": "yuri",
    "display_name": "Yuri",
    "tier": "admin",
    "created_at": "...",
    "has_password": true,
    "verified_channels": [
      { "channel_type": "email", "masked_value": "y***@artelonga.com.br" }
    ]
  },
  "universes": [
    {
      "key": "co",
      "name": "CO",
      "role": "owner",
      "is_owner": true,
      "is_member": true,
      "is_subscriber": false,
      "last_seen_at": "2026-05-09T...",
      "metadata": {
        // per-universe metadata bag — opaque JSON. Schema below.
      }
    },
    {
      "key": "quilomboaraucaria",
      "name": "Quilombo Araucária",
      "role": "membro",
      "is_owner": false,
      "is_member": true,
      "is_subscriber": false,
      "last_seen_at": null,
      "metadata": {
        "papel": "membro",
        "bio": "...",
        "foto_url": "...",
        "telefone": "+55..."
      }
    }
  ]
}
```

### Metadata sources

Each universe's metadata bag is filled from the source-of-truth for that universe:

| Universe | Source | Fields |
|---|---|---|
| Any in `users` | `universe_members` row | `role`, `joined_at` |
| Any in `subscriptions` | `subscriptions` row | `pinned_state`, `subscribed_at` |
| `quilomboaraucaria` (when local) | `quilombo_usuarios` row by `linked_co_user_id` | `papel`, `bio`, `foto_url`, `telefone`, `email` |
| Other deployments (future) | API call to that deployment's bridge endpoint | varies |

For now, only **local** sources are read — cross-deployment fetches are deferred to CO-172v2 (which will add the API mesh CO-173 will then consume).

### Schema

No migration needed for v1 — read from existing tables. If we later add user-defined per-universe metadata (tags, custom fields), introduce:

```sql
CREATE TABLE user_universe_metadata (
    user_id      TEXT NOT NULL,
    universe_key TEXT NOT NULL,
    metadata     TEXT NOT NULL DEFAULT '{}',  -- JSON
    updated_at   TEXT NOT NULL,
    PRIMARY KEY (user_id, universe_key)
);
```

But ship v1 without it.

### Implementation slice (one PR)

1. New struct `UserUniverseEntry` in `models.rs` with the per-universe shape.
2. New struct `MeResponseV2` superset of `MeResponse`. Keep old fields for back-compat; add `universes: Vec<UserUniverseEntry>`.
3. New `Storage::list_user_universes_with_metadata(user_id)` walks `universes` joined to `universe_members` + `subscriptions` + (LEFT JOIN) `quilombo_usuarios on linked_co_user_id = user_id`, builds the metadata JSON per universe.
4. `me_handler` calls the new function and returns the extended shape.
5. Old `MeResponse` stays as a `pub use` alias for one release; migrate consumers.

Tests:
- User in 0 universes → `universes: []`
- User in 1 universe (member only) → role + joined_at populated
- User in 1 universe (subscriber only) → subscription metadata populated
- User linked to quilombo → metadata includes `papel`, `bio`, `telefone`
- User in N universes → list ordered deterministically (alphabetical by key? by joined_at?)

### SPA consumption (separate small PR)

After 1 ships, the SPA's `bootAppForUniverse` and `renderSidebar` can pick metadata from `me.universes` instead of issuing separate requests. Out of scope for this ticket — keeps the API shape change isolated.

## Acceptance

- [ ] `MeResponseV2` returned from `/api/v1/auth/me` with backward-compat fields preserved
- [ ] `universes` array present, one entry per universe the user has any relation to
- [ ] Each entry has: `key`, `name`, `role`, `is_owner`, `is_member`, `is_subscriber`, `last_seen_at`, `metadata`
- [ ] Quilombo metadata folded in via `linked_co_user_id`
- [ ] At least 5 unit tests covering 0/1/N universes + quilombo link + subscription-only
- [ ] No regression on existing `/me` consumers — old fields still present at the same JSON paths

## Out of scope

- Cross-deployment fetches (depends on CO-172v2 architecture decision)
- Per-universe `last_seen_at` tracking (would need to record on every request — separate ticket if useful)
- User-defined per-universe tags / custom fields (the empty `user_universe_metadata` table is reserved but not used yet)
- SPA refactor to consume the new shape (separate PR after API ships)
