## Contexto
O co-auto hoje captura usage por **stream-json** e o re-parseia à mão
(`dev/co-auto/src/usage.rs`, **401 linhas** de NDJSON defensivo) antes de reportar
ao CO. O Claude Code já **emite usage como métricas OTel nativas**
(`claude_code.*`), então o produtor artesanal do CO-425 é redundante. A
infra OTLP já existe (CO-291, `co-web/src/infra/telemetry.rs`) — porém na direção
**export** (co-web → collector); aqui precisamos de co-web como **receiver**
(Claude Code → co-web), reusando as mesmas libs OTLP na direção de ingestão.

> **Por que não some o /usage/summary:** OTel é **push-only**. O downshift do
> CO-427 precisa **perguntar** "quanto gastei nas últimas 5h" (`GET /usage/summary`),
> o que um stream fire-and-forget não responde. Logo o **resumo consultável**
> permanece — mas é um read pequeno sobre dados OTLP ingeridos, não motivo pra
> parsear o produtor à mão.

## Design (opção self-hosted, sem infra nova)
1. **Produtor (co-auto)**: em `auto.rs`, ao lançar o Claude Code headless, **ligar a
   telemetria nativa** por env-var (`CLAUDE_CODE_ENABLE_TELEMETRY=1` +
   `OTEL_EXPORTER_OTLP_*` apontando pro receiver do co-web) e anexar **resource
   attributes** que o co-auto já conhece: `task_id`, `model`, `universe`, **`pr_url`**
   (recupera o pr_url que hoje é raspado do stdout). **Deletar `dev/co-auto/src/usage.rs`**
   e as chamadas em `lib.rs`/`auto.rs`/`routing.rs`.
2. **Receiver (co-web)**: endpoint OTLP de **métricas** (HTTP/protobuf — reusa deps
   do CO-291) que ingere `claude_code.*` e grava em **`agent_sessions`** (CO-275/426).
3. **Consumidor (mantém CO-426)**: `GET /usage/summary` (janela 5h pro CO-427) +
   `/usage/active` + dashboard Gestão — passam a ler o dado ingerido via OTLP.

## Perdas aceitas (menores)
- **`pr_url`** não vem no stream de métrica → recuperar como **resource attribute**
  (o co-auto já sabe o pr_url ao abrir o PR).
- Auth por subscription/keychain **não reporta USD** → `claude_code.cost.usage` pode
  vir **0**. Tudo bem: **token counts fluem** e é isso que a conta de orçamento
  (CO-427 budget math) usa.

## Acceptance
- [ ] `dev/co-auto/src/usage.rs` removido; sem regressão de compilação/uso em `lib.rs`/`auto.rs`/`routing.rs`.
- [ ] `auto.rs` liga a telemetria nativa do Claude Code (env-vars) com resource attrs `task_id,model,universe,pr_url`.
- [ ] co-web expõe um **OTLP metrics receiver** (reusa libs do CO-291) que grava `claude_code.*` em `agent_sessions`.
- [ ] `GET /usage/summary` (janela 5h) + `/usage/active` + dashboard (CO-426) continuam corretos lendo o dado ingerido.
- [ ] CO-427 downshift continua funcionando contra `/usage/summary` (token-based; USD pode ser 0 sob keychain).
- [ ] Testes: receiver ingere um OTLP metric de exemplo → linha em `agent_sessions`; `/usage/summary` agrega a janela.
- [ ] `cargo test` + `clippy -D warnings` + `fmt` limpos; sem MCP.
- [ ] Migração: só se o receiver precisar de coluna nova em `agent_sessions` — checar trem (tip atual v85 após CO-399); senão, **sem migração**.

## So that
Mesma observabilidade, menos superfície: o usage anda nos trilhos OTLP que o CO-291
já assentou, **menos ~400 linhas** de parsing NDJSON do CO-425 — antes de ligar a
telemetria pra **wave da janela-de-reset**.

## Não no escopo
- Rodar um OTel Collector separado (opção 2; só se o receiver self-hosted não bastar).
- Tocar o lado de export de traces do CO-291 (continua como está).
- Mudar a math de orçamento do CO-427 (só a fonte do dado muda).
