> **Phase 1 done.** `POST /api/v1/universes/:source/duplicate` with bulk-copy of all entry types into a target universe owned by the caller (1.20.0-1.20.1). Used for `quilombo-blog` clone during latency testing. Phases 2-4 (op log, replay, merge) are Tier 3 work in `ROADMAP-V1-LAUNCH.md` — likely months scale per the original framing, weeks with co-auto if we attack each phase as a distinct ticket.

GIVEN universes today are flat (one row per universe; entries scoped by `universe_key`) with no notion of lineage, and the user wants to:
- Duplicate `quilomboaraucaria` → `quilombo-blog` for parallel scalability + latency analysis
- Generalize this to a "dev branch" model where any universe can be forked, edited independently, and deployed alongside its parent
- Have state changes be immutable (append-only) so any state is deterministically reconstructible from `(parent + ops)`
- Convert easily from one branch to another (promote dev → main, revert main → previous snapshot, merge selectively),
WHEN we layer (1) **immediate**: an owner-controlled snapshot duplication endpoint shipped as 1.20.0; (2) **near-term**: an op log per universe (CO-61 lite) recording every entry mutation as an append-only event; (3) **medium-term, lands with CO-77**: per-universe SQLite where branching becomes a filesystem copy-on-write of the universe's DB file; (4) **long-term**: full git-like operations (merge / cherry-pick / revert) on the op log,
THEN universes gain Git-equivalent branching: snapshots are O(1) copies (after CO-77), every edit is replay-able, branches deploy independently at distinct `/co/<slug>` URLs, and the platform exercises the "deterministic content history" model that earlier specs (CO-61, CO-75) anticipated.

## The four properties (user's spec)

| Property | Status today | Achieved by |
|----------|-------------|-------------|
| **Independently deployable** | ✓ already (each universe has its own `/co/<slug>`) | Already true — no work needed |
| **State changes immutable** | ✗ entries table is mutable | CO-61 lite (Phase 2) — record ops; entries become a materialized projection |
| **Deterministically copyable** | ✗ today's `clone_universe` is best-effort SQL | CO-95 Phase 1 (snapshot) → Phase 4 (op replay) for fully deterministic |
| **Easily convertible** (promote / merge) | ✗ no merge primitive | CO-95 Phase 4 — apply branch's ops onto another base; conflict resolution via CO-54 idempotency |

## Phasing

### Phase 1 — owner-controlled snapshot duplication (1.20.0, this commit)

**The user's immediate need.** New endpoint:

```
POST /api/v1/universes/:source/duplicate
Body: { "key": "quilombo-blog", "name": "Quilombo Blog (perf-test)", "description": "..." }
Auth: Bearer JWT or API token (resolve_user_id helper)

Effect:
- Verify caller has read access to :source (owner / member / public / template)
- Verify target key is unused
- Bulk-copy entries from :source → new universe (single transaction)
- New universe owned by caller; visibility = private (default)
- Returns new universe metadata
```

Differences from existing `/clone`:
- Requires authentication (no anon-clone path here)
- Allows duplicating ANY universe the caller has access to (not just public/template)
- New owner = the caller (not anon-XXX with cookie)

Storage method: reuses `Storage::clone_universe` (existing — already does deep entry copy with project key renumbering).

### Phase 2 — universe-scoped op log (1.22.0+, CO-61 lite)

Add an `ops` table:

```sql
CREATE TABLE ops (
    universe_key TEXT NOT NULL,
    op_id INTEGER NOT NULL,        -- monotonic per universe
    op_type TEXT NOT NULL,         -- 'put_entry' | 'delete_entry' | 'rename' | …
    path TEXT NOT NULL,
    payload_hash TEXT,             -- SHA-256 of new body (for `put_entry`)
    payload BLOB,                  -- the new body (or NULL on delete)
    parent_op_id INTEGER,          -- previous op on same path (for chains)
    author_id TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (universe_key, op_id)
);
CREATE INDEX idx_ops_universe_path ON ops(universe_key, path);
```

Every PUT / DELETE on `/api/v1/universes/:k/vault/*` ALSO appends to `ops`. The `entries` table becomes a materialized projection of "current state" derived from the ops history. Reads still hit `entries` (fast). The op log is the source of truth.

Recording-only at first; replay engine comes in Phase 3.

### Phase 3 — replay engine + true determinism (CO-75 era, after CO-77)

Given `(base_universe, base_op_id, target_op_id)`, the replay engine reconstructs entry state by re-applying ops in order. Useful for:
- "Show this entry as of last Tuesday" (CO-75)
- "What's the diff between branch A and branch B at op X?"
- Forensic / audit trails

Branches now have lineage:

```sql
ALTER TABLE universes ADD COLUMN parent_universe_key TEXT;
ALTER TABLE universes ADD COLUMN forked_at_op_id INTEGER;
ALTER TABLE universes ADD COLUMN forked_at TEXT;
```

Branch creation now records lineage. After CO-77 (per-universe SQLite), branch creation is filesystem copy-on-write — O(1) regardless of universe size. The op log is preserved across the fork; the branch starts with a fresh op_id sequence.

### Phase 4 — merge / promote / revert (3.x)

Operations on branches:

| Operation | Semantics |
|-----------|-----------|
| **Promote** branch → main | Replay branch's ops onto main's HEAD. Conflicts surface via CO-54 idempotency rules (3-way merge, last-write-wins or manual resolve). |
| **Revert** main to snapshot | Create a new branch at the historical op, then promote it. Original main becomes an orphan branch (kept for history). |
| **Cherry-pick** ops | Apply selected ops from one branch onto another. |
| **Diff** branches | Walk both op logs from their common ancestor; surface adds, deletes, conflicts. |

API surface:

```
POST   /api/v1/universes/:branch/promote      # merge into parent
POST   /api/v1/universes/:branch/revert?to=<op_id>
POST   /api/v1/universes/:branch/cherry-pick   { from: "...", op_ids: [12, 17, 23] }
GET    /api/v1/universes/:branch/diff?against=<other-branch>
```

This is the full git-like surface.

## Use cases

1. **Latency / scalability A/B testing** (the user's stated case):
   - Duplicate `quilomboaraucaria` → `quilombo-blog`
   - Configure different cache / index / replica settings per universe (manifest CO-70)
   - Hit each with synthetic load; compare metrics in the dados universe (CO-46 telemetry)

2. **Materialized dev branch**:
   - `co` (main, public) ↔ `co-dev` (development board) — already informally exists; CO-95 makes it formal
   - Drafts of changes land in `co-dev`; promotion writes them to `co`
   - Pre-production verification before user-visible rollouts

3. **Pre-publish preview**:
   - Author makes a "preview" branch of their public-static universe
   - Edits in preview don't affect public traffic
   - When ready: promote preview → public

4. **Disaster recovery**:
   - Per-universe snapshots become trivial backups
   - Restore = create a branch at the desired op, then promote

5. **Experimentation**:
   - Try a new manifest schema (CO-70) on a branch
   - If it works: promote to main
   - If it doesn't: drop the branch

## Tradeoffs

- **Phase 1 is a snapshot, not a branch.** No lineage, no merge. Source and copy diverge as independent universes. This is the SHIP-TODAY answer; full branching arrives in 2.x with op log + per-universe SQLite.
- **Op log adds storage cost.** Every PUT writes twice (entries + ops). Acceptable: ops are bounded; entries are the projection. Periodic compaction prunes old ops once snapshots cover them.
- **Merge conflicts are hard.** Three-way merge of structured content (frontmatter + body) needs care. Phase 4 starts with last-write-wins; manual conflict resolution comes later (CO-54).
- **Branch proliferation.** Without UI hygiene, users could create dozens of stale branches. Mitigation: branch lifecycle (active / archived / deleted); per-user quota (CO-80).

## Acceptance

### Phase 1 (this release)

- `POST /api/v1/universes/quilomboaraucaria/duplicate` with body `{"key":"quilombo-blog","name":"…","description":"…"}` returns 201 + new universe metadata
- The new universe has all source entries (verified via `/api/v1/universes/quilombo-blog/vault/`)
- New universe is owned by the caller, visibility = private
- Source universe is unchanged
- Subsequent edits to source DON'T affect the copy and vice versa

### Phase 2

- Every vault PUT/DELETE writes a row to `ops` (visible via internal endpoint)
- Op count grows monotonically per universe
- Crash mid-write doesn't desync (transaction includes both entries + ops)

### Phase 3

- `GET /api/v1/universes/<u>/replay?to_op=<n>` returns the entry state at op N
- Diff between two op IDs shows exact change set
- Per-universe SQLite (CO-77) makes branch creation O(1)

### Phase 4

- Promote / revert / cherry-pick / diff endpoints functional
- Merge conflicts surface clearly (not silently dropped)
- Audit log shows every promote with author + timestamp
