GIVEN universes can ship code (Scala, Python, TypeScript, Rust, etc.), the manifest declares which doc generators to invoke, and these tools take 10-60s — they cannot block request threads,
WHEN doc-generator runs are submitted as jobs to the worker queue (CO-78), each producing entries with `type: doc.<format>`,
THEN documentation appears on the board alongside hand-written content, refreshed on universe sync or webhook.

## Adapters (v1)

- scaladoc → entries with parsed sections (package, class, method)
- sphinx → entries from `.rst` builds (HTML output → markdown via `rehype`)
- mkdocs → entries from rendered Markdown
- redoc / openapi → entries per endpoint with request/response schemas
- rustdoc → similar to scaladoc
- jsdoc / typedoc → for JS/TS

## Tasks

- [ ] Job submission API: `POST /api/v1/universes/:slug/jobs/doc-gen` (owner only)
- [ ] Worker pool integration (CO-78): jobs run in dedicated Fly machines with sandbox toolchains pre-installed
- [ ] Adapter trait: `fn run(source_dir: Path, output_type: String) -> Result<Vec<Entry>>`
- [ ] Idempotency: same source hash + adapter version = same output entry set; skip rerun
- [ ] Failure surfacing: store last error on universe; expose in UI ("scaladoc failed at 2026-04-26 …")
- [ ] Resource limits per job: 5 min wall time, 2 GB RAM, 1 GB output

## Scale notes

- Doc generators are CPU-heavy — **must** run on dedicated workers, never request threads
- Per-universe rate limit (CO-80): max 10 doc-gen runs per hour per universe
- Output entries can be hundreds of MB (large APIs); store payload references to blobs (CO-81), not inline
- Worker concurrency: pool of 4-16 machines; autoscale on queue depth
- Cold start: pre-installed Docker images per adapter (Scala, Python, Node, Rust)

## Acceptance

- `_universe.yaml` declaring scaladoc on `src/main/scala` produces entries on the board within 60s of repo update
- Failed doc-gen run surfaces error to owner; doesn't crash worker
- Concurrent doc-gen jobs across universes don't starve each other (queue fairness)
