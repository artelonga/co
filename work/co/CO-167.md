## As

an existing quilombo user who registered with a username and password (no email) before CO-166 unified auth existed

## I Need

a way to attach an email address to my quilombo account

## So That

(a) I can link my quilombo account to a CO identity via the OIDC flow from CO-166,
(b) I can receive notifications (events, missions, messages) when CO-168 ships,
(c) account recovery has a channel that isn't "ask an admin"

---

## Current state (1.76.0)

`quilombo_usuarios` schema: `id, usuario, nome, senha_hash, papel, bio, foto_url, linked_co_user_id, criado_em, atualizado_em`.

No `email` field. CO-166 added `linked_co_user_id` but users can't link without a CO account, and they can't create a CO account without an email. This is the gap.

## Design

### Storage

Migration v34 — add nullable unique email column to `quilombo_usuarios`:

```sql
ALTER TABLE quilombo_usuarios ADD COLUMN email TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_quilombo_usuarios_email ON quilombo_usuarios(email) WHERE email IS NOT NULL;
```

Nullable (existing users have no email). Unique so two users can't share an address.

### API changes

**`PUT /api/v1/quilombo/perfil`** gains an optional `email` field. Validates format, checks uniqueness, writes to DB.

**`POST /api/quilombo/auth/login` response** gains a `missing_email` boolean flag (true when the authenticated user has no email set). The client uses this to decide whether to show the nudge.

**`GET /api/v1/quilombo/admin/usuarios`** gains an `email` field per user so admins can see who has linked.

### UX flow (client-side, documented — Rust delivers the data, front-end implements the banner)

1. User logs in with username/password → response includes `missing_email: true`
2. Client shows a dismissible banner: *"Adicione um email para habilitar recuperação de conta e notificações."*
3. Banner has an input + "Salvar" button → `PUT /api/v1/quilombo/perfil` with `{ email: "..." }`
4. On success: banner disappears, `missing_email` omitted from next login response

### Admin visibility

`GET /api/v1/gestao/quilombo/stats` (or extend existing admin summary) returns:
- `total_usuarios`
- `com_email` (count with email set)
- `vinculados_co` (count with `linked_co_user_id` set)

## Acceptance

- [ ] Migration v34 adds `email TEXT` (nullable, unique) to `quilombo_usuarios`
- [ ] `PUT /api/v1/quilombo/perfil` accepts and validates `email`; returns 409 if already taken
- [ ] `POST /api/quilombo/auth/login` response includes `"missing_email": true` when user has no email
- [ ] `GET /api/v1/quilombo/admin/usuarios` includes `email` per user row
- [ ] Admin stats endpoint exposes `com_email` + `vinculados_co` counts
- [ ] Test: setting email works; duplicate email returns 409; login response flag correct

## Out of scope

- Email verification (sending a code to confirm ownership) — useful but deferred; trust for now
- Forced email requirement at login — nudge only, not a gate
- Password reset via email — separate ticket (CO-165 recovery, post-CO-168 when email channel exists)

~½ day. Migration + two small API changes + tests.
