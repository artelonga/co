## As
A platform operator wanting sister-repo content (mbya lexicon, topologia adapters, comunicacao sources, ArteLonga refs, etc.) to land on the prod CO instance, not just localhost

## I Need
CO universes to optionally pull their content from a remote git URL on the production machine, mirroring what `local_repo_path` does on localhost.

## So That
- Content from sister repos (e.g., the 13 source records just added to `~/projects/comunicacao/sources/`) reaches `co-artelonga.fly.dev` without requiring a Docker rebuild + CO redeploy
- Yggdrasil + ArteLonga can query CO's prod API for canonical lexicon/source data without each site shipping a duplicated copy
- The "deploy-free content integration" principle (CO-330) extends from localhost to prod

## Problem

CO-330 added `universes.local_repo_path` for local-dev bindings. The seed orchestrator walks that path on every `co serve` boot. **On prod the path doesn't exist** — there's no `~/projects/comunicacao/` on the Fly machine, only the `/data` volume.

Today, prod content reaches CO via three mechanisms:
1. CO's own `work/co/` → Docker `COPY work/co/ /app/seed-co/` at build time (CO-310)
2. Admin-seeded universe rows (template, quilombo, yggdrasil, timeline trio) via `seed_admin_content_universes`
3. User CRUD via the API

Sister-repo content (mbya, topologia, comunicacao sources, ArteLonga refs) reaches **only localhost**. Prod gets a stub at best.

## Design

### Schema extension

Add `remote_url` to the `universes` table (additive, nullable):

```sql
ALTER TABLE universes ADD COLUMN remote_url TEXT;          -- "https://github.com/artelonga/comunicacao"
ALTER TABLE universes ADD COLUMN remote_ref TEXT;          -- "main" | "v1.2.3" | "<sha>"
ALTER TABLE universes ADD COLUMN remote_last_sync TEXT;    -- ISO timestamp of last successful clone/pull
```

### Resolution order (when seeding a universe's content)

1. If `local_repo_path` is set AND the path exists → use that (existing CO-330 behavior; dev convenience)
2. Else if `remote_url` is set → clone/pull to `<data-dir>/remote-repos/<universe_key>/`, then walk `content_subdirs` of that
3. Else → no content seeded (existing behavior)

The same `seed_universe_from_local_repo` machinery is reused for step 2 — only the path differs.

### Clone/pull mechanism

Reuse CO-331's `vcs::` abstraction:
- First sync: `git clone --depth=1 <remote_url> <data-dir>/remote-repos/<universe_key>/`
- Subsequent: `git fetch && git checkout <remote_ref>` (or `git pull --ff-only`)
- Auth: SSH key from Fly secrets for private repos; HTTPS for public

Cadence:
- At `co serve` boot
- On a configurable interval (default: every 15 min in prod)
- Webhook-triggered (Phase 2): `POST /api/v1/universes/<key>/refresh` fires a re-sync on demand

### Universe management API extension

```
PATCH /api/v1/universes/<key>/source
{
  "local_repo_path": "~/projects/comunicacao",            // dev override
  "content_subdirs": ["docs", "content", "sources"],
  "remote_url": "https://github.com/artelonga/comunicacao",
  "remote_ref": "main",
  "anon_published_only": false
}
```

All fields optional. CO-330's existing PATCH already accepts `local_repo_path` + `content_subdirs` + `anon_published_only`; this adds `remote_url` + `remote_ref`.

### Sync orchestrator

New `run_remote_sister_repo_seeds(config)` step that:
1. Queries universes WHERE `remote_url IS NOT NULL`
2. For each: ensures clone exists at `<data-dir>/remote-repos/<key>/`, fetches latest
3. Walks `content_subdirs` of that clone (same logic as CO-330 + CO-319 — upsert; idempotent)
4. Updates `remote_last_sync` to now

Runs at boot + every 15 min via a background tokio task.

### Authentication for private repos

Most sister repos are public; `https://github.com/artelonga/<repo>` clones fine without auth.

For private repos:
- Env var `CO_GIT_SSH_KEY_PATH` pointing at a Fly secret (mounted file)
- Or HTTPS with `CO_GIT_TOKEN` env var (GitHub personal access token)

Document both in `docs/sister-repo-sync.md` (new file).

### Initial deployment plan (one-time backfill)

After v2.39.0 (this PR ships) deploys:

```bash
# Set remote_url for each sister universe — via PATCH or one-shot migration
flyctl ssh console -a co-artelonga -C "sqlite3 /data/meta.db \
  \"UPDATE universes SET remote_url='https://github.com/artelonga/comunicacao', remote_ref='main' WHERE key='comunicacao';\""
# Repeat for mbya, topologia, ArteLonga, yggdrasil, rfq-gateway

# Restart machine to trigger first sync
flyctl machine restart -a co-artelonga
```

Or include the backfill UPDATEs in the migration if the patterns are stable.

## Dependencies

- **CO-330** ✓ shipped — local_repo_path + content_subdirs columns + filter
- **CO-331** ✓ shipped — `vcs::` helpers (git + jj-compatible) reusable
- **CO-319** ✓ shipped — always-reseed on boot (no skip threshold)
- **CO-334** ✓ shipped — once remote content lands, changelog aggregator picks up sister CHANGELOG.md files automatically

## Not in scope

- Push (write content back to remote) — out of scope; CO is read-only consumer
- Selective file sync / partial clone — full clone with shallow depth=1; refinements later
- Conflict resolution between local + remote — local wins by design (dev override)
- Multi-branch tracking — single ref per universe
- Submodule support — git clone with `--recurse-submodules=no` (avoid complexity)
- Webhook-driven instant sync — Phase 2 follow-up

## Why now

- **Immediate trigger**: the 13 source records (and the migrated nhandereko/ayvu-rapyta terms) just landed in `~/projects/comunicacao/sources/`. Localhost picks them up on next `co serve`. Prod can't, today. Yggdrasil's planned `/fontes` route depends on CO prod serving these.
- **Architectural alignment**: CO-330 promised "any repo, any content, no deploy." That's only true for localhost today. CO-337 finishes the job.
- **Yggdrasil integration**: once sister-repo content is on prod, Yggdrasil can fetch from CO's public API (`GET /api/v1/universes/comunicacao/entries?type=source`) — single source of truth across the platform.
