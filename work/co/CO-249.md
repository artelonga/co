## As

An operator (yuri today, anyone tomorrow) maintaining the ArteLonga repo cluster on their local machine and on prod

## I Need

`gari` — the cleanup script born during Phase C — to integrate with CO as a first-class state-change emitter, so every deletion is auditable, queryable, and surfaced in the CO board / web UI

## So That

Cleanup stops being a black-box "I freed some disk" and becomes a first-class event stream: "Gari deleted 259 GiB on 2026-05-19 at 10:22 UTC across these 43 paths, on host yuri@Yuris-MacBook-Pro." Visible in CO, queryable via DuckDB attach (CO-244), exportable to Iceberg.

## Context

- **Principles:** §7 (event-driven — every action is a state change), §3 (static typing — typed JSONL schema), §4 (reduced coupling — Gari emits events; CO consumes; no shared state)
- **Status now (Phase 1 — already shipped):**
  - `scripts/gari` runs locally (macOS first; should work on Linux with the `du -sb` shim already added).
  - `--execute` / `--dry-run` / `--only <cat>` / `--yes` (non-interactive) / `--event-log <path>` flags.
  - Each deletion appends one JSONL row to `$HOME/projects/co/data/gari-events.jsonl` with: `{ts, host, user, mode, category, path, bytes_freed}`.
  - First run reclaimed 259.1 GiB (43 events: 15 target/, 19 stale worktrees, 9 node_modules).

- **What's missing for "every action is a state change in CO":**
  - The JSONL stays local. CO's board / web doesn't see it.
  - No cross-machine view (yuri's laptop + future contributors + prod).
  - No structured aggregation, no audit trail in entry_events.
  - No web-side Gari (prod has its own cruft — stale anonymous clones, expired tokens, ageing assets).

## Scope

### Phase 2 — local-to-CO event upload

After each `gari --execute` run, post a single batch event entry to a new CO universe `ops`:

```
POST /api/v1/universes/ops/vault/events/2026-05-19/2026-05-19T10:22:12Z-<host>-<runid>.md
Content-Type: text/markdown

---
ts: 2026-05-19T10:22:12Z
host: Yuris-MacBook-Pro
user: yuri
gari_version: 0.1.0
mode: execute
total_bytes_freed: 278246002688
events_count: 43
categories:
  target: { count: 15, bytes: 276983468032 }
  worktree: { count: 19, bytes: 357412864 }
  node_modules: { count: 9, bytes: 905121792 }
---

## Per-event detail

```jsonl
{"ts":"2026-05-19T10:22:12Z","category":"target","path":"/Users/yuri/projects/co/target","bytes":223178653696}
{"ts":"2026-05-19T10:22:13Z","category":"target","path":"/Users/yuri/projects/co/.worktrees/CO-21/target","bytes":1304891392}
…
```
```

The `ops` universe:
- Owner: system
- Visibility: `private` (admin-only)
- Schema: defines `gari-run` content_type with the frontmatter above
- Every write logs to `entry_events` (Iceberg-compatible per the transaction-log doc)

Implementation: a `--co-upload` flag on `gari` that requires `CO_AUTH_TOKEN` env var (API token, 90-day, per CO-236 future CLI). Best-effort — upload failure logs to stderr but doesn't fail the cleanup.

### Phase 3 — web aggregation view

Add a `/ops/gari` view in the CO web SPA showing:
- Recent runs table (host, ts, total freed, categories)
- All-time total reclaimed per host
- Category breakdown chart (SVG)
- "Stale worktrees that came back" alert (worktree X deleted twice in 30 days = co-auto isn't cleaning up properly)

Uses the `ops` universe's entries + the same chart engine as the existing dashboard.

### Phase 4 — web-side Gari (prod cleanup)

A complementary `gari-prod` that runs ON the Fly machine via cron / launchd:
- **Stale anonymous universes**: clones unused for >30 days with `content_count < 5` and no logged-in claim → delete
- **Expired API tokens**: hard-delete rows in `api_tokens` where `expires_at < now`
- **Old encrypted assets without entry references**: orphaned blob files (CO-148 trail allows this)
- **Old entry_events rows** (optional, with explicit retention policy): events >1 year old can be exported to Iceberg cold storage + dropped from SQLite

Each deletion → entry in `ops` universe via internal vault PUT. Same audit trail as local Gari.

Configurable per-policy retention. Defaults conservative.

### Phase 5 — multi-platform parity

Currently macOS-first. Make `gari` work on:
- **Linux**: `du -sb` works natively. Already handled via shim. Verify on Fly machine + a Ubuntu dev VM.
- **Windows**: harder — bash + `du` + `find` need WSL or Cygwin. Or: port to a Rust binary `co gari` in co-cli (cleaner). Aligns with CO-235 "co clone <url>" + CO-236 "co auth" CLI vision — `co gari --execute` becomes the canonical path.

## Acceptance

### Phase 2
- New CO universe `ops` exists in seed with the gari-run content type.
- `gari --execute --co-upload` uploads a single entry per run.
- `entry_events` of the `ops` universe contains one row per Gari run.
- Curl `/api/v1/universes/ops/entries?type=gari-run` returns the run history.
- Token-based auth (Bearer) supported; cookie fallback for interactive use.

### Phase 3
- `/ops/gari` view in SPA shows aggregated runs.
- Sortable by host / category / date.
- Empty-state message when no runs yet.

### Phase 4
- `gari-prod` binary or shell script deployed to Fly + scheduled via launchd / cron.
- Conservative defaults; explicit `--execute` required.
- Each prod deletion writes to `ops` universe just like local.

### Phase 5
- `co gari` subcommand in co-cli (Rust port).
- Tested on macOS + Linux + (optional) Windows via WSL.
- Bash version (`scripts/gari`) remains for backward compat; deprecated in 6+ months.

## Blast radius

- Phase 1: Done — zero impact (additive script).
- Phase 2: New `ops` universe + 1 new env var + 1 new flag. Backward compat preserved.
- Phase 3: New SPA route + DuckDB query path. Add-only.
- Phase 4: New scheduled job on prod. Requires careful default policies + dry-run mode.
- Phase 5: co-cli port — replaces bash script over time. Discoverability win.

## Cross-cutting

- Builds on **CO-244** (Python/R REPL via DuckDB attach) — once events live in `ops/data.db`, analysts can query directly.
- Builds on **CO-236** (`co auth` CLI) — auth flow shared with `co gari`.
- Builds on **CO-148** (encrypted assets) — phase 4's orphan-blob cleanup uses the same path/key scheme.
- Builds on the **transaction-log roadmap** (`co::public/transaction-log.md`) — Gari events become a stream in the Iceberg catalog.
