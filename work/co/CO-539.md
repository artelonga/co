GIVEN after the Fly → M4 cutover (CO-538) prod runs on a SINGLE box — the Mac M4 —
whose accepted near-term resilience is anti-sleep + UPS + auto-restart + off-box
backups, but the owner wants a real failover path EVENTUALLY (a single box can die:
hardware, network, prolonged power loss, a botched upgrade),
WHEN we add cloud resilience without re-introducing a managed-prod dependency,
THEN provide a small cloud failover/backup standby the Cloudflare edge can use when
the M4 is unreachable, with a tested failover/restore drill — and keep it cheap and
scale-to-zero so the M4 stays the primary.

> **DEFERRED.** Anti-sleep + UPS + auto-restart + verified off-box backups (CO-538
> step 5) is the accepted profile for now. This task is the next increment, not a
> launch blocker.

## Options (pick one to start; (a) is the floor)

- **(a) Minimum — cold restore to cloud (already mostly covered).** Off-box
  replication exists (Litestream `meta.db` + `restic`/tar of `universes/`). The new
  work is a *documented, tested* cold-restore-to-cloud runbook: stand up a throwaway
  cloud node (or a re-pointed Fly/Modal/Fly-CPU box), `litestream restore` meta.db +
  extract the latest `universes/` snapshot, boot `co-web --no-build` on the prebuilt
  binary, flip the Cloudflare route. RTO = minutes-to-an-hour, RPO = last replica.
- **(b) Warm standby — Cloudflare failover origin.** A tiny scale-to-zero cloud node
  (the same `target/release/co-web` + a periodically-synced `$CO_WEB_DATA` from the
  backups) registered as a **secondary origin** behind a Cloudflare Load Balancer
  with health-check failover (or a failover-origin rule). When the M4 health check
  goes red, the edge fails traffic over to the standby automatically; reads keep
  working, writes reconcile on M4 recovery (define the write-during-failover policy —
  read-only standby is the safe default to avoid split-brain on SQLite).

## Acceptance

- [ ] The standby exists (option (a) runbook fully written + scripted, or option (b)
  standby node + Cloudflare LB/failover config provisioned).
- [ ] A **failover drill** is performed and documented: simulate M4-unreachable,
  confirm the Cloudflare edge serves from the standby (option b) or the cold-restore
  runbook brings prod back on cloud within the target RTO (option a).
- [ ] A **restore drill** proves the standby's data is current: `verify-restore.sh`
  (or equivalent) green against the standby's copy; RPO documented.
- [ ] No split-brain: the write/reconcile policy for failover is defined (read-only
  standby default) and tested — SQLite is the operational truth, so concurrent writers
  are forbidden.
- [ ] Cost stays near-zero at rest (scale-to-zero standby) so the M4 remains primary.
- [ ] `docs/SELF-HOST.md` gains a "Cloud failover / standby" section pointing at the
  drill.

## Notes

- Stay inside the self-host posture (CO-497): the standby is *our* operator choice,
  the app never *requires* managed infra. The standby runs the identical binary.
- Cloudflare GPU/Fly GPU deprecation does not apply (this is a CPU web node).
- Sequence after CO-538 lands and the M4 has soaked as prod.
