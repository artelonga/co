GIVEN the agent bridge already groups tools into **capability packs** (`PACKS` in
`tools/whatsapp-bot/bridge/capabilities.py`) so an agent gets a curated, enable-able
set of tools — but CO's native runtime has no equivalent, so capabilities can't be
scoped per-universe or per-user,
WHEN we promote capability packs into CO as a first-class concept (a named group of
canonical tools with per-universe / per-user enable + config),
THEN an operator can decide *which* tools a given agent has in a given universe for a
given user, without code changes — the grouping is data, not hardcoded.

## Acceptance

- [ ] A **capability pack** is a named set of canonical tools (CO-503) with optional
  per-tool config; packs are enumerable and describable.
- [ ] **Per-universe enablement**: a universe can enable/disable packs; an agent in
  that universe only sees the enabled capabilities.
- [ ] **Per-user enablement/config**: a user's grants can further narrow (or configure)
  what an agent may do on their behalf, consistent with CO identity/consent.
- [ ] The bridge's existing `PACKS` are **migrated** to the CO capability registry
  (the bridge consumes CO's packs, not its own copy).
- [ ] **DB-driven**, not hardcoded: enablement/config lives in storage so adding or
  scoping a pack needs no deploy (per `feedback_no_hardcoded_content_mappings`).
- [ ] No tenant-specific pack names baked into the open platform; tenant scoping is a
  mapping row, not code.

## Notes
- Depends on CO-503 (tools) and CO-504 (runtime that consumes packs).
- Packs are how an operator answers "what can this agent do here?" — the unit of
  least-privilege for agents.
- Term is **capability/capacidade** + **agent/agente**, never "bot".
