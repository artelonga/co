GIVEN today's content travels as raw markdown over HTTP — readable but un-typed (frontmatter is YAML strings until parsed), un-versioned, un-signed, with attachments referenced by path that the receiver may not have, and no compression/encryption envelope; AND the platform aims to be the canonical home for content that flows between localhost ↔ API ↔ web ↔ mobile with privacy as a first-class concern,
WHEN we define `co` as a self-describing protobuf-encoded data type that wraps `frontmatter (typed) + form (presentation hints) + content (markdown body) + attachments + signatures + telemetry`, with full markdown round-trip and an extensible attachment graph,
THEN every transport (filesystem, Vault API, sync protocol, mobile, peer-to-peer) carries the same self-contained binary; encryption / compression / signing become composable layers around the same envelope; markdown stays the primary authoring medium but stops being the wire format.

## Rationale: why a binary protocol-buffer format

Markdown is the *authoring* surface, not the *transport* surface. Plain `.md` over HTTP is:
- **Untyped** — frontmatter is a YAML blob the receiver re-parses; types drift
- **Un-versioned** — no schema_version field; breaking changes require parallel parsers
- **Un-signed** — no integrity check; man-in-the-middle on a flaky network can corrupt silently
- **No native encryption envelope** — TLS protects in transit but the file at rest is plaintext
- **Bloated for transfer** — repeated YAML keys, whitespace, no compression
- **Attachments-by-reference** — `![](images/foo.png)` requires a second fetch and breaks offline
- **Unparseable streaming** — must read whole file before semantic content available

A protobuf-wrapped envelope addresses all of these in one shape and stays markdown-compatible.

## Wire format (proto3)

```protobuf
syntax = "proto3";
package co.v1;

// Top-level container. Every transport carries one of these per logical file.
message CoFile {
    // --- Header: always cleartext for routing/dispatch ---
    string version = 1;             // semver of the schema, e.g. "1.0.0"
    string content_type = 2;        // "co/markdown", "co/composite", "co/encrypted"
    string content_hash = 3;        // SHA-256 of the canonical body bytes (post-decrypt)
    int64  created_at_ns = 4;       // nanos since epoch UTC
    int64  modified_at_ns = 5;
    string author_id = 6;           // who wrote this revision
    string universe_key = 7;        // scoping namespace
    string entry_path = 8;          // logical path within universe (e.g. "sobre.md")

    // --- Metadata: typed frontmatter ---
    Frontmatter frontmatter = 9;

    // --- Form: presentation hints (CO-63 manifest declares the schema) ---
    Form form = 10;

    // --- Body: the actual content (one of) ---
    oneof body {
        bytes markdown = 11;        // raw UTF-8 markdown
        bytes compressed = 12;      // zstd-compressed markdown
        Encrypted encrypted = 13;   // chacha20-poly1305 envelope
        Composite composite = 14;   // multipart (e.g. markdown + many attachments)
    }

    // --- Attachments graph (images, embeds, transcripts) ---
    repeated Attachment attachments = 15;

    // --- Signatures (Ed25519 by default) ---
    Signature signature = 16;

    // --- Wire-level telemetry (server populates; clients may include) ---
    Telemetry telemetry = 17;
}

message Frontmatter {
    // Common typed fields. Anything else lands in `extra` (Struct = JSON-like).
    string title = 1;
    string description = 2;
    string entry_type = 3;          // "page", "task", "evento", "doc.scala", …
    repeated string tags = 4;
    string status = 5;              // "todo", "doing", "done", or content-type-specific
    string priority = 6;
    string parent = 7;              // parent entry path
    string assignee = 8;            // user id (CO-74 ref:pessoa)

    // Temporal (CO-73)
    int64 created_at_ns = 20;
    int64 due_at_ns = 21;
    int64 scheduled_at_ns = 22;
    int64 event_at_ns = 23;
    int64 published_at_ns = 24;
    int64 expires_at_ns = 25;
    int64 effective_at_ns = 26;
    string timezone_iana = 27;      // "America/Sao_Paulo" — needed when human-meaningful

    // Open extension for content-type-specific fields, validated against
    // the universe's manifest (CO-70).
    google.protobuf.Struct extra = 30;
}

message Form {
    string theme = 1;               // palette key
    string layout = 2;              // "board", "list", "calendar", "graph", "gantt"
    string view_hint = 3;           // free-form layout token
    google.protobuf.Struct overrides = 4;  // CSS custom-property overrides
}

message Attachment {
    string id = 1;                  // stable id (sha256 of content; matches blob CAS)
    string name = 2;                // "diagram.png", "audio.mp3"
    string mime = 3;                // "image/png"
    int64  size_bytes = 4;
    AttachmentSource source = 5;
    Encryption encryption = 6;      // optional per-attachment envelope
}

message AttachmentSource {
    oneof source {
        bytes inline = 1;           // small attachments (<256 KB) inline
        string blob_ref = 2;        // CO-81 blob store: "sha256:abcd..."
        string url = 3;             // external (signed url, etc.)
    }
}

message Composite {
    bytes markdown = 1;             // primary body
    // attachments referenced by id from the markdown lend coherence
}

message Encrypted {
    string algo = 1;                // "chacha20-poly1305"
    bytes  ciphertext = 2;
    bytes  nonce = 3;
    bytes  encrypted_key = 4;       // wrapped per recipient
    string key_recipient = 5;       // recipient's public key id
}

message Encryption {
    string algo = 1;
    bytes  encrypted_key = 2;
}

message Signature {
    string algo = 1;                // "ed25519"
    bytes  signature = 2;
    string signer_pubkey_id = 3;
}

message Telemetry {
    int64 size_uncompressed = 1;
    int64 size_compressed = 2;
    int64 size_on_wire = 3;         // post-encryption
    string codec = 4;               // "raw" | "zstd-3" | "zstd-19" | "br-11"
    int64  encode_ns = 5;
    int64  decode_ns = 6;
}
```

## Markdown ↔ `.co` round-trip

```
.md (authored) ──parse──> CoFile { frontmatter, body=markdown(...) } ──encode──> bytes (.co)
                                                   │
bytes (.co) ──decode──> CoFile ──serialize_markdown──> .md (faithful: same frontmatter + body)
```

- `frontmatter` field maps 1:1 to YAML keys; round-trip preserves order via `Struct` field ordering rules.
- `body.markdown` field is the literal markdown bytes (UTF-8). No transformation.
- An encoder MUST produce a byte-identical decode for the same input (modulo whitespace normalization in YAML re-emit, which is acceptable per Keep-A-CHANGELOG-style tolerance).

## Protocol stack composition (informs CO-87)

The same `CoFile` is the message at every layer:

```
                    [ application — user reads/writes markdown ]
                                       │
                              encode/decode CoFile
                                       │
                  ┌──── compression layer (zstd/brotli/none) ────┐
                  │                                               │
                  ├──── encryption layer (chacha20 / none) ───────┤
                  │                                               │
                  ├──── signing layer (Ed25519 / none) ───────────┤
                  │                                               │
                  ├──── transport layer (file / api / s3) ────────┤
                  │                                               │
                  └─────────── physical layer (disk / net) ───────┘
```

Each layer is implemented as a trait (CO-87) and composed at call site. Same `CoFile` flows through.

## Why protobuf (not JSON / msgpack / bincode / cbor)

| Format | Self-describing? | Versioned? | Cross-lang? | Binary efficient? | Schema as code? |
|--------|------------------|------------|-------------|-------------------|-----------------|
| JSON | partial | no | yes | no | no |
| YAML | partial | no | yes | no | no |
| msgpack | yes | no | yes | yes | no |
| cbor | yes | no | yes | yes | no |
| bincode | no | no | Rust-only | yes | no |
| **protobuf** | **yes** | **yes** | **yes** | **yes** | **yes** |
| flatbuffers | yes | yes | yes | yes (zero-copy) | yes |

Protobuf wins on schema-evolution + cross-language. Flatbuffers is a fair alternative; chose protobuf because the `prost` crate is already in the co-web dep tree (used by `core/proto/`) and the platform team's mental model is protobuf-native. Flatbuffers is a reconsideration point if read-side allocation cost matters.

## Naming + extensions

- File extension on disk: `.co`
- Mime type: `application/vnd.co+protobuf` (registered with IANA later)
- Magic bytes: first 4 bytes are `b"co\x01\x00"` for fast discrimination from `.md`
- Plain markdown remains supported via a "auto-wrap" decoder: a bare UTF-8 markdown file is wrapped on read into a default `CoFile` with empty signatures/encryption.

## Acceptance

- A 10 KB markdown file round-trips through encode/decode with byte-identical body and frontmatter equivalence
- A `.co` with `body=encrypted{...}` decrypts only with the right key; tampering changes the SHA-256 and fails verification
- A `.co` with `signature=...` verifies under the signer's pubkey; mutating any byte fails
- Vault API serves both `text/markdown` and `application/vnd.co+protobuf` for the same entry, content-negotiated
- Server-side telemetry tracks bytes-on-wire vs uncompressed, per universe (feeds CO-88)
- CLI `co inspect` shows: `version`, `content_type`, `size_uncompressed`, `size_on_wire`, `signed=yes/no`, `encrypted=yes/no`, `attachment_count`

## Tradeoffs

- **Schema rigidity** — adding new typed frontmatter fields requires a `.proto` change + recompile + version bump. Mitigated by `Struct extra = 30;` for content-type-specific fields validated against the manifest (CO-70).
- **Build complexity** — protobuf adds `prost-build` to the build (already there for `core/proto/`). No regression.
- **Authoring surface unchanged** — users still write `.md`; `.co` is the wire format.
- **Backward compat** — markdown auto-wrap on read; explicit encode on write. Existing universes work without re-import.

## Out of scope (deferred)

- Streaming decode (whole-file decode is fine for files < 10 MB; revisit if larger files become common)
- Field-level encryption within a single `CoFile` (encrypt the whole `body` or nothing for v1)
- Sub-second timestamps for events (nanosecond precision is overkill for v1; document as future-proof)
- Multipart streaming uploads (deferred until a real user flow demands it)
