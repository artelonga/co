GIVEN the three CONTAINED auth findings tracked under CO-469 (F2 `CO_ENV`
fail-open, F3 vault path-traversal, F4 plaintext magic-codes at rest), each one
a small, localized hardening,
WHEN the server boots, serves vault file CRUD, and stores magic-login codes,
THEN an unset `CO_ENV` fails closed (prod-safe), the `{*path}` capture can no
longer escape the universe content root, and the redb `AuthStore` never persists
a live login code in plaintext.

This is the follow-up to CO-469 (which shipped the JWT_SECRET boot guard). The
larger "retire the legacy redb `AuthStore`" refactor is explicitly **deferred**
(see Remaining, below).

## Acceptance

- [ ] **F2 — `CO_ENV` fail-open.** `is_local_or_test()` no longer matches the
      empty string; an empty/unset `CO_ENV` is treated as prod (fails closed),
      so the inline `dev_code` login code is never leaked by a deploy that left
      `CO_ENV` unset.
- [ ] Config tests updated: `is_local_or_test_non_prod_envs` and
      `is_local_or_test_prod_returns_false` no longer assert on `""`, and a new
      `is_local_or_test_empty_env_fails_closed` asserts empty CO_ENV is NOT
      local/test.
- [ ] The prod constructor default is confirmed `"prod"`
      (`from_secrets`/`From<Args>` use `get_or("CO_ENV","prod")`), so this only
      tightens the explicitly-empty case; no `is_local_or_test()` caller relied
      on empty=local for correctness.
- [ ] **F3 — vault path-traversal guard.** `is_safe_vault_path(&str) -> bool`
      rejects empty paths, a leading `/` or `\`, a `:` (drive/ADS), any `..`
      path segment (split on `/` and `\`), and NUL bytes.
- [ ] The guard is applied on every `{*path}` vault handler (GET / PUT / POST /
      PATCH / DELETE), returning 400 `BadRequest` before any filesystem use.
- [ ] Unit tests cover safe + unsafe paths; an integration test asserts
      encoded `%2e%2e` traversal returns 400 on GET, PUT and DELETE.
- [ ] **F4 — hash legacy magic-codes at rest.** `VerifyCodeEntry.code` stored
      via `AuthStore::store_code` is an Argon2id hash, not the plaintext code
      (same scheme as the CO-190 onboarding store).
- [ ] `verify_handler` compares the submitted code against the stored hash via
      `verify_code` (off the async runtime); attempts / expiry / rate-limit
      logic is preserved, and the off-prod inline `dev_code` (plaintext at
      generation time) still works end-to-end.
- [ ] Tests: stored value is not the plaintext code; verify still succeeds with
      the right code and fails with the wrong one.
- [ ] `cargo test`, `cargo clippy --workspace -- -D warnings`, `cargo fmt` all
      green. No route changes ⇒ no api-catalog update.

## Remaining (deferred — NOT in this change)

- **Retire the legacy redb `AuthStore`.** Make `/auth/login` + `/auth/verify` a
  thin adapter over the SQLite CO-190 onboarding store, removing the dual-store
  single-slot overwrite bug. This is a larger behavioral refactor and is
  intentionally out of scope for CO-474 — track separately.
- **Out of scope here:** the parallel game-auth code path
  (`universes/game/game_routes.rs::verify`) stores a separate `VerifyCodeData`
  in `game_storage` (its own redb) and still compares `entry.code != code` in
  plaintext. It is a different store/struct from the magic-code `AuthStore`
  hardened here; fold it into the deferred retirement work.
