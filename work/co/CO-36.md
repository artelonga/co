GIVEN CO already stores its own tasks as `.md` files with YAML frontmatter (`data/co/CO-21.md`), CO-21/22/23 implemented universe CRUD with SQLite (7 tables, 11 migrations), and the project needs Obsidian compatibility + compact wire format,
WHEN I generalize this pattern so that ALL entities are `.md` files with typed frontmatter, SQLite indexes them, and protobuf defines the wire format,
THEN:

## Core Abstraction

Every entity in a CO universe is an **Entry**: a markdown file with YAML frontmatter.

```
<universe>/
├── .universo.yaml              # form config (theme, layout, fonts)
├── projects/
│   └── <key>/
│       ├── _project.md         # type: project
│       ├── 1.md                # type: task
│       ├── 2.md                # type: task
│       └── comments/
│           ├── 1-1.md          # type: comment (task 1, comment 1)
│           └── 2-1.md          # type: comment
├── events/
│   ├── reuniao-semanal.md      # type: event
│   └── lancamento-v1.md        # type: event
├── messages/
│   └── 2026-04-06-release.md   # type: message
├── content/
│   ├── sobre.md                # type: page
│   └── guia-inicio.md          # type: page
└── clips/
    └── artigo-interessante.md  # type: clip (from Obsidian Clipper)
```

### Entry Format (universal)

```yaml
---
type: task                    # REQUIRED: entity type
id: 21                        # REQUIRED: unique within scope
title: "Universe CRUD API"    # REQUIRED: display name
created: 2026-04-06T00:00:00Z
modified: 2026-04-06T12:00:00Z
tags: [mvp, backend]          # Obsidian-compatible (= CO labels)
---

Optional markdown body = description.
Supports [[wikilinks]], #inline-tags, and all GFM.
```

### Type-specific frontmatter (extends base)

**task:**
```yaml
type: task
status: in_progress           # todo | in_progress | in_review | done
priority: high                # low | medium | high | critical
assignee: yuri
due: 2026-04-10
parent: 20                    # [[CO-20]] wikilink equivalent
project: MP                   # parent project key
```

**project:**
```yaml
type: project
key: MP
status: active                # active | archived
next_id: 15
```

**event (evento):**
```yaml
type: event
date: 2026-04-10
time: "14:00"
location: Online
status: scheduled             # scheduled | cancelled | completed
organizer: yuri
```

**message (mensagem):**
```yaml
type: message
from: yuri
to: team                      # or specific user
thread: release-planning      # groups messages
```

**comment (comentário):**
```yaml
type: comment
task: 21                      # parent entity
author: yuri
```

**page (página):**
```yaml
type: page
slug: sobre
parent: index                 # hierarchy (jardim pattern)
order: 1
```

**clip (recorte):**
```yaml
type: clip
source: "https://example.com/article"
author: "Author Name"
published: 2026-04-06
```

All types share: `type`, `id`/`slug`, `title`, `created`, `modified`, `tags`.

## SQLite Index

SQLite is the **materialized index**, not source of truth. Rebuilt from files.

- [ ] New module `core/src/entry.rs`:
  ```rust
  pub struct Entry {
      pub path: String,           // vault-relative
      pub entry_type: String,     // from frontmatter `type`
      pub frontmatter: serde_json::Value,  // full frontmatter as JSON
      pub body: String,           // markdown body
      pub body_hash: String,      // SHA256 for change detection
      pub stat: FileStat,         // ctime, mtime, size
  }
  
  pub struct FileStat {
      pub created: DateTime<Utc>,
      pub modified: DateTime<Utc>,
      pub size: u64,
  }
  ```

- [ ] New table `entries`:
  ```sql
  CREATE TABLE entries (
      path TEXT PRIMARY KEY,           -- vault-relative path
      universe_key TEXT NOT NULL,
      entry_type TEXT NOT NULL,        -- 'task', 'project', 'event', etc.
      title TEXT,
      frontmatter_json TEXT NOT NULL,  -- full YAML as JSON for queries
      body_hash TEXT NOT NULL,
      created_at TEXT,
      updated_at TEXT,
      FOREIGN KEY (universe_key) REFERENCES universes(key)
  );
  CREATE INDEX idx_entries_type ON entries(universe_key, entry_type);
  CREATE INDEX idx_entries_updated ON entries(universe_key, updated_at);
  ```

- [ ] `EntryIndex::rebuild(universe_path)` — scans all `.md` files, parses frontmatter, upserts into `entries` table
- [ ] `EntryIndex::upsert(entry)` — single file change → index update (called on file write)
- [ ] `EntryIndex::query(universe, type, filters)` — query entries by type + frontmatter fields:
  ```rust
  // Example: all open tasks in project MP, sorted by priority
  index.query("my-universe", "task", json!({
      "project": "MP",
      "status": {"$ne": "done"},
      "$sort": {"priority": -1}
  }))
  ```
- [ ] `EntryIndex::search(universe, query)` — full-text search across title + body (FTS5 on entries table)
- [ ] `EntryIndex::tags(universe)` — aggregate all `tags` arrays across entries, return with counts
- [ ] `EntryIndex::tree(universe, type)` — build hierarchy from `parent` field (reuse jardim pattern)

## API Layer (replaces current board CRUD)

The existing board API (`/api/projects/:key/tasks`) becomes a thin layer over the entry index:

- [ ] `GET /api/v1/universes/:slug/entries?type=task&project=MP` — list entries (replaces `/api/projects/:key/tasks`)
- [ ] `GET /api/v1/universes/:slug/entries/:path` — read single entry
- [ ] `POST /api/v1/universes/:slug/entries` — create entry (body: `{ type, frontmatter, body }`) → writes `.md` file → indexes
- [ ] `PUT /api/v1/universes/:slug/entries/:path` — update entry → rewrites file → re-indexes
- [ ] `DELETE /api/v1/universes/:slug/entries/:path` — delete file → remove from index
- [ ] `GET /api/v1/universes/:slug/entries/tags` — list all tags with counts
- [ ] `GET /api/v1/universes/:slug/entries/tree?type=page` — hierarchical tree
- [ ] Backward compatibility: keep `/api/projects/*` routes working by translating to entry queries internally

## Obsidian Dataview Compatibility

Because everything is frontmatter, Obsidian Dataview queries work natively on synced vaults:

```dataview
TABLE status, priority, assignee, due
FROM "projects/MP"
WHERE type = "task" AND status != "done"
SORT priority DESC
```

```dataview
TABLE date, time, location, status
FROM "events"
WHERE type = "event" AND date >= date(today)
SORT date ASC
```

```dataview
TABLE from, to, thread
FROM "messages"
WHERE type = "message" AND thread = "release-planning"
SORT created ASC
```

- [ ] Frontmatter field names chosen to match Dataview conventions (lowercase, no underscores where possible)
- [ ] `tags` field (not `labels`) — Dataview recognizes `tags` natively
- [ ] Date fields as ISO 8601 — Dataview parses these automatically
- [ ] `parent` as numeric ID or `[[wikilink]]` — both work in Dataview

## Three-Tier Storage Architecture

```
┌─────────────────────────────────────────────────┐
│  TRUTH: .md files (YAML frontmatter + body)     │
│  Human-readable, Git-diffable, Obsidian-native  │
│  Atomic writes (temp + rename)                  │
└──────────────────┬──────────────────────────────┘
                   │ parse/serialize
┌──────────────────▼──────────────────────────────┐
│  INDEX: SQLite (entries table + FTS5)            │
│  Fast queries, aggregations, tree building      │
│  Rebuilt from files on startup                   │
│  Disposable — delete co.db, it rebuilds         │
└──────────────────┬──────────────────────────────┘
                   │ encode/decode
┌──────────────────▼──────────────────────────────┐
│  WIRE: Protobuf (API responses, CRDT state)     │
│  Compact binary, schema-enforced, gRPC-ready    │
│  Used for: HTTP API, WebSocket sync, export     │
└─────────────────────────────────────────────────┘
```

Why this split:
- **Files** because Obsidian needs them, Git needs them, humans need them
- **SQLite** because queries are hard on files (FTS5, JOIN, COUNT, ORDER BY)
- **Protobuf** because JSON is verbose on the wire, and schema enforcement prevents drift between client/server

## Protobuf Schema

- [ ] New file `core/proto/entry.proto`:
  ```protobuf
  syntax = "proto3";
  package co.entry;

  message Entry {
    string path = 1;
    string entry_type = 2;       // "task", "event", etc.
    string title = 3;
    map<string, Value> frontmatter = 4;
    string body = 5;
    string body_hash = 6;
    FileStat stat = 7;
  }

  message FileStat {
    int64 created_ms = 1;        // unix millis
    int64 modified_ms = 2;
    uint64 size = 3;
  }

  message Value {
    oneof kind {
      string string_value = 1;
      int64 int_value = 2;
      bool bool_value = 3;
      double float_value = 4;
      ListValue list_value = 5;
    }
  }

  message ListValue {
    repeated Value values = 1;
  }

  message EntryList {
    repeated Entry entries = 1;
    uint64 total = 2;
  }

  message EntryQuery {
    string universe = 1;
    string entry_type = 2;
    map<string, string> filters = 3;
    string sort_by = 4;
    bool sort_desc = 5;
    uint32 limit = 6;
    uint32 offset = 7;
  }

  message TagCount {
    string tag = 1;
    uint64 count = 2;
  }

  message TreeNode {
    Entry entry = 1;
    repeated TreeNode children = 2;
  }
  ```

- [ ] Add `prost` + `prost-build` to `core/Cargo.toml`
- [ ] `core/build.rs`: compile `.proto` → Rust types
- [ ] API responses: `Accept: application/protobuf` → binary, `Accept: application/json` → JSON (default)
- [ ] Content-type negotiation in Axum middleware (protobuf for native clients, JSON for browser/curl)

## File Operations

- [ ] `write_entry(universe, entry) -> Result<()>` — serialize frontmatter + body → write `.md` file atomically (temp + rename) → upsert index
- [ ] `read_entry(universe, path) -> Result<Entry>` — parse `.md` file → return Entry
- [ ] `delete_entry(universe, path) -> Result<()>` — delete file → remove from index
- [ ] `move_entry(universe, old_path, new_path) -> Result<()>` — rename file → update index → update references
- [ ] Content count: `SELECT COUNT(*) FROM entries WHERE universe_key = ?` (replaces manual `content_count` column)

## Migration from Current Model (CO-21/22/23 compatibility)

CO-21/22/23 implemented universe CRUD with 7 SQLite tables (`projects`, `tasks`, `comments`, `activity_log`, `users`, `universes`, `universe_members`). The entry abstraction must coexist:

- [ ] **Phase A (dual-write):** Board API writes to BOTH old tables AND new `.md` files. Entry index reads files. Old API routes still work.
- [ ] **Phase B (read from entries):** Board API reads from entry index. Old tables become write-behind cache (for backward compat).
- [ ] **Phase C (entries only):** Drop old `tasks`, `projects`, `comments` tables. `entries` table + files are the only storage.
- [ ] `co migrate entries` CLI command: reads existing SQLite data → writes `.md` files in vault structure → rebuilds entry index
- [ ] **Preserved from CO-21/22/23:**
  - `universes` table stays (metadata, not content)
  - `universe_members` table stays (access control, not content)
  - `users` table stays (auth, not content)
  - Universe slug routing, template system, usage gate logic — all intact
  - Content count derives from `entries` table instead of manual increment/decrement
- [ ] Entry index rebuilds from files on startup (files are truth, index is disposable)
