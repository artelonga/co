GIVEN the auth/login security review (`infra/e2e/SECURITY-REVIEW.md`, finding F2)
flagged the absence of a `Content-Security-Policy` header, weakening XSS
containment for the SPA and served gardens,
WHEN we add a baseline CSP in **report-only** mode to the global response-header
layer stack (next to `X-Content-Type-Options` / `Referrer-Policy`),
THEN browsers evaluate the policy and report violations **without blocking** —
gaining the compliance header + violation visibility with zero risk of breaking
the inline-script SPA, the esm.sh-loaded atlas, or the static gardens. The policy
is promoted to an enforcing `Content-Security-Policy` header in a follow-up once
real-world reports are clean.

## Acceptance

- [x] `Content-Security-Policy-Report-Only` set on all responses via
  `SetResponseHeaderLayer` in `server/router.rs`, alongside the existing headers.
- [x] Policy: `default-src 'self'`; `script-src` allows `'unsafe-inline'` + esm.sh
  (the SPA/atlas need them); `connect-src` allows `https:`/`wss:` (WS surfaces);
  `frame-ancestors 'self' https://*.artelonga.com.br`; `object-src 'none'`.
- [x] Report-only → no behavioural change; verified live (header present on
  `/api/health` next to `X-Frame-Options`/`nosniff`/`Referrer-Policy`).
- [x] `cargo build` + `cargo clippy -- -D warnings` + `cargo fmt` clean.

## Out of scope / follow-up

- **Enforcing CSP**: flip to `Content-Security-Policy` after collecting report-only
  violations and tightening `'unsafe-inline'` (ideally nonce/hash-based scripts).
- A `report-uri`/`report-to` collector endpoint to capture violations.
