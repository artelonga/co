## As

a CO operator wanting real-time analytics joins beyond what ClickHouse-batch can deliver

## I Need

a Flink job consuming `events.page_view` from Redpanda, sessionizing by `(user_id, 30-min idle gap)`, writing aggregated rows to ClickHouse `sessions_aggregated`, with exactly-once semantics

## To

prove the streaming-compute layer end-to-end on a non-trivial but contained job, and ship the first piece of analytics that **only** stream compute can deliver — sessionization with bounded latency

## Given / When / Then

GIVEN Redpanda + Iceberg + ClickHouse are live (CO-125, CO-126, CO-123),
WHEN we deploy a Flink job (1 JobManager + 2 TaskManagers on Fly) reading from `events.page_view` and writing to ClickHouse,
THEN 5 page-view events sharing a `session_id` (or inferred via 30-min gap) produce **1** row in `sessions_aggregated` within ≤30s of the last event, with `event_count = 5`, `duration_ms` filled, and exactly-once on replay.

## Job shape (sketch)

```java
DataStream<PageView> events = env.fromSource(
    KafkaSource.<PageView>builder()
        .setBootstrapServers(REDPANDA)
        .setTopics("events.page_view")
        .setStartingOffsets(...)
        .setValueOnlyDeserializer(new PageViewDeserializer())
        .build(),
    WatermarkStrategy.<PageView>forBoundedOutOfOrderness(Duration.ofSeconds(30)),
    "page-views");

events
    .keyBy(PageView::userId)
    .window(EventTimeSessionWindows.withGap(Time.minutes(30)))
    .process(new SessionAggregator())
    .sinkTo(new ClickHouseSink<>("sessions_aggregated", ...));
```

## Why Flink, not Spark Structured Streaming

Per `platform-evaluation.md` §11 and the SR-plan §A endorsement: Flink's exactly-once via two-phase commit + per-event windowing is the right tool for sessionization. Spark micro-batch would aggregate the same data at coarser latency without a real win.

## Acceptance

- [ ] Flink cluster deployed (1 JM + 2 TM, RocksDB state backend, S3-compat checkpoints to R2)
- [ ] Job artifact deployable via `flink run` and observable at `/flink-ui`
- [ ] 1k synthetic page views grouped into 200 sessions produce 200 rows in `sessions_aggregated`
- [ ] Replay test: kill TM mid-job, restart, no duplicate rows in ClickHouse
- [ ] p95 end-to-end latency (event produce → ClickHouse row) ≤30s
- [ ] Flink job source committed under `streaming/jobs/session-stitch/`

## Out of scope

- Multi-tenant Flink (per-universe job isolation) — Phase 5
- ML feature pipelines — Phase 5
- Anomaly detection / alerting — Phase 4+

## Risks

- **State-backend disk pressure.** Mitigation: RocksDB on dedicated Fly Volume; alert at 70% full
- **Exactly-once via ClickHouse sink.** ClickHouse doesn't support 2PC natively. Mitigation: idempotent sink with `ReplacingMergeTree` keyed by `(session_id, version)`
