GIVEN the scalability review found the single local model is the binding constraint
(~2 msg/min sustained, ~5 concurrent) and tier-2 makes that *graceful* but does not
*raise* it,
WHEN we need hundreds of concurrent chatters / many hot tenants,
THEN move past the single-stream ceiling and remove the remaining storage/ingress
limits.

## Acceptance

- [ ] **Horizontal inference:** the model is the scaling unit — scale the bridge/model
  out or move to a hosted/GPU endpoint (note: Fly GPUs deprecated after 2026-07-31 →
  Modal/RunPod/Lambda). Pairs with the tier-2 opt-in Claude spill as the burst valve
  (privacy-policy update required if spill is enabled — CO-491).
- [ ] **meta.db read concurrency:** an r2d2/rusqlite read pool (or `RwLock` Storage)
  for the global `Mutex<Storage>` auth-lookup path (low-thousands req/s ceiling today).
- [ ] **Missing indexes:** `idx_users_whatsapp`, `idx_universes_owner`,
  `idx_universe_members_user` (coordinate the migration number across branches).
- [ ] **UniversePool tuning:** explicit `PRAGMA cache_size`/`mmap_size`, raise/verify
  `RLIMIT_NOFILE`, size the pool from the fd limit, make capacity env-configurable;
  gate cold-open per-universe migration scans behind a `schema_version` check.
- [ ] **Ingress shedding:** the co-web webhook still parks an unbounded task per
  message under flood (tier-2 residual) — add an mpsc + try_send shed at ingress so
  parked-task memory is hard-bounded.
- [ ] **Cloud API at scale:** track each recipient's 24h window → fall back to an
  approved template outside it; honor 429 backoff; watch messaging-tier warming
  (250→1k→10k→100k) and the single-number throughput funnel.

## Notes
- Tier ladder + envelope in `docs/whatsapp-launch.md`. First launch stays in the
  tier-2 envelope (~10–50 linked users, light usage) until these land.
