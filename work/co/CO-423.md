## As
Quem importa um repositório para um universo (jornada 2), QUERO que o
toolchain de deploy faça o universo ficar **completo** — pai correto, página
inicial, fonte detectada — sem remendos manuais, PARA destravar CO-419 e
qualquer import futuro.

## Lacunas reais expostas pelo deploy do CO-419 (2026-06-12)
1. **Re-parent impossível por API.** `UpdateUniverseRequest`
   (`universe_routes.rs:62`) só aceita name/description/visibility — não
   `parent_key`. Um `PUT` com parent_key é silenciosamente ignorado; `nlp`
   ficou com `parent_key: null` em vez de `yuri`.
2. **Existence-check do adapter é enganado pelo SPA fallback.** `co source add`
   faz GET e vê 200 (a SPA responde 200 pra rota desconhecida) → conclui
   "existe" erradamente; e quando não existe, tenta criar via TOKEN (POST
   /universes exige session) → 401.
3. **Sem index/landing.** O import materializa os arquivos mas não cria uma
   página inicial — o universo abre sem ponto de entrada curado.

## Acceptance Criteria
- [ ] `UpdateUniverseRequest` aceita `parent_key: Option<String>`; o handler
      atualiza `universes.parent_key` (owner-only); teste cobre re-parent.
- [ ] Após deploy, `nlp` tem `parent_key = yuri` (o caso concreto do CO-419).
- [ ] `co source add` detecta existência por uma checagem REAL (ex.: a API de
      universo retorna um JSON com `key`, não o shell da SPA) — não por
      status 200; e cria o universo quando ausente usando a credencial certa
      (session/token conforme a rota exigir), aceitando `--parent <key>`.
- [ ] `co source add` cria (ou garante) um `index.md` mínimo se o repo não
      trouxer um — ponto de entrada navegável (flag `--no-index` para desligar).
- [ ] CO-419 re-verificado: §E passa (visibility/parent/index/metrics OK).
