## As

a CO operator who watched 1.22.4 ship as a defensive bridge, leaving prod in a valid-but-degraded state

## I Need

a one-time data fix that ensures prod's `universes` table has the `parent_key` column **and** the timeline trio (`tempo`, `humanity`, `universo`) carries `parent_key='template'` — closing the gap between prod's current observed state (`parent_key=None`) and the CO-98 acceptance criterion

## To

restore feature parity with UAT, where the timeline trio renders nested under template in the sidebar tree (CO-98 acceptance #4 + #5), and confirm the migration framework after the structural fix from CO-137

## Given / When / Then

GIVEN 1.22.4's defensive read path tolerates a missing `parent_key` column,
AND prod observably returns `parent_key=None` for the trio (vs UAT's `parent_key="template"`),
AND CO-137 is investigating whether the column is actually missing or the seed UPDATE didn't match,
WHEN CO-137's diagnostic confirms the prod schema state and CO-137's `ensure_column` helper ships,
THEN this ticket runs the backfill (either via the next deploy's idempotent migration, or via a one-shot script if needed).

## Backfill paths (depending on CO-137's diagnosis)

### Path A — column missing (most likely)

CO-137's `ensure_column` helper, applied to v22, is idempotent. The next deploy will run it, succeed in adding the column, and the **existing** seed UPDATE in `seed_timeline_universe` will then populate the trio:

```rust
// already in seed_timeline_universe since 1.22.0:
let _ = self.conn.execute(
    "UPDATE universes SET parent_key = 'template' \
     WHERE key = ?1 AND parent_key IS NULL \
     AND owner_id = 'system' AND visibility = 'public-static'",
    params![key],
);
```

After deploy, verify:

```bash
curl -s https://co.artelonga.com.br/api/v1/universes/tempo | jq .parent_key   # → "template"
```

### Path B — column exists but UPDATE didn't match

If CO-137 finds the column but the trio rows didn't get updated, the seed's UPDATE constraints (`owner_id = 'system' AND visibility = 'public-static'`) may not match prod's data. Inspect:

```sql
SELECT key, owner_id, visibility, parent_key FROM universes
WHERE key IN ('tempo','humanity','universo');
```

Then choose:
- Relax the UPDATE constraints (drop `owner_id` and/or `visibility` checks since the key match alone is unambiguous), OR
- One-shot SQL via `flyctl ssh console -a co-artelonga -C "sqlite3 /data/co.db \"UPDATE universes SET parent_key='template' WHERE key IN ('tempo','humanity','universo');\""` (requires `sqlite3` to be available — check; if not, deploy a debug image with it).

### Path C — column exists, UPDATE matched, but values dropped later

Lowest probability. Inspect the WAL log for any concurrent writer. Investigate locking / connection scoping in seed_timeline_universe.
