## As
The operator preparing v3.0 mobile public release

## I Need
A separate Fly app `co-artelonga-staging` at `staging.co.artelonga.com.br` with its own volume, nightly reset, and a sandbox config so I can run the full Playwright suite against it without touching prod.

## So That
- Every PR merge to main auto-deploys to staging; suite runs; red blocks prod release.
- The bi-weekly Thursday 15:00 BRT release gets a pre-flight gate that catches schema/regression bugs before users see them.
- Risky migrations (CO-366 billing, CO-367 KB schema) get validated on real-running storage before prod.
- Reverses the prior "no UAT" decision only for **automated** validation — manual UAT remains off the table.

## Context

Earlier feedback (memory `feedback_no_uat`): no dedicated UAT, deploy direct to prod with smoke test + A/B as state(t) vs state(t+1). That covered the manual-verification gap; staging here covers the **automated-contract-verification** gap — different role, different cost model.

Cost: ~$3/mo for a 256 MB shared-cpu-1x machine. Worth it: Wave 4 lands 16 PRs with heavy schema + UI changes; validating against running infra catches drift no unit test will.

## Design

### Fly app

```bash
flyctl apps create co-artelonga-staging --org personal
```

Config: new `fly.staging.toml` (mirrors `fly.uat.toml` from the removed UAT — recycle the pattern):

```toml
app = "co-artelonga-staging"

[build]
  dockerfile = "Dockerfile"

[env]
```

### DNS

```
staging.co.artelonga.com.br  →  co-artelonga-staging.fly.dev
```

Proxied OFF (so cert validation works on first deploy), can flip ON later.

### Secrets (matched to prod where shared)

```bash
flyctl secrets set JWT_SECRET=$(flyctl secrets get JWT_SECRET -a co-artelonga) -a co-artelonga-staging
flyctl secrets set CO_SEED_ADMIN_EMAIL=yuri@artelonga.com.br -a co-artelonga-staging
flyctl secrets set CO_SEED_ADMIN_PASSWORD_HASH=$(flyctl secrets get CO_SEED_ADMIN_PASSWORD_HASH -a co-artelonga) -a co-artelonga-staging
flyctl secrets set CO_TRUSTED_IPS="0.0.0.0/0" -a co-artelonga-staging  # disable rate limits on staging
```

**Security note**: shared `JWT_SECRET` means a staging compromise lets attacker forge prod tokens. Mitigation Phase 1 (CO-377): rotate quarterly. Mitigation Phase 2 (CO-377-B): OIDC federation (staging trusts prod issuer; no shared secret).

### Test isolation via per-run universe namespaces (no global wipe)

Wiping the staging DB nightly is wasteful + destroys test artifacts we may want to inspect. Better pattern, aligned with CO's existing anonymous-clone namespace pattern + jj's revertible-VCS philosophy:

1. **Each Playwright run creates universes with run-scoped keys**: `u-test-<sha>-<random>` (e.g. `u-test-abc1234-xyz9`). Reuses CO-44's anonymous-clone naming.
2. **Test data lives inside those universes** — no cross-contamination.
3. **TearDown** (per scenario) optionally deletes the universe; default = leave it for inspection.
4. **Weekly retention sweep** (Sunday 03:00 BRT): cron deletes `u-test-*` universes older than 7 days, keeping the most recent 100 for forensics.

This means a failing test leaves data on staging so you can reproduce manually. No "reset every night" destruction.

### Baseline fixture universes (seeded once per deploy)

These are stable, NEVER touched by tests:
- **`co`** (mirrors prod) — for general user-route tests
- **`recursion-A`** (top-level, public) — universe recursion fixture
- **`recursion-A/B`** (sub-universe of recursion-A)
- **`recursion-A/B/C`** (sub-sub-universe)
- **`funnel-fixture`** — pre-seeded with mixed leads + users for funnel report tests
- **`mbya-staging`** + **`yoruba-staging`** — workspace template fixtures

Reseeded on every fresh Fly deploy via existing `seed_admin_content_universes` extension. Tests never CRUD on these — they're read-only baselines.

### Migration validation (jj-style snapshot/restore)

For CO-376 (pre-prod migration validation), we use SQLite's `.backup` API as the snapshot primitive:

```rust
// co-web/src/storage/snapshot.rs
pub fn snapshot_db(src: &Path, dest: &Path) -> Result<()> {
    let conn = Connection::open(src)?;
    let backup_conn = Connection::open(dest)?;
    let backup = Backup::new(&conn, &backup_conn)?;
    backup.run_to_completion(100, std::time::Duration::ZERO, None)?;
    Ok(())
}
```

Flow:
1. Pre-migration: `snapshot_db("/data/meta.db", "/data/snapshots/pre-co-xxx.db")`
2. Apply migration
3. Run smoke queries
4. If pass: keep snapshot for 24h then delete
5. If fail: restore from snapshot, alert

Same primitive works for per-universe DBs. Snapshots are point-in-time, jj-compatible mentally (each is a labeled revertible state).

### No daily wipe needed

Original "daily 03:00 BRT reset" removed. Replaced by:
- Per-test universe isolation (above)
- Weekly retention sweep of test universes
- Migration snapshot/restore for risky changes
- Baseline fixtures stay stable across runs

### Deploy automation

`.github/workflows/staging-deploy.yml`:

```yaml
on:
  push:
    branches: [main]

jobs:
  staging-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - uses: actions/checkout@v4
      - run: flyctl deploy --config fly.staging.toml --remote-only
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
```

Triggers: every push to main. Runs ~3 min.

### Health endpoint reports env

`/api/health` extension: add `env: "staging" | "production"`. Read from `CO_ENV` env var. Default `production` if unset.
