## As
Autor revisando conteúdo importado, QUERO ver o markdown renderizado no
localhost, editar o necessário e publicar como uma feature convencional e
semver-aligned que **rastreia de volta** à fonte e à task que pediu, PARA que
toda publicação seja auditável da origem ao pedido.

## Acceptance Criteria
- **Render local**: entrada importada/editada é renderizada (markdown → HTML)
  no `co serve` antes de publicar — o passo de review do invariante CO-398.
- **Editar**: ajustes salvam draft sem publicar.
- **Publicar**: gera um commit **convencional** (`feat(...)`/`docs(...)`) com
  bump semver-aware, e carimba na entrada metadados de proveniência:
  - `source` — URL/ref da fonte original (de CO-417, ex. `github:owner/repo@sha`)
  - `requested_by` — a task CO-N que pediu a publicação
- **Traceback navegável**: a partir da entrada publicada dá pra chegar à fonte
  e à task (relação tipada, reusa CO-74); some na UI como "Origem" + "Pedido por".
- Publicar é idempotente; re-publicar sem mudança não cria commit novo.
- Teste: publicar uma entrada importada produz commit convencional + os dois
  campos de proveniência resolvíveis.

## Acceptance
- [x] Render local: entrada importada serve markdown limpo (frontmatter
      removido no parse) → renderizável no `co serve`/SPA antes de publicar.
- [x] Editar: o publish aceita `frontmatter`/`body` patch; o draft (CO-354
      suggest/review) continua salvando sem publicar.
- [x] Publicar gera commit convencional (`feat(...)`/`docs(...)`) com bump
      semver-aware (`feat→minor`, `fix|docs→patch`), sem tocar `Cargo.toml`.
- [x] Carimba `requested_by: CO-N` e preserva `source` (CO-417) intactos.
- [x] Traceback como relação tipada (CO-74): `origin → source` e
      `requested_by → task`, derivadas do frontmatter (sobrevivem a
      `sync_entry_relations`), retornadas no GET da entrada.
- [x] Publicar é idempotente: re-publicar sem mudança não cria commit novo
      (`published_sha` estável, `published: false`).
- [x] Teste: publish de entrada importada produz commit convencional + os dois
      campos de proveniência resolvíveis como relações.

## Implementação
- Rota: `POST /api/v1/universes/{slug}/publish` (owner-only) em
  `co-web/src/content/review_routes.rs`.
- Relações de proveniência: `extract_provenance_relations` em
  `co-web/src/content/relation_index.rs`, integrada a `sync_entry_relations`.
- Campos carimbados: `requested_by`, `published_commit`, `published_semver`,
  `published_sha`, `published_at` (em `frontmatter_json` — sem migração nova).
- Evento EDA `entry.published` com commit message + semver + traceback.
