## What this slice does

Adds a `--staging` flag to `co serve` (CO-282) that wraps each trait-backed plug (storage, blob, cache, workers) with simulation decorators: latency injection, occasional 503s, simulated cache eviction pressure. The result is a localhost instance that *behaves* like production for testing.

## Scope

1. New decorators in `co-web/src/infra/staging/`:
   - `LatencyInjectedStorage` — wraps any `Storage` impl, adds 5-50ms artificial delay per call (configurable distribution)
   - `FlakyBlobStore` — wraps any `BlobStore`, returns 503 on ~5% of calls
   - `EvictingCache` — wraps any `Cache`, evicts entries at a rate simulating a constrained cache size
   - `RetryProneWorkerExecutor` — wraps any `WorkerExecutor`, makes 10% of jobs fail (forcing retry-path coverage)
2. `co serve --staging` flag (in `co-cli/src/commands/serve.rs` from CO-282) selects these decorators
3. Config knobs: `--staging-latency-ms` (default 20), `--staging-error-rate` (default 0.05)
4. Each decorator is opt-in via env var so you can mix-and-match: `CO_STAGING_LATENCY=true`, `CO_STAGING_FAULT_INJECTION=true`
5. Docs: `docs/staging.md` covering how to use `co serve --staging` for pre-deploy verification

## Acceptance

- [ ] `co serve --staging` starts a server that demonstrably injects latency (curl `/api/health` is 50-100ms slower than normal)
- [ ] About 5% of blob ops return 503 (verified by hammering an upload endpoint in a loop)
- [ ] All decorator wrapping is opt-out per plug (you can disable any individual one)
- [ ] Normal `co serve` (no `--staging`) is unaffected
