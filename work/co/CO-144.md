## As

a CO user who wants a single place that summarizes activity across all universes I touch

## I Need

(a) every signed-up user gets a private universe with key = their username, automatically created on signup, **and** (b) a cross-universe activity feed that auto-populates that universe (and the global `dados` system universe) whenever entries change in any other universe

## To

deliver the "dashboard interactivity" the user described on 2026-05-02: "it works like a dashboard, changing a file in other universes or adding a new universe populates that, obviously one (private) per user"

## Given / When / Then

GIVEN today (1.34.5):
- The `dados` system universe exists with `universos/<key>.md` and `dispositivos/*.md` content shape — but the files are static, not auto-populated from live activity
- The `yuri` universe exists for the admin (re-homed in 1.34.6 via `ensure_admin_owns_personal_universes`)
- New users (password signup, magic-link) do NOT get a slug-keyed personal universe — only the admin gets one via the re-home path

WHEN we (a) hook user creation to also create a private universe with key = `users.username`, and (b) emit cross-universe activity events that materialize as entries in (i) the global `dados` universe and (ii) each user's personal slug-named universe (filtered to universes they own / are member of / subscribed to),

THEN every user has a single dashboard surface that updates as content changes elsewhere, the existing `dados` universe transitions from snapshot to live feed, and the per-user pattern becomes the natural way users see "what changed in my world".

## Phase A — auto-create per-user dashboard universe

### Trigger points

- `POST /api/v1/auth/password-login` (signup branch — user not yet in `users`)
- Magic-link verify (`POST /api/v1/auth/verify`)
- Admin seed path (already done for `yuri` via PERSONAL_KEYS — generalizes here)
- UAT-only `POST /api/v1/auth/uat-login` first-call

### Function shape

```rust
/// Idempotent: creates a private universe with key = username, owned by
/// user_id, if not already present. Skips if username is empty.
pub fn ensure_user_personal_universe(
    &mut self,
    user_id: &str,
    username: &str,
) -> anyhow::Result<bool> { ... }
```

Called from each trigger point (and from `seed_admin_user_from_env` for the env-seeded admin path). Idempotent → safe on every boot.

### Visibility

- Default: `private`
- Owner: the user
- Default content: a `_universe.yaml` manifest describing the dashboard content type + a placeholder `index.md`

## Phase B — cross-universe activity events

### Source

`upsert_entry_row` (called on every entry write across the system) is the choke point. Adding an emit-event call there captures every CRUD.

### Event shape

```json
{
  "type": "entry.upsert",
  "timestamp": "2026-05-02T...Z",
  "universe_key": "<source>",
  "entry_path": "...",
  "entry_type": "task | page | event | clip | ...",
  "title": "...",
  "actor_id": "<user_id>",
  "diff_summary": { "field": "status", "from": "todo", "to": "done" }
}
```

### Two consumers

1. **Global `dados` universe** — append a row to `dados/feed/YYYY-MM-DD.md` (one file per UTC day) for ANY universe write. System-owned, read by admins.
2. **Per-user `<username>` universe** — append to `<username>/feed/YYYY-MM-DD.md` for any write to a universe the user owns / is member of / subscribes to. Filter by `universe_members` + `subscriptions` membership.

### Implementation note

The existing `telemetry_events` table (CO-46) already captures entry-touching events. Phase B can ride on that — a periodic (or per-write) job that translates `telemetry_events` rows into markdown lines in the dashboard universes.

A simpler v1: emit synchronously inside `upsert_entry_row`, append to the appropriate dashboard universe's filesystem entry and per-universe DB. Cost: one extra write per write. Manageable at our scale.

## Phase C — Dashboard rendering in SPA

The SPA already renders `feed/YYYY-MM-DD.md` as plain markdown. Optionally, add a Painel-style view for the dashboard universe that:

- Aggregates by date + universe + entry_type
- Shows sparkline of activity per universe
- Highlights "new universe joined / created" events
- Filters by universe / actor / entry_type

Reuses the existing `renderDashboard()` view in `app.js` — extend, don't rewrite.

## Acceptance

### Phase A
- [ ] Signup paths (password, magic-link, UAT) trigger `ensure_user_personal_universe(user_id, username)`
- [ ] Idempotent — re-call on boot or re-signup is a no-op
- [ ] Username conflict (duplicate slug) is logged and gracefully skipped — does not break signup
- [ ] Tests cover: new user signup → private universe created with key=username; pre-existing universe → no overwrite

### Phase B
- [ ] Every `upsert_entry_row` produces an event consumed by both `dados` and the user-scoped universe
- [ ] Event content: timestamp, source universe, entry path, type, title, actor, brief diff
- [ ] Filter logic: per-user feed shows only universes the user has access to (membership / subscription)
- [ ] No PII or content-body in event payload — only metadata (per privacy doctrine)

### Phase C
- [ ] Dashboard view renders the feed in reverse chronological order
- [ ] Universe filter / actor filter / entry-type filter work
- [ ] No-content state ("Nenhuma atividade ainda") for new users

## Out of scope

- Real-time push (WebSocket fan-out) — Phase 1 polls / refreshes on navigation
- Cross-account dashboards (admin views all users' feeds) — separate ticket
- Activity events for non-entry actions (theme changes, member adds, etc.) — Phase 2
- Encryption at rest (CO-86 envelope) — Phase 4 platform-plan territory
