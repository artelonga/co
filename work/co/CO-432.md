## As
Um desenvolvedor do co-web, QUERO que `content/` deixe de ser uma god-folder e
que o template de camadas (domain/dto/repository/service/mapper) — provado em
`entries` no CO-390 — cubra as entidades de maior valor, PARA que cada entidade
seja testável, isolada e siga um único padrão.

## Contexto técnico (do audit 2026-06-12)
`co-web/src/content/` tem 37 arquivos flat misturando 10+ entidades
(entries, vault, references, relations, proposals, reviews, assets, graph,
search, workspace, translate, op_log…). O CO-390 deixou `domain/ dto/
repository/ service/ mapper/` mas só para `entries` (~10% de adoção). Vários
arquivos passam de 500 LoC (`entry_routes.rs` 1930, `vault_routes.rs` 1942,
`reference_routes.rs` 1469) e ainda embutem I/O + validação + cache nos handlers.

## Acceptance
- [ ] `content/` reorganizado em subpastas por entidade: ao menos
      `entries/`, `vault/`, `references/`, `relations/`, `graph/`, `workspace/`
      (rotas + index movidos para dentro de cada uma). Sem `*_routes.rs` soltos.
- [ ] O template de camadas (CO-390) propagado para **pelo menos 2 entidades
      novas além de entries** — alvo: `references` e `relations` (ou `vault`):
      `domain/` (tipo puro), `dto/`, `repository/` (trait + impl SQLite),
      `service/` (regras de negócio fora dos handlers), `mapper/`.
- [ ] `entry_index.rs` / `reference_index.rs` passam para trás dos respectivos
      repositories (não mais acessados direto pelos handlers).
- [ ] Nenhum arquivo de produção novo > 500 LoC; arquivos de teste grandes
      divididos por grupo (padrão CO-215 `tests/`).
- [ ] **Zero mudança de comportamento**: testes de caracterização antes de
      extrair; `cargo test -p co-web` verde; clippy limpo; sem drift de rotas.

## Notas
Esta é a tarefa "revisar e terminar o último refactor". Não redesenhar o
template — copiar o de entries. Migração de arquivos é mecânica; o risco está
nos `mod.rs`/`use` paths — rodar a suíte a cada extração.
