## As

The operator (and contributors) of CO

## I Need

Every co-auto invocation to **emit a session-summary event** capturing what Claude Code actually did — tokens consumed, tool calls, skills loaded (post-CO-274), files touched, duration, exit code, final commit SHA, PR number — and have that metadata visible on the kanban card of the task it produced.

## So That

The kanban view stops being just "what tasks exist" and becomes "what tasks exist + how they were built + at what cost". The "Claude Code wrapper across universes and boards" architecture sketched at CO-272/273/274 actually closes: every card on every universe board carries its own agent-session provenance.

## Context

### What we have today

After this session of ~30 co-auto runs:

- The agent ran, wrote code, committed, opened PRs
- Token cost was approximately 150k/session (per user observation, addressed by CO-274 → ~30k post-fix)
- Tool call distribution per session is **completely opaque** — we don't know if a typical task burns 8 Reads + 5 Edits or 50 Reads + 2 Edits
- Skills loaded post-CO-274 are listed in agent context but not persisted anywhere queryable
- Duration is "however long the bash command took" — not split between thinking, tool calls, and waiting

This is **flying blind**. Every successful task hides whether it was 12 min and tight or 28 min with 4 retries.

### Where the metadata exists

Claude Code (the CLI) emits:

- **Token counts** — via the API response usage data; co-auto sees these in stdout if running with `--debug` or by parsing the final summary line
- **Tool calls** — Claude Code reports tool invocations to stderr in some modes; alternatively, we can patch claude's stdin/stdout for our wrapper
- **Duration** — wall clock from co-auto spawn to claude exit
- **Exit code** — already captured by co-auto for branching (success / fail)

The other bits (skills loaded, files touched, commit SHA, PR #) come from co-auto's own state (post-spec-routing in CO-274) or the resulting git operations.

### Where it needs to live

| Layer | Storage |
|---|---|
| Raw event | DomainEvent::AgentSessionComplete on the CO-220 event bus |
| Durable record | `agent_sessions` table in the `co` universe's DB |
| Joined to task | A view or `JOIN` on `task_id = path_basename` |
| Surfaced on UI | Kanban card footer line; details panel; admin dashboard graph |

## Scope

### 1. Backend — `agent_sessions` table + endpoint

New migration v17 (or whatever's next):

```sql
CREATE TABLE agent_sessions (
    id INTEGER PRIMARY KEY,
    task_id TEXT NOT NULL,           -- "CO-272"
    universe_key TEXT NOT NULL,      -- "co"
    started_at INTEGER NOT NULL,     -- unix ts
    finished_at INTEGER NOT NULL,
    duration_ms INTEGER NOT NULL,
    exit_code INTEGER NOT NULL,
    tokens_in INTEGER,               -- nullable until claude exposes them reliably
    tokens_out INTEGER,
    tool_calls TEXT,                 -- JSON: {"Read": 8, "Edit": 5, ...}
    skills_loaded TEXT,              -- JSON array: ["spa-conventions", "rust-architecture"]
    context_chars INTEGER,           -- the assembled-prompt size (post-CO-274)
    final_commit_sha TEXT,
    pr_number INTEGER,
    model TEXT,                      -- "sonnet" / "opus-4-7" / etc.
    co_auto_version TEXT,            -- "0.1.0"
    raw_log_blob_sha TEXT,           -- optional: SHA of the full stdout log stored in blob store
    INDEX (task_id),
    INDEX (universe_key, started_at)
);
```

New endpoint:

```
POST /api/v1/agent/sessions       — co-auto POSTs at session end (auth: vault token)
GET  /api/v1/agent/sessions?task_id=CO-272      — list all sessions for a task
GET  /api/v1/agent/sessions/latest?task_id=CO-272 — most recent session
```

DomainEvent variant on the CO-220 event bus:

```rust
pub enum DomainEvent {
    // ...existing variants...
    AgentSessionComplete {
        task_id: String,
        universe_key: String,
        duration_ms: u64,
        tokens_in: Option<u64>,
        tokens_out: Option<u64>,
        tool_calls: HashMap<String, u32>,
        skills_loaded: Vec<String>,
        context_chars: u64,
        exit_code: i32,
        final_commit_sha: Option<String>,
        pr_number: Option<u32>,
    },
}
```

Subscribers can consume this for analytics, notifications, etc.

### 2. co-auto — capture + emit

In `dev/co-auto/src/auto.rs`, after each `claude` subprocess exits:

```rust
let session = AgentSessionRecord {
    task_id: task.id.clone(),
    universe_key: space_to_universe(&space),
    started_at: spawn_time,
    finished_at: now(),
    duration_ms: elapsed.as_millis() as u64,
    exit_code: status.code().unwrap_or(-1),
    tokens_in: parse_token_count(&stdout, "input"),
    tokens_out: parse_token_count(&stdout, "output"),
    tool_calls: parse_tool_calls(&stdout),
    skills_loaded: assembled_skills.clone(),
    context_chars: assembled_context_size,
    final_commit_sha: read_head_after()?,
    pr_number: parse_pr_number(&stdout),
    model: cli.model.clone(),
    co_auto_version: env!("CARGO_PKG_VERSION").to_string(),
    raw_log_blob_sha: None, // optional Phase 2
};
post_to_co(session).await?; // best-effort; warn but don't fail the run
```

Parsing token counts and tool calls is the tricky bit:

- **Tokens**: Claude Code reports them in stdout in `--debug` mode; alternatively, parse the summary block at session end. If neither available, mark `tokens_in: None` and accept "duration + tools" as the signal.
- **Tool calls**: Claude Code's stderr stream has lines like `Tool: Edit ...`. Count them up. If parsing fails, store `{}` and tolerate.

Both parsers ship with **graceful degradation** — if Claude's output format changes, we lose visibility but don't break the run.

### 3. Kanban + entry-card UI

Post-CO-272 we render entries as kanban cards. CO-275 enriches each card with a footer line:

```
┌─────────────────────────────────────────────────────┐
│ CO-272 — kanban dogfooding close                   │
│ 🟢 done · feat · critical                           │
│ ─────────────────────────────────────────────────  │
│ Last agent run: 14m · 18k tokens · 8R/5E/3B/2W     │
│ Skills: spa-conventions, rust-architecture         │
│ Commit: 5099bd6 · PR #89                            │
└─────────────────────────────────────────────────────┘
```

Clicking the footer expands to the full session record. The kanban view code (now in `co-web/static/variants/a/modules/views/kanban.js`) fetches `/api/v1/agent/sessions/latest?task_id=<key>` per card lazy-load.

### 4. Cross-universe propagation

Sister universes (artelonga, rfq, qb, yggdrasil) need co-auto to post sessions to **their own** universe's CO endpoint. The vault token they use (per CO-267) gates which universe's `agent_sessions` table they write into.

For CO-275 v1: only **local co universe** gets sessions. Sister-universe propagation = CO-275 phase B once CO-267 sync is wired in CI.

## Acceptance

- After deploy, every successful co-auto run emits an event + persists a row to `agent_sessions` with `task_id`, `duration_ms`, `tool_calls`, `skills_loaded`, `final_commit_sha`
- `GET /api/v1/agent/sessions/latest?task_id=CO-272` returns the session that built CO-272
- Kanban card on `/co` shows the agent-run footer line for each task that has a session
- Failure modes: claude crashes → exit_code != 0 row written; co-auto can't POST → warn + retry once, then drop (don't fail the user)
- New Playwright spec asserts the footer renders on at least one card
- New integration test posts a fake session, then asserts retrieval + card render

## Blast radius

- **Backend**: ~200 LOC (migration + endpoint + event variant + parse helpers)
- **co-auto**: ~150 LOC (parsing + POST + graceful degradation)
- **Frontend**: ~80 LOC kanban.js (lazy fetch + render footer)
- **Tests**: 3-4 new tests

## Why critical

Without this, the "Claude Code wrapper" architecture is incomplete — the provenance layer that makes the kanban+deploy+changelog trio truly mean something is missing. With this, **every CO-N task carries its own receipt**: what it cost, how it was built, what skills it required. Combined with CO-260 (cross-version changelog) and CO-273 (deployment dashboard), the operator has a fully queryable history of *every artifact the platform produces*.
