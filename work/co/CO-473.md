GIVEN CO-470 (Phase 1) shipped the block model over markdown — `Block`,
`parse_blocks`, `serialize_blocks`, the standard CommonMark/GFM `BlockType` set,
and a read-only `GET /blocks` projection — but the platform still cannot express
Notion-class *container* structure (callouts, toggles, multi-column, nested
pages) and offers no write path back into the block tree,
WHEN we add the CO-native extended block types using the portable
**fenced-directive** container syntax (Pandoc / `remark-directive`), a
deterministic block-id assignment helper, and a `PATCH /blocks` endpoint that
applies id-addressed ops (replace / insert_after / delete / move) and re-writes
the entry through the same lossless markdown vault path,
THEN CO gains structured container blocks and block-level editing while staying
markdown-canonical, lossless, and degradation-friendly for plain markdown tools.

## Scope

1. **Extended block types.** Add `Callout`, `Toggle`, `Columns`, `Column`,
   `ChildPage` to `BlockType`. Serialize/parse via fenced-directive containers
   (`:::name {attrs}` … `:::`) with recursive inner markdown. A focused container
   pre-parse splits `:::` regions out of the body and recurses `parse_blocks` on
   the inner content; a matching serializer re-emits them. Unknown `:::name`
   degrades to `Raw` so non-CO markdown tools are unaffected.
2. **`PATCH /api/v1/universes/{slug}/entries/blocks?path=<path>`** — accept
   `{ "ops": [ {"op":"replace","id":..,"block":..}, {"op":"insert_after",..},
   {"op":"delete","id":..}, {"op":"move","id":..,"after":..} ] }`. Load body,
   `parse_blocks`, `assign_ids`, apply ops, `serialize_blocks`, write back via the
   same vault write path `update_entry` uses (one write, re-indexed). Owner/member
   auth; registered on the visibility-gated router.
3. **Deterministic id assignment.** `co::block::assign_ids(&mut [Block])` derives
   stable `blk_…` ids so PATCH can address blocks. IDs serialize into the
   directive `{id=…}` for extended blocks and an unobtrusive `{#blk_…}` trailer for
   standard blocks **only when present** (unreferenced prose stays clean).
4. Update `docs/architecture/api-catalog.md` and regenerate openapi.

## Acceptance

- [ ] `Callout`, `Toggle`, `Columns`, `Column`, `ChildPage` round-trip via the
  fenced-directive container syntax (`parse(serialize(parse(md))) == parse(md)`).
- [ ] An unknown `:::name` directive degrades to a `Raw` block (graceful
  degradation for non-CO markdown tools).
- [ ] `co::block::assign_ids` assigns deterministic, stable `blk_…` ids; ids are
  optional for unreferenced prose and survive a parse→serialize→parse cycle.
- [ ] `PATCH /blocks` applies id-addressed ops (replace / insert_after / delete /
  move) and the resulting on-disk body is valid markdown that re-parses to the
  expected tree.
- [ ] `PATCH /blocks` requires owner/member auth and is gated by the universe
  visibility middleware; unknown ids / malformed ops return a 4xx.
- [ ] No database migration is introduced (the write reuses the existing vault
  path; the block tree is a derived view).

## Out of scope

- Block editor UI (slash menu, drag-reorder).
- CO-468 CRDT wiring — PATCH is plain parse→apply→serialize→vault-write.
- Notion import/export adapters (Phase 3).

## Why

Phase 1 made the block tree readable; Phase 2 makes it *structured* and
*writable*. Container blocks unlock the Notion-class layout vocabulary, and an
id-addressed PATCH gives editors a surgical write path — all without leaving the
markdown-canonical, lossless, edit-anywhere model.
