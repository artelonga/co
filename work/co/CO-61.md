GIVEN multiple clients (quilombo-blog interim, co-web, co-cli, Obsidian plugin, future Tauri desktop, future federated peers) need to sync content bidirectionally without conflicts and without overwriting concurrent changes,
AND GIVEN UAT↔prod sync is the immediate driver (quilombo-blog today, co-web soon),
AND GIVEN Automerge/CRDT rich-text editing (CO-66) and git-backed canonical state (CO-68) must compose on top of this protocol without rework,
WHEN I formalize the v1 sync protocol,
THEN the spec covers: op log shape, Hybrid Logical Clock semantics, content-addressed blob store, 3-way merge algorithm, recursive conflict resolution, idempotency/atomicity guarantees, transport, auth, and test vectors.

## Foundational principles

1. **Op log is canonical. State is derived.** The reducer `(ops, Estado₀) → Estado` is pure; any state is rebuildable from ops.
2. **Every change is an op** — content, schema, config, even conflict resolutions. One primitive, infinite expressivity.
3. **Merge is a function, not a feature.** Given a base HLC and two op sets, the merge function returns `(aplicadas, conflitos, novas_remotas)` deterministically.
4. **Resolutions are ops.** Recursive by construction. Termination guaranteed by strict HLC monotonicity.
5. **Prod-wins by default.** User-facing traffic always takes precedence; UAT changes require explicit promotion.

## Core types

### Operacao

```rust
struct Operacao {
    id: Uuid,                     // UUIDv7, 128-bit, time-sortable
    hlc: Hlc,                     // (wall_ms: u64, counter: u32, node: u128)
    ator: Ator,                   // { node_id: Uuid, user_id: Option<Uuid> }
    tipo: String,                 // dotted path: "foto.adicionar", "conteudo.atualizar.campo"
    alvo: Alvo,                   // { tipo: String, id: String, campo: Option<String> }
    args: serde_json::Value,      // tipo-specific payload
    pai: Vec<Uuid>,               // causal parents (usually 1, multiple for merges)
    assinatura: Option<Ed25519Sig>, // optional, reserved for federation
}
```

### Hlc (Hybrid Logical Clock)

Per Kulkarni et al. 2014. Serialized as `{wall_ms}:{counter}:{node_hex}`, 36 bytes text / 28 bytes binary.

Rules:
- On local event: `counter = counter + 1 if wall unchanged else 0; wall = max(local_wall, prior_hlc.wall)`
- On receive: `local_hlc = hlc_update(local, received)` — max wall, max counter among matching walls, +1
- Total order within a node; partial across nodes; cycle-free given unique node_id

### Ator (Actor Identity)

```rust
struct Ator {
    node_id: Uuid,    // stable per installation, generated at first boot
    user_id: Option<Uuid>, // null for system-emitted ops (migrations, resolvers emitted by server policy)
}
```

Serialized as `{node_id}#{user_id}` (user_id omitted if null).

### Alvo

The addressed entity + optional field. Examples:
- `{ tipo: "foto", id: "<sha256>", campo: null }` — whole photo
- `{ tipo: "relato", id: "oficina-agua", campo: "titulo" }` — one field of a relato
- `{ tipo: "conflito", id: "<conflict_hash>", campo: null }` — a conflict record

### Manifesto

```rust
struct Manifesto {
    node_id: Uuid,
    hlc_atual: Hlc,

```

Peers compare manifestos to detect divergence without transferring full op lists.

### Proposta (sync "pull request")

```rust
struct Proposta {
    id: Uuid,
    peer_origem: Uuid,                // sender's node_id
    base_hlc: Hlc,                    // last HLC shared with target
    ops: Vec<Operacao>,                // ops originated on peer since base_hlc
    blobs_disponiveis: Vec<Sha256>,    // what sender has (target requests missing)
    criado_em: DateTime<Utc>,
}
```

### RelatorioMesclagem (merge report)

```rust
struct RelatorioMesclagem {
    proposta_id: Uuid,
    aplicadas: Vec<Uuid>,              // ops from proposta that landed cleanly
    conflitos: Vec<Conflito>,          // ops requiring resolution
    novas_ops_remotas: Vec<Operacao>,  // target's ops since base_hlc (for sender's display)
    blobs_solicitados: Vec<Sha256>,    // which blobs sender must upload
}

struct Conflito {
    id: Uuid,
    op_local: Uuid,       // target (prod) op
    op_remota: Uuid,      // sender (uat) op
    alvo: Alvo,
    opcoes: Vec<String>,  // ["prod", "uat", "copia", "manual"]
    sugestao: String,     // default = "prod"
}
```

## Merge algorithm

```
function mesclar(base_hlc: Hlc, ops_local: [Op], ops_remota: [Op]) -> RelatorioMesclagem:
    # 1. Partition local ops: those since base_hlc
    ops_local_pos_base = [op for op in ops_local if op.hlc > base_hlc]

    # 2. For each remote op, check for conflict with any local post-base op
    aplicadas, conflitos = [], []
    for r in ops_remota:
        concorrentes = [l for l in ops_local_pos_base
                        if l.alvo == r.alvo and not causal_ancestor(l, r) and not causal_ancestor(r, l)]
        if not concorrentes:
            aplicadas.append(r.id)
        else:
            conflitos.append(Conflito {
                id: hash_sorted([r.id] + [l.id for l in concorrentes]),
                op_local: concorrentes[0].id,  # first concurrent; all reported in ops list
                op_remota: r.id,
                alvo: r.alvo,
                opcoes: ["prod", "uat", "copia", "manual"],
                sugestao: "prod",
            })

    return RelatorioMesclagem { aplicadas, conflitos, novas_ops_remotas: ops_local_pos_base }
```

**Complexity**: O(|ops_remota| * |ops_local_pos_base|) naive. Optimization: index ops_local_pos_base by `alvo` → O((|local| + |remota|) log n). Good enough for 10⁵ ops per sync.

**Causality check**: `causal_ancestor(a, b)` → walk `b.pai` transitively; true iff `a.id` reachable. Cached via op_id → ancestor_set lookup table rebuilt on reducer bootstrap.

## Recursive resolution

A `conflito.resolver` op may introduce new conflicts (e.g., "copia" synthesizes new entity ops that collide with existing slugs). These are detected by re-running merge on resolver's emitted sub-ops. Nested conflicts queue as new pending conflicts. Admin resolves each in turn. Termination:

**Theorem**: Conflict resolution terminates.
**Proof**: Each resolver op has hlc_resolver > max(hlc_op_a, hlc_op_b). Each emitted sub-op has hlc > hlc_resolver. There are finitely many ops in any sync proposal. HLC is monotonically increasing. Therefore the resolver DAG has bounded depth ≤ |proposta.ops|.

## Transport

### HTTP endpoints (REST)

| Endpoint | Method | Auth | Body | Response |
|---|---|---|---|---|
| `/sync/api/manifesto` | GET | none | — | `Manifesto` |
| `/sync/api/ops?desde_hlc=X` | GET | Bearer | — | NDJSON `Operacao` stream |
| `/sync/api/blob/{sha256}` | GET | Bearer | — | bytes (Content-Type from stored mime) |
| `/sync/api/proposta` | POST | Bearer | `Proposta` | `RelatorioMesclagem` |
| `/sync/api/proposta/{id}/blob/{sha256}` | POST | Bearer | bytes | `{ ok: true }` |
| `/sync/api/proposta/{id}/resolver` | POST | Bearer | `{ resolucoes: [...] }` | `{ estado_final: ..., novo_hlc: ... }` |
| `/sync/api/proposta/{id}` | GET | Bearer | — | proposta status + last report |
| `/sync/api/proposta/{id}` | DELETE | Bearer | — | cancel open proposta |

All state-mutating endpoints wrap application in SQLite transaction → atomic.

### WebSocket (v1.1, reserved for CO-67)

`GET /ws/sync/{universe}` — duplex op stream for real-time.

## Auth

### v1.0 (shared secret)

`Authorization: Bearer {SYNC_TOKEN}` — rotatable via env var. Simple, sufficient for admin-to-admin sync.

### v1.1 (federation, reserved)

JWT per node, ed25519-signed ops, capability tokens per universe. Unlocked when CO-67/CO-68 land.

## Idempotency & atomicity guarantees

| Operation | Guarantee | Mechanism |
|---|---|---|
| `POST /proposta` | idempotent by `Proposta.id` | op IDs are UUIDv7; `INSERT OR IGNORE` |
| `POST /proposta/{id}/resolver` | idempotent by resolver op ID | same |
| Sync cycle mid-failure | no partial state | wrapped in transaction; rollback on error |
| Double-submit | no duplicate ops | id UNIQUE constraint |
| Out-of-order blob upload | safe | blobs content-addressed; verify sha256 before accept |

## Reducer rules

- Ops are applied in **HLC-topological order** (pai-DAG-respecting).
- When a `conflito.resolver` op is applied:
  - Ops in `ops_superadas` are marked overridden in the index — reducer ignores them when computing state.
  - Ops in `ops_efetivas` are retained. Unique constraint: each op may be superseded by at most one resolver.
- Re-applying a resolver with same id = no-op.
- Reverting a resolution: emit a new `conflito.resolver` with opposite `ops_efetivas` / `ops_superadas`. The DAG reflects override chain.

## Compatibility with the existing sync track (CO-51, CO-54, CO-55, CO-58)

The op-log protocol in v1 is **not a replacement** for the existing CLI + file-based sync track. It is the layer underneath. File-level sync becomes a projection of the op log.

### Mapping file-based concepts to op-log

| CO-51 / CO-54 / CO-58 concept | CO-61 v1 equivalent |
|---|---|
| `sync.json` file hashes | `Manifesto.ops_merkle_root` + per-entry hash derived from reducer |
| `last-write-wins` | `conflito.resolver { estrategia: "prod" | "uat" }` picked by HLC comparison |
| `local-wins` | `estrategia: "uat"` (client always resolves its way) |
| `remote-wins` | `estrategia: "prod"` (default policy) |
| `manual` (`.local/.remote/.base` sidecar files) | `estrategia: "manual"` + server-side projection of sidecar files for CLI consumption |
| `merge` (3-way auto on non-overlapping hunks) | Non-conflicting ops merge cleanly; overlapping ops open `Conflito` |
| CO-54 `entry_versions` table | Materialized view rebuildable from op log (each version = reducer state at HLC_k) |
| CO-54 `.conflict` marker file | Optional server-side projection: for every open `Conflito`, write `{path}.conflict` to vault. CLI reads it. |
| CO-58 desktop tray file watcher | Watches vault files → diffs against current reducer state → emits ops via `POST /sync/api/proposta` |
| CO-58 PWA offline write queue | IndexedDB holds pending ops (same `Operacao` shape); flushes on reconnect via same endpoints |

### Guarantees for file-based clients

CO-51 can be implemented against CO-61 endpoints without knowing about ops:

1. `co sync pull` = `GET /sync/api/manifesto` + reconstruct files from current reducer state (provided by `GET /sync/api/vault/notes` — a file-facing API on top of the reducer, shipped with CO-63).
2. `co sync push` = read local files, compute diff vs last-known manifesto, POST `Proposta` containing derived ops (`conteudo.atualizar`, `foto.adicionar` as needed).
3. Server applies proposta with merge. Returns `RelatorioMesclagem`. CLI maps back to file-level outcomes + writes `.conflict` files for any pending conflitos.
4. `co sync status` = `GET /sync/api/manifesto` + compare to local sync.json.
5. `co sync watch` = polling or (later) WebSocket subscription.

### CO-55 (SSH keys) orthogonal

SSH key management is for git clone. Sync protocol auth is `SYNC_TOKEN` (v1) / JWT+ed25519 (v1.1). Different layer. No conflict.

### CO-58 (desktop tray + PWA) natively supported

Tray app and PWA both consume `/sync/api/*` endpoints. No protocol changes needed. WebSocket upgrade for live push comes in CO-67.

### CO-54 idempotency rules — preserved and strengthened

CO-54's idempotency table maps onto CO-61:

| CO-54 operation | CO-61 behavior |
|---|---|
| PUT with same content = no-op | Identical op (same args produce same derived ID when canonicalized) = `INSERT OR IGNORE` |
| DELETE non-existent = 204 | `foto.remover` on unknown sha256 = emit op marked `no_effect: true` in reducer audit, no state change |
| Task status same = no-op | `conteudo.atualizar` with matching meta_delta → reducer detects no change, emits op but marks effective=false |
| co-auto lockfile | Orthogonal — still enforced per-task by co-auto runtime |

### Migration path

- CO-51 v1 ships against file-level hashes. CO-51 v2 (future) migrates to emitting ops internally while preserving CLI surface.
- CO-54's `entry_versions` table is kept as read-model; new writes go through op log; reducer populates entry_versions on apply.
- CO-58 starts on CO-61 endpoints directly — no file-hash sync.json needed if using op manifesto.

### Why this works

The core observation: **any file state is derivable from a sequence of ops, and any file diff can be encoded as a sequence of ops.** So file-based and op-based are isomorphic, with op-based strictly more expressive (it also encodes intent, authorship, partial changes, atomic multi-file transactions).

Adopting op-log as the server's internal canonical model while keeping the file-level API means:
- CO-51/54/58 ship without knowing about ops if they don't want to
- CO-66 (Automerge) nests inside ops without affecting file consumers
- CO-68 (git projection) writes canonical files from ops, closing the loop
