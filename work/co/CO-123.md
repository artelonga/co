## As

a CO operator who has outgrown WAE's cardinality and wants ad-hoc analytics

## I Need

a single-node ClickHouse on Fly Machines with persistent volume, the `iceberg(...)` table function enabled, and a regular WAE export pipeline so ClickHouse can answer the queries WAE can't

## To

bridge the gap between WAE (cheap, low-cardinality, real-time) and the full Iceberg lake (Phase 3) — without committing to Pinot or Tinybird, and with the option to swap in Iceberg sources later

## Given / When / Then

GIVEN WAE handles real-time low-cardinality telemetry but not multi-day joins or high-cardinality dimensions,
WHEN we deploy `clickhouse/clickhouse-server` as a Fly app with a 50 GB Volume and a daily WAE export job,
THEN yuri can answer ad-hoc analytics questions (top-N universes by activity, retention curves, error rate by build) in <1s, and the same engine will read Iceberg directly when Phase 3 lands.

## Topology

```
WAE dataset ──(daily SQL export → S3-compatible R2)──→ ClickHouse Volume
                                                            ▲
                                                            │
                                  ad-hoc queries ───────────┘ (admin-only auth)
```

## Why ClickHouse, not Pinot

Per `docs/platform-evaluation.md` Part II §12 and the SR-plan review §B.3:
- ClickHouse is a single binary; Pinot needs Controller + Broker + Server + Minion
- ClickHouse's `iceberg(...)` table function makes Phase 3 transition trivial
- Pinot's win is sub-second QPS at thousands of QPS, which CO does not have a product surface for yet
- Move to Pinot in Phase 5 only if a kQPS-shaped surface emerges (CO-136)

## Acceptance

- [ ] Fly app `co-clickhouse` deployed with 4 vCPU / 8 GB / 50 GB Volume
- [ ] Internal-only access (Fly private network or `fly proxy` for queries)
- [ ] Daily WAE → ClickHouse export job (Fly Machine cron)
- [ ] Sample queries documented: top-10 universes by activity (24h), error rate by deploy, retention 7d/30d
- [ ] `iceberg(s3, '...')` table function enabled and tested against an empty Iceberg table on R2 (smoke test for Phase 3 readiness)
- [ ] `docs/OPERATIONS.md` updated with how to run a query, where to read results, how to back the volume up

## Out of scope

- Replication / multi-node — single-node is fine until ≥1 TB
- ClickHouse Cloud migration — re-evaluate if self-host ops become a burden
- User-facing analytics surfaces — Phase 5

## Risks

- **Volume size exhaustion.** Mitigation: WAE export keeps last 90 days only; older data lives in WAE itself or Iceberg (Phase 3)
- **Cardinality blowup on `path`/`user_agent`.** Mitigation: pre-aggregate at export time; store dimensions only on sampled rows
