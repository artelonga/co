## As

a CO operator

## I Need

`co-web` to write low-cardinality real-time events (page views, A/B exposures, error counts, deploy markers) directly to a Cloudflare Workers Analytics Engine dataset

## To

get a queryable real-time telemetry surface today, at near-zero cost, before justifying a Redpanda + Iceberg streaming bus — and to set the API shape that the Phase 1 A/B tooling will reuse

## Given / When / Then

GIVEN we have a Cloudflare account hosting the `co.artelonga.com.br` zone (CO-117),
WHEN we provision a WAE dataset and a tiny Worker that proxies POST `/api/internal/wae` to `env.WAE.writeDataPoint(...)`, AND wire `co-web` to emit events to that endpoint via the existing telemetry pipeline,
THEN telemetry rows are queryable via the WAE SQL API within ≤60s of the originating event, scoped per universe via tags.

## Event shape

```rust
struct TelemetryEvent {
    event_type: String,    // "page_view" | "ab_exposure" | "error" | "deploy"
    universe_id: String,   // partition key
    user_kind: String,     // "anon" | "authed" | "admin"
    flag_key: Option<String>,    // for ab_exposure
    variant: Option<String>,     // for ab_exposure
    duration_ms: Option<u32>,
    status: Option<u16>,
    // NEVER carry user content text or PII
}
```

## Privacy boundary (load-bearing)

The ingest path **rejects** any payload field whose length exceeds 256 bytes, or whose key matches `/content|body|text|markdown|prose/i`. This is enforced at the Worker proxy and again in `co-web`'s emitter. Tested as a guarantee, not a convention. See `docs/platform-evaluation.md` §20.

## Acceptance

- [ ] WAE dataset `co_telemetry` provisioned
- [ ] Worker proxy deployed at `wae.co.artelonga.com.br` (or as a route on the apex zone) with API-key auth
- [ ] `co-web` `telemetry` module gains `emit(TelemetryEvent)` helper using async fire-and-forget
- [ ] Synthetic exposure event from UAT visible in WAE SQL within 60s
- [ ] Privacy filter test: payload with a 1KB `body` field is rejected with a structured error
- [ ] Existing telemetry tables in OLTP keep working (parallel write, not replacement)

## Out of scope

- Replacing OLTP `telemetry_events` table — runs in parallel until Phase 2 ClickHouse query parity is proven
- A/B assignment logic — that's CO-121, this ticket only emits exposures
- Anomaly detection / alerting — Phase 2+

## Risks

- **WAE row sampling.** WAE samples high-volume datasets. At our scale that's fine; document the threshold.
- **Cloudflare account-level limits.** WAE has a free tier; verify CO sits comfortably inside it before relying on it.
