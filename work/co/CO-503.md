GIVEN CO has two incompatible tool systems — Rust trait-based tools (`co/src/tool.rs`,
3 tools) and the agent's Python `CoTools` (Anthropic JSON-schema shape, in
`tools/whatsapp-bot/bridge/capabilities.py`) — and a tool is only useful to an
agent when it presents an LLM-shaped contract (a name, a description, a JSON
`input_schema`, and a `run(args) → result`),
WHEN we define **one canonical tool contract** that both the Rust tools and the
agent's CoTools implement,
THEN any tool — native or bridge-side — is callable from the same tool-calling
loop, and the core CO operations (entry CRUD, telemetry, the `me/export|erase|forget`
endpoints) become **first-class tools**, not just HTTP routes that only the SPA knows about.

## Acceptance

- [ ] **One tool contract** defined: `name` / `description` / JSON `input_schema` /
  `run(args) → result`, expressed so a Rust trait tool and a Python `CoTool` are
  two implementations of the *same* shape (the LLM never sees which language ran it).
- [ ] **Entry CRUD surfaced as tools** (create/read/update/delete/move entries) — the
  agent can mutate a universe through the canonical contract, not by reimplementing
  HTTP calls.
- [ ] **Telemetry surfaced as a tool** (record an event) under the canonical contract.
- [ ] **`me/export | me/erase | me/forget` surfaced as first-class tools** (data-autonomy
  operations the agent can invoke on the user's behalf), with the same consent/identity
  guards as their HTTP routes.
- [ ] **Tool registry** enumerates available tools and emits their JSON `input_schema`
  in the LLM-ready shape (the format both Ollama and Claude backends consume).
- [ ] No tenant-specific tool names (no `quilombo`/`rfq`); tools are generic CO
  operations. Any tenant mapping lives in the DB, not in the tool's identity.
- [ ] **Format-agnostic contract**: one `name` / `description` / `input_schema` / `run`
  shape that BOTH CO's Rust tools AND the agent's Python `CoTools` satisfy — swapping a
  tool's implementation is a flag, not a refactor.
- [ ] **`tool_type` distinguishes script-tools from LLM-tools**: `tools/schema.yaml`
  carries `tool_type: deterministic | predictive` so deterministic script-tools (CO-521)
  and LLM-backed tools (CO-522) are registered and dispatched under the same contract.
- [ ] **yt-summarizer is the reference adapter** — the canonical front-door shape new
  tools (deterministic and predictive) target.

## Notes
- This is the keystone of the **agents-not-bot** release: a single tool contract is
  what lets CO's native agents (CO-504) and capability packs (CO-505) work without
  the bridge being the only runtime that can call tools.
- "Tools as routes" stays true — the canonical tool can wrap the existing axum
  handler — but the *contract* is the tool, so an agent and the SPA share the same
  underlying operation.
- Term is **tool/ferramenta** and **agent/agente** — never "bot".
