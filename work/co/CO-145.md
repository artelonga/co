## As

a CO user (and especially an admin moving the 506 MB quilomboaraucaria content into the platform) who needs every file — markdown, image, video, audio, PDF — to be **encrypted at rest**, **indexable without decryption**, **available by request through a stable per-asset endpoint**, and **lazily loaded** for large media

## I Need

a content-addressable asset layer that stores each file as a sha256-keyed ciphertext blob in the per-universe directory, indexes plaintext metadata (filename, mime, size, sha256, frontmatter, tags) in the per-universe SQLite, and serves bytes only via authenticated GET endpoints with HTTP range + cache headers

## To

unblock binary content (images/video) that the Vault API rejects today, deliver the privacy-at-rest claim the platform makes implicitly, and make lazy-load + offline-first viable in the SPA

---

## Design

Full design at `docs/research/encrypted-indexable-assets.md`. Summary:

- **Index plaintext, encrypt body bytes** — searchable encryption is a trap; instead split metadata (clear) from bytes (ciphertext).
- **Per-universe DEK** wrapped under owner KEK derived from password/OAuth via Argon2id. Single-owner v1; multi-recipient deferred.
- **ChaCha20-Poly1305 AEAD** with `universe_key || sha256` AAD — binds ciphertext to its identity.
- **Storage at `data/universes/<aa>/<bb>/<key>/blobs/<aa>/<bb>/<sha256>`** — content-addressed, sharded, dedupes within universe.
- **Lazy-load via per-asset GET** with `Cache-Control: private, immutable` + ETag = sha256. Range requests supported by full-decrypt-then-slice (acceptable up to ~50 MB; revisit chunked-AEAD for large video later).

## Phases (one ticket each)

| Phase | Ticket | Deliverable | Why this order |
|---|---|---|---|
| 1 | CO-146 | Binary upload + sha256 CAS, per-universe `assets` table, GET endpoint (plaintext) | Unblocks the 506 MB upload that's stuck today |
| 2 | CO-147 | Indexable metadata: list/filter endpoint, tags, mime filter, frontmatter extraction | Enables search/asset-browser UI |
| 3 | CO-148 | Per-universe DEK + ChaCha20-Poly1305 envelope at write/read; key wrapping under owner KEK | Delivers the encryption claim |
| 4 | CO-149 | HTTP range, ETag, immutable cache, IndexedDB cache contract | Streams large media efficiently |
| 5 | CO-150 | SPA `<img loading="lazy">` + `<video preload="none">`, asset browser UI, frontmatter excerpt endpoint | The user-facing lazy load |

## Acceptance (epic-level)

- 506 MB of quilomboaraucaria content (markdown + images) successfully uploads to a CO universe without the API rejecting binary bytes.
- Anyone with disk-level access to `data/universes/.../blobs/` sees opaque ciphertext, not plaintext images. (Phase 3 acceptance.)
- A 5 MB image fetched twice in a session hits IndexedDB on the second fetch (zero server traffic). (Phase 4 acceptance.)
- The board view loads with markdown frontmatter only, fetching image bytes lazily on scroll. (Phase 5 acceptance.)
- A 50 MB video plays in the browser via HTTP range requests. (Phase 4 acceptance.)

## Out of scope (deferred to future epics)

- Multi-collaborator key sharing (need a recipient-list scheme; v1 is single-owner).
- Streaming-AEAD for files > 50 MB (STREAM construction or age's chunked format).
- Server-side thumbnails (client-side derives + uploads its own thumbnail blob).
- Body-text full-search across encrypted blobs (open question; client-side IndexedDB index is the leading candidate).
