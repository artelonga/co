## As

A maintainer who has to keep CO's API documentation honest — today both /Users/artelonga/projects/co/docs/architecture/api-catalog.md (357 lines) and /Users/artelonga/projects/co/co-web/openapi.yaml (1804 lines) exist, with **zero enforcement** that they describe the same surface.

## I Need

A codegen script that emits openapi.yaml from the catalog (the human-readable manifest), and a CI check that fails the build when the two diverge.

## So That

- The catalog stays the single source of truth — operators read it, machines generate from it.
- Adding a route requires a catalog row, which forces the maintainer to assign auth tier + tags + summary at the moment the route lands (not "later").
- Drift between docs and yaml stops being a recurring cleanup task.

## Context

Quilombo already runs this pattern. See:

- /Users/artelonga/projects/quilomboaraucaria/web/scripts/generate-openapi.ts — parses `docs/architecture/api-catalog.md` (markdown table), walks `src/routes/**` to discover actual HTTP methods, asserts every route in code has a catalog row and vice versa.
- /Users/artelonga/projects/quilomboaraucaria/web/package.json:
  - `openapi:gen` regenerates the yaml
  - `openapi:check` exits 1 on drift (no write)
  - The repo's top-level `check` script chains `openapi:check` after svelte-check.

CO's setup is similar in spirit — `api-catalog.md` lives in /Users/artelonga/projects/co/docs/architecture/ — but no generator and no CI gate exist.

CO routes are Rust (axum), not SvelteKit. Walking the route tree to discover handlers is harder. Two viable paths:

1. **TS port** of quilombo's script that grep-walks `co-web/src/**/*_routes.rs` for axum router builder calls (`.route("/path", get(handler))`) and extracts method + path.
2. **Rust binary** in `co-web/src/bin/generate_openapi.rs` that imports `crate::server::router` and walks the assembled `axum::Router` to enumerate routes (axum exposes `Router::into_make_service` but not a route iterator — would need a custom registry).

Path (1) is faster to ship and matches the quilombo precedent. Path (2) is more robust but invasive.

## Design

### Choose Path 1 — TS port

Add /Users/artelonga/projects/co/co-web/scripts/generate-openapi.ts modelled directly on the quilombo script. Differences:

- Routes dir: `co-web/src/**/*_routes.rs` (multi-glob: `content/`, `server/`, `routes/`).
- Route discovery: regex over Rust source for `.route("(/[^"]*)",\s*(get|post|put|patch|delete)\(`.
- Catalog parsing: identical (markdown table with `| Method | Path | Summary | Tags | Auth |` header).
- Output: `co-web/openapi.yaml` (overwrites the existing file when `--gen`; diffs when `--check`).
- The generator emits the OpenAPI 3.0 envelope, `paths`, and basic operation objects (`summary`, `tags`, `security`). Schemas (`components/schemas`) stay hand-written and are concatenated in from `co-web/openapi-components.yaml` (new file, extracted from current openapi.yaml).

### Wiring

```json
// co-web/package.json (extend the existing one if present, else create)
{
  "scripts": {
    "openapi:gen":   "node --import tsx scripts/generate-openapi.ts",
    "openapi:check": "node --import tsx scripts/generate-openapi.ts --check"
  },
  "devDependencies": {
    "tsx": "^4",
    "js-yaml": "^4"
  }
}
```

### CI

Add /Users/artelonga/projects/co/.github/workflows/openapi-check.yml:

```yaml
name: OpenAPI drift check
on:
  pull_request:
    paths:
      - 'co-web/src/**/*_routes.rs'
      - 'docs/architecture/api-catalog.md'
      - 'co-web/openapi.yaml'
      - 'co-web/scripts/generate-openapi.ts'
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: cd co-web && npm install --no-audit --no-fund
      - run: cd co-web && npm run openapi:check
```

### One-time bootstrap

The first run will likely flag drift between the existing catalog and openapi.yaml. Resolve by:

1. Add a catalog row for every route the regex discovers.
2. Remove (or move to a `## Deprecated` section) every catalog row whose path no longer exists.
3. Regenerate openapi.yaml from the now-aligned catalog.
4. Commit the resulting catalog + yaml in the same PR.

### Failure mode messages

The script should print actionable diffs on `--check` failure:

```
[generate-openapi] DRIFT detected:
  + Route in code but missing from catalog: POST /api/v1/me/graph-views
  - Route in catalog but missing from code: GET /api/v1/legacy/foo
  ~ Catalog says auth='-' but route has auth middleware: PATCH /api/v1/universes/{slug}/source
```

- [ ] `npm run openapi:gen` regenerates co-web/openapi.yaml from the catalog without manual edits.
- [ ] `npm run openapi:check` exits 0 when in sync, exits 1 with a readable diff when drifted.
- [ ] CI workflow `openapi-check.yml` runs on PRs that touch any of: `*_routes.rs`, `api-catalog.md`, `openapi.yaml`, the generator script.
- [ ] Bootstrap commit aligns catalog + openapi.yaml so `--check` passes on `main` immediately after merge.
- [ ] A deliberate test PR that adds a new route without a catalog row fails CI.
- [ ] README or `docs/architecture/api-catalog.md` header gains a 3-line "How to add a route" note.

## Blast radius

- 1 new generator script (~250 lines TS, ported from quilombo)
- 1 new GitHub Actions workflow (~20 lines)
- 1 new `co-web/package.json` (if it doesn't exist) or extension of the existing one
- ~0–50 line cleanup of `api-catalog.md` rows to match reality
- Regenerated `openapi.yaml` (large diff, mechanical)
- No Rust code change. No migration.

## Not in scope

- Type-level schema generation (component schemas stay hand-written via `openapi-components.yaml`).
- Generating client SDKs from the yaml (separate ticket).
- Migrating to Rust-native OpenAPI codegen (`utoipa` crate) — that's the Path-2 alternative, defer until Path 1 hits limits.
- Auto-publishing the yaml to a public docs site.
- Versioning openapi.yaml (v1 stays the only public surface for now).
