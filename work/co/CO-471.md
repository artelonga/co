GIVEN CO's public API grew an inconsistent vocabulary (`entries`, `vault`,
`graph`, `query`, …) while the platform now wants a clean, stable, **one-word
noun per interface** — the contract that import/export adapters (Notion,
Obsidian, Logseq, Quartz) wrap, so CO's API is the portable superset and no tool
is the data model,
WHEN we name each interface with a single brand-aligned noun and expose it as a
thin wrapper over existing internals,
THEN adapters become mechanical per-route mappers and CO's surface reads in its
own voice (Cocriar · Colaborar · **Conectar**).

## Canonical interfaces

`universes` · `entries` · `blocks` · `properties` · `schemas` · **`connections`**
(pt `conexões`) · `comments` · `assets` · `users` · `search`. Typed links use
**connections/conexões** (the Conectar pillar), never the generic "relations".

## Acceptance

- [ ] `GET /{slug}/search` serves the CO-74 query DSL — a true alias of `query`
  (identical status for the same expression); `query` kept as a deprecated alias.
- [ ] `GET /{slug}/connections?path=…` returns an entry's outbound + inbound
  typed links (CO-74), as a thin wrapper over the relation repository.
- [ ] `GET /{slug}/entries/blocks?path=…` (CO-470) is recorded in the catalog.
- [ ] `docs/architecture/api-catalog.md` documents the new routes and the
  `query`→`search` deprecation; `openapi.yaml` regenerated with no *new* drift.
- [ ] Integration tests: connections shape (outbound/inbound arrays) + search
  alias parity.

## Out of scope (follow-ups)

- New `comments` resource (net-new behavior + storage) — its own PR.
- Promoting `entries/blocks` to top-level `blocks` and other route relocations —
  cosmetic, deferred to avoid churn while the contract settles.
- The `graph` HTML visualization stays as-is (distinct from the `connections`
  data API).
