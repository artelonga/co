## As

a CO user who wants their universe published to **their own** infrastructure choice

## I Need

a `deploy.yaml` manifest schema as a first-class universe artifact, a deployer-adapter trait, and at least two reference adapters (`static-on-R2`, `cloudflare-pages`) so deployment is platform-pluggable

## To

make "CO is the only surface" structurally true — users author content + rules + code + deployment manifest in a self-contained universe, CO orchestrates the deploy to whichever target the manifest names, and adding new targets becomes a new adapter, not an architecture change

## Stories

- CO-133 — `deploy.yaml` schema + universe-level manifest validation
- CO-134 — Deployer adapter trait + first impl (`static-on-R2`)
- CO-135 — Second deployer adapter (`cloudflare-pages`)
- CO-136 — Pinot evaluation (only if user-facing kQPS analytics surface justifies it)

## Acceptance gates

- [ ] A malformed `deploy.yaml` is rejected with a specific, actionable error
- [ ] Universe `u_test` with `target: static-on-R2` deploys end-to-end; public URL serves the landing page
- [ ] Same universe with `target: cloudflare-pages` deploys to `*.pages.dev` without source changes
- [ ] Cross-universe analytics query returns federated result for 3+ universes
- [ ] Pinot evaluated against the live analytics surface: either justified and adopted, or explicitly deferred with documented reason

## Out of scope

- Vercel and Fargate deployer adapters — file as follow-up tickets after the trait is stable
- Marketplace (Tier 5 capstone) — separate epic
- Per-universe paid hosting / billing — separate epic

## Why now

This is what makes CO a control plane vs. a single-tenant app. Phase 5 because it depends on Phase 1 (co-agent), Phase 2 (multi-target telemetry), and Phase 3 (streaming bus for federated analytics). Building it earlier would prematurely lock the abstraction.
