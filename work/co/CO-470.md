GIVEN CO stores an entry's content as a flat markdown body, so the platform
cannot offer block-level editing (slash menu, drag-reorder, toggles, callouts,
nested pages, inline collections, multi-column) — the single largest gap vs.
Notion-class editors — and GIVEN we explicitly do **not** want to depend on
Notion's API or data model (it is one possible interop target, not our schema),
WHEN we introduce a **block model that is a typed AST *over* the markdown body**
— markdown stays the canonical on-disk form, every block round-trips losslessly
to markdown, and non-CommonMark blocks use a portable container syntax — and
expose it through a small read/patch API,
THEN CO gains block-level editing and structure while remaining markdown-native,
git/grep-friendly, and portable; Notion (and any other tool) becomes an optional
import/export **adapter** that maps into our block schema, never a dependency.

## Design principles (non-negotiable)

1. **Markdown is canonical.** The block tree is a *parsed view* of the entry
   body, not a replacement store. Source of truth on disk stays `.md` (and the
   `.co` envelope). Any block edit re-serializes to markdown. No second content
   store, no DB-only block rows that can drift from the file.
2. **Lossless round-trip.** `parse(serialize(blocks)) == blocks` and
   `serialize(parse(md)) == md` (modulo normalization). A file edited in Obsidian
   and a file edited in CO's block editor converge — ties into the CO-51 sync /
   edit-anywhere round-trip already validated by `scripts/e2e-sync.sh`.
3. **No Notion coupling in core.** Core block types are CommonMark/GFM-derived
   plus a small CO-native extended set. No Notion IDs, no Notion-specific fields.
   Forward-compatibility = our block schema is a **superset that Notion blocks
   map into**, handled entirely in an optional adapter (see Phase 3).
4. **Graceful degradation.** Extended blocks use a documented container syntax
   that any markdown reader renders as *something* sane (never raw JSON in the
   body). A plain markdown tool that doesn't understand `:::callout` still shows
   the inner content.

## The block model

A `Block` is a node in the entry's content tree:

```
Block {
  id:       String,        // stable, content-addressed or nanoid; survives round-trips
  type:     BlockType,     // see below
  attrs:    Map<String,Json>, // type-specific (heading level, language, callout icon…)
  text:     Option<RichText>, // inline content where applicable (rich text model)
  children: Vec<Block>,    // recursive — pages and blocks form one tree
  span:     Option<ByteSpan>, // source range in the markdown body (for incremental edits)
}
```

- **Standard blocks (direct CommonMark/GFM ↔ block):** `paragraph`, `heading`
  (1–6), `bulleted_list_item`, `numbered_list_item`, `to_do` (GFM task list),
  `quote`, `code` (with language), `table`, `image`, `divider`, `link`/inline via
  rich text. These need **zero extension syntax** — they already are markdown.
- **Extended blocks (CO-native, container syntax):** `callout`, `toggle`,
  `columns`/`column`, `child_page`, `child_collection` (inline data-source view,
  ties to CO-93 universe types), `embed`, `synced_block`. Serialized with the
  **fenced-directive / fenced-div** convention (Pandoc / `remark-directive`):

  ```markdown
  :::callout {icon="💡" id="blk_a1b2"}
  Body is **normal markdown** — fully portable, degrades gracefully.
  :::

  :::toggle {summary="Details" id="blk_c3d4"}
  Hidden content here.
  :::
  ```

  This keeps extended blocks *inside markdown*, human-readable, diff-able, and
  parseable by other tools. No HTML blobs, no JSON-in-body.
- **Rich text** (inline): text + annotations (bold/italic/code/strike/link) +
  **mentions** (`[[key::path]]` wikilinks — CO's existing cross-universe syntax,
  CO-340) + dates. Maps to markdown inline; mentions stay wikilinks.

### Stable block IDs

Addressing (comments, realtime cursors, deep links, block-level permissions)
needs stable IDs without polluting plain prose. Standard blocks get an **optional**
trailing anchor only when something references them (e.g. a comment); extended
blocks carry `id=` in their directive attrs. Anchor convention: an invisible
`{#blk_…}` attribute (kramdown/`remark-attr` style) that round-trips and is
stripped by readers that don't support it. IDs are never required for a block to
exist — unreferenced prose stays clean.

## API surface (read + patch, all serialize to markdown)

- `GET  /api/v1/universes/{slug}/entries/{path}/blocks` → the block tree (parsed
  from the canonical body).
- `PATCH /api/v1/universes/{slug}/entries/{path}/blocks` → block ops
  (insert/update/move/delete by id); server re-serializes the whole body to
  markdown and writes via the existing vault path (one write, indexed as today).
- Realtime: blocks layer **on top of the existing CO-468/Yjs `/ws/doc` CRDT** —
  the doc is the markdown text; block ops are derived edits. No new socket.

## Acceptance

- A `Block` tree parses from and serializes to a markdown body losslessly for all
  standard CommonMark/GFM constructs (property-test: `serialize(parse(md))==md`).
- Extended blocks (callout, toggle, columns, child_page) round-trip via the
  container syntax and degrade gracefully in a plain markdown renderer.
- Block IDs are stable across a parse→edit→serialize→parse cycle and optional for
  unreferenced prose.
- `GET /blocks` returns the tree; `PATCH /blocks` applies id-addressed ops and the
  resulting on-disk body is valid markdown that re-parses to the expected tree.
- Edit-anywhere holds: a file changed in an external editor and one changed via
  the block API converge (extends `scripts/e2e-sync.sh`).
- **Zero** Notion identifiers/fields in `core` or `co-web` block code.

## Out of scope / phasing

- **Phase 1 (this spec):** the block model + lossless markdown serializer +
  read/patch API + standard blocks. No new editor UI yet.
- **Phase 2:** extended blocks + the block editor UI (slash menu, drag-reorder)
  on top of the CO-468 CRDT editor; `child_collection` inline views over CO-93
  data sources; multi-view (table/board/calendar/gallery).
- **Phase 3 (optional, separate crate/module):** import/export **adapters** —
  Notion (`blocks` → CO blocks), Obsidian/Logseq (already markdown), Quartz
  export. Adapters depend on the block schema; the block schema depends on none
  of them. This is where "forward compatibility & portability" is realized:
  add a target by writing an adapter, never by changing core.

## Why

The block model is the keystone Notion-class abstraction (page = properties +
recursive block tree). Building it *over* markdown rather than as a parallel
store preserves CO's identity — markdown-canonical, git/grep-friendly,
edit-anywhere, AGPL-portable — while unlocking structured editing. Treating
Notion as an adapter, not a dependency, means CO can interop with Notion (and
Obsidian, Logseq, Quartz) without ceding its data model to any of them.
