## As

Any logged-in user with a private universe (e.g. yuri) — and the operator running CI

## I Need

Two related, currently-broken invariants restored:

1. **Every universe — template, private, public, sister-deployable — must contain at least one default project on first access.** Visiting an empty universe must never render "no project found"; it must render an empty default project ready to accept entries.
2. **The template universe must seed its 9 onboarding tasks under the canonical project key** (currently the test expects `CO`, the code seeds `TUTORIAL`, the tests assert `9`, the code seeds `0`). Choose one and align all sides.

## So That

- Yuri's private universe (the operator's own workspace) stops showing the empty "no project found" view — it's currently a dead-end for the platform's most active user.
- CI on `main` goes green again — the 4 cascading `template_tests.rs` failures are blocking every deploy since 2026-05-20.
- The "platform always has a place to put entries" promise — central to CO's content-graph model — holds at every entry point.

### The underlying mess

Recent commits touched template / seed / universe-rename code:

- `631005e fix(co-seed): wipe stale entries before re-seeding co universe on boot` — added a wipe-before-seed step. Suspect: the wipe runs but the re-seed doesn't, or the re-seed targets a different project key.
- `6f34b62 fix: universe hierarchy + co rename + pdf error UX` — "co rename" almost certainly renamed something CO→TUTORIAL but didn't update the tests or all downstream consumers.

Need to:

1. Read `co-web/src/storage/seed.rs` (or the actual seed entry point) and confirm what project key it now writes.
2. Reconcile: tests want `CO`, code writes `TUTORIAL` — decide which is the truth and align both.
3. Inspect the private-universe creation path — does it call `seed_default_project()` on first access? If not, add it.
4. Find why writes to template now return 500 instead of 403 — likely a panic in the write-protection layer that masked the intended 403 response.

## Decision

### Project naming — pick one

| Option | Pros | Cons |
|---|---|---|
| **A. Standardize on `CO`** as the template's project key | Matches existing tests, matches CHANGELOG history, matches what's in production today (2.28.0 serves `CO`) | Requires reverting the rename in `6f34b62` |
| **B. Standardize on `TUTORIAL`** as the template's project key | More semantically clear ("tutorial" vs the platform name `CO`) | Requires updating 4+ tests + any frontend code referencing `CO`, plus any production data that already has `CO` rows |

**Recommendation: A (`CO`)** — production has `CO` data, prod is 2 versions behind main, and reverting the rename is one localized change vs touching tests + frontend + migration data. Save `TUTORIAL` as a `name:` display field if needed.

### Every-universe default project

Add a `seed_default_project(universe_key, project_key, project_name)` helper called at:

1. Template universe creation (current path, but with `CO` not `TUTORIAL`)
2. Anonymous-clone creation (currently works — keep as reference impl)
3. **Authenticated user's universe creation** (the missing path — yuri's private universe should hit this)
4. **Sister-universe ingestion** (when artelonga/yggdrasil/rfq/qb sync in, they need a project to host their entries)

The helper is idempotent: if a project with that key already exists in the universe, no-op.
