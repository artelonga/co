## As

A developer who wants to spin up a new universe from a local repo without manually configuring storage, projects, or seed paths

## I Need

A single command (`co launch`) that, run inside any directory, provisions a universe in localhost CO populated from that directory's content — same UX shape as `fly launch --now`.

## So That

I can go from `git clone` to "this repo's content is visible in my localhost CO" in two commands.

## Reference UX

```bash
git clone https://github.com/me/myproject.git
cd myproject
co launch --now
# → "Universe 'myproject' provisioned with 87 entries (3 pages, 84 tasks)"
# → "Serving on http://localhost:54321/myproject"
# → browser opens
```

## Scope

### New command `co launch`

| Flag | Default | Behavior |
|---|---|---|
| `--key <slug>` | derived from dir basename, lowercased + sanitized | universe key |
| `--name <s>` | dir basename | display name |
| `--public` | false | mark `public-subscribable` (otherwise `private`) |
| `--now` | false | also run `co serve --open` after provisioning |
| `--data-dir <p>` | platform default (same as `co serve`) | where the universe lives |

### What it does

1. **Resolve repo root**: walk up from CWD looking for `.git/` (or use CWD if no git). Use that path as the source for content seeding.
2. **Derive universe key**: lowercase + sanitize basename (`MyProject` → `myproject`, `rfq-gateway` → `rfq-gateway`).
3. **Open or initialize storage** at `--data-dir`.
4. **Create universe row** if missing, with `visibility` from `--public`.
5. **Seed content** by invoking the existing `seed_universe_from_local_repo` (`docs/`, `content/`) and `seed_universe_work_tasks_from_local` (`work/<space>/{PREFIX}-N.md`) — both already idempotent.
6. **Print summary**: `Universe '<key>' provisioned: <N pages>, <M tasks> across <K projects>`.
7. **`--now`**: call into `commands::serve::run()` with the resolved data-dir + default port + `open: true`. Browser lands on `/<key>` so the user sees their universe immediately.

### Implementation

New file: `co-cli/src/commands/launch.rs`. Mirrors the structure of `commands/serve.rs`. Reuses `co_web::config::WebConfig` to construct the storage; bypasses the HTTP server entirely (calls `Storage::new` directly and runs the two seed functions in-process).

Wire `Launch { ... }` into `co-cli/src/main.rs` enum + match arm.

### Acceptance

- [ ] `co launch` in a clean dir creates a universe with the dir's name as key
- [ ] `co launch --key foo` overrides the derived key
- [ ] `co launch --public` makes the universe `public-subscribable`
- [ ] `co launch --now` opens browser on `http://localhost:<port>/<key>`
- [ ] Re-running `co launch` in the same dir is idempotent (upsert, not duplicate)
- [ ] Output prints clear summary: N pages + M tasks ingested
- [ ] `co launch --help` example block matches the reference UX above

### Not in scope

- Pushing the universe to a deployed CO server (separate spec — would be `co deploy`)
- File-watcher live sync after launch (CO-319 already re-seeds on `co serve` restart)
- OAuth / cross-deployment auth (separate spec)
- Reading a `co.yaml` config file in the repo (future enhancement; CLI flags cover MVP)

## Blast radius

- 1 new file `co-cli/src/commands/launch.rs` (~100 lines)
- 1 enum variant + 1 match arm in `co-cli/src/main.rs`
- 0 backend changes
- 0 SPA changes
- No new dependencies

## Why now

Following CO-310 → CO-320 the localhost flow works; this command is the missing onramp. Without it, "set up a new universe from a repo" requires running `co serve`, finding the right config, and waiting for the boot-time sister-repo seeding to maybe pick it up. `co launch` makes it one command.
