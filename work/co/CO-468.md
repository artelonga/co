GIVEN the JSON WebSocket fan-out paths (`/api/v1/events` LiveTimeline and chat
rooms) re-serialized the *same* event inside each per-connection loop — N
identical `serde_json::to_string` calls for N connected clients — wasting CPU
linearly with connection count on the hottest streams,
WHEN we serialize each event once at the single fan-out point and share the
result (`Arc<str>`) across all subscribers, keeping the per-client visibility
filter,
THEN every client receives byte-for-byte the same payload with one serialization
per broadcast, matching the binary paths' existing design.

## Acceptance

- LiveTimeline channel carries a pre-serialized frame (`TimelineFrame { event, json }`);
  the event is serialized once in `TimelineForwarder`, not per socket
- The `/api/v1/events` handler reuses the shared JSON and still applies the
  per-client `can_see` visibility filter
- Chat room channel carries pre-serialized `Arc<str>`; all publish sites go
  through a `broadcast_event` helper that serializes once
- Binary paths (`sync/ws`, doc CRDT) and sala (`RoomMsg.json`) reviewed —
  already serialize once, unchanged
- Single-machine in-process fan-out assumption + horizontal scale-out risk
  documented in `events_ws.rs` and `sync_ws.rs`
- All existing eda + chat tests pass; new tests assert the shared JSON equals a
  single serialization

## Out of scope (deferred)

- Cross-machine event distribution for horizontal scale-out (Redis/NATS or
  per-universe sticky routing) — required only if `co-artelonga` runs ≥2 machines.
- `permessage-deflate` / binary encoding for `/api/v1/events` — axum does not
  expose WS compression cleanly today.
