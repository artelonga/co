GIVEN CO already has a chat/message system (rooms, messages, DMs, a serialize-once
broadcast bus — CO-193/198/204/468) AND the CO-471 contract reserved a `comments`
interface, but comments and chat were heading toward two parallel stores,
WHEN we recognize that **a message IS a comment in a thread** — comments and chat
messages are the same primitive — and generalize the existing chat room into a
**thread**,
THEN comments compose with messages under ONE unified model: a thread belongs to a
universe, may be **anchored** to an entry (that anchored thread IS the entry's
comments), may be **recursive** (a message spawns a child thread = nested replies),
and is scoped to **all members** / a **subset** / **self** (notes-to-self). Live
delivery reuses the chat `ChatEvent` broadcast, so a posted comment reaches
connected members exactly the way a chat message does.

## Design

No standalone `comments` table. `chat_rooms` is generalized into a thread via
migration **v092** (additive columns, legacy defaults preserve every existing
room/DM):

| Column | Meaning |
|--------|---------|
| `anchor_entry_path` | `NULL` = standalone (chat room / DM / notes); set = anchored to an entry (its comments) |
| `anchor_block_id` | `NULL` = whole-entry anchor; set = a specific block |
| `parent_thread_id` | `NULL` = top-level; set = recursive child (nested replies) |
| `scope` | `universe` (all members) · `subset` (explicit member list) · `self` (creator only) |

- Messages reuse `chat_messages` + `post_chat_message` (unchanged).
- Membership reuses `chat_room_members` (subset / self).
- Live delivery reuses `broadcast_event(&ChatBroadcast, &ChatEvent)` (CO-468
  serialize-once) — the comment POST publishes `ChatEvent::MessageCreated`.
- The `comments` interface (CO-471) is a **VIEW** over the anchored thread for an
  entry: `GET/POST /{slug}/comments?path=…` on the visibility-gated entry router.

### User paths

- **Comment on an entry** — `POST /{slug}/comments?path=…` auto-creates the
  entry's anchored thread on the first comment and appends a message; `GET`
  returns the threaded view (200 with an empty/null thread before any comment).
- **Recursive reply** — `POST …/comments` with `parent_id` spawns a child thread
  (nested replies); `GET` returns it under `replies`.
- **Subset-member thread / DM** — `Storage::create_scoped_thread("subset", …)`;
  only listed members may read/post (others 403 via `can_access_thread`).
- **Self-note** — `create_scoped_thread("self", …)`; private to the creator.
- **Live delivery** — every comment POST fans out a `ChatEvent` so connected
  members (chat WS subscribers on that thread) receive it live.

## Acceptance

- [x] `chat_rooms` generalized into a thread via migration **v092**
  (`anchor_entry_path` / `anchor_block_id` / `parent_thread_id` / `scope`),
  registered in `migrations/mod.rs`, `LATEST_VERSION` bumped to 92, guarded
  `if current_version < 92`, additive + idempotent — existing chat rooms keep working.
- [x] Comment-on-entry: `POST /{slug}/comments?path=…` auto-creates the anchored
  thread and appends a message; returns 201.
- [x] `GET /{slug}/comments?path=…` returns the threaded view (top-level comments
  + recursive child threads); empty/200 before the first comment.
- [x] Recursive reply: a `parent_id` in the POST body creates a recursive child
  thread (nested replies), returned under `replies` on GET.
- [x] Subset-member thread: only members read/post; a non-member is rejected (403)
  and a member is accepted.
- [x] Self-note thread: private to the creator (other universe members denied).
- [x] Live delivery via the event queue: posting a comment publishes a
  `ChatEvent` over the chat broadcast bus (asserted via a broadcast subscriber),
  reusing the CO-468 serialize-once `broadcast_event` path — no regression.
- [x] Permissions: anchored-thread access follows the universe visibility gate +
  membership (member-or-above may post); subset/self gated by `chat_room_members`.
- [x] Integration tests (`tower::ServiceExt::oneshot`, in-process) cover every
  user path above; storage unit tests cover anchored/idempotent, subset, self,
  and recursive-child semantics.
- [x] `docs/architecture/api-catalog.md` documents `GET/POST /{slug}/comments`;
  `openapi.yaml` regenerated with no drift (`npm run openapi:check`).
- [x] `cargo test` green; `cargo clippy --workspace -- -D warnings` clean; `cargo fmt`.

## Implemented now

A coherent first slice that fully unifies comments with the existing chat
primitive and ships all the listed user paths end-to-end with tests:

- v092 thread schema (anchored / recursive / scoped) on `chat_rooms`.
- Storage thread primitives (`storage/threads.rs`): anchored-thread get/create,
  scoped-thread create (subset/self), recursive reply thread, scope-aware
  `can_access_thread`.
- The `comments` interface (entry-anchored thread view) with live `ChatEvent`
  delivery, on the visibility-gated entry router.

## Deferred follow-ups

- **HTTP routes for standalone scoped threads** (create-subset-thread / create-self
  -thread / list-my-threads) — the storage primitives + tests exist, but the
  net-new REST surface for non-anchored threads is deferred to keep this PR
  focused on comments-as-anchored-threads; the existing chat-room + DM routes
  already cover the unanchored case in production.
- **Resolve / archive a thread** as a first-class comment action (today `archived_at`
  on the room still applies).
- **Migrating task comments** (`/projects/{key}/tasks/{id}/comments`, a separate
  legacy store) onto the unified thread model — tracked separately to avoid
  churning the kanban surface.
