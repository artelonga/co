## As

A user (developer, contributor, or curious visitor) who wants to understand what changed across multiple CO releases

## I Need

A **CHANGELOG viewer page** that:

1. Accepts an **arbitrary version range** (e.g., `from=2.11.0 to=2.22.0`) and shows every release entry in that range
2. Groups entries **by conventional-commit type** (`feat`, `fix`, `refactor`, `docs`, `chore`)
3. Within each type group, **sorts by PR size** (LOC diff = additions + deletions) descending — biggest refactor first, biggest feature first, etc.
4. Also offers a **time-ordered sequential view** of all versions (every version listed, newest-first by tag date)
5. **Type filter chips** — click `feat` to see only features, click `fix` for only fixes, etc.
6. Spans **major / minor / patch** transparently — 2.11 → 2.22 covers 11 minor bumps and dozens of patches

## So That

A user can answer questions like:

- *"What are the biggest features added between 2.13 and 2.21?"* → filter `feat`, sort by size, look at top 5
- *"What refactors landed in 2.18?"* → filter `refactor`, view 2.18.x range
- *"Show me everything fix/security between v2.12 and v2.20"* → filter `fix`, sort by size
- *"List every release ever"* → time-ordered sequential view, no filter

The CHANGELOG.md text is good for narrative reading but useless for these structured queries today.

## Context

### Data we already have

| Source | What it provides |
|---|---|
| `CHANGELOG.md` | Per-version block with title, theme, prose body |
| Git tags (`v2.X.Y`) | Tag → commit SHA mapping + tag date |
| Git commits between tags | Conventional-commit prefix (feat/fix/refactor/etc.) + PR # |
| GitHub PR API | additions + deletions per PR (size proxy for complexity) |
| `work/co/CO-N.md` | Spec metadata: labels, semver_bump, priority, blast_radius (when filled) |

### Why CO-260 vs extending CO-129

CO-129 renders the **op-log of one universe** as a Jujutsu DAG. CO-260 renders the **CHANGELOG.md + git history across versions** as a structured browseable artifact. Different data sources, different shape, different UX.

CO-260 can **link back** to CO-129's per-universe DAG view from each row (e.g., "show op-log for this version") but is fundamentally a different page.

## Scope

### Backend

- **`GET /api/v1/changelog`** — new endpoint, public, returns structured JSON
  - Query params: `from=<ver>&to=<ver>&type=<feat|fix|refactor|docs|chore>&sort=<size|date>`
  - Response:
    ```json
    {
      "range": { "from": "2.11.0", "to": "2.22.0" },
      "versions": [
        {
          "version": "2.21.0",
          "date": "2026-05-21",
          "tag_sha": "c58946e",
          "theme": "Wave B — REPL + DuckDB + inline CodeMirror + deploy.yaml schema",
          "entries": [
            {
              "ticket": "CO-244",
              "type": "feat",
              "title": "Python/R REPL + DuckDB attach",
              "pr": 71,
              "pr_size": 714,
              "additions": 712,
              "deletions": 2,
              "commit_sha": "86dd0ec",
              "author": "yuri",
              "spec_url": "/co/CO-244"
            },
            ...
          ]
        },
        ...
      ]
    }
    ```
- Parser reads CHANGELOG.md to extract per-version header + theme
- Walks `git tag -l 'v*'` + `git log v2.11.0..v2.22.0 --pretty='%H %s'`
- For each commit, extracts type from conventional prefix + PR # from `(#N)` suffix
- For each PR # found, queries `gh api repos/.../pulls/N` for additions/deletions (cached locally — populate at release-commit.sh time so the endpoint stays fast)

### Frontend

- **New route** `/changelog` (different from CO-129's `/<universe>/changelog` op-log DAG)
- Top bar: **range picker** (two version dropdowns), **type filter chips**, **sort selector** (size / date)
- Body, two display modes via toggle:
  - **Grouped (default)** — sections per type, entries sorted by `pr_size` desc within each group
  - **Sequential** — flat list of versions, each version showing its entries (any order)
- Each entry row: ticket pill (links to `/co/CO-N`), title, size bar (LOC visualization), date, PR link
- Type chips use semantic color (feat = green, fix = blue, refactor = purple, docs = gray, chore = gray)
- Mobile responsive — chips wrap, size bars become hidden, dates abbreviated

### Cached data store

- New table `changelog_cache(version TEXT, ticket TEXT, type TEXT, pr_number INT, pr_size INT, additions INT, deletions INT, commit_sha TEXT, indexed_at INT)`
- Populated by `scripts/release-commit.sh` after each tag — calls `gh api` for each PR # in the release range, persists rows
- Endpoint reads from cache (no live `gh api` calls)
- Provides a manual `co changelog reindex` CLI command for full rebuild

## Acceptance

- `GET /api/v1/changelog?from=2.11.0&to=2.22.0` returns valid JSON with all 12 minor versions and their entries
- `?type=feat` filters to feature commits only
- `?sort=size` orders entries within each version by PR size descending
- `?sort=date` orders versions newest-first (default)
- Frontend `/changelog` page renders both grouped + sequential views
- Type chip filter works client-side (instant; no re-fetch)
- Range picker auto-detects valid version range from existing tags
- Page loads in < 500ms on cached data
- New Playwright spec `co-web/e2e/changelog-viewer.spec.ts` verifies range + type filter + sort
- Documentation page links to `/changelog` from `/co` universe home

## Blast radius

- **Backend**: ~250 LOC for parser + endpoint + cache, new migration v15
- **Frontend**: ~400 LOC new `modules/views/changelog-viewer.js` + ~80 LOC CSS
- **Tooling**: ~30 LOC addition to `scripts/release-commit.sh` to populate cache on each release
- No breaking changes to existing CHANGELOG.md format

## Why now

This session has produced 7+ release tags (v2.13.4 → v2.22.0). Without a structured viewer:
- A new contributor can't quickly answer "what was Wave B?"
- A user upgrading from 2.13 can't see what they're getting
- The narrative CHANGELOG.md is good for one release but bad for comparative analysis

The CHANGELOG-PENDING regime (CO-258) plus the release-commit theme tagging already gives us all the data we need. CO-260 just exposes it.
