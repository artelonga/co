## As
An external service (a universe runtime, Yggdrasil, a CLI), QUERO depender de
`core` para obter o trait `Universo` e seus tipos de domínio — e poder fornecer
minha própria implementação — PARA reusar o modelo de universo sem arrastar o
servidor inteiro (axum/sqlite) nem dar fork no co-web.

## Contexto técnico (do audit 2026-06-12)
Hoje `trait Universo` + tipos (`Tarefa`, `Nota`, `Evento`, `Membro`, `Relato`,
`Conteudo`, `Entrada`) vivem em `co-web/src/content/universo.rs`. O trait é
limpo (9 métodos, sem dependência de storage), mas:
- está em co-web → consumidores externos precisam puxar todo o servidor;
- só existe `UniversoLocal`, instanciado direto nos handlers → trocar a impl
  exige editar o co-web (sem factory).

## Acceptance
- [ ] `Universo` trait + tipos de domínio movidos para `core` (`core/src/universo.rs`
      ou submódulo), **sem** nenhuma dependência axum/rusqlite/tokio. co-web
      re-exporta para compatibilidade (`pub use core::universo::*`).
- [ ] `UniversoLocal` (impl de filesystem) permanece em co-web (lê disco), agora
      implementando o trait vindo de `core`.
- [ ] Novo `trait UniversoFactory: Send + Sync { fn abrir(&self, key: &str,
      root: &Path) -> Result<Box<dyn Universo>, ...> }` injetado no AppState; os
      handlers obtêm o universo via factory, não por `UniversoLocal::abrir`
      hardcoded. A factory default é a de filesystem.
- [ ] Um teste prova a troca: um `UniversoFactory` fake/in-memory plugado no
      AppState faz os mesmos handlers servirem um universo não-filesystem, sem
      tocar nas rotas.
- [ ] Zero mudança de comportamento: contratos HTTP idênticos; `cargo test -p
      co-web -p core` verde; clippy limpo; sem drift de openapi/api-catalog.
- [ ] `core` continua sem vazar concerns de servidor (checagem: `grep -r axum
      core/src` vazio).

## Notas
Keystone do epic: desbloqueia consumo externo (universes/Yggdrasil) e prepara o
terreno para backends de universo alternativos (CO-433). Sem migração de dados.
