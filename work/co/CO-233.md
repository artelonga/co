## As

An editor or admin pushing content updates into a CO universe

## I Need

The latest changes (vault PUTs, board edits, content tree mutations) to appear on `co.artelonga.com.br` within seconds, not hours

## So That

Edits are trustworthy: I can publish a correction and refresh to verify, without wondering whether the prod cache or sync pipeline ate the change.

## Context

- **Surface:** "Latest changes not synced to web" (reported 2026-05-18 alongside CO-232).
- **Suspected causes (need to isolate):**
  1. Long-lived browser cache (per `feedback_cache_headers.md`, CSS/JS must use short cache without immutable; HTML/data routes should also have short Cache-Control). Has a recent deploy regressed any of these headers?
  2. Stale CDN / edge caching in front of the Fly machine.
  3. Periodic background worker (re-index, content-tree compute, derived view rebuild) not running or panicking under a `Mutex<Storage>` (per `feedback_no_panic_under_mutex.md` — was the 2026-05-12 incident fully resolved or is there a fresh poisoning?).
  4. Universe membership / visibility cache returning a stale snapshot.
- **First diagnostic:** `curl -I https://co.artelonga.com.br/api/v1/universes/artelonga/entries` → inspect `Cache-Control`, `Last-Modified`, `ETag`, `X-Cache` (if any). Compare DB row's `updated_at` vs the response timestamp.
- **Second diagnostic:** `flyctl logs -a co-artelonga --no-tail | grep -E "panic|poisoned|worker|reindex"` for the last 24h.

## Acceptance

- The diagnostic above identifies the actual stale layer (cache header / CDN / worker / DB).
- A regression test (or e2e probe) writes a known content edit and asserts the GET response reflects it within ≤2 seconds (browser + cold-curl).
- If the cause is a missing/wrong header, fix is a one-line `Cache-Control` change with the test.
- If the cause is a worker panic poisoning a Mutex, fix follows the `feedback_no_panic_under_mutex.md` pattern (worker must never panic under `Mutex<Storage>`).
- CHANGELOG.md notes the root cause + fix.

## Blast radius

Unknown until root cause is isolated. Likely small (header fix) to medium (worker restart logic + panic handling).
