## As

a user who has been told "your content is encrypted at rest" and wants that to be true

## I Need

every blob written by CO-146's asset endpoint to be wrapped in a ChaCha20-Poly1305 envelope using a per-universe data-encryption-key (DEK) that is itself wrapped under the owner's key-encryption-key (KEK), derived from password/OAuth via Argon2id

## To

deliver encryption-at-rest as more than a tagline — anyone with disk access sees only ciphertext

## Implementation

### Key hierarchy

```
Password / OAuth token
        │ Argon2id (id, t=3, m=64MB, p=1) + per-user salt
        ▼
    Owner KEK (256-bit)
        │ ChaCha20-Poly1305 wrap
        ▼
  Per-universe DEK (256-bit, generated on universe create)
        │ ChaCha20-Poly1305 + per-blob nonce + AAD = universe_key||sha256
        ▼
     Blob ciphertext
```

### Storage additions

```
data/universes/<aa>/<bb>/<key>/
  keys/
    universe.kek.enc    (DEK wrapped under owner KEK; binary file)
    nonce               (nonce used to wrap the DEK)
```

```sql
-- per-universe data.db
ALTER TABLE assets ADD COLUMN nonce       BLOB;
ALTER TABLE assets ADD COLUMN cipher_size INTEGER;
ALTER TABLE assets ADD COLUMN encrypted   INTEGER NOT NULL DEFAULT 0;
```

`encrypted=0` rows are Phase 1 plaintext blobs (legacy). `encrypted=1` are ChaCha20-Poly1305 ciphertext.

### Migration

For existing Phase 1 plaintext blobs:
- Background job rewrites each plaintext blob to ciphertext + populates `nonce`, `cipher_size`.
- Atomic per-blob: write ciphertext to temp, fsync, rename, update row, unlink plaintext.
- Resumable: skip rows where `encrypted=1`.

### KEK derivation

Owner KEK lives in process memory only — derived on login from password (Argon2id) and held for the session, dropped on logout. Server cannot decrypt without an active session. **This is the point.**

For background tasks (e.g. backup-cron) the owner runs them while logged in, or supplies the password via env var, or the task only operates on ciphertext (which works for backup — `tar` doesn't need to decrypt).

### Multi-recipient (deferred)

V1 is single-owner. Multi-collaborator universes need a recipient list (each collaborator's pubkey), DEK wrapped once per recipient, and a key-rotation flow. That's CO-145's Phase-6+ work.

### Code shape

New module `co-web/src/crypto.rs`:
```rust
pub fn derive_kek(password: &str, salt: &[u8; 16]) -> [u8; 32] { ... } // Argon2id
pub fn wrap_dek(dek: &[u8; 32], kek: &[u8; 32]) -> (Vec<u8>, [u8; 12]) { ... }
pub fn unwrap_dek(wrapped: &[u8], nonce: &[u8; 12], kek: &[u8; 32]) -> Result<[u8; 32]> { ... }
pub fn encrypt_blob(plaintext: &[u8], dek: &[u8; 32], aad: &[u8]) -> (Vec<u8>, [u8; 12]) { ... }
pub fn decrypt_blob(ciphertext: &[u8], nonce: &[u8; 12], dek: &[u8; 32], aad: &[u8]) -> Result<Vec<u8>> { ... }
```

Existing CO-86 `co-format/encryption.rs` uses the same primitives — share the module if CO-86 ships first.

### CO-86 integration

Aligned with CO-86's `Encryption` message:
- Same algo: chacha20-poly1305
- Same wrap shape: `encrypted_key` + `nonce` + `key_recipient`
- Phase 3's `keys/universe.kek.enc` IS the `encrypted_key` for the universe-DEK recipient.

If CO-86 ships first, this ticket's `crypto.rs` becomes a thin wrapper around `core/src/co_format/encryption.rs`. Otherwise this ticket ships the primitives and CO-86 reuses them.

## Acceptance

- [ ] New universe creation generates a 256-bit DEK and wraps it under the owner's KEK
- [ ] `POST /assets` encrypts on write; bytes on disk are ciphertext (verify with `xxd | grep -c <plaintext-marker>` → 0)
- [ ] `GET /assets/{sha}` decrypts on read with active session; returns plaintext bytes to authorized caller
- [ ] Without an active session, server cannot decrypt (background job that tries to read fails cleanly with `ERR_NO_KEY`)
- [ ] Tampering any byte of the ciphertext or nonce fails Poly1305 verification
- [ ] AAD binding: ciphertext from universe A copied into universe B's blobs/ fails to decrypt (AAD mismatch)
- [ ] Migration job rewrites all `encrypted=0` rows to `encrypted=1` without data loss; resumable
- [ ] CHANGELOG entry; threat model documented at `docs/research/encrypted-indexable-assets.md`

## Out of scope

- HTTP range support (CO-149) — note: full-decrypt-then-slice is correct here
- Multi-recipient key sharing (future)
- Streaming-AEAD for files > 50 MB (future)
- Encryption of `entries.content` markdown body column (Phase 3.5; the column moves to `assets` rows when CO-86 ships)
