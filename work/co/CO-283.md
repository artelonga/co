## As

The operator (and any user) who wants to see, manipulate, and connect content across every universe they have access to — in a spatial, intuitive view

## I Need

A **whiteboard-style canvas** at `/graph` (or `/canvas`) that:

1. Renders content from every accessible universe as **draggable post-it cards**
2. Supports **interactive CRUD** — create new post-its by clicking empty canvas, edit by clicking a card, delete via context menu
3. Each post-it has **title + description + metadata** (creation date, status, source universe) — flexible shape that accommodates either tasks OR general entries (`pessoa`, `comunidade`, `evento`, `relato`, etc.)
4. **Wikilink syntax `[[entry-slug]]` and `[[universe/entry-slug]]`** in card descriptions renders as a visible link between cards on the canvas — Obsidian-style, cross-universe-aware
5. Runs natively in the **local `co serve` instance** (CO-282) so it's a true client-side rendering against the user's local data — fast, offline-capable

## So That

- The operator stops switching tabs between 5 universe boards to remember "what's connected to what"
- New content can be added directly from the spatial view without breaking flow ("write a quick post-it about this person while looking at the event card")
- The platform's content-graph nature (CO = Collective Consciousness, per branding memory) is **finally visible as a graph** — not just implied by the entry-relation table (CO-74)
- Cross-universe wikilinks promote the "everything is one graph" mental model — `[[yggdrasil/SHN-1]]` in a CO note pulls Shandara's spec onto the same canvas

### What "post-it" means concretely

A `Postit` is a SPA-side projection of an underlying `Entry`. Every post-it on the canvas is backed by exactly one entry in some universe. The canvas adds **per-user spatial state** (x, y position, color, optional collapsed state) without changing the entry's canonical shape.

| Post-it field | Backed by | Notes |
|---|---|---|
| `id` | `entry.id` | 1:1 with entry |
| `title` | `entry.title` or `entry.path` basename | |
| `description` | `entry.body` (first 200 chars + ellipsis) | Click expands full body |
| `status` | `entry.frontmatter.status` if present | Tasks have `todo`/`in_progress`/`done`/`blocked`; entries can be `draft`/`published`/`archived`; default `none` |
| `kind` | `entry.entry_type` | `task`, `user-story`, `pessoa`, `comunidade`, `evento`, `relato`, `nota`, etc. |
| `universe` | `entry.universe_key` | Source universe (cross-universe canvas shows multiple) |
| `created_at` / `updated_at` | entry metadata | |
| `color` | `canvas_state.color` per-user | Phase 2 (post-MVP) |
| `position` (x, y) | `canvas_state.position` per-user | Persisted per user via new `canvas_views` table |

The "flexible input + later categorization" the user mentioned maps to: at MVP, all post-its render with the same visual treatment. At Phase 2, the `kind` field drives color (e.g. `evento` = blue, `pessoa` = green, `task:in_progress` = yellow). At Phase 3, users can override color and add free-form links.

### Wikilink syntax — what we render

| Markdown in description | Renders as |
|---|---|
| `[[YG-64]]` | Link to entry `YG-64` in the **current canvas's primary universe** — visualized as a line from this post-it to that one |
| `[[yggdrasil/SHN-1]]` | Cross-universe link to `SHN-1` in `yggdrasil` — line plus a small universe-label glyph |
| `[[#tag]]` | Link to all post-its with that tag — visualized as a "tag chip" (defer rendering connection lines) |
| `[https://...]` | External link — small ↗ icon, no canvas line |

The link parser is identical to what's already in the markdown renderer (Obsidian-compat per CO-141 / Vault API CO-267). We're just **rendering** the parsed links visually.

### "Universe syntax"

The user mentioned "universe syntax". This codifies it:

- `[[entry-id]]` → same-universe link
- `[[universe-key/entry-id]]` → cross-universe link
- `[[..parent/entry-id]]` → up-tree (parent universe) link (per CO-277 recursive)
- `[[../sibling-universe/entry-id]]` → sibling-universe link
- `[[#tag]]` → tag link
- `[[date:2026-05-24]]` → reserved for date-anchored entries (deferred)

The parser lives once in `co-web/static/shared/wikilink.js` (or wherever the existing markdown parser is). The canvas + the entry view both consume it.

## Decision — MVP scope and three phases

### MVP (Phase 1) — read-only canvas with CRUD

Ships in 1-2 weeks:

1. New SPA route `/graph` (Portuguese: `/grafo`)
2. Fetches entries from all accessible universes (current user's subscribed list) via existing `GET /api/v1/universes/{slug}/entries`
3. Renders each entry as a post-it on an HTML5 Canvas (or SVG — see "Canvas vs SVG" decision below)
4. Initial layout: force-directed (using a small library like `d3-force` — ~50KB) for the first load, then positions persist per user
5. Drag-to-move: updates `canvas_views` table via `PATCH /api/v1/me/canvas/{view-id}`
6. **CRUD**: click empty canvas → modal to create new post-it (creates new entry in user's default universe per CO-279); click post-it → edit modal (title + description); right-click → context menu with delete
7. **Wikilink rendering**: parse all post-it descriptions, draw lines for `[[entry-id]]` references; tooltip shows source/target on hover
8. Pan + zoom (standard whiteboard interaction)
9. Keyboard shortcuts: `N` for new post-it, `Del` to delete selected, `Cmd+F` for search-and-jump
10. Mobile fallback: read-only view + tap-to-focus (no drag — phones aren't great for canvases)

### Phase 2 — categorization + colors (1 week, post-MVP)

- Color rules engine: post-its colored by `kind` and `status` per a user-editable mapping
- Filter sidebar: show only `evento`s, only `done` tasks, only this-week's entries, etc.
- Search bar with fuzzy matching
- Saved layouts: "Project planning view", "Quilombo content view", "All my universes overview"

### Phase 3 — free-form connections + collaboration (1-2 weeks)

- Click-and-drag from one post-it to another → creates a `[[target-id]]` link in the source's description
- Multi-user real-time editing via existing CRDT layer (CO-272 + sync_ws)
- Cursor presence (see other users' cursors on the canvas, like Figma)
- Comments on post-its (anchored, threaded)

## Canvas vs SVG vs DOM — the rendering call

| Option | Pros | Cons | Recommendation |
|---|---|---|---|
| **HTML5 Canvas** (e.g. via `konva.js` or hand-rolled) | Best perf at 1000+ post-its | More work to make accessible, harder text editing | Phase 1 if we expect many post-its |
| **SVG** | Better accessibility, easier styling, clickable nodes natively | Slower past ~500 nodes | Phase 1 if we expect &lt; 500 post-its initially |
| **DOM (absolute-positioned divs)** | Easiest to build, native text editing, accessible by default | Worst perf at scale (500+ slows down) | Phase 1 if we want the fastest path to MVP |

**Recommendation: start with DOM (Phase 1)** — fastest MVP, easiest interactive editing of post-it titles/descriptions (input fields work natively), accessibility comes free. Migrate to SVG or Canvas only if perf becomes a bottleneck (likely past 1000 post-its, which the average user won't hit for months).

Use a small library for pan/zoom: `panzoom` (~2KB) or hand-roll the transform math (~80 LOC).

User's exact words (2026-05-24):
*"we want a centralized graph view across all universes ... mvp includes ability to crud interactively on a white board like application (similar to miro / draw.io) but user can add post its of content, post its have title and description and can be tasks or universe entries (eg pessoas, comunidades, eventos etc) ... for now the graph view will only display in-line links like obsidian, with universe syntax"*

This is the natural next step after Wave J/K shipped:
- CO-272 made entries the platform's content unit
- CO-264 made universes recursive
- CO-267 made entries syncable across universes
