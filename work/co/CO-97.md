GIVEN Co's `quilombo_telemetria.rs::telemetry_middleware` issues a `visitante_id` cookie scoped to the bare host with `HttpOnly`, AND the marketing site (`assets/analytics.js`) sets `al_vid` scoped to the apex `.artelonga.com.br` with JS-readable visibility, AND the same physical visitor traversing both surfaces ends up with two distinct visitor tokens,
WHEN we converge on a single canonical visitor token across both surfaces (with a documented security trade-off if loosening `HttpOnly`),
THEN attribution funnels (marketing landing → Co signup → in-app behaviour) stitch correctly without a server-side join, and analytics queries can filter by `site=artelonga|co` against a unified token.

## Context

- **Co cookie**: `visitante_id`, set by `quilombo_telemetria.rs::telemetry_middleware`. Bare host (`co.artelonga.com.br`). `HttpOnly`. Server-side only.
- **Marketing cookie**: `al_vid`. Apex (`.artelonga.com.br`). JS-readable.
- Both are random tokens with no auth role — they identify a visitor for analytics only.
- After the 2026-04-29 work that pointed marketing's `ENDPOINT` at `https://co.artelonga.com.br/api/v1/telemetry/events`, requests now hit Co's middleware carrying both cookies. Today the middleware ignores `al_vid` and either reads or generates `visitante_id`, so the funnel still splits.

## Options

### Option A — Co adopts `al_vid`

- Read `al_vid` first in `telemetry_middleware`. If present, use it as the visitor token.
- Fall back to existing `visitante_id` (compat window for visitors who hit Co before marketing).
- Emit `al_vid` cookie scoped to apex with `SameSite=Lax`, `Secure`, **drop `HttpOnly`** so the marketing site's JS can keep reading and writing it.
- Pro: marketing site already has the cookie at the right scope.
- Con: loosening `HttpOnly` exposes the token to client-side JS (XSS / cross-site script).

### Option B — Marketing adopts `visitante_id`

- Marketing site reads `visitante_id` from `document.cookie` if present, falls back to `al_vid`.
- Requires Co to scope `visitante_id` at apex (`.artelonga.com.br`) and drop `HttpOnly` so JS can read it.
- Same security trade-off as Option A.

### Option C — Server-side stitch (no security trade-off)

- Keep both cookies as-is.
- When Co receives a request whose `Referer` is on the marketing site **and** there's an `al_vid` cookie, store an entry in a `visitor_alias(canonical_id, alternate_id, first_seen, last_seen)` table.
- Telemetry queries do a `UNION` through `visitor_alias` to merge both tokens.
- Pro: no `HttpOnly` loosening, no client-side exposure.
- Con: complex; lossy when `Referer` is missing or stripped; requires schema + migration; query performance hit.

## Security trade-off (A and B)

Loosening `HttpOnly`:
- XSS on either subdomain can read the token.
- Cross-site scripts loaded by either surface can read it.

Mitigations / why this is probably acceptable:
- Visitor token is **never** an authentication credential. Its only use is analytics attribution.
- Worst case of theft: an attacker can fake page-views or skew session attribution. **No account takeover risk.**
- Token rotates on a schedule (e.g., daily salt rotation in `ip_hash`, similar treatment for visitor token).
- CSP tightened on both subdomains to limit XSS surface.

## Recommendation

**Option A** with documented trade-off. Confirms what marketing already does, adds Co reading. Server-side stitch (C) is correct but the implementation cost outweighs the benefit for the privacy posture we already have.

- [ ] Marketing site cookie scoped at apex

- [ ] No regression in existing telemetry queries (visitor count not double-counted during compat window)
- [ ] CSP review on both subdomains; document any tightening

## Out of scope

- Stitching server-side with `visitor_alias` table (Option C) — not pursued unless A and B are both rejected.
- Cross-device visitor stitching (logged-in user_id is the right primitive for that, separate concern).
- IP-based fingerprint correlation (no — privacy boundary).
