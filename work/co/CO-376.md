## As
The platform operator avoiding data-loss from bad migrations

## I Need
Every PR that adds a migration to run that migration against a snapshot of staging's database, with smoke queries verifying the migration didn't break the data shape — before the PR is mergeable.

## So That
- Wave 4 has heavy schema changes (CO-352 workspace state, CO-366 billing, CO-353 WS rooms). Each is a data-loss risk.
- The CO-44 / CO-279 / CO-330 pattern of "migration drift heals on next boot" is fragile — a bad migration can corrupt entries silently.
- Catches the next CO-1.22.4 incident (per memory `feedback_migration_column_reads`) before it hits prod.

## Design

### Trigger

GitHub Action triggers on PR if `git diff` includes changes to:
- `co-web/src/storage/migrations.rs`
- `co-web/src/storage/migrations/*.sql`

### Flow

```
1. SSH into co-artelonga-staging
2. Snapshot meta.db + all universes/*/data.db → /data/snapshots/pr-<n>-<sha>/
   (uses CO-379's snapshot primitive: sqlite Backup::new)
3. Check out PR branch, build co-web binary
4. Run migrations against the snapshot (not the live DB)
5. Execute smoke queries:
   - SELECT COUNT(*) FROM entries WHERE universe_key = 'co' (should be ~1227)
   - SELECT * FROM universes LIMIT 5
   - SELECT * FROM users WHERE email = 'yuri@artelonga.com.br'
   - For each new column: SELECT <new_col> FROM <table> LIMIT 1
6. If all pass: post green check, allow merge
7. If any fail: post red check + the failing query, block merge
8. Discard the snapshot (don't pollute staging)
```

### What "smoke queries" means

Per-PR, the spec author can extend with custom smoke queries in `migrations/<vN>.smoke.sql` — read-only assertions against the post-migration shape.

Default smoke set (auto-run):
- All FK references resolve
- All NOT NULL columns are populated
- All UNIQUE constraints hold
- Row counts within ±5% of pre-migration

### Snapshot lifecycle

- Created at PR check trigger
- Retained 24h for debugging if check fails
- Auto-deleted after 24h

### Endpoint for human inspection

`GET /api/v1/admin/migrations/snapshots` (admin-only): list pending snapshots + status. Useful for the operator to see what migrations are in flight.

## Acceptance

- [ ] PR with migration changes triggers the validation workflow — **deferred** (gating Action)
- [x] Snapshot created from staging's live DB (no live data modified) — extracted-copy model; obtained via admin backup endpoint / nightly artifact
- [x] Migration runs against snapshot; success/failure detected (`migrate_check` bin)
- [x] Default smoke queries run + report results (wave tables/columns, yuri row, count drift)
- [ ] Custom smoke queries from `migrations/<vN>.smoke.sql` honored — **deferred**
- [x] PR check is red if migration fails; green if all queries pass — exit 1 on any failure, 0 if all pass
- [ ] 24h snapshot retention for failed runs — **deferred** (belongs with gating Action)
- [x] No live data on staging touched — operates on an extracted copy only
- [x] Doc `docs/migration-checklist.md` describes the workflow

**MVP delivered** 2026-06-09 (CI-sandbox + MVP scope, per decisions taken):
`co-web/src/bin/migrate_check.rs` + `docs/migration-checklist.md`. Validator mechanics
verified synthetically (migrations apply v0→v68; failures caught with exit 1). Real
staging-snapshot run is **pending** a snapshot source (admin token to trigger the backup
endpoint, or a nightly artifact). Deferred items (gating GitHub Action,
`/api/v1/admin/migrations/snapshots`, custom `.smoke.sql`, 24h retention) are a CO-376 follow-up.
