GIVEN composability must mean **any open-source tool becomes an optional CO add-on
without rewriting or recompiling the binary** — and CO's own native external-tool
adapter (NOT MCP) is the mechanism — a tool is wired by a **manifest** the operator
drops in, behind the canonical tool contract (CO-503), so adding a tool is a config
change, not a code change,
WHEN we define a generic external-tool adapter (a subprocess invoker and an HTTP
invoker) that satisfies the canonical contract and is fed by manifests **discovered
at boot from a single TRUSTED location only** (the `tools/` catalog or a `tools.d/`
drop-in dir), opt-in and **default OFF**,
THEN any external program or service declared by a manifest is callable from the
same tool-calling loop as the native Rust tools — zero binary change — within an
explicit trust/sandbox boundary that the operator controls.

## Acceptance

- [ ] **Generic subprocess invoker** behind the canonical contract — runs a declared
  command, passes `args` as JSON on stdin (or mapped flags), returns stdout as the
  tool `result`. One-shot `run(args) → result` shape (CO-503).
- [ ] **Generic HTTP invoker** behind the canonical contract — POSTs `args` to a
  declared `url`, returns the response body as the tool `result` (the shape CO-525
  targets for an external add-on).
- [ ] **Manifest schema** for declaring a tool without recompiling: `name`,
  `description`, `input_schema`, `tool_type` (deterministic | predictive), and the
  invoker binding (`command` for subprocess, `url` for HTTP).
- [ ] **Boot-time discovery from a TRUSTED location only** — scan the `tools/` catalog
  / `tools.d/` drop-in dir, load valid manifests into the registry (CO-503). Manifests
  outside the trusted location are ignored.
- [ ] **Opt-in, default OFF** — external tools are not registered/callable unless the
  operator enables them; the default binary exposes only native tools.
- [ ] **Trust/sandbox boundary documented and enforced** — what an external tool may
  read/write/reach, run with least privilege; the manifest declares no capabilities it
  is not granted. Self-host posture (`infra/SELF-HOST-SECURITY.md`) applies.
- [ ] **Map delivered-vs-remaining against the CO-503 PR** — the one-shot subprocess
  case (yt-summarizer reference adapter, registry, `tool_type`) is largely shipped by
  the CO-503 PR; explicitly mark which acceptance items that PR delivers vs which remain
  here (HTTP invoker, drop-in `tools.d/` discovery, opt-in gating, sandbox boundary).

## Notes
- This is **not MCP** (see `feedback_no_mcp.md`) — it is CO's native external-tool
  adapter, expressed through the canonical tool contract (CO-503). The manifest is the
  composability seam: OSS in, recompile out.
- Builds directly on CO-503 (one canonical contract, `tool_type`, registry, reference
  adapter). The one-shot subprocess path is largely **DELIVERED** by the CO-503 PR; this
  task generalizes it into a discovery + trust engine for arbitrary add-ons.
- Term is **tool/ferramenta** and **agent/agente** — never "bot".
