# `public-subscribable` vs `requires_login`

Both let any authenticated user read & write. The difference is what an **anonymous** visitor sees:

| | Anonymous | Authenticated | Subscribe? |
|---|---|---|---|
| `public-subscribable` | sees **metadata** (title, description, content_count) — can be discovered, listed in search, indexed | full read + write | yes (track updates without becoming a member) |
| `requires_login` | **HTTP 401 "Login required"** — sees nothing about the universe except that something exists at this slug | full read + write | no |
| `private` | **HTTP 404** — slug looks like it doesn't exist at all | only owner + members | no |

## Concrete examples

- **`time`** (`public-subscribable`): an anonymous visitor at `/time` sees "Time — earth, sky, and system events" with a subscribe button. They can't view the events themselves, but they know the universe is there. Once they sign up, all events become readable.
- **`yggdrasil`** (`requires_login`): an anonymous visitor at `/yggdrasil` gets bounced to the login page with no preview. Used for game/community spaces where even the existence is "members of the platform only", but you don't want to fragment by per-universe membership.
- **`rfq`** (`private`): an anonymous visitor at `/rfq` gets a 404 — looks identical to a slug that was never created. Used for personal universes where you don't want to leak even the existence.

## Implementation pointers (in case you want to verify)

- The bit that creates the anon/metadata/login-required split is in `co-web/src/storage.rs:3625-3672` (`check_universe_access` returning `MetadataOnly | LoginRequired | ReadOnly | Denied`).
- DB shape: two boolean columns map to the four states:
  - `is_public=1, requires_login=0` → `public-subscribable`
  - `is_public=0, requires_login=1` → `requires_login`
  - `is_public=0, requires_login=0` → `private`
  - `is_template=1` → `template` (special — anyone can clone)

## So when do you pick each?

- **`public-subscribable`** — content you want to share publicly *and* market/list for discovery.
- **`requires_login`** — content for the platform's authenticated users only, where existence is itself "behind the login wall" but you don't care about per-universe membership.
- **`private`** — content visible only to you (and explicitly invited members). Slug-existence hidden.

In your current setup `requires_login` is only used for `yggdrasil` (the game space). Most universes are `public-subscribable`. If you're not running gated community spaces beyond Yggdrasil, you could deprecate `requires_login` and collapse to just `public-subscribable | private` (+ `template`). Want me to do that?

## What CO doesn't replace yet (the actual gap)

**Branches** — divergent named states of a universe. Today your local `~/projects/co/work/co/` is *the* state; there's no `staging` vs `main` vs `feature/foo` separation per universe.

**Merge events** — explicit "promote this state into the canonical one" with a record. CRDT auto-merges on the data plane, but there's no human-facing "I reviewed this and accepted it" event.

**Version pins** — immutable named snapshots a subscriber can pin to (cf. git tags / npm versions). Subscribers today follow head-of-line; if they want "the universe as it was on 2026-05-01," there's no API for that.

**Cross-universe change requests** — fork → propose → merge back to source. Today you can duplicate, but the loop back is one-way (no "PR"-equivalent).

What ships in each phase:

**Phase 1 — Snapshots (≈3 days)**
- `POST /universes/:slug/snapshots` → walks all entries, hashes them, writes a `snapshot` entry (`{author, message, parent: <prev_snapshot_path>, entries: [{path, body_hash, frontmatter_hash}, ...]}`)

- `proposal` content type for cross-universe change requests (you fork → write → submit; source owner reviews + accepts)
- `merge` event records the acceptance, captures the snapshot range, the actor, the message

- Subscribers can pin to a `snapshot` ID instead of head-following

2. **Move the source of truth** — stop seeding `co` from baked-in `/app/seed-co/` and let auto-sync from `~/projects/co/work/co` handle it (the boot seed becomes redundant).
3. **Pick a different universe to dogfood** — version CO platform development inside `comunicacao` or a new `co-dev` universe instead.

Option 1 is the smallest fix; option 2 is the right long-term move (eliminates the divergence between baked seed and your local source); option 3 sidesteps but doesn't solve the underlying issue.
