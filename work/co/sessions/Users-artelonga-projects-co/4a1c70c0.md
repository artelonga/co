## Content / Form Separation — AS IS vs TO BE

### The problem being solved

The quilombo subsystem currently mixes two concerns in every layer:

**Content** = what the community produced (relatos, eventos, membros, missoes, paginas)  
**Form** = how it's presented (theme, layout, fonts, locale, i18n strings)

Right now these are tangled: some content lives in Markdown+frontmatter, some in SQLite, and the SvelteKit frontend is consuming the API directly without a clean contract.

---

### AS IS

```
quilomboaraucaria/ (filesystem)
  .universo.yaml          ← only: nome, descricao, tipo, locale
  relatos/*.md            ← frontmatter (titulo, data, tags, publicado, slug) + body
  paginas/*.md            ← frontmatter (titulo, slug) + body
  schema.yaml             ← content type definitions

co-web SQLite             ← quilombo_usuarios, quilombo_eventos, quilombo_missoes,
                             quilombo_comentarios, quilombo_mensagens, perfis, telemetria

co-web/src/quilombo_routes.rs  ← mixed: reads markdown for relatos/paginas,
                                  reads SQLite for eventos/missoes/membros
```

**Two content sources, no form layer:**
- Relatos and paginas → filesystem Markdown (parsed on demand, no index)
- Eventos, missões, membros, comentários → SQLite (dynamic, mutable)
- Form: **none** — the SvelteKit app hardcodes all presentation (palette, fonts, layout) in `app.css`
- The `.universo.yaml` has no presentation fields at all

**Split by accident, not design:**

| Type | Source | Indexed? | Editable via API? |
|------|--------|----------|-------------------|
| relatos | .md files | No (scan on each request) | No |
| paginas | .md files | No | No |
| eventos | SQLite | Yes | Yes (editor+) |
| missoes | SQLite | Yes | Yes (admin) |
| membros | SQLite | Yes | Via perfil endpoint |
| comentarios | SQLite | Yes | Yes (anon) |

---

### TO BE

The model CO-36 established for the board universe should extend to quilomboaraucaria:

```
quilomboaraucaria/ (filesystem — single source of truth)
  .universo.yaml          ← CONTENT identity: nome, descricao, locale
                             FORM config:     theme_preset, font_headline, font_body,
                                              layout, custom_tokens
  relatos/*.md            ← frontmatter + body  (unchanged)
  eventos/*.md            ← frontmatter + body  (replaces SQLite-only eventos)
  membros/*.md            ← frontmatter + body  (replaces SQLite-only membros)
  missoes/*.md            ← frontmatter + body  (replaces SQLite-only missoes)
  paginas/*.md            ← frontmatter + body  (unchanged)
  comentarios/*.md        ← optional (or keep in SQLite — they're ephemeral)

co-web SQLite (index only — disposable, rebuildable)
  entries table           ← path, entry_type, title, frontmatter_json, body, body_hash
  quilombo_comentarios    ← keep in SQLite (ephemeral, high-write, no .md needed)
  quilombo_mensagens      ← keep in SQLite (contact form submissions)
  quilombo_usuarios       ← keep in SQLite (auth-critical, not content)
  quilombo_participacoes  ← keep in SQLite (relational join table)
```

**Clean separation:**

| Layer | What it holds | How accessed |
|-------|---------------|--------------|
| **Content** | `.md` files — relatos, eventos, membros, missoes, paginas | `GET /api/v1/universes/quilomboaraucaria/entries?type=relato` |
| **Form** | `.universo.yaml` form fields → `UniverseFormConfig` | `GET /api/v1/universes/quilomboaraucaria/config` |
| **Dynamic** | comentarios, mensagens, participacoes, usuarios | Quilombo-specific SQLite endpoints |
| **CSS** | Generated at runtime from `UniverseFormConfig` | `GET /api/v1/universes/quilomboaraucaria/theme.css` |

---

### What this means for the SvelteKit frontend

**AS IS** (current quilomboaraucaria web/):
- `app.css` hardcodes all palette/font choices (614 lines, copied from quilombo-blog)
- `src/lib/api.ts` calls `/api/v1/quilombo/publicacoes`, `/api/v1/quilombo/eventos` etc.
- No awareness of form config — theme is baked into the build

**TO BE**:
```typescript
// On app init: fetch form config
const config = await api.getUniverseConfig('quilomboaraucaria')
// → { theme_preset: "scholarly", font_headline: "Newsreader", locale: "pt-BR" }

// Load dynamic CSS (same engine as the board)
const link = document.createElement('link')
link.href = `/api/v1/universes/quilomboaraucaria/theme.css`
document.head.appendChild(link)

// Fetch content via unified entries API
const relatos = await api.getEntries('quilomboaraucaria', { type: 'relato', published: true })
const eventos  = await api.getEntries('quilomboaraucaria', { type: 'evento' })
const membros  = await api.getEntries('quilomboaraucaria', { type: 'membro' })
```

Content types become **uniform** — the same `Entry` type serves all content, frontmatter fields differ per type:

```typescript
interface Entry {
  path: string
  entry_type: 'relato' | 'evento' | 'membro' | 'missao' | 'pagina'
  title: string | null
  frontmatter: Record<string, unknown>  // titulo, data, tags, publicado, slug…
  body: string                          // markdown
}
```

---

### The migration gap

Right now the block is that `quilombo_routes.rs` serves content from two places using quilombo-specific paths (`/api/v1/quilombo/publicacoes`). The SvelteKit app was built against that API.

The clean path forward:

1. **Migrate eventos/membros/missoes from SQLite-only → .md files + SQLite index** (same as CO-36 did for board tasks). Keep SQLite for comentarios, mensagens, usuarios, participacoes.

2. **Add form fields to `.universo.yaml`** of quilomboaraucaria — so the SvelteKit app can load the palette/font from config instead of hardcoding it.

3. **Update SvelteKit `api.ts`** to use the unified entries API (`/api/v1/universes/quilomboaraucaria/entries?type=relato`) instead of the quilombo-specific routes, while keeping the quilombo routes as an alias layer during transition.

4. **Let `app.css` shrink** — most palette/font rules move to `theme.css` generated by the engine, leaving only layout/structural CSS in the SvelteKit app.
