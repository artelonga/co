---

For open-source S3-compatible storage with Apache Iceberg compatibility, the main options are:

**MinIO** — the dominant choice. S3-compatible API, runs anywhere, actively maintains Iceberg table format support. It's what most self-hosted Lakehouse setups use.

**Garage** — lightweight, written in Rust, S3-compatible, designed for geo-distributed multi-node setups. Simpler than MinIO, but Iceberg support depends on the client (Spark/Trino/Pyiceberg) doing the Iceberg catalog work — Garage just stores the files.

**SeaweedFS** — S3-compatible, FUSE-mountable, higher throughput focus. Same story as Garage for Iceberg — it stores the `.avro`/`.parquet`/metadata files but doesn't speak Iceberg natively.

The tradeoff: Iceberg compatibility isn't really a storage property — it's a **catalog** property. Any S3-compatible store works as the backing storage. What you actually need alongside the object store is a catalog: **AWS Glue-compatible** (via REST Catalog), **Project Nessie**, or **Apache Polaris**. MinIO ships a demo Lakehouse stack with those.

If you're evaluating this for the CO project's backup/archival path, MinIO is the safest bet — it has the most Spark/Trino/Pyiceberg ecosystem integration tested against it. Want me to sketch what an Iceberg-over-MinIO setup would look like for CO's data?

## Iceberg + MinIO for CO

### What it enables

CO's SQLite data (entries, tasks, telemetry) exported as Iceberg tables into MinIO, queryable by DuckDB without running the server. Universe content becomes an open, time-travelable data format — readable by any analytics tool even without CO.

### Architecture

```
co-web (Fly.io)
  └── LiteFS/SQLite ──────────────────────────────────────┐
                                                           │ daily export job
                                                           ▼
                                                    MinIO / S3
                                                    ├── co-backups/       ← existing SQLite .db tarballs (CO-104)
                                                    └── co-lakehouse/     ← NEW: Iceberg tables
                                                        ├── universes/    (universe metadata, owner, visibility)
                                                        ├── entries/      (all .md entries, indexed by universe+path)
                                                        ├── tasks/        (board tasks + status history)
                                                        └── telemetry/    (CO-46 events, anonymised)

DuckDB (local, or on any machine with MinIO access)
  └── SELECT * FROM iceberg_scan('s3://co-lakehouse/entries/')
       WHERE universe_key = 'quilomboaraucaria'
         AND entry_type = 'evento'
         AND date >= '2026-01-01'
```

### Why MinIO specifically

The existing CO-104 backup pipeline points at AWS S3 (`artelonga-co-backups`). MinIO is a drop-in: same endpoint format (`s3://`), same `aws-sdk-s3` / `aws CLI` commands. Self-hosters who can't or won't use AWS just run MinIO in Docker and point the env vars at it — zero code change.

Or, even simpler to start: a Python/DuckDB script that reads SQLite and writes Iceberg:

```python
import duckdb

con = duckdb.connect()
# Read from SQLite
con.execute("ATTACH '/data/co.db' AS co (TYPE sqlite)")
# Write as Iceberg to MinIO (DuckDB has native Iceberg write support since v0.10)
con.execute("""
  COPY (SELECT * FROM co.entries) 
  TO 's3://co-lakehouse/entries/'
  (FORMAT parquet, PARTITION_BY (universe_key, entry_type))
""")
# Register as Iceberg table (DuckDB ICEBERG extension)
con.execute("""
  CREATE TABLE IF NOT EXISTS lakehouse.entries 
  USING iceberg 
  LOCATION 's3://co-lakehouse/entries/'
""")
```

The existing `iceberg.rs` generates manifests for universe content — it's already producing the Iceberg metadata format for `.co/` directories. The `.co/` manifest in each universe repo would stay as-is (it's the per-universe schema + file catalog). The MinIO Iceberg layer is the cross-universe aggregate view.
