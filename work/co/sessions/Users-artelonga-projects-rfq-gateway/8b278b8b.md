## Avellaneda-Stoikov for Prediction-Market RFQ — Research, Design, Plan

### What A-S gives us, and where it breaks for our market

A-S (2008) provides two closed-form pieces:

- **Reservation price** — inventory-skewed mid: `r = s − q·γ·σ²·(T−t)`
- **Optimal spread** — `δ* = γ·σ²·(T−t) + (2/γ)·ln(1 + γ/k)`

Parameters: `γ` (risk aversion), `σ` (mid vol), `k` (fill-rate decay), `T−t` (horizon), `q` (inventory), `s` (mid).

**Three structural mismatches with our context:**

1. **Unbounded diffusion.** A-S assumes `dS = σ·dW` on (−∞, ∞). Our price lives in [0, 1000] centavos with terminal pinning at {0, 1000}. Vanilla `σ²·(T−t)` overshoots near the boundaries and produces quotes outside the range.
2. **Symmetric two-sided quoting.** A-S's spread is round-trip P&L. In RFQ you only ever get hit on the side the counterparty chose — the spread term becomes a *markup over reservation* for the requested side, not a half-spread.
3. **No adverse selection.** `k` is a fill-rate, not a *conditional-on-informed* fill rate. A-S assumes order flow is noise. Prediction markets near catalysts are saturated with informed flow.

### Adapted model (the proposal)

**Layer cake — from the fair-value cache we just built, upward:**

```
quote = clamp(reservation + adverse_premium ± markup, 1, 999)

reservation   = fair_value.price_cents
              − sign(q)·γ·σ_eff²(p)·(T−t)                 ← Jacobi vol, bounded
σ_eff²(p)     = σ_0² · p·(1−p)                             ← Wright-Fisher / Restocchi 2019
adverse_premium = θ_vpin·VPIN_ext + θ_div·|p_poly−p_kalshi| + θ_cat·catalyst_proximity
markup        = (1/γ)·ln(1 + γ/k̂)                         ← one-sided, ln not 2·ln
sign selection: YES side adds markup, NO side adds markup on the 1000−p complement
```

**Why this shape:**

- `fair_value.price_cents` is the signal we already compute and cache. A-S sits on top.
- Jacobi volatility `σ_0²·p(1−p)` handles the bounded-payout problem (Restocchi-McGroarty-Gerding 2019 is the clean reference for prediction markets). Collapses inventory penalty near 0 and 1000 — correct behavior.
- `adverse_premium` is **where insider-trading protection lives**. Three independent observables, each rolling in memory.
- `k̂` is the fill-intensity estimate. MVP = constant from config; Phase N = learned from our own RFQ history.

### Insider / adverse-selection module — "prevent insider information"

Four signals, all in-memory, layered into `adverse_premium` or triggering kill-switches:

| Signal | Observable | Source | Action |
|--------|-----------|--------|--------|
| **VPIN** (Easley-López de Prado-O'Hara 2012) | rolling buy/sell volume imbalance on Polymarket (signed volume bucketed by fixed volume bars) | Polymarket CLOB feed | `θ_vpin·VPIN` added to spread; hard-reject at `VPIN > 0.8` |
| **Cross-venue divergence** | `|p_polymarket − p_kalshi|` moving > N centavos over short window | both feeds | `θ_div·divergence` added; pause if > 100c with Kalshi moving first |
| **Catalyst proximity** | time to known news window (CPI, FOMC, election, halving) | `CatalystCalendar` YAML per ticker | `θ_cat·exp(−(T−t_catalyst)/τ)` → blows up spread minutes before catalyst |
| **Counterparty fingerprint** | rolling post-fill adverse Polymarket drift per API key per ticker | our own fill log | per-counterparty multiplier `μ_c ∈ [1, 5]` on `adverse_premium` |

**Kill switches (reject with `LOW_CONFIDENCE`, reason `insider_signal:*`):**

- `VPIN > 0.85` + catalyst within 10 min
- Cross-venue divergence > 150c
- One-sided RFQ burst: > 3 requests same side same ticker in 30s from same counterparty near catalyst
- Counterparty adverse-drift EMA > threshold (they've been right too often)

# Recommended Rollout — Cold Start → Spread Capture

The intel stack is now rich enough to run multiple operating regimes off the same codebase. The right strategy is a **staged rollout** where each phase accumulates the data the next phase needs. Don't try to spread-capture on day one — you'll bleed to adverse selection because `k̂` and `σ₀` are wrong and you have no counterparty history.

---

## Phase 0 — First order (hours 1 to ~24)

**Goal:** prove the pipeline works end-to-end with real money on the line; accumulate observations; build zero P&L expectation.

**Config:**
```
RFQ_STRATEGY=avellaneda_stoikov
RFQ_TICKER_ALLOWLIST=AAPL-2026APR17-290,MSFT-2026APR17-420   # 2 supersets only
RFQ_AS_K_HAT=0.01                 # tiny → 100c+ markup, very defensive
RFQ_AS_MAX_INVENTORY=50           # hard cap: max 50 contracts exposure
RFQ_AS_SOFT_CAP_START=10          # γ escalates fast
RFQ_AS_VPIN_KILL_THRESHOLD=0.5    # trip early
RFQ_AS_DIVERGENCE_KILL_THRESHOLD_CENTS=100
RFQ_FAIR_VALUE_MIN_CONFIDENCE=0.45
RFQ_FAIR_VALUE_MAX_AGE_SECS=15    # stale = reject aggressively
```

**Economic rationale:** We don't know the real fill intensity `λ(δ) = A·exp(−k̂·δ)`. Setting `k̂=0.01` means the markup formula `(1/γ)·ln(1 + γ/k̂)` ≈ `(1/γ)·ln(γ/k̂)` returns a huge number — we quote wide. Partners either pay or walk away. Either outcome is data.

**What to monitor (every 30 minutes):**
- `GET /admin/intel/cache` — are fair values landing from Polymarket?
- `GET /admin/intel/signals` — VPIN / divergence realistic? Any kill switch firing?
- Fly logs for `"as quote computed"` events — breakdown field shows reservation, markup, adverse_premium per quote

**Advance criteria to Phase 1:**
- [ ] Seen ≥ 10 accepted fills across the 2 supersets
- [ ] Zero pipeline errors (no `cache_miss`, no WS reconnect loops)
- [ ] Inventory never crossed the hard cap
- [ ] A-S kill switches didn't misfire on normal flow

---

## Phase 1 — Calibration (week 1-2)

**Goal:** replace guessed parameters with measured ones. Still not profit-seeking.

**Process:**
1. **Measure hit rate vs markup width.** Query Phase-0 fills, bucket by markup amount, fit `k̂` to `count(hit)/count(quoted)`. Typical outcome: real `k̂` is 5–20× your Phase-0 guess.
2. **Per-superset σ₀ calibration.** Pull Polymarket mid history for each mapped superset, compute realized volatility in centavos/√sec, feed into `RFQ_AS_SIGMA0`. NVDA will be 10× more volatile than AAPL.
3. **Use the backtest harness.** Replay actual Phase-0 RFQs against candidate `(γ, σ₀, k̂)` tuples via `backtest::sweep`, pick the combo that maximizes P&L on the historical set.

**Config drift to target (example):**
```
RFQ_AS_K_HAT=0.1              # roughly 10× looser from Phase 0
RFQ_AS_GAMMA=0.1              # default — adjust after backtest
RFQ_AS_SIGMA0=0.012           # per-superset-average from real vol
RFQ_AS_MAX_INVENTORY=200      # cautious lift
RFQ_AS_VPIN_KILL_THRESHOLD=0.7
```

**Advance criteria to Phase 2:**
- [ ] Measured `k̂` stable across 2 consecutive days
- [ ] Backtest shows positive gross-P&L on Phase-0 replay under chosen params
- [ ] Counterparty fingerprint has at least 20 measured fills per partner/superset (`GET /admin/intel/signals` shows non-zero drift EMAs)
- [ ] Confidence floor no longer rejecting good RFQs (single-source confidence 0.5 > floor 0.45)

---

## Phase 2 — Spread capture (month 1+)

**Goal:** systematic positive expectancy per fill, with risk kept bounded by the A-S inventory skew.

**What's now live:**
- **Inventory skew** does real work — if you're long 100 NVDA YES contracts, reservation drops by `100·γ·σ_eff²·(T−t)` centavos. You'll quote cheaper on YES (offload) and richer on NO (accumulate the other side). The math automatically mean-reverts your book.
- **Jacobi volatility** correctly collapses the skew near `p=0` and `p=1000` — you won't over-react to inventory on a market that's already resolving.
- **VPIN + divergence** charge a premium on the specific RFQs where informed flow is present. On quiet markets the premium is ~0; on catalyst days it widens spreads automatically.
- **Counterparty fingerprinting** rides on top — partners whose flow consistently shows post-fill adverse drift pay extra `θ_counterparty × fingerprint` on every quote.

**Config:**
```
RFQ_AS_K_HAT=<calibrated from Phase 1>
RFQ_AS_GAMMA=0.1
RFQ_AS_THETA_VPIN=20
RFQ_AS_THETA_DIVERGENCE=0.3
RFQ_AS_THETA_COUNTERPARTY=15
RFQ_AS_MAX_INVENTORY=1000
RFQ_TICKER_ALLOWLIST=<unset — all mapped supersets>
```

**This is the regime where you earn the spread.** Every accepted fill captures `markup + adverse_premium` centavos in expectation, with the inventory-skew term guarding tail risk.

**Monitoring:**
- Daily P&L attribution: `markup` component (pure spread capture) vs `adverse_premium` component (adverse-selection insurance) vs realized fill drift (leakage).
- `fingerprint > 0.3` on any partner for 2 days running → investigate that partner's flow.
- `divergence_cents > 100` for sustained periods → our mapping has drifted; re-verify the Polymarket token.

---

## Phase 3 — Aggressive (when confidence has been earned)

**Optional. Only worth doing after 3+ profitable months.**

**Additions:**
- **Per-strike interpolation** instead of the current nearest-strike approximation. Requires the schema change to represent interpolation in mapping.yaml + a pricing-core extension.
- **Tighter markup** via lower `k̂` — captures more spread but more sensitive to flow-intensity estimation error.
- **Catalyst calendar wired** via `StaticCatalog` → real events (CPI prints, FOMC, NVDA earnings). The `catalyst_proximity` term then contributes meaningfully to `adverse_premium`.
- **Larger position caps** as your P&L history justifies the tail-risk exposure.

---

## Cross-cutting

**Dashboarding from day 1.** Grafana or similar pulling from `/admin/intel/*`. You cannot operate this blind; the admin endpoints exist precisely so you don't have to.

**Parameter hygiene.** Every config change gets a git commit. The backtest harness replays historical fills against the new params before deploy. No knob-twiddling in prod without a recorded baseline.

**What breaks first.** In practice, the thing that breaks first is the mapping — Polymarket markets roll off (weekly series expire), new Hedix tickers appear. You need weekly mapping review built into ops, not just code review. The `TODO_VERIFY` entries (AMZN, TESLA) and the OUROO question are examples of what regular review catches.

Phase 0 = prove it works. Phase 1 = measure your parameters. Phase 2 = earn the spread with the inventory and adverse-selection machinery doing real work. Phase 3 = optimize. Don't skip phases — the A-S model is valid only when its inputs are measured, and your measurements only become real after Phase 0 runs on live flow for a non-trivial period.

The entire pipeline we built is designed around this arc. The per-strike schema, the fingerprinting, the VPIN aggregator — none of them matter in Phase 0, but they're pre-wired so the transition to Phase 2 is a config change, not a code deploy.

## Scaling the symbol list to all of Polymarket

**Current state (works for ~10 tokens, not 10k):**
- `MappingTable::mapped: HashMap<String, Mapping>` — single in-memory table, cloned into every task's `Arc<MappingTable>`.
- Polymarket WS feed: **one connection**, subscribes to every token in one `{assets_ids: [...]}` payload.
- REST feed: **sequential** poll loop, one HTTP call per token per poll.
- Matcher: single task consuming the whole bus.
- Cache: single `DashMap<String, CachedFairPrice>`.

At 10k+ tokens this breaks in three places: (a) one WS connection almost certainly caps out or lags, (b) REST poll becomes O(N) serial, (c) memory footprint of cloning strings everywhere.

---

## Recommendation: shard by token, not by superset

**Why shard by token, not by Hedix superset:** the user said "each unit can be probed independently" — the unit IS the Polymarket token. Hedix supersets are the read side (RFQ handler); Polymarket tokens are the write side (feed). They should scale independently.

### Three-layer design

**1. `SymbolRegistry`** (new) — replaces `MappingTable`'s reverse index for the feed side. Holds the **universe** of subscribed tokens with O(1) (source, token) → cache_keys lookup. Partitioned internally into N shards via consistent hashing of the token string. Memory: `DashMap<(SourceId, Arc<str>), SmallVec<[Arc<str>; 2]>>` — interned strings, SmallVec since 99% of shared tokens have ≤2 cache keys.

**2. `ShardedFeed` abstraction** (new) — a `ShardedPolymarketWs` spawns `N` independent WS tasks, each subscribing to `tokens.len() / N` tokens. Reconnects are per-shard; one bad shard doesn't take down the others. Config: `RFQ_POLYMARKET_WS_SHARDS=8` default. Same abstraction for REST: N parallel-poll workers using `futures::stream::FuturesUnordered`.

**3. Lazy subscription** (Phase X+1, when we really do cover all of Polymarket) — don't pre-subscribe to tokens with no Hedix mapping. Gamma API exposes a catalog of live markets; a daemon reconciles "what Polymarket has" vs "what Hedix has" vs "what we've subscribed to" on a slow cadence (e.g. hourly).

### Memory optimizations (quick wins)

| Current | Proposed | Saves |
|---|---|---|
| `String` for token / cache_key | `Arc<str>` interned in `SymbolRegistry` | ~40 bytes/instance × N references |
| `Vec<OrderbookLevel>` bids+asks | `SmallVec<[_; 5]>` | Heap alloc avoided for typical books |
| Clone `OrderbookSnapshot` per cache_key in matcher | `Arc<OrderbookSnapshot>` shared across fan-out | One alloc per snapshot |
| `HashMap<(SourceId, String), Vec<String>>` reverse index | `DashMap<(SourceId, Arc<str>), SmallVec<[Arc<str>; 2]>>` | Concurrent reads without mutex + interned |

### Compute optimizations

- **Bus: `tokio::broadcast` → per-subscriber `mpsc` with selective routing.** Current bus sends every event to every subscriber; at 10k events/sec that's wasteful. Route by event kind + source.
- **Matcher parallelism:** one matcher task per shard, each owning its own per-cache-key state. Today's single matcher becomes a bottleneck at high event rates.
- **Cache partitioning:** `DashMap` already shards; at 10k+ keys, tune `shard_count` explicitly.

### Horizontal scalability (across Fly machines)

Fly already runs multiple machines for the gateway. To split the intel workload:
- **Leader election** via Fly's built-in DNS + health checks (one machine owns intel, others proxy RFQs to it), OR
- **Redis-backed shared cache** (each machine runs its own feed shards, all write to Redis) — no leader election, eventual consistency. Matches the Kafka/Flink/Pinot design doc's evolution path.

## Current shortcomings for the two goals

### 1. Price-prediction testing — what's missing

| Gap | What it blocks |
|---|---|
| **No fair-value history** — cache is point-in-time, each update overwrites | Can't measure "our prediction at T₀ vs. realized outcome at Tₙ" |
| **No resolution capture** — we never record when a market settles YES/NO | No ground truth. Brier score / log-loss / calibration curves need the 0-or-1000 target. |
| **No replay path** — feeds assume live WS/REST; no way to say "ingest this NDJSON file of book events from last week" | Can't iterate on model changes deterministically; can't rerun the same data with different params |
| **No rejection log** — `FillObservationRing` captures only accepts; rejections silently vanish after tracing | Can't measure "how many RFQs would have filled if we loosened X" |

### 2. MM-performance testing — what's missing

| Gap | What it blocks |
|---|---|
| **Clock is `Utc::now()` everywhere** — staleness, catalyst, age all read real time | No virtual-time backtest; a 1-hour sim can't run in 10s |
| **Inventory is prod-tied** | Can't reset to q=0 for each scenario |
| **No synthetic RFQ stream** — we only get real Hedix traffic | Can't probe "what if Hedix sends 100 YES/min at 400c?" |
| **No PnL tracker** — we know our_price, not theoretical PnL `(mid − our_price) × signed_qty` | Can't compare two parameter sets' profitability without manual math |
| **Strategy state-change model lives only in the running process** — tests stub the trait, prod has 100% coverage, nothing in between | No way to play a recorded session forward with tweaks |

### 3. Data reality (the hard constraint)

- Only **12 active Hedix markets** right now, **4 mapped**. Per-ticker stats are noisy at this N.
- Polymarket WS gives us ~10 events/sec total across 10 tokens. Weeks of data to get statistical confidence.
- Hedix RFQ volume observed so far: **1** (the 2026-04-20 fan-out). We literally have no order-flow distribution to draw from.

## What paper-trading scaffolding needs to look like

**Four building blocks, each self-contained:**

**A. Observability expansion (unlocks measurement without simulation)**
- `FairValueHistoryRing` — mirror of fills-ring, one bounded buffer per superset, appended on every `FairValueUpdated` bus event
- `RejectionLogRing` — captures every quote rejection with reason + context
- Admin endpoints for both

**B. Virtual clock (unlocks everything time-dependent in backtest)**
- `trait Clock: Send + Sync { fn now(&self) -> DateTime<Utc> }`
- `SystemClock` for prod (wraps `Utc::now`), `VirtualClock` for sim (manually advanced)
- Thread through `AvellanedaStoikovStrategy`, matcher, monotonicity, staleness check

**C. Replay harness + synthetic RFQ generator (unlocks simulation)**
- NDJSON event format: `{ts, source, token, bids[], asks[]}` one per line
- `BacktestRuntime` — replays events into `IntelBus`, advances `VirtualClock`, captures everything
- `SyntheticRfqStream` — Poisson arrivals, side/qty distributions, informed-trader mode
- `PaperMode` — route goes through strategy normally; accepts record to in-memory ledger, no Hedix call

**D. Evaluation binaries**
- `cargo run --bin fv-eval --history H.ndjson --outcomes R.yaml` → Brier, log-loss, calibration, MAE at horizons
- `cargo run --bin mm-sim --events H.ndjson --rfq-config stream.yaml --strategy-config params.yaml` → PnL, inventory path, fill rate, rejection mix, drift distribution

## The ordering question

The **fastest path to actionable data** isn't simulation — it's observability. Two rings (FairValue history + rejections) take a day to ship, and immediately unlock:

- "Over the last 24h, what's the distribution of our fair-value changes per ticker?" (prediction stability)
- "What's our rejection mix? Is `cache_miss` dominating or is `confidence_X`?" (tuning signal)
- "For the 1-2 real fills we got, does the T+60s drift (we already capture) validate the fair-value prediction?"

Then once we have a week of that data, the simulation harness has real distributions to draw from instead of us guessing.

**Simulation first** gives you scenario testing (great for "what if") but its outputs are only as good as the parameters we feed in. With 0 real RFQs in our history, those parameters would be guesses.

## My recommendation

**Phase 1 (ship this week):** Observability rings — FV history + rejection log + endpoints. 
**Phase 2 (next week, after a week of live data):** Virtual clock + replay harness. 
**Phase 3:** Synthetic RFQ generator + `mm-sim` binary. 
**Phase 4:** FV evaluator + resolution feed.

The counter-argument for doing simulation first is speed-of-feedback for strategy research. If you want to iterate on A-S parameters in a closed loop today without waiting for real RFQ volume, we go Phase 3 before Phase 1.

**Which ordering do you want?** 
- **(a)** Phase 1 first (observability → real-data-driven calibration, takes ~1 day, then wait for traffic)
- **(b)** Phase 3 first (simulation → parameter search today, takes ~1 week, no waiting but uses guessed input distributions)
- **(c)** Parallel tracks (ship Phase 1 this week, start Phase 2/3 next week)
