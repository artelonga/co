## 1. Safety rails (build FIRST, before any Hedix call)

New module `tests/hedix/safety.rs` — nothing reaches Hedix except through it.

| Rail | Behavior | Default |
|------|----------|---------|
| Environment guard | Refuse `api.hedix.com.br`; only allow `*.staging.hedix.com.br` unless `--allow-prod` | staging only |
| Read/write mode | `HedixMode::ReadOnly` blocks `POST /api/mm/orders`, `DELETE /api/mm/orders/{id}` | ReadOnly |
| Rate limiter | Token bucket (`governor` crate), per-endpoint QPS cap | 2 req/s |
| Request budget | Hard ceiling per test run; abort on exceed | 200 GETs, 5 POSTs |
| Circuit breaker | Open on 3 consecutive 5xx or any 429; cooldown 30s | on |
| Timeouts | Per-request connect + total | 2s / 10s |
| Collateral ceiling | Sum of `price_cents × qty` across test run | 10 000 cents (R$100) |
| Quantity cap | Per order | 2 contracts |
| Idempotency prefix | `client_intent_id = "e2e-<run_id>-<seq>"` always unique | enforced |
| Dry-run | Logs the request it *would* have sent, returns a canned response | on by default |
| Kill switch | `HEDIX_E2E_KILL=1` env var aborts immediately on boot | check at start |

Wire these into a `HedixClient` wrapper (`tests/hedix/client.rs`) around `reqwest`. Every call goes through `client.get(...)` / `client.post(...)` which applies all rails. No direct `reqwest` in tests.

Gate the Hedix integration test file behind `#[ignore]` + a `HEDIX_E2E=1` env check so `cargo test` in CI never reaches Hedix.

## 3. Market selection

`GET /api/mm/markets` (paginated) through the safe client → raw snapshot → filtered shortlist.

**Filter composition** (`MarketFilter` trait, combine with `.and()`):

1. `StatusActive` — `status == "active"` (API already filters but double-check).
2. `ExpirationWindow { min_days: 7, max_days: 180 }` — avoid markets about to settle.
3. `HasLiquidity { min_depth_contracts: 50 }` — fetch orderbook, reject if thin.
4. `SpreadBelow { max_spread_cents: 100 }` — `best_ask - best_bid ≤ 10%`.
5. `PriceNearMid { tolerance_cents: 200 }` — last trade in `[300, 700]` to avoid extremes.
6. `CategoryAllowlist(["economics", "sports"])` — keep domains bounded.

**Output artifact** `markets_selected.md`:

```
| ticker | title | spread | last | expires | chosen |
|--------|-------|--------|------|---------|--------|
| ...    | ...   | 20c    | 470  | 34d     | yes    |
```

Raw JSON also dumped to `markets.json` for reproducibility — future runs can replay against a snapshot.

## 4. Quoting strategy

```rust
pub struct MarketView {
    pub market: Market,
    pub book: Orderbook,
    pub our_balance: Balance,
}

pub enum Decision {
    Accept { price_cents: i32, quantity: u64, ttl_seconds: u32 },
    Reject { code: &'static str, reason: String },
}

pub trait QuotingStrategy: Send + Sync {
    fn name(&self) -> &'static str;
    fn decide(&self, view: &MarketView, req: &CreateQuoteRequest) -> Decision;
}
```

**Initial implementations:**

| Strategy | Accepts when | Price | Rejects when |
|----------|-------------|-------|--------------|
| `Placeholder` | always | config constant (current behavior) | qty==0 |
| `Midpoint` | spread ≤ cap | `(best_bid + best_ask) / 2` | book empty, spread too wide |
| `Conservative` | spread ≤ 50c AND qty ≤ top-of-book size AND price ∈ [200,800] | midpoint − margin on our side | any of the above fail → `INSUFFICIENT_LIQUIDITY` |

The RFQ route (`src/routes/quote.rs`) currently hardcodes pricing; wiring a real strategy into production is a later step. For the e2e test, strategies live in the test crate and drive assertions: we call the gateway, then assert the response matches what the strategy *would* have decided given the current `MarketView`.

## 5. User interaction cycle

The canonical flow the pipeline must cover. Each row is an assertion target.

### Scenario A — **Accept**

| # | Actor | Action | Expected |
|---|-------|--------|----------|
| 1 | User | Places BUY YES, ticker T, qty 1 on Hedix UI | Hedix ingests order |
| 2 | Hedix server | `POST /api/v1/rfq/quote` → gateway: `{ticker:T, side:yes, quantity:1, auto_accept:true, client_intent_id:"e2e-<run>-A1"}` with `X-API-Key` | RFQ receives |
| 3 | RFQ gateway | Auth → validate → strategy.decide(view, req) → Accept | — |
| 4 | RFQ gateway | `200 OK` body: `{status:"accepted", price_cents, filled_quantity:1, fee_cents, accepted_at, quote_id}` | Assert shape + invariants (`price ∈ [1,999]`, `fee_cents == price*fee_bps/10000`) |
| 5 | Hedix server | Matches user order at `price_cents`, reserves collateral, updates user position | Verified by next step |
| 6 | Verifier (read-only poll) | `GET /api/mm/positions?market_ticker=T` on our MM account | New/updated position reflects delta of 1 contract at `price_cents`; `GET /api/mm/orders?market_ticker=T` shows a FILLED order |
| 7 | User output | "Ordem preenchida: 1 @ R$X.XX, taxa R$Y.YY" | Synthesized from RFQ response |

### Scenario B — **Reject**

Trigger reject from the RFQ gateway using a real market-driven condition (not just a malformed input).

| # | Actor | Action | Expected |
|---|-------|--------|----------|
| 1 | User | Places BUY YES, ticker T, qty = (top-of-book depth + 100) — exceeds liquidity | Hedix ingests |
| 2 | Hedix server | Forwards RFQ with auto_accept=true, `client_intent_id:"e2e-<run>-B1"` | — |
| 3 | RFQ gateway | strategy.decide → Reject (Conservative strategy sees qty > liquidity) | — |
| 4 | RFQ gateway | `422 UNPROCESSABLE_ENTITY` body: `{code:"INSUFFICIENT_LIQUIDITY", message}` | Assert code + status |
| 5 | Hedix server | Does NOT fill, returns error to user | — |
| 6 | Verifier | `GET /api/mm/orders?market_ticker=T` poll — no new order on our account for this `client_intent_id`; `GET /api/mm/positions` unchanged | Confirms no side-effect |
| 7 | User output | "Ordem recusada: liquidez insuficiente" | Synthesized |

**Key invariant across both:** a 4xx from RFQ must leave Hedix-side state for our MM account unchanged. The verifier step is what makes this real-e2e rather than just local assertions.

**Note on current code gap:** today's `routes/quote.rs` has no path to produce `INSUFFICIENT_LIQUIDITY` (it only rejects qty==0 and duplicates). Scenario B requires extending the route to call a `QuotingStrategy` — this is a prerequisite, flagged explicitly in §7 below.
