Two-tier makes sense: **Fly volume = optimized derivatives** (jpeg, h264 mp4, lqip), **object storage = originals** (cr3, dng, source mp4), pulled on demand.

For the cold tier, **Cloudflare R2** is the right pick — free egress (so admin/user retrieval of a 200MB raw doesn't cost anything), $0.015/GB·month storage, S3-compatible API. Tigris (Fly's native object storage) is the alternative if you want everything in one bill, but it charges egress. Backblaze B2 is cheapest for pure storage but charges to read back.

The flow that actually solves the "100MB Fly proxy" problem:

1. Client requests a **presigned PUT URL** from our backend (`POST /api/v1/quilombo/upload/iniciar` → returns `{upload_id, presigned_url, key}`).
2. Client uploads the original file **directly to R2** using that URL. No Fly proxy in the path → no size cap, native progress events, resumable via S3 multipart for big files.
3. Client posts `{upload_id}` to `/api/v1/quilombo/upload/finalizar`. Server fetches from R2, runs `ffmpeg`/`exiftool` to produce the derivatives (h264 1080p, jpeg preview from cr3/dng, lqip), stores those on the Fly volume + writes the `fotos`/`videos` row with `original_key` pointing to R2.
4. Public site serves only the Fly-side derivatives. Admin "download original" hits `GET /api/v1/quilombo/upload/:id/original` which returns a 5-min presigned R2 GET URL → client streams from R2 directly.

This sidesteps client-side ffmpeg.wasm (25MB payload, slow on phones) — server CPU does the transcoding once, R2 stores the original cheaply, browsers only ever see optimized output.

Three decisions before I build:

- **R2 vs Tigris** — R2 needs a Cloudflare account (free) and one set of API credentials in Fly secrets. Tigris is `fly storage create`. R2 is the better long-term call IMO; want me to go with R2?

**The pivot from "Added / Changed / Fixed" → CRUD-by-surface**

Standard Keep-a-Changelog gives you three buckets: *Added*, *Changed*, *Fixed*. They're informative for engineers but they make the reader scan an entire release to figure out "did anything change about how I post a relato today?". For a community-driven site where the audience is admins, members, and the occasional curious visitor — none of them developers — that's friction.

| Standard format | My take | Why |
|---|---|---|
| Added | (split across surfaces, tagged CREATE) | "What did I gain the ability to make?" |
| Changed | (split across surfaces, tagged UPDATE/READ) | Behavior changes belong with the thing they changed |
| Fixed | (rolled into surface) | Users don't think of bug fixes as a separate category — they just notice the broken thing got better |

**2. DNG uploads — currently blocked, by design.**

The endpoint allows `image/jpeg|png|webp` only, capped at **8 MB per file / 80 MB per batch / 50 files**. A DNG is typically 20–50 MB and sharp can't decode the raw bayer data, so even if you bypass the mime check, the variant pipeline crashes before producing thumbnails. Three paths to unblock, in order of effort:

| Path | What you get | What you give up |
|---|---|---|

## 1. URL grammar (the contract)

Keep URL params flat and human-readable. One JSON-blob `?q=` is tempting but kills shareability and makes `/mural/<id>` filter persistence opaque. The grammar:

```
─── what ────────────────────────────────────────────────────────────────
?evento=<slug>             single event; comma-list for multi (OR)
?relato=<slug>             single relato; comma-list for multi (OR)
?credito=<name>            case-insensitive; comma-list for multi (OR)
?tag=<a>,<b>,<c>           AND semantics by default — has all listed tags
?tag_any=<a>,<b>,<c>       OR — has any of the listed tags
?tipo=relato|evento|pagina single content type
?de=YYYY-MM-DD             date floor (inclusive)
?ate=YYYY-MM-DD            date ceiling (inclusive)
?destaque=1                only featured photos
?q=<text>                  substring across legenda + credito + parent titulo
?contem=<usuario>          [phase 2] photo includes this person
?sem=<query>               [phase 3] semantic search

─── how ─────────────────────────────────────────────────────────────────
?ordem=data_desc           default; data_asc / aleatorio / relevancia
?p=<n>                     page number (existing)
?foto=<arquivo>            lightbox deep-link (existing)
```

The semantics rules:
- Multiple **different** params combine with **AND**: `?evento=arraia&credito=Yuri` = arraia AND Yuri's photos.
- Multi-value **within one** param: documented per-param. `tag` defaults to AND because that's the rare strict case; `evento`/`relato`/`credito` default to OR because picking 2+ from a dropdown is naturally OR.
- **Empty values** drop the filter entirely. Removing a chip = removing the param.
- Order of params doesn't matter (server normalizes).

Why flat-params over `?q=<json>`:
- Shareable text-by-text in a chat
- Already how mural `filtro_json` is structured (just an object, persists fine in either shape)
- No base64 noise in the URL bar
- Simple enough that any contributor can add a new filter dimension by following the existing pattern

```ts
export function calcularFacetas(galeria: GaleriaFotoEnriquecida[], f: FiltroGaleria): Facetas;
export function ordenar(galeria: GaleriaFotoEnriquecida[], ordem: FiltroGaleria['ordem']): GaleriaFotoEnriquecida[];
```

**Internal shape — registry of dimensions** (the "extensible" lever):

```ts
interface DimensaoFiltro<T> {
  nome: string;
  parse: (p: URLSearchParams) => T | undefined;
  serializar: (v: T) => [string, string][];   // for URL round-trip
  aplicar: (galeria: G[], v: T) => G[];
  facetar?: (galeria: G[]) => { valor: T; n: number }[];
}

const DIMENSOES: DimensaoFiltro<unknown>[] = [
  evento, relato, credito, tags, tipo, dataRange, destaque, freeText,
  // contem, sem, ...   (added in later phases)
];
```

Adding a new dimension = pushing one entry to that array + writing a 30-line `DimensaoFiltro` for it. The new dimension automatically:
- gets parsed from URL
- contributes to `aplicarFiltro`
- (optionally) shows up in facet counts
- round-trips through `filtroParaUrl`

This is what "flexible extendable" actually means in code.

**Facet computation** uses the **leave-one-out** principle: facet counts for dimension X are computed from the result set with all OTHER filters applied but X removed. So when you filter by `evento=arraia`, the tag facets show counts within Arraia photos. That's the natural "what else can I narrow by?" semantics every faceted-search UI uses.

## 6. Phase 3 — semantic search ("animais", "pessoas dançando", "pôr-do-sol")

Embedding-based image-text search. Architecture:

**Schema (migration v016):**
```sql
ALTER TABLE fotos ADD COLUMN embedding BLOB;          -- 512 float32 = 2 KB per photo
ALTER TABLE fotos ADD COLUMN embedding_modelo TEXT;   -- 'siglip-base-patch16-224'
ALTER TABLE fotos ADD COLUMN embedding_em TEXT;
```
At ~2 KB per photo, 10k photos = 20 MB of embeddings — fine in SQLite. Beyond 100k start considering `sqlite-vec` extension for ANN.

**Model choice** — three contenders:

| Model | Size | Quality (image-text) | Latency on shared-cpu-1x |
|---|---|---|---|
| OpenAI CLIP-ViT-B/32 | 150 MB | Baseline | ~200 ms/image, ~50 ms/query |
| Google SigLIP-base | 200 MB | Notably better | ~250 ms/image, ~70 ms/query |
| SigLIP-base-multilingual | 250 MB | Same + handles Portuguese queries | same |

**SigLIP-base-multilingual** is the right pick for a Portuguese-language site. "fotos com animais" and "photos with animals" should both work.

**Inference path**:
- Server-side via `@huggingface/transformers` (transformers.js, runs in Node). One-shot model load on first use.
- Image embeddings computed at upload time, stored in `embedding` column.
- Text query: `?sem=animais` → encode "animais" once → cosine against all embeddings → top-K (default 60).

**Hybrid query**: combine semantic with hard filters. `?evento=arraia&sem=criancas` = "kids at the Arraia". The semantic stage runs **after** the hard filters narrow the set, so it's fast and naturally ranked.

```ts
{
  nome: 'sem',
  parse: (p) => p.get('sem') || undefined,
  aplicar: async (galeria, query) => {
    const queryVec = await embedText(query);
    return galeria
      .map(f => ({ f, score: cosine(decode(f.embedding), queryVec) }))
      .filter(x => x.score > 0.20)            // threshold tuned by experiment
      .sort((a, b) => b.score - a.score)
      .map(x => x.f);
  }
}
```

**Backfill**: existing photos need embeddings. A boot-time `embedFotosNaoIndexadas()` like `migrarFotosSeNecessario()` — runs in batches, ~250 ms each, eventually catches up. 190 photos take about a minute.

**Effort estimate**: 3–4 days. Dominated by getting transformers.js working in the Fly Alpine image (native deps for ONNX runtime can be tricky), tuning threshold, and writing the backfill.
