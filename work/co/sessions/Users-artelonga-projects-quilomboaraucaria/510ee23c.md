**2. CDN caching (free for static assets)**

**3. SQLite compaction (~10K articles)**
- WAL checkpointing (already on)
- `VACUUM` periodically

**4. Protobuf/binary markdown (~100K+ articles)**

```
Plain markdown frontmatter:    ~200-500 bytes/article
Protobuf metadata:             ~40-80 bytes/article  (4-6x smaller)
Binary markdown (AST):         ~60-70% of source     (marginal win)
```

- Columnar storage for analytics (visitas table gets big fast)

## `visitas_monthly` — Rolling Aggregation

### The problem

Every pageview writes a row to `visitas`. Each row is ~200-300 bytes with path, referrer, user_agent, ip_hash, status_code, duracao_ms, etc. The raw data is valuable for debugging and real-time dashboards, but after 90 days nobody queries individual rows — they query aggregates: "how many unique visitors hit `/encontros` in March?"

Current schema stores **everything forever**. At moderate traffic:

| Traffic | 1 month | 1 year | 3 years |
|---------|---------|--------|---------|
| 100/day | 3K rows, 0.6 MB | 36K, 7 MB | 109K, 22 MB |
| 1K/day | 30K, 6 MB | 365K, 73 MB | 1.1M, 220 MB |
| 5K/day | 150K, 30 MB | 1.8M, 365 MB | 5.5M, 1.1 GB |
| 10K/day (fleet) | 300K, 60 MB | 3.6M, 730 MB | 11M, 2.2 GB |

SQLite handles millions of rows fine, but query performance on the admin dashboard degrades once you're doing `GROUP BY path, date` over 1M+ rows. More importantly, the DB file size matters on a VPS with 20-40 GB disk.

### The solution: rollup + prune

Two-phase approach:

**Phase 1 — Aggregate** into `visitas_monthly` at the end of each month (or daily, into `visitas_diarias` for finer grain):

```sql
CREATE TABLE visitas_mensais (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ano INTEGER NOT NULL,
    mes INTEGER NOT NULL,
    path TEXT NOT NULL,
    secao TEXT,                    -- derived: 'home', 'encontros', 'blog', etc.
    visitantes_unicos INTEGER,     -- COUNT(DISTINCT visitante_id)
    pageviews INTEGER,             -- COUNT(*)
    usuarios_unicos INTEGER,       -- COUNT(DISTINCT usuario_id) WHERE NOT NULL
    ips_unicos INTEGER,            -- COUNT(DISTINCT ip_hash)
    avg_duracao_ms INTEGER,
    erros INTEGER,                 -- COUNT WHERE status_code >= 400
    referrers TEXT,                -- JSON: [{"origin": "google.com", "count": 42}, ...]
    user_agents TEXT,              -- JSON: {"iOS": 30, "Android": 25, "macOS": 40, ...}
    por_hora TEXT,                 -- JSON: [0,0,2,0,...,15,20,...] (24 entries)
    por_dia_semana TEXT,           -- JSON: [12,8,15,20,18,25,10] (dom-sab)
    criado_em TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(ano, mes, path)
);
```

**Phase 2 — Prune** raw rows older than the retention window:

```sql
DELETE FROM visitas
WHERE criado_em < datetime('now', '-90 days');
```

### Rollup job

A scheduled script (cron, or a SvelteKit server-side scheduled task) runs on the 1st of each month:

1. Aggregate the previous month's `visitas` into `visitas_mensais`
2. Verify row counts match (sanity check)
3. Delete raw rows older than 90 days
4. Run `PRAGMA wal_checkpoint(TRUNCATE)` to reclaim disk

The admin dashboard then queries:
- **Last 90 days**: raw `visitas` table (real-time, full detail)
- **Older than 90 days**: `visitas_mensais` (pre-aggregated, instant)

### Size comparison

At 5K pageviews/day over 3 years:

| Approach | Rows | Size |
|----------|------|------|
| Raw forever | 5.5M | ~1.1 GB |
| Raw 90 days + monthly rollup | 450K raw + 36 × ~50 rollup rows | ~95 MB |

**12x reduction.** And the dashboard is faster because monthly queries hit 36 rows instead of scanning millions.

### Tier 0 — Launch (now, quilomboaraucaria v1)
**Trigger**: going live

What you already have. No optimization needed. SQLite with WAL, filesystem uploads, Caddy with cache headers. This carries a single site to ~1K daily pageviews without thinking about it.

### Tier 1 — Image Pipeline (month 2-3, or when uploads exceed 1 GB)
**Trigger**: `du -sh data/uploads/` > 1 GB, or noticeable page load slowness

Images are 100-1000x larger than text. This is the single highest-impact optimization.

- [ ] **WebP conversion on upload** — sharp already in Dockerfile, add `.webp` output at upload time (profile photos, comment images)
- [ ] **Responsive thumbnails** — generate 3 sizes on upload: 150px (avatar), 400px (card), 800px (full). Serve appropriate size via `srcset`
- [ ] **EXIF stripping** — already done in your upload endpoint via sharp
- [ ] **Lazy loading** — `loading="lazy"` on all `<img>` below the fold
- [ ] **Max dimensions** — resize anything over 1920px wide on upload

Expected savings: **50-70% of upload storage**, plus significantly faster page loads.

---

### Tier 2 — Telemetry Rollup (month 6-12, or when visitas exceeds 500K rows)
**Trigger**: admin dashboard feels slow, or `SELECT COUNT(*) FROM visitas` > 500K

- [ ] **Create `visitas_mensais` table** (schema above)
- [ ] **Monthly rollup script** — `scripts/rollup.ts`, run via cron or GitHub Actions scheduled workflow
- [ ] **90-day raw retention** — prune older rows after rollup
- [ ] **Similarly for `atividades`** — rollup into `atividades_mensais` (action counts by entity type, user)
- [ ] **VACUUM after prune** — reclaim disk space
- [ ] **Add indexes** if not present: `CREATE INDEX idx_visitas_criado ON visitas(criado_em)` and `CREATE INDEX idx_visitas_path ON visitas(path, criado_em)`

Expected savings: **10-12x reduction** in visitas table size. Dashboard queries from seconds to milliseconds on historical data.

---

### Tier 3 — CDN + Object Storage (when running 5-10 template sites, or egress costs matter)
**Trigger**: deploying 3rd+ template site, or Fly.io/VPS bandwidth spikes

- [ ] **Cloudflare in front of Caddy** — free tier, zero-egress caching for all static assets and images
- [ ] **Cloudflare R2 for uploads** — S3-compatible, zero egress fees. Move `data/uploads/` to R2, serve via Cloudflare CDN
- [ ] **Signed upload URLs** — client uploads directly to R2, bypasses your server entirely
- [ ] **Per-site subdomains** — `quilomboaraucaria.org`, `outrositio.org` all behind one Cloudflare account

This decouples storage from compute. VPS only serves dynamic HTML; all images come from the edge.

---

### Tier 4 — Database Scaling (when running 10+ sites, or single DB > 2 GB)
**Trigger**: template fleet grows, or SQLite write contention becomes measurable

- [ ] **One SQLite DB per site** — if running multi-tenant on one VPS, each site gets its own `data/{site}.db`. Isolates data, simplifies backup, eliminates cross-site contention
- [ ] **Shared analytics DB** — fleet-wide telemetry in a separate SQLite (or Postgres) so you can compare sites
- [ ] **Read replicas via Litestream** — stream SQLite WAL to S3, read from replicas for analytics without impacting production writes
- [ ] **Consider Turso** — distributed SQLite-compatible DB, one URL per site, automatic replication. Natural evolution from local SQLite with zero schema changes

---

### Tier 5 — Wire Format + Serialization (when API payloads or inter-service communication matters)
**Trigger**: 100K+ articles across fleet, or building a mobile app / external API consumers

This is where protobuf and binary formats finally pay off — not for storage, but for **transfer**:

- [ ] **Protobuf for API responses** — event listings, member lists, comment feeds. 4-6x smaller than JSON on the wire, typed schemas
- [ ] **MessagePack as JSON alternative** — drop-in replacement, 20-30% smaller, faster parse. Lower lift than protobuf
- [ ] **Binary frontmatter index** — instead of parsing YAML frontmatter on every request, build a binary index at build time (like a search index). Lookup by slug/tag in O(1) instead of scanning files
- [ ] **Content-addressed storage** — hash-based filenames for uploads (deduplication across sites in the fleet)

---

### Tier 6 — Archival + Compliance (when data is measured in years, or legal requirements arise)
**Trigger**: 3+ years of operation, LGPD audit, or user deletion requests

- [ ] **Cold storage tier** — move rolled-up data older than 1 year to compressed SQLite archives (gzipped, stored on R2)
- [ ] **IP hash rotation** — periodically re-hash IP data with a new salt so old hashes can't be correlated
- [ ] **Right to deletion** — `visitantes` linked to `usuario_id` must be anonymizable. Script to null out user references while preserving aggregate counts
- [ ] **Backup verification** — automated restore-and-query test from backups monthly

---

| Tier | Trigger | Timeframe (estimate) |
|------|---------|---------------------|
| 0 — Launch | Now | Week 1 |
| 1 — Images | uploads > 1 GB | Month 2-3 |
| 2 — Telemetry rollup | visitas > 500K rows | Month 6-12 |
| 3 — CDN + object storage | 3+ sites or bandwidth | Month 12-18 |
