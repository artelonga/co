# Markdown vs SQLite — scalability review for Quilombo

Context-specific: this repo is already hybrid. `content-import.ts` parses markdown → `conteudo` table (zlib body + `versoes` history), `fotos` is a BLOB table with sha256 dedupe, and sync v1 (v006 migration) is content-addressed. The question is *what belongs where* as the community grows.

## Dimension-by-dimension

| Dimension | Markdown files | SQLite | Winner at scale |
|---|---|---|---|
| **Single-author edits** | Obsidian/VS Code/Git, offline, zero-infra | Requires app or SQL | **Markdown** |
| **Concurrent writes** | Merge conflicts on same file; Git required | Row-level locking, WAL mode handles 1 writer + many readers | **SQLite** for multi-user web editing; **markdown** if workflow is PR-based |
| **Cold reads (N items)** | `readdirSync` + parse each file: O(N) disk ops; ~1–5 ms each | Prepared statement + index: <1 ms for 10k rows | **SQLite** above ~200 items |
| **Filter/sort/join** | Scan all files every request (or cache) | Indexed queries, joins with comments/visitas/atividades | **SQLite** — huge gap |
| **Full-text search** | grep or build external index | FTS5 extension (already in sqlite build of better-sqlite3) | **SQLite** |
| **Version history** | Git = perfect + free + signed | `versoes` table works but duplicates Git for content already in a repo | **Markdown** (Git is unbeatable) |
| **Audit for dynamic data** (comments, visits, sessions) | Impossible in files | Purpose-built | **SQLite** — no contest |
| **Backups / disaster recovery** | `git push` everywhere | One volume snapshot (Fly 5-day retention) | **Markdown** — distributed by design |
| **Portability to co-web (Rust)** | `universo.rs` reads any content dir; `co validate` enforces schema.yaml | Would need schema mirroring | **Markdown** — aligns with stated architecture |
| **Editorial review** | Git PRs, diffs | Custom admin UI + audit log | **Markdown** for institutional content, **SQLite** for member UGC |

## Images specifically

This is where the choice matters most and is *not* simply "markdown wins".

**Current mix** (already sound):
- Markdown frontmatter declares `fotos[]` with `{arquivo, legenda, credito, destaque}` — metadata
- Actual bytes in `fotos` table (BLOB, sha256, deflated only if non-image)
- Served via `/api/fotos/[filename]` with metadata stripping on first access
- Sync v1 uses content-addressed blobs (sha256) with `foto_refs` pointing markdown → blob

**At scale, what matters for images**:

1. **Dedupe** — sha256 content-addressing (already implemented) means the same flyer reused across 13 "Reunião Geral" events costs one row. Git LFS or raw filesystem would duplicate. **SQLite + content-addressing wins.**
2. **EXIF/GPS/face stripping** — already done in the serving layer via sharp. Easier to enforce in one write path than across a markdown+fs+git workflow where a contributor can commit raw IMG_1234.jpg with GPS coords.
3. **Hot-path serving** — SQLite BLOB reads are memory-mapped and fast up to ~100 MB rows; for 2–5 MB photos it's fine. Past ~10 GB total, filesystem + CDN edges out SQLite, because Fly Postgres-style buffer pool isn't in play and WAL checkpoints on a large DB slow writes.
4. **Responsive variants** — neither format generates them. Needs a derivation cache (sharp → `{slug}-{w}.webp`) keyed by sha256. Works on top of either backing store.
5. **Thumbnail-heavy pages** (gallery, calendar flyers) — N photos × N requests. SQLite with `Cache-Control: public, max-age=31536000, immutable` on hashed URLs is fine; filesystem+CDN is slightly better but the difference doesn't show until 5-digit DAU.

**Scale ceiling for image BLOBs in SQLite**: practically ~5–20 GB on a Fly volume before backup/snapshot times become painful. Past that, cut photos over to object storage (S3/Tigris) keyed by sha256 — but keep the `fotos` table as the registry with `dados IS NULL AND url IS NOT NULL`.

## Recommendation for this project

**Keep hybrid, sharpen the boundary:**

- **Markdown = authored content** (relatos, eventos, jardim pages, membros, mission specs): source of truth lives in `quilomboaraucaria/`, edited in Obsidian, validated with `co validate`, versioned by Git. App reads it.
- **SQLite = dynamic + machine data**: sessions, comments, visits, atividades, sync ops, permissões — plus a *mirror* of markdown for fast queries and FTS (the current `conteudo` table is this).
- **Images = frontmatter metadata + content-addressed blobs**: keep `fotos[]` in markdown, keep bytes in `fotos` table with sha256 dedupe, add a URL-fallback column now so the migration to object storage later is a one-line switch, not a schema rewrite.

Net: the hybrid pattern is already correct for this scale. The migration to `quilomboaraucaria` doesn't change the backing-store split — it moves authored content from this repo's `content/` into the universo repo, while SQLite keeps its role as the dynamic-data + query-cache layer.
