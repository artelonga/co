## Gallery optimization plan — emergency

### Root causes of current slowness (baseline audit)

1. **Full-size originals are served to grid thumbnails.** No srcset, no thumbnails. Every tile = full-res photo.
2. **`sharp.metadata()` runs on every `/api/fotos/:filename` GET** (`src/routes/api/fotos/[filename]/+server.ts:9`). This blocks the Node event loop on each hit.
3. **`Cache-Control: max-age=86400`** on `/api/fotos` (1 day) vs. `immutable` on `/api/upload` (1 year). Stable content cached for only 24h.
4. **Blobs stored as SQLite `BLOB`s** (`fotos.dados`). `better-sqlite3` is synchronous → binary reads block the event loop. Cannot stream.
5. **No pagination:** `listarFotosGaleria()` returns the entire library on every `/galeria` hit.
6. **`listarFotosGaleria()` runs twice** per request (once for filtered set, once for filter-option aggregation).
7. **No blur/LQIP placeholder** → scroll shows blank rectangles until each image fully arrives.

---

### Phase 1 — Mural layout + pagination (Svelte, deterministic, no repeats)

**Route:** `/mural` (new) — keeps `/galeria` intact as a linear fallback until mural is validated on UAT.

**Server contract** (`+page.server.ts`): returns **only metadata** (slug, sha8, w, h, destaque, legenda, credito, lqip) — never binary, never full URLs.

**Selection algorithm — no repeats within session:**
- Compute `seed` = hash(filters + cookie `mural_session_id`). Persist cookie for 30 days.
- Produce deterministic permutation of the eligible photo list (seeded Fisher-Yates, server-side).
- Page N = slice `[N·K, (N+1)·K)` of that permutation. Guarantees:
  - No repeats within a mural
  - No repeats across pages *in the same session*
  - Stable deep-link: `/mural?p=3` always shows the same photos for the same seed
- "Novo mural" button rotates the cookie → fresh random ordering.

**Layout — PowerPoint-ish mural cells:**
- CSS Grid with fixed track count per breakpoint:
  - mobile (<640): 4 cols × 6 rows/page → **K≈8**
  - tablet (640-1024): 6 cols × 8 rows → **K≈12**
  - desktop (≥1024): 12 cols × 8 rows → **K≈18**
- Each photo gets a cell size deterministically picked (seeded by `sha8 + pageN`):
  - **Destaque** → 2× the "large" footprint (mobile: 4×4, tablet: 4×4, desktop: 6×6). **Minimum floor enforced.**
  - **Regular large** → ~30% chance (mobile 4×3, tablet 3×3, desktop 4×4)
  - **Regular medium** → ~50% (mobile 2×2, tablet 2×2, desktop 3×3)
  - **Regular small** → ~20% (mobile 2×2 floor, tablet 2×2 floor, desktop 2×2 floor) — the **minimum reasonable** floor you asked for.
- `grid-auto-flow: dense` fills gaps.
- Same seed → same layout (SSR hydration matches). Different `pageN` or new mural → different mosaic.

**Navigation:** ← → keys, swipe, prev/next buttons, `/mural?p=N` URL.

---

### Phase 2 — Image delivery optimizations (pick once, don't revisit)

**2a. Generate variants at upload (not per-request).**
- On upload (`/api/upload/[filename]` + `/admin/fotos/api/upload`): sharp produces four WebP sizes:
  - `xs` 240w (grid mobile small)
  - `sm` 480w (grid mobile large, tablet small)
  - `md` 960w (desktop destaque, tablet large)
  - `lg` 1600w (lightbox)
- Plus LQIP: 16×16 AVIF, inlined base64 (<200B) stored in `fotos.lqip` column.
- Orig kept for download/admin.

**2b. Move blobs out of SQLite.**
- SQLite `fotos` keeps metadata only: `sha256, mime, width, height, lqip, tamanho, criado_em`.
- Binaries on disk: `UPLOAD_DIR/blobs/{sha[:2]}/{sha}.orig.{ext}` + `UPLOAD_DIR/thumbs/{size}/{sha[:2]}/{sha}.webp`.
- One-time migration script exports existing `fotos.dados` → disk, then drops `dados` column.
- **Why:** better-sqlite3 is sync; BLOB reads block the event loop. Filesystem serving uses kernel `sendfile` via SvelteKit/Node stream → zero-copy.

**2c. New serving routes:**
- `GET /api/fotos/{size}/{sha}.webp` (and `/orig/{sha}.{ext}`)
- `Cache-Control: public, max-age=31536000, immutable`
- `ETag: "{sha}"` (handles 304s)
- Pure static-file serve; **no sharp on the read path.**

**2d. Markup uses `srcset` + native lazy:**
```html
<img
  src="/api/fotos/sm/{sha}.webp"
  srcset="/api/fotos/xs/{sha}.webp 240w, /api/fotos/sm/{sha}.webp 480w, /api/fotos/md/{sha}.webp 960w"
  sizes="(max-width: 640px) 50vw, (max-width: 1024px) 33vw, 25vw"
  loading="lazy" decoding="async" fetchpriority="low"
  width={w} height={h}
  style="background-image: url({lqip})"
/>
```
Destaques get `fetchpriority="high"`. `width`/`height` set → no CLS.

**2e. Prefetch next page:**
- On mural N render, inject `<link rel="prefetch" as="image" href="/api/fotos/sm/{sha}.webp">` for each photo of page N+1.
- Browser fetches at idle priority → page N+1 swap is instant.

**2f. Remove `stripMetadata` from request path.** Stripping happens at upload only (already mostly there for `/api/upload`). `/api/fotos/:filename` becomes a pure `stat + stream` handler.

## Linking proposal: relato ↔ evento

Your idea = the right one. Once a relato is written, the evento's URL becomes a stale duplicate. Redirecting consolidates intent.

**Proposed behavior — three states:**

| Linked relatos | What `/encontros/[slug]` does |
|---|---|
| **0** | Stays as today: evento detail page (flyer, date, local, descrição, comentários) |
| **1** | **Redirects to `/blog/[relato_slug]`** (302) — the relato becomes canonical. Evento data shown in the relato's "Encontro" sidebar. |
| **2+** | Stays as evento page but body becomes a **hub**: relato cards listed, flyer as header. (When two people write about the same event, the evento is the natural index.) |

**Admin override:** a `manter_pagina_evento: true` toggle on the evento (admin UI checkbox) skips the redirect even with one linked relato. Useful when the flyer itself is the artifact people will share (e.g. a recurring event series page).

**On the relato side** — a "Encontro" sidebar block with:
- Evento title, date, time, local
- Link back to evento (with `?evento=1` query string that bypasses the redirect, so people can still see the original page)

## Reliability model

**Not via markdown sync** (it was never designed to represent deletions + admin edits). Markdown is a **seed**, not a **source**.

**Reliability comes from three locked-in properties:**

1. **One canonical source per data type** — no ambiguity:

2. **Hash-aware import preserves admin edits** — `content-import.ts` skips any `conteudo` row whose `atualizado_em != criado_em` (admin touched it, repo no longer authoritative for that row)
3. **UAT state = prod state via volume refork, not markdown**

4. Destroys old UAT machine (keeps old volume until `--destroy-old`)

6. Runs `fly deploy --config fly.staging.toml`

### What happens during cutover

1. **Pre-flight snapshot** of prod volume (rollback safety, ~1 min)
2. **Update `quilomboaraucaria/fly.toml`** to target `quilombo-araucaria` (currently `quilombo-araucaria-dev`) + health path + mount source = `quilombo_data`

No — **prod volume is separate**, so migrations run fresh on prod this time); foto variant migration (130 fotos, ~2 min with keeper warming); import-videos (picks up sobre YouTube); video backfill
5. **Content-import runs** (first boot only pattern does NOT apply to quilomboaraucaria — its Dockerfile imports EVERY boot, but now with hash-aware skip)

### Risks

| Risk | Mitigation |
|---|---|
| Boot migration v007 fails on fotos.dados NOT NULL like it did on UAT | Already fixed — we use empty blob `x''` on insert, no NULL update |
| Session cookies break (usuarios table unchanged) | Schema matches; sessions continue |
| First foto request while migration runs → slow | First request serves via `localizarFoto` fallback with on-demand migration; subsequent fast |

| Legacy `/api/fotos/{filename}` URLs in emails/external | 301 redirect to `/md/` preserves them |
