## Ultrathink: sync, multi-user editing, and forward-compat with `co`

Pulling on this thread changes the framing. The right question isn't "how do we sync UAT→prod", it's "what data model survives the SvelteKit→`co`-Rust transition, supports real-time multi-user editing, and makes sync a free consequence rather than a feature we build and throw away."

### The core realization

All three problems — sync, multi-user editing, conflict resolution, and `co`-migration — collapse into one decision: **make state derivable from an append-only, causally-ordered operation log**, with **content-addressed binary assets**, layered under a CRDT. Get that right and:

- Sync is `exchange missing ops + replay` → free
- Version history is the op log itself → free
- Multi-user editing is CRDT merge on the op log → free
- Migration to `co` is porting the op-log reducer to Rust → a bounded refactor, not a rewrite
- Git-native storage (`quilomboaraucaria/` repo) is a projection of the op log

Current SvelteKit code mutates tables imperatively. That's the anti-pattern to retire.

### Foundations (non-negotiable design choices)

1. **Local-first philosophy** (Ink & Switch). Every node — prod, UAT, a laptop, a future peer — is fully functional offline. Sync is additive, never authoritative. No "the prod DB is canonical" — instead the **op log is canonical**; prod is just the node most people happen to read from.

2. **Content-addressed photos**. Internal filename = `{sha256[:16]}.{ext}`. Immutable. Dedup is free. Sync is "do you have this hash? no? here it is." Store human mapping (slug, index, destaque) in a separate `foto_refs` table. The current `{slug}-{N}.{ext}` naming becomes a URL-layer convenience, not a storage identity.

3. **Append-only `operacoes` table**. Every mutation produces an op:
   ```
   { id: uuid-v7, ts_logico: hlc, ator: node_id#user_id, 
     op: "foto.adicionar" | "foto.remover" | "foto.vincular" |
         "conteudo.criar" | "conteudo.atualizar" | "conteudo.excluir",
     args: {...},
     pai: uuid-v7 | null }  // causal parent for CRDT ordering
   ```
   State (`conteudo`, `fotos`, `foto_refs`) is derivable by folding the op log. Keep the tables as a read-model cache; rebuildable from ops.

4. **Hybrid Logical Clocks** (HLCs) for timestamps. Wall clocks lie across nodes; pure Lamport clocks lose human time. HLCs give you both. 40 lines of code.

5. **Schema-first**. `schema.yaml` in the `quilomboaraucaria` repo defines content types (`relato`, `pagina`, `evento`, `foto`, ...) with Portuguese keys (`titulo`, `data`, `publicado`, `autor`, `fotos`, `tags`). Every op validates against the schema. When `co` takes over, nothing changes — it reads the same schema.

### Technology — state of the art in 2026

For CRDT / rich-text collab, the real contenders:

| | Automerge | Loro | Yjs |
|---|---|---|---|
| Rust native | ✅ mature | ✅ newer, faster | ⚠️ via y-crdt (port) |
| JS bindings | ✅ | ✅ | ✅ (original) |
| Rich-text | Good | Best-in-class | Best-in-class |
| Local-first DNA | ✅ (Ink & Switch origin) | ✅ | Less opinionated |
| Ecosystem | Growing | Young | Largest |

**Recommendation: Automerge**. Because `co` is Rust-first, the Ink & Switch design philosophy aligns with federation aspirations, and the Rust impl is used in production. Loro is technically more performant but younger — pick it if the editing UX turns out to need faster character-level merging. Yjs is the most battle-tested but its Rust story (y-crdt) is a port, not the canonical implementation.

**Binary assets**: not inside CRDT docs. Content-addressed blob store. For now: SQLite `fotos` table keyed by hash (current implementation works). Migration path to S3-compatible (R2, Backblaze B2) or git-lfs when `co` writes to git. Decision deferrable.

**Transport**:
- **WebSocket** for real-time op streaming (`/ws/ops`)
- **HTTPS REST** for initial sync + blob fetch
- **Automerge Sync Protocol** once we introduce CRDT docs (Phase 3)

### What this buys you — concretely

- **Sync (Phase 1)**: solved, with clean audit trail. Not a throwaway.
- **Version history**: free, forever, because it's the op log itself.
- **Undo/redo**: ops are reversible.

## The core insight — why conflict resolution has to be a universal primitive

The pattern you're describing is **the 3-actor problem**, and every distributed system that solves it well collapses to the same abstraction. Git, Automerge, Ink & Switch's Upwelling, even CRDT theory all land here:

> **State is not primary. The operation log is.**
> **Every change — content, schema, config, even conflict resolution — is an operation.**
> **Merge is a pure function on the op DAG.**
> **Resolutions are operations too, which is why the system is recursive.**

If the primitive is right, conflict resolution is not a feature — it's a derivation.

### Formal model

```
Operacao = {
  id:       uuid7,                              // globally unique, time-ordered (for efficient merkle/B-tree indexing)
  hlc:      (wall_ms: u64, counter: u32, node: u128), // hybrid logical clock, total order within node, partial across nodes
  ator:     "{node_id}#{user_id}",              // who performed the change
  tipo:     string,                             // "foto.adicionar" | "conteudo.atualizar" | "schema.estender" | "conflito.resolver" | ...
  alvo:     { tipo: string, id: string, campo?: string },  // what entity + field
  args:     json,                               // operation-specific payload
  pai:      [op_id],                            // causal parents — usually size 1, multiple for merges
  assinatura?: ed25519                          // optional, for federation later
}

Estado = reduzir(ops_em_ordem_topologica, Estado₀)      // pure fold
```

The reducer is **agnostic about domain**. It dispatches on `tipo`; adding a new content type needs a new op handler, not a new merge algorithm.

### Conflict detection — one predicate to rule them all

```
conflito(op_a, op_b) :=
  op_a.alvo == op_b.alvo AND
  neither op_a nor op_b is a causal ancestor of the other in the HLC DAG
```

Two ops conflict **iff** they target the same (entity, field) AND are concurrent. That's it. No domain knowledge.

### The merge function

```
mesclar(estado_base, ops_uat, ops_prod) → {
  aplicadas: [op],        // ops from uat with no conflict, applied cleanly to prod
  conflitos: [{           // pairs requiring resolution
    id: sha256(sorted(op_uat.id + op_prod.id)),
    op_uat, op_prod,
    alvo, campo,
    opcoes: ["prod", "uat", "copia", "manual"],
    sugestao: "prod"      // default per policy
  }],
  novas_ops_prod: [op],   // prod's post-base ops that uat didn't have (reported back for UAT display)
}
```

### Resolution is itself an operation (the recursion)

```
ConflitoResolver = Operacao {
  tipo: "conflito.resolver",
  alvo: { tipo: "conflito", id: conflito_id },
  args: {
    estrategia: "prod" | "uat" | "copia" | "manual",
    ops_efetivas: [op_id],      // which ops become effective
    ops_superadas: [op_id],     // which are superseded (stay in log for audit, ignored by reducer)
    detalhes?: { novo_slug?, campos_fundidos?, ... }
  }
}
```

When `copia` is chosen, the resolver op also emits sub-ops (`entidade.criar` with a suffixed slug + `campo.atualizar` for each UAT change, targeting the new entity). Those sub-ops can themselves conflict (e.g., suffix collision). Detection → yet another resolver. **Recursion.**

**Termination is guaranteed** by the HLC monotonicity: every resolver op has strictly greater HLC than the ops it resolves. The DAG is finite. Therefore the resolution tree has finite depth.

### Idempotency, atomicity, associativity

- **Idempotency** ← op IDs are UUIDv7; `INSERT OR IGNORE ON CONFLICT(id)`. Re-sending same proposal = no-op.
- **Atomicity** ← prod wraps `aplicar(proposta)` in a SQLite transaction. Rollback on any failure.
- **Associativity across syncs** ← because the reducer is pure over the op DAG, any order of merges yielding the same op set produces the same state.
- **Commutativity (partial)** ← non-conflicting ops commute. Conflicting ones are explicitly ordered by resolver op.

### The sync cycle, as a pull request

```
1. UAT deploy/reset:
   ├─ UAT's SQLite is snapshotted from current prod state (fork)
   ├─ sync_base table records base_hlc = MAX(hlc) in the forked log
   └─ UAT has full prod history up to base_hlc

2. Users edit on UAT (admin/editors test features):
   └─ Each change appends an Operacao with hlc > base_hlc, ator = uat_node#user_id

3. Users continue editing on prod (independent, normal traffic):
   └─ Prod appends ops with hlc > base_hlc, ator = prod_node#user_id

4. Admin on UAT clicks "Abrir proposta de promoção":
   ├─ UAT builds proposta: { base_hlc, ops: [uat_ops since base], blobs: [missing hashes on prod] }
   ├─ POST /sync/api/proposta to prod
   └─ Prod computes mesclar(base_hlc, uat.ops, prod.ops_since_base)

5. Prod returns:
   ├─ aplicadas: list of UAT ops landed (no conflict)
   ├─ conflitos: list requiring decision, default suggestion = prod
   ├─ novas_ops_prod: prod changes UAT didn't have (for display)
   └─ proposta_id: handle for resolution round-trips

6. UAT renders a PR-style review UI:
   ├─ Summary: N applied, M conflicts, K prod changes you missed
   ├─ Per conflict: show both versions + the three options
   └─ Admin selects per-conflict OR bulk-picks "prod wins / uat wins / copy"

7. UAT POST /sync/api/resolver { proposta_id, resolucoes: [...] }:
   ├─ Prod applies each resolver as a new op in the same transaction
   └─ Returns success + new prod HLC

8. Sync complete. Prod state = prod's own changes ⊕ applied UAT ops ⊕ resolvers.

9. Next UAT reset → fork fresh prod → base_hlc = new prod HLC.
   └─ UAT now has: its previously merged changes + prod's further changes + all resolvers.
```

**Why this satisfies every constraint you stated**:
- Atomic/idempotent append ✓ (transaction + UUID dedup)
- Doesn't overwrite non-conflicting prod changes ✓ (conflict predicate is strict)
- Prod wins by default on conflict ✓ (sugestao = "prod")
- Manual overwrite possible ✓ (estrategia = "uat")
- Copy fallback ✓ (estrategia = "copia")
- At new UAT load, sync includes latest prod state AND previously merged UAT changes ✓ (fork = everything)
- Pull-request analogy ✓ (proposta + revisão + aplicação = PR open + review + merge)
