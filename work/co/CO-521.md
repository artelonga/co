GIVEN the componentization review identified deterministic, on-demand operations
buried inside the bridge that should be first-class tools under the canonical
contract (CO-503), and the yt-summarizer adapter already shows the front-door shape,
WHEN we extract the top-5 deterministic tools,
THEN each is a `name` / `description` / `input_schema` / `run` tool registered in
`tools/schema.yaml` with `tool_type: deterministic`, callable from any agent loop —
not logic locked inside the bridge.

## Acceptance

- [ ] **audit-serve** extracted as a deterministic tool under the canonical contract.
- [ ] **verify-restore** extracted as a deterministic tool.
- [ ] **intake-classify** extracted — the deterministic envelope/router half of
  `intake.py`, split out from the LLM synthesis half (which stays predictive).
- [ ] **mission-route** extracted as a deterministic tool.
- [ ] **consent-render** extracted as a deterministic tool.
- [ ] **Registered in `tools/schema.yaml`** with `tool_type: deterministic`, each
  following the yt-summarizer adapter front-door shape.
- [ ] **Generalist**: no tenant names in any tool identity; tenant mapping stays in the DB.

## Notes
- DEPENDS ON CO-503 (the canonical tool contract) — that contract must land first;
  this task is the first batch of adapters that target it. Note the ordering.
- Deferred to a second wave (storage-coupled, tools-over-DB): lead-digest, and
  me-export / me-erase / me-forget — these need the storage-backed tool path, not the
  deterministic on-demand path.
- "agente não bot": these tools are deterministic capabilities an agent calls, not
  bot endpoints.
