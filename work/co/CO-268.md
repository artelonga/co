## As

Anonymous visitor to `/co` (or any public universe)

## I Need

The `items` array of `GET /api/v1/universes/co/entries?limit=N` to return the **same N entries** that the `total` count reflects.

## So That

CO-266 fixed `total` (now returns 258 for `/co`) but `items` still returns `[]`. There's a second filter applied only to the items SELECT, not to the count query. Both should use the **identical** WHERE clause.

## Hypotheses (narrowed after CO-266)

The two queries in `entry_routes.rs::list_entries` clearly diverge. Likely candidates:

1. **JOIN on a side table for items only**: e.g., items SELECT joins `universe_members` to check authorship; COUNT doesn't. Anonymous → no rows.
2. **Stricter visibility column** for items: e.g., `WHERE is_published = 1 AND visibility = 'public'`. COUNT uses a more relaxed predicate.
3. **ORDER BY column with NULL values**: items SELECT has `ORDER BY published_at DESC` which excludes rows where `published_at IS NULL`. COUNT(*) doesn't apply the ORDER BY.
4. **Per-row "can view" function in Rust** runs after SQL: items go through `entries.iter().filter(can_view)` while COUNT comes from raw SQL.

Item 4 is the most likely — the `total` query likely returns the SQL row count, but the `items` go through an additional Rust-level `Vec::filter` for ACL.

## Scope

- Read `list_entries` end-to-end (now at `co-web/src/content/entry_routes.rs` post-CO-224)
- If a Rust-level ACL filter exists between SQL → response: either:
  - Apply the SAME filter to the COUNT query (so `total` reflects post-ACL count), OR
  - Remove the Rust-level filter when the universe is public-subscribable + the caller is anonymous
- If the SQL diverges: align the two queries to the same WHERE clause

## Acceptance

- `GET /api/v1/universes/co/entries?limit=3` (anonymous) returns `total > 0 AND items.length > 0`
- `total` and `items.length` are consistent — `min(total, limit)`
- The kanban / conteúdo view on `/co` actually shows entries
- New integration test: anonymous list → items not empty
