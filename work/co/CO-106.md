GIVEN `/api/health` returns 200 as long as the process is up — including pathological states where the DB is locked, the Fly volume is read-only, or the SQLite WAL is corrupt — AND the smoke test (CO-103) wants to fail loud on those exact conditions, AND production downtime that "passes the healthcheck" is the worst category of incident,
WHEN we add a sibling `/api/health/deep` that exercises the actual code paths (read a row, insert + delete a row, write + read a temp file on the volume) and returns a structured result,
THEN UptimeRobot / external monitors / smoke scripts can detect *real* problems within their poll interval, instead of cheerfully reporting "200 OK" while users see hangs.

## Endpoint

`GET /api/health/deep`

**Response on healthy server (200):**
```json
{
  "status": "ok",
  "version": "1.21.x",
  "checks": {
    "db_read": { "ok": true, "ms": 1.2 },
    "db_write": { "ok": true, "ms": 2.7 },
    "disk_writable": { "ok": true, "path": "/data" }
  },
  "as_of": "2026-04-30T08:50:00Z"
}
```

**Response on any failure (503):**
- Same shape, with `status: "degraded"` and the failing check having `ok: false` + `error: "<message>"`.
- The endpoint MUST return a JSON body even on failure (don't 5xx with HTML — monitors can't parse that).

## Probes

1. **db_read** — `SELECT 1 FROM users LIMIT 1` (or `sqlite_master` if `users` might be empty). Time it; report ms.
2. **db_write** — atomic insert + delete in a dedicated `health_probes` table (single row, primary key = "probe", `INSERT OR REPLACE`). Avoids cluttering real tables. Time it; report ms.
3. **disk_writable** — write a 16-byte file at `${data_dir}/.health_probe`, read it back, delete. Catches "Fly volume mounted read-only" / "out of space" cases.

If any check exceeds **500 ms**, mark it as `ok: true` but `degraded: true` so monitors can alert on slow-but-not-broken.

## No-cache headers

`Cache-Control: no-cache, no-store, must-revalidate` — health endpoints must never be cached by anything.

## Schema

The `health_probes` table is created lazily on first probe:

```sql
CREATE TABLE IF NOT EXISTS health_probes (
    id TEXT PRIMARY KEY,
    last_check_at TEXT NOT NULL
);
```

Single row with `id = 'probe'`. Touched on every deep-health hit.

## Constraints

- No auth required — reachable from external monitors.
- Total endpoint runtime ≤ 100 ms on a healthy machine.
- Must not log a line per probe — monitors hit it every 30-60 seconds and we don't want the log noise. Only log on transitions (ok → degraded, degraded → ok).
- Rate-limit exempt (CO-80 must whitelist this path).

## Acceptance

- [ ] `GET /api/health/deep` returns 200 + JSON with all three check results on a healthy machine.
- [ ] Returns 503 + JSON with the specific failing check when:
  - `data_dir` mounted read-only (test by setting permissions on a tempdir in unit test)
  - DB connection deliberately closed
- [ ] Endpoint listed in `docs/OPERATIONS.md` (CO-100) under Health checks.
- [ ] Smoke script (CO-103) check #2 calls this endpoint and fails on 5xx (already in spec).
- [ ] Rust unit test for the success path; integration test for at least one failure path.
- [ ] No regression on `/api/health` (the shallow endpoint stays untouched).

## Out of scope

- Per-component breakdown beyond the three probes (e.g. external services). Keep to the local truth.
- Latency histograms / percentile tracking (Prometheus territory — separate ticket).
- Rate limiting (CO-80 will whitelist this path; not this ticket's job).
