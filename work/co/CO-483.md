GIVEN the companion app called the bot brain (the `whatsapp-bot` bridge `/api/chat`)
directly, and the bridge is **loopback-only + unauthenticated** — so for remote/guest
users the only way to make chat work would be to expose an unauthenticated
model+CO-write endpoint to the LAN (a security gap that blocked R1→R2),
WHEN we add `POST /api/v1/bot/chat` behind `require_auth` (JWT session/Bearer) +
the global CO-80 rate limiter, which proxies to the loopback bridge,
THEN chat works for authenticated remote users while the bridge **never leaves
loopback** — co-web is the single authenticated front door (matches the
"route through co-web's authenticated layer" decision).

## Acceptance

- [x] `POST /api/v1/bot/chat` (`integrations/bot_proxy_routes.rs`) behind
  `require_auth`; unauth → **401** (verified on a live instance).
- [x] Proxies `{text}` → `CO_BOT_BRAIN_URL` (default loopback `:8765`), returns
  `{reply, intent}`; `503` if the brain is unreachable, `502` if it returns no reply.
- [x] Pure `parse_reply` (reply + intent, intent defaults to `chat`); unit-tested.
- [x] Companion app chat now calls `${CO}/api/v1/bot/chat` with
  `credentials:'include'` (session cookie); shows a login hint on 401.
- [x] `cargo test` + `cargo clippy -- -D warnings` + `cargo fmt` clean.

## Notes / follow-up

- Bridge stays loopback-bound + out of the firewall allowlist — confirmed by
  `infra/e2e/exposure-scan.sh`.
- Guests authenticate to co-web (password-login / magic code) before chatting.
- Future: per-user rate-limit on `/bot/chat`; the brain's CO writes already use a
  scoped token (CO-448).
