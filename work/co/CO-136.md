## As

a CO operator deciding whether to add Pinot to the stack

## I Need

a documented evaluation that compares ClickHouse (current) and Pinot for CO's actual analytics surface as it stands at Phase 5, with a decision rationale committed to the repo, **regardless of which way it goes**

## To

avoid carrying Pinot-as-vague-future-option through three roadmap phases; force a yes/no with evidence; satisfy the §B.3 rebuttal of the SR plan's "pick on operator taste"

## Given / When / Then

GIVEN ClickHouse single-node ships in Phase 2 (CO-123) and the Iceberg lake in Phase 3 (CO-126),
WHEN we have a real analytics surface in Phase 5 (or even in the late stages of Phase 3-4),
THEN we run a 1-week evaluation comparing ClickHouse and Pinot on **the workload that's actually emerging** and document the recommendation.

## Evaluation rubric

| Dimension | ClickHouse | Pinot | Weight |
|-----------|-----------|-------|--------|
| Sub-second p99 at our actual QPS | ? | ? | High |
| Operational cost (engineer hours/month) | Low (single binary) | High (4-component cluster) | High |
| Iceberg-native read | Yes (`iceberg(...)` table fn) | Yes (varies by version) | High |
| Real-time ingest (segment commit ≤ 1s) | Yes | Yes (segment commit ~1s) | Medium |
| Star-tree / hot-aggregate optimization | No (relies on materialized views) | Yes (built-in) | Workload-dependent |
| User-facing API ergonomics | SQL | SQL + REST | Medium |
| Cost in $$ | Low (Fly Machine) | Higher (more components) | Medium |

## Decision criteria

Pinot only justified if **all** of:
- A real product surface exists with sustained ≥1k QPS
- ClickHouse p99 measurably falls short for that surface (not theoretically — measured)
- Operator capacity exists to run a 4-component cluster

Otherwise: **stay on ClickHouse** and document why.

## Acceptance

- [ ] 1-week eval log in `work/co/evals/pinot-vs-clickhouse-{date}.md`
- [ ] At least one workload tested end-to-end on both
- [ ] Recommendation committed (either "adopt Pinot" with migration plan, or "stay on ClickHouse" with rationale)
- [ ] If "stay," this ticket closes as `wontfix` with a link to the eval log
- [ ] If "adopt," follow-up tickets opened for the migration

## Out of scope

- StarRocks / Apache Doris / Druid — call out in the eval as alternatives only if shortlisted
- Tinybird (managed ClickHouse) — eval as a separate axis if vendor-managed becomes attractive
- ClickHouse Cloud — same

## Risks

- **Evaluation paralysis.** Mitigation: 1-week timebox; "stay on current" is an acceptable outcome
- **Premature optimization.** Mitigation: only run this eval **after** a real product surface exists, not preemptively
