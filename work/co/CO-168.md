## As

an operator of CO and quilombo deployments who wants to send notifications (WhatsApp, email, SMS) when things happen — new events, new missions, new messages — without hardcoding provider integrations into the CO binary

## I Need

an outbound webhook system where CO emits signed HTTP POST events, and a notification queue table that n8n/Zapier (or a future Rust adapter) drains to call providers

## So That

(a) adding a new notification channel (WhatsApp, SMS, push) requires only configuring n8n, not deploying new CO code,
(b) failed deliveries retry automatically with backoff,
(c) the system scales from SQLite + job worker today to a message broker (NATS) later without changing the event emission surface

---

## Current state (1.76.0)

CO emits telemetry events to WAE (Cloudflare Workers Analytics Engine) fire-and-forget. No outbound webhooks. No notification queue. The job_queue table handles doc-gen jobs only (CO-72). No external integrations beyond WAE.

## Design

### Architecture

```
Request handler
  └── emit_event("quilombo.evento.criado", payload)   ← new helper, synchronous write to DB
        └── notifications table (pending)
              └── webhook_worker (background, polls every 5s)
                    ├── claim row
                    ├── POST {webhook.url} with HMAC-SHA256 signature
                    ├── mark sent / failed
                    └── retry up to 3× with exponential backoff (5s, 30s, 2min)
```

n8n/Zapier sits between CO's webhook and the provider (WhatsApp, email, SMS). CO delivers one canonical JSON event; n8n routes it to whatever channel.

### Storage — Migration v35

```sql
-- Registered webhook endpoints (admin-configured)
CREATE TABLE IF NOT EXISTS webhooks (
    id TEXT PRIMARY KEY,
    url TEXT NOT NULL,
    secret TEXT NOT NULL,       -- HMAC-SHA256 key, shown once at creation
    events TEXT NOT NULL,       -- JSON array of event types, e.g. ["*"] or ["quilombo.evento.*"]
    enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL
);

-- Outbound notification queue
CREATE TABLE IF NOT EXISTS notifications (
    id TEXT PRIMARY KEY,
    webhook_id TEXT NOT NULL REFERENCES webhooks(id) ON DELETE CASCADE,
    event_type TEXT NOT NULL,
    payload TEXT NOT NULL,       -- JSON
    status TEXT NOT NULL DEFAULT 'pending',  -- pending | sent | failed | dead
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT NOT NULL,
    sent_at TEXT,
    error TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_notifications_pending
    ON notifications(status, next_attempt_at)
    WHERE status IN ('pending', 'failed');
```

### Webhook signature

Each delivery includes:

```
X-CO-Event: quilombo.evento.criado
X-CO-Delivery: <notification_id>
X-CO-Signature-256: sha256=<hmac_hex>
```

HMAC-SHA256 over the raw request body using the webhook's secret. Matches GitHub's webhook signature scheme so existing n8n/Zapier GitHub nodes work with minimal adaptation.

### Event catalogue (initial)

| Event type | Trigger |
|------------|---------|
| `quilombo.usuario.cadastro` | New quilombo user registered |
| `quilombo.usuario.login` | User logged in |
| `quilombo.evento.criado` | New event created |
| `quilombo.missao.criada` | New mission created |
| `quilombo.missao.participou` | User joined a mission |
| `quilombo.mensagem.criada` | New internal message |
| `co.universe.criado` | New universe created |
| `co.entry.criado` | New entry created (opt-in; high volume) |
| `co.usuario.cadastro` | New CO user registered |

Wildcard matching: `quilombo.*` matches all quilombo events. `*` matches everything.

### Admin API

```
POST /api/v1/gestao/webhooks          — register webhook (returns secret once)
GET  /api/v1/gestao/webhooks          — list webhooks (secret redacted)
PUT  /api/v1/gestao/webhooks/:id      — update url / events / enabled
DELETE /api/v1/gestao/webhooks/:id    — delete (cascades notifications)
GET  /api/v1/gestao/webhooks/:id/deliveries — delivery log (last 100)
```

All routes require GitHub admin auth (existing `require_github_admin` middleware).

### Worker

Extend the existing `job_queue::spawn_worker` or add a parallel `webhook_worker::spawn` that:
1. Polls `notifications WHERE status='pending' AND next_attempt_at <= now()` every 5 seconds
2. Claims one row atomically via `UPDATE … RETURNING`
3. Finds matching webhooks for the event type (wildcard pattern match)
4. POST to webhook URL with HMAC signature, 10s timeout
5. On 2xx: marks `sent`
6. On non-2xx or network error: increments `attempts`, sets `next_attempt_at` to `now + 5s * 2^attempts` (cap at 2 min), marks `failed` if attempts ≥ 3 → `dead`

### n8n integration guide

Documented in `docs/webhooks.md`:
1. Set up a Webhook node in n8n pointing to `https://n8n.example.com/webhook/co`
2. Register the n8n URL via `POST /api/v1/gestao/webhooks`
3. Validate `X-CO-Signature-256` in the n8n Code node
4. Route by `X-CO-Event` to WhatsApp / email / SMS nodes

- [ ] `POST /api/v1/gestao/webhooks` creates a webhook, returns secret once (admin only)
- [ ] `GET /api/v1/gestao/webhooks` lists webhooks with secret redacted

- [ ] `emit_event(event_type, payload)` helper writes a notification row for each matching enabled webhook
- [ ] Webhook worker starts at boot, polls every 5s, delivers with HMAC-SHA256 signature
- [ ] Retry: up to 3 attempts with 5s / 30s / 2min backoff; 4th failure marks `dead`
- [ ] Wildcard event matching: `quilombo.*` and `*` work correctly
- [ ] At least 3 quilombo events wired: `quilombo.evento.criado`, `quilombo.missao.participou`, `quilombo.mensagem.criada`

- [ ] `docs/webhooks.md` documents the event catalogue and n8n setup guide
