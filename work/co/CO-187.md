## As

a maintainer

## I Need

the legacy HS256 `sign_handover_jwt` helper removed from `co-web/src/auth.rs`
now that all production handover-token issuance and verification use ES256
via JWKS (CO-186, live since 1.93.x; QB-12 verifier deployed on quilombo)

## So That

future readers don't see a dead function with "kept for the brief
migration window" comments and copy it as a template, and we collapse
the two-helper pattern (`sign_handover_jwt` + `sign_handover_jwt_es256`)
into a single canonical signer.

---

## Why this is safe now

The legacy HS256 helper exists for the brief overlap window where
quilombo's verifier still accepted HS256 alongside ES256. That overlap
is over:

| | |
|---|---|
| CO-186 (ES256 + JWKS) live | 1.93.x — handover tokens have been ES256-signed for ~7 days |
| QB-12 jose-based JWKS verifier on quilombo | confirmed live ("all working qb 12 pass") |
| Callers of `sign_handover_jwt` (HS256) in co-web | **zero** (grep confirms) |
| Callers of `sign_handover_jwt_es256` | `maybe_attach_co_handover_token` |

The only references to `sign_handover_jwt` are the function definition
and two doc-comment cross-references. No external API consumers — this
is an internal helper.

## NOT in scope (do not touch)

- **HS256 for session JWTs.** The session cookie JWT continues to use
  HS256 (lines ~300, 350, 390 of `auth.rs`). That's a separate migration
  with much larger blast radius (every active session would be
  invalidated). Out of scope here.
- **`decode_jwt` fallback chain** that tries ES256 first then HS256
  (line ~236). Keep — supports session-cookie validation.
- **Quilombo-side verifier** (in the quilombo `usuarios` SvelteKit
  routes). Quilombo can keep its HS256-fallback as long as it wants;
  this ticket only removes the CO-side *signer*.

## Files touched

co-web/src/auth.rs   (remove sign_handover_jwt fn + update doc comment on _es256 fn)
