## As

a CO operator whose user-edited content on prod (`quilomboaraucaria`, `artelonga`, `rfq`) is currently not backed up anywhere

## I Need

the CO-104 backup-cron infrastructure (`infra/backup-cron/`) actually deployed as a Fly app, OR the GitHub Actions cron (`.github/workflows/backup.yml`) actually configured with the AWS + Fly secrets — whichever path you prefer

## To

ensure that "we have prod changes" (user feedback 2026-05-02) doesn't become "we lost prod changes" the next time the Fly volume hiccups

## Given / When / Then

GIVEN CO-104 (1.28.0) shipped backup automation infrastructure:
- `scripts/backup-prod.sh` — manual snapshot
- `infra/backup-cron/` — Alpine Fly app config (Dockerfile + entrypoint + fly.toml)
- `.github/workflows/backup.yml` — GitHub Actions daily cron alternative

AND `flyctl apps list` on 2026-05-02 showed only `co-artelonga` and `co-artelonga-uat` — **the backup-cron app was never created**, AND there's no evidence in `gh secret list` that the GitHub Actions secrets (`BACKUP_AWS_ACCESS_KEY_ID`, `BACKUP_AWS_SECRET_ACCESS_KEY`, `FLY_API_TOKEN`) are set,

WHEN we (a) verify the S3 bucket `artelonga-co-backups` exists with lifecycle, (b) provision the IAM user with PutObject+GetObject on that bucket, (c) deploy the cron via Option A or Option B,

THEN every prod write becomes durable within ≤24h to a region-independent location, and a single Fly volume failure no longer means lost user content.

## Action items (pick one path)

### Option A — Fly cron app (recommended, runs in the same infra)

```bash
# 1. One-time bucket setup (idempotent — skip if already done)
BUCKET=artelonga-co-backups bash infra/s3/setup.sh

# 2. Generate IAM credentials with the policy in infra/s3/setup.sh's comments
# 3. Create the cron app
cd infra/backup-cron
flyctl apps create co-backup-cron --org personal
flyctl secrets set FLY_API_TOKEN=<your-token> -a co-backup-cron
flyctl secrets set AWS_ACCESS_KEY_ID=<key> -a co-backup-cron
flyctl secrets set AWS_SECRET_ACCESS_KEY=<secret> -a co-backup-cron
flyctl secrets set AWS_DEFAULT_REGION=us-east-1 -a co-backup-cron
flyctl secrets set BUCKET=artelonga-co-backups -a co-backup-cron
flyctl deploy -a co-backup-cron

# 4. Verify cron is running
flyctl logs -a co-backup-cron
# Should see "[backup] uploaded to s3://..." within 24h.
```

### Option B — GitHub Actions cron

```bash
gh secret set BACKUP_AWS_ACCESS_KEY_ID --body "<key>"
gh secret set BACKUP_AWS_SECRET_ACCESS_KEY --body "<secret>"
gh secret set FLY_API_TOKEN --body "$(flyctl auth token)"
# Trigger first run manually to verify
gh workflow run backup.yml
gh run watch
```

## Interim — local-only backups (no S3 / R2 yet)

Operator decision 2026-05-02: capture snapshots **locally** until cloud storage is provisioned.

`scripts/backup-prod-local.sh` was written for this:
- Default destination: `~/co-backups/` (outside the repo)
- Output: `data-<UTC>.tar.gz` (full `/data/` tree — `meta.db` + per-universe `data.db` files + content `.md` + `auth.redb`) + `manifest-<UTC>.txt`
- No AWS / cloud credentials required — only `flyctl` (already logged in)
- Runs in ~30 seconds for current prod (~7 MB tarball)

**First snapshot captured 2026-05-02 10:08 UTC:**
- File: `~/co-backups/data-20260502-100848.tar.gz` (6.9 MB)
- Contents verified: rfq + artelonga + quilomboaraucaria (85 files) — all user-edited prod content present
- meta.db + WAL + SHM all included → recoverable SQLite snapshot

**Limitations of the local-only path:**
- Single-host durability (laptop loss = data loss)
- No retention policy (manual prune)
- Not automated — operator must remember to run it

**Promote to S3/R2 when ready:**
1. Run `infra/s3/setup.sh` against either S3 or an R2 bucket (same API)
2. Set credentials (Option A or B below)
3. Original `scripts/backup-prod.sh` works once `sqlite3` is added to the Fly runtime image, OR adapt it to use the same tar-everything strategy as `backup-prod-local.sh` (recommended — simpler, sqlite3-free)
