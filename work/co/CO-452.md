## Contexto
CO-278 (API pública) é um épico de 5-7 sub-stories. **CO-278-B (token scopes)** já
saiu no CO-448; **a spec OpenAPI já é servida** pelo CO-211 (`openapi_routes.rs`
faz `include_str!` de `docs/api/openapi.yaml`). Falta a peça **C**: um **Swagger UI
interativo** + discovery, pra terceiros/sister-repos explorarem a API documentada
sem engenharia reversa. É aditivo, sem migração, e reusa o que já existe.

## Acceptance
- [ ] **Swagger UI** servido em `GET /api/docs` (página HTML que carrega a spec via
      `/api/openapi.json`). Usar o bundle Swagger UI **vendorizado** em
      `co-web/static/` (não CDN externo — CSP-safe, sem dependência de terceiros).
- [ ] **Discovery**: `/api/openapi.json` retorna a spec OpenAPI (reusar/alinhar com o
      que o CO-211 já serve — não duplicar; se hoje serve YAML, adicionar JSON ou
      apontar o Swagger pro endpoint existente). Header `X-API-Version: v1`.
- [ ] Link "API docs" descobrível (rodapé/`/seguranca` do CO-210, ou um item simples).
- [ ] A spec servida == `co-web/openapi.yaml` gerado do catálogo (sem drift; o
      `openapi:check` continua a fonte de verdade).
- [ ] Rota no `api-catalog.md` (seção SPA/page-routes, sem demandar handler de API)
      + sem drift no `openapi:check`.
- [ ] Teste e2e: `GET /api/docs` → 200, página Swagger carrega a lista de endpoints;
      `GET /api/openapi.json` → 200 com `openapi: 3...`.
- [ ] Sem migração; anon-readable (a doc é pública; os endpoints continuam gated).

## So that
A API do CO vira um **contrato documentado e explorável** — base pro CO-278-A
(versioning/envelope), CO-278-D (agent dispatch) e futuros SDKs, e pro "open
developer surface" que sister-repos (yggdrasil, qb, rfq) consomem.

## Não no escopo
- Versioning/envelope `{data,meta,errors}` (CO-278-A) · agent dispatch (CO-278-D) ·
  telemetria/analytics endpoints (CO-278-E) · SDK (CO-278-F). Só docs/Swagger aqui.
- Rate-limits por rota (parte do CO-278-B/-A) — fora desta fatia.
