## Today (2.5.0)

`test` job is green (548+ tests pass). `e2e` job has been red since
2026-04-30 (along with `test` until 2.4.x). With protoc + dbus + the
parking_lot + stale-assertion fixes shipped in 2.4.x, `test` is now
healthy. `e2e` accumulated 12 days of API + behavior drift that the
test fixtures don't know about.

## Failure modes seen in run 25769394457

### 1. API contract drift

- `auth-crdt.spec.ts:104` expects `body.is_anonymous === true` but the
  field is `undefined`. Field was renamed/removed in CO-170 or
  CO-184. Test needs the new field name (likely something on the
  `Universe` struct).

### 2. Rate-limit collisions

- Fixtures POST many universe/signup creations in a row → trigger
  CO-190's 100-account/day or 5-email/hour rate limit. Subsequent
  fixture POSTs return 429.
- Cascade: SPA gets nothing back → expected elements never render →
  `toBeVisible` timeouts on a long tail of tests.

Two fix paths:

**(a) Bypass in tests**: `JWT_SECRET=ci-test...` is set; add a
`CO_BYPASS_RATE_LIMIT=1` env that the rate_limit module honors when
`co_env=test`. Default off; only set in CI's e2e env. Strict-mode in
prod unchanged.

**(b) Reset rate limit state between fixture runs**: each test gets a
fresh `data_dir` (it already does) but the rate-limit module uses
in-process state. Hook to reset between tests.

(a) is simpler — one flag, one fixture line. Recommended.

### 3. Possibly more pre-existing drift

Once (1) and (2) are fixed, expect more failures behind them
(currently masked because tests bail early on 429). Plan for 2-3
iterations of "fix the next visible drift, run, repeat."
