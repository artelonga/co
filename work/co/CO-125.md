## As

a CO operator graduating beyond WAE/ClickHouse for streaming analytics

## I Need

a small Redpanda cluster (1-3 brokers on Fly Machines, or Redpanda Cloud BYOC) with Iceberg Topics enabled, the Schema Registry running, and topics provisioned for the core event classes

## To

land event data directly in Iceberg-on-R2 (Parquet) **without a separate Kafka Connect cluster** — the SR plan's structurally-correct call (per `platform-evaluation.md` §10) — so downstream Flink and ad-hoc engines can read a uniform table format

## Given / When / Then

GIVEN we want the streaming bus + lake hop to be one product, not two,
WHEN we deploy Redpanda with Iceberg Topics enabled and produce events to one of the configured topics,
THEN the events appear as Parquet files in R2 under an Iceberg table within ≤60s, queryable from DuckDB / ClickHouse / Spark.

## Topics (initial)

| Topic | `redpanda.iceberg.mode` | Purpose |
|-------|--------------------------|---------|
| `events.exposure` | `value_schema_latest` | A/B exposures (CO-121 ships here once Phase 3 lands) |
| `events.page_view` | `value_schema_latest` | Page views |
| `events.deploy` | `value_schema_latest` | Deploy markers |
| `events.error` | `value_schema_latest` | Structured errors |
| `events.encrypted` | `key_value` | Per-universe ciphertext payloads (Phase 4) |

## Hosting decision

§F.6 of the platform roadmap review left this open. Default proposal:
- **Self-host on Fly:** 3× `performance-1x` Machines (8 GB RAM each) in the same region as `co-web`. Storage on Fly Volumes.
- **Alternative:** Redpanda Cloud BYOC — pay for managed control plane, brokers run in our cloud account. Re-evaluate at Phase 4 boundary.

## Known limitations to design around

Per [docs.redpanda.com](https://docs.redpanda.com/current/manage/iceberg/about-iceberg-topics/):
- Cannot append to non-Redpanda-created Iceberg tables → Redpanda owns the table lifecycle from day one
- No backfill of existing topic data when the integration is enabled → enable at topic creation
- Parquet only
- CPU overhead is non-trivial during translation → size for 30% headroom

## Acceptance

- [ ] Redpanda 3-broker cluster deployed (or Cloud BYOC active) with persistent storage
- [ ] Schema Registry reachable on internal network
- [ ] All five topics created with appropriate `redpanda.iceberg.mode`
- [ ] 1k synthetic events produced to `events.exposure` land in R2 as Parquet within 60s
- [ ] Iceberg table queryable via DuckDB and ClickHouse `iceberg(...)` table function
- [ ] `docs/OPERATIONS.md` updated with broker management runbook

## Out of scope

- Multi-region Redpanda — single-region until traffic justifies otherwise
- MirrorMaker / cross-cluster replication — separate ticket
- Encrypted-payload topics (`events.encrypted`) — Phase 4 (this ticket creates the topic shape only)

## Risks

- **Broker disk pressure.** Mitigation: short retention on raw topics (7 days); long-term truth lives in Iceberg
- **Schema Registry as SPOF.** Mitigation: local schema cache in producers; degrade gracefully if registry is unreachable
