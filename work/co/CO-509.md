GIVEN `co-web/src/universes/quilombo/` embeds a **private tenant's** backend directly
into the open platform — `quilombo_routes` / `storage` / `telemetria` / `permissoes`,
`lib.rs` re-exports, `migrate_quilombo.rs`, `quilombo_legacy_login` referenced from
scrum/eda, and Quilombo-specific fields in `auth.rs` — which violates the generalist
principle (CO must carry no tenant-specific names),
WHEN we extract the quilombo backend into the **private quilombo repo** and replace
the embedded coupling with CO's generic, DB-driven mechanisms,
THEN CO stays tenant-agnostic — any tenant is a data mapping, not Rust code in the
open platform — and the private tenant's logic lives where it belongs.

## Acceptance

- [ ] `co-web/src/universes/quilombo/` (routes/storage/telemetria/permissoes) **removed**
  from the open platform and relocated to the private quilombo repo.
- [ ] `lib.rs` quilombo re-exports removed; `migrate_quilombo.rs` removed or generalized
  into a tenant-agnostic migration mechanism.
- [ ] `quilombo_legacy_login` removed from scrum/eda paths; any needed behavior expressed
  generically (DB-driven) or moved to the private repo.
- [ ] Quilombo-specific fields removed from `auth.rs`; auth stays generic.
- [ ] **DB-driven mappings** replace any hardcoded tenant coupling (per
  `feedback_no_hardcoded_content_mappings`): adding/serving a tenant needs no platform code.
- [ ] Build/tests/CI green; the quilombo deployment still works via the extracted
  private backend + CO's generic mechanisms (no functional regression for the tenant).
- [ ] `grep -ri quilombo co-web/src` returns nothing in the open platform (beyond
  intentional generic test fixtures, if any).

## Notes
- This is the structural half of generalist-cleanup; CO-510 is the docs/changelog half.
- The private tenant's code is not deleted, it **moves** — extract to the private repo,
  then remove from co-web. Coordinate so the tenant's prod deploy is never broken.
- Generalist invariant: no `quilombo`/`rfq` names in the open platform; tenants are data.
