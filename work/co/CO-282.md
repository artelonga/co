## As

Any developer/operator who wants to run CO locally (offline-first, no Fly account required), and the operator looking to distribute CO as a downloadable tool

## I Need

A **localhost-first distribution** of CO that wraps the existing Rust `co` binary into a single-command "open the platform on my own machine" experience — no Docker, no Fly account, no manual server config.

Three progressive shells (each builds on the previous):

1. **Phase 1 — `co serve --open`**: single command launches the embedded co-web server on `127.0.0.1:<port>` and pops the user's default browser to that URL. The same Rust binary that runs on Fly today, just bound to localhost.
2. **Phase 2 — Tauri desktop shell**: native desktop app (macOS / Linux / Windows) wrapping the localhost server. System tray, menu bar, native window. ~10MB binary, no Chromium bloat.
3. **Phase 3 — Mobile** (deferred): Tauri 2.0 Mobile or Capacitor wrapper for iOS / Android. Same web UI, native shell.

## So That

- **Developers** can run the platform offline against their own SQLite, no Fly dependency
- **Privacy-conscious users** (e.g. quilombo members, journalists) get a self-hosted CO without needing to manage a server
- **Operator's contributors** can install CO with one command and see the full UI without learning Fly or Docker
- **The platform stops being inseparable from `co.artelonga.com.br`** — it becomes a tool people install, not a service they subscribe to
- Sets the foundation for offline-first sync (the CRDT layer already exists; just need a local host that doesn't require internet)

## Context

### What we have today

- `co-cli` — Rust binary with subcommands (`init`, `new`, `show`, `validate`, etc.) but no `serve`
- `co-web` — Axum HTTP server that today is bound to `0.0.0.0` in Fly deployments
- SPA static assets — already embedded into the binary via `rust-embed` (CO-22x family, observable in `co-web/static/`)
- SQLite-per-universe storage — fully local-capable
- All auth flows (UAT login, password login, email magic-code) work against local SQLite already

The Rust binary is **already 90% of what a local distribution needs**. What's missing is the developer ergonomics around it.

### What's missing

1. No `co serve` command — `co-web` is invoked via `cargo run` in dev, via the Fly Docker image in prod. There's no shipped CLI entry point.
2. No "open my browser" affordance — operator has to remember `http://localhost:8080` and the right port
3. Binary today is built for the Fly target only — no per-OS releases on GitHub
4. SPA assumes `co.artelonga.com.br`-style absolute URLs in a few places — needs audit for fully-relative URLs
5. No "data dir" convention — local users need a sensible default for `~/.co/universes/` or similar
6. No native window — running in a browser tab is fine for devs, awkward for end-users

### Why Tauri (not Electron)

| Aspect | Tauri | Electron |
|---|---|---|
| Binary size | ~10MB | ~150MB |
| Language match | Rust-native (mirrors our stack) | Node.js bridge required |
| Memory footprint | ~80MB | ~300MB |
| Webview | System (WKWebView / WebView2 / WebKitGTK) | Bundled Chromium |
| Maintenance | Tauri team active, v2.0 mobile support | Mature, but heavier |
| Our familiarity | New (learning curve) | Common (more StackOverflow) |

Tauri wins decisively for our stack — Rust-to-Rust integration is trivial, the binary stays small, and the same architecture extends to mobile (Tauri 2.0 added iOS/Android targets). Electron is the safer choice if we hire JS devs, but for a Rust-first team Tauri matches our trajectory.

### Why phase it

Phase 1 ships the **80% value** with **5% of the work** — same binary, one new command, browser auto-launch. We can decide whether Phase 2 (Tauri) is worth it after Phase 1 lands and we see actual usage.

## Decision

### Phase 1 — `co serve --open` (1 week)

Add a `serve` subcommand to `co-cli` that:

```bash
co serve                          # default: bind 127.0.0.1:54321, log to stderr
co serve --open                   # also launches the user's default browser
co serve --port 8080              # custom port
co serve --data-dir ~/my-co       # custom data directory (default: $XDG_DATA_HOME/co)
co serve --public                 # bind 0.0.0.0 (operator opt-in, warning printed)
```

Under the hood:
1. Resolve data dir (default: `dirs::data_dir() / "co"`)
2. Run all SQLite migrations against `<data-dir>/co.db`
3. Boot `co-web` server with `bind = (127.0.0.1, port)`
4. If `--open`: spawn the default browser via the `open` crate (`open::that(format!("http://127.0.0.1:{port}"))`)
5. On Ctrl-C: graceful shutdown (drain WebSockets, fsync SQLite, exit)

Audit + fix any SPA assumptions:
- Hardcoded URLs to `co.artelonga.com.br` → use relative paths
- OAuth callback URLs → use `request.origin` not env var
- Asset references → already relative via `rust-embed`

Release artifacts:
- GitHub Actions build matrix: `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`
- `cargo dist` (the standard Rust release-binary tool) — generates installers, Homebrew formula, scoop manifest
- `co-cli` binary attached to each tagged release

User experience after Phase 1:
```
$ brew install artelonga/tap/co     # or curl https://co.artelonga.com.br/install.sh | sh
$ co serve --open
✓ co 2.30.0 listening on http://127.0.0.1:54321
✓ Opening browser...
[user sees the full SPA running locally against their own SQLite]
```

### Phase 2 — Tauri desktop shell (2 weeks, optional)

New crate `co-desktop` (or `desktop/` subdirectory):

- Tauri 2.0 frontend, system webview
- Wraps Phase 1's localhost server as a sidecar process
- Native window (no browser chrome)
- System tray icon with "Open CO" / "Stop server" / "Quit" menu
- Menu bar: File / Edit / View / Help (standard macOS menu structure)
- Auto-update via Tauri's updater (TLS-signed manifests served from `co.artelonga.com.br/desktop/updates.json`)
- Notifications: native OS notifications for chat messages (extends CO-220's event bus)

Distribution:
- `.dmg` for macOS (with bundle icon + DMG background)
- `.AppImage` for Linux
- `.msi` for Windows (Wix-based, signed via free Windows code-signing certs from Sectigo if budget allows)

### Phase 3 — Mobile (deferred — measure Phase 1/2 adoption first)

Tauri 2.0 Mobile or Capacitor wrapping the same web UI. Local SQLite via platform APIs (SQLite is on all mobile OSes). Sync via the existing vault API. Decide AFTER Phase 2 ships and we see whether users actually want a mobile app vs. just visiting the web URL on their phones.

## Why now

User's exact words: *"we should be able to revisit a localhost version that is a local ui and wrappr for the co cli rust distribution"*.

The memory `project_mvp_roadmap.md` flagged Electron + Capacitor as v1.0 roadmap items that got deferred. They were deferred because we hadn't built the full SPA yet. **Now we have**: kanban (CO-272), agent sessions (CO-275), deployment dashboard (CO-273), every major flow lives in the SPA. The SPA is mature enough to wrap in a local shell.

Three convergent reasons:

1. **CO-281 Fly cost work** is making us think about "where does CO actually need to run?" — and the honest answer is "often locally". Fly is for the public-facing universes; local is for private/dev/offline use.
2. **CO-278 public API** will need a stable distributable client — `co serve` is the natural reference implementation.
3. **The user just hit the macOS Gatekeeper issue** trying to run `co-auto` locally. Once we ship `co` properly (with signing + GitHub releases), that whole class of "fresh-build amfid hang" problems goes away because users download an Apple-notarized binary, not a freshly-compiled one.

Phase 1 alone is **1 week** of work. The payoff: every contributor on macOS/Linux/Windows can run CO in 60 seconds with two commands. The macOS Gatekeeper issue I hit this session never bites a user again because they don't `cargo install` — they download a pre-built release.
