GIVEN quilombo-blog is the interim community platform and its UAT (quilombo-araucaria-uat.fly.dev) is reforked from prod on every deploy,
AND GIVEN admins upload photos to UAT for review and want them promoted to prod atomically without overwriting prod-side changes,
AND GIVEN CO-61 defines the canonical sync protocol v1,
WHEN I implement the CO-61 subset for photos in quilombo-blog,
THEN admins can open a promotion "pull request" from UAT → prod with automatic 3-way merge, conflict flagging (prod-wins default), and recursive resolution — all persisted as ops in the shared log.

## Scope v0 (today)

- **Entity type**: `foto` only. Conteudo ops deferred to CO-65+.
- **Direction**: UAT → prod. Prod does not sync to anywhere (it IS the origin).
- **Refork**: UAT volume is destroyed and recreated from a fresh prod snapshot on every UAT deploy. This makes UAT's base_hlc auto-update to current prod state.

## Prerequisite: UAT refork runbook

Before running CO-62 tests, verify UAT volume is freshly forked from current prod. Script:

```bash
# 1. Snapshot prod volume
fly volumes snapshots create vol_<prod_vol_id> -a quilombo-araucaria

# 2. Wait for snapshot (poll fly volumes snapshots list until the new one is 'created')

# 3. Destroy UAT machine + volume (Fly name collisions are an issue; use unique names per refork)
fly machine destroy <uat_machine_id> -a quilombo-araucaria-uat --force
# fly volumes destroy is sometimes flaky — if it errors "not found", the volume is orphaned
# but harmless; pick a new unique name

# 4. Create new UAT volume from snapshot with unique name (e.g. quilombo_uat_r{N+1})
fly volumes create quilombo_uat_r<N> --snapshot-id vs_<id> --region gru --size 1 --yes -a quilombo-araucaria-uat

# 5. Update fly.staging.toml source to match new volume name

# 6. Deploy UAT
fly deploy --config fly.staging.toml

# 7. Verify UAT pulled ALL current prod state (events count, new content URLs)
curl -sS -o /dev/null -w "%{http_code}\n" https://quilombo-araucaria-uat.fly.dev/<recent-prod-url>
```

**This runbook is codified in `scripts/uat-refork.sh` as part of CO-62 delivery.**

## Database migration v006

```sql
CREATE TABLE atores (
  id TEXT PRIMARY KEY,           -- uuid for the ator record
  node_id TEXT NOT NULL,         -- stable per install; uuid
  user_id INTEGER,               -- references usuarios.id; null for system ator
  criado_em TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(node_id, user_id)
);

CREATE TABLE operacoes (
  id TEXT PRIMARY KEY,           -- uuidv7, string form
  hlc_wall INTEGER NOT NULL,
  hlc_counter INTEGER NOT NULL,
  hlc_node TEXT NOT NULL,
  ator_id TEXT NOT NULL REFERENCES atores(id),
  tipo TEXT NOT NULL,
  alvo_tipo TEXT NOT NULL,
  alvo_id TEXT NOT NULL,
  alvo_campo TEXT,
  args_json TEXT NOT NULL,
  pai_json TEXT NOT NULL DEFAULT '[]',
  superada_por TEXT REFERENCES operacoes(id),    -- null = effective; set by resolver
  criado_em TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_operacoes_hlc ON operacoes(hlc_wall, hlc_counter);
CREATE INDEX idx_operacoes_alvo ON operacoes(alvo_tipo, alvo_id, alvo_campo);

CREATE TABLE sync_base (
  peer_id TEXT PRIMARY KEY,             -- the peer node_id this row pertains to (prod's, for uat)
  base_hlc_wall INTEGER NOT NULL,
  base_hlc_counter INTEGER NOT NULL,
  base_hlc_node TEXT NOT NULL,
  atualizado_em TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE propostas (
  id TEXT PRIMARY KEY,                  -- uuid for the proposta
  peer_origem TEXT NOT NULL,            -- sender node_id
  base_hlc_wall INTEGER NOT NULL,
  base_hlc_counter INTEGER NOT NULL,
  base_hlc_node TEXT NOT NULL,
  estado TEXT NOT NULL CHECK(estado IN ('aberta', 'mesclada', 'cancelada')),
  aplicadas_count INTEGER NOT NULL DEFAULT 0,
  conflitos_count INTEGER NOT NULL DEFAULT 0,
  criado_em TEXT NOT NULL DEFAULT (datetime('now')),
  mesclada_em TEXT
);

CREATE TABLE conflitos (
  id TEXT PRIMARY KEY,                  -- sha256 of sorted([op_local, op_remota])
  proposta_id TEXT NOT NULL REFERENCES propostas(id),
  op_local TEXT NOT NULL REFERENCES operacoes(id),
  op_remota TEXT NOT NULL REFERENCES operacoes(id),
  alvo_tipo TEXT NOT NULL,
  alvo_id TEXT NOT NULL,
  alvo_campo TEXT,
  estado TEXT NOT NULL CHECK(estado IN ('pendente', 'resolvido')),
  resolver_op_id TEXT REFERENCES operacoes(id),
  criado_em TEXT NOT NULL DEFAULT (datetime('now'))
);
```

## Op emission

Every existing mutation in `conteudo.ts` is wrapped to emit an op AND update read-model tables in the same transaction:

- `salvarFoto(arquivo, dados, mime)` → emits `foto.adicionar` (if new sha256) + `foto.vincular` (slug+idx).
- `excluirFoto(arquivo)` → emits `foto.desvincular` + `foto.remover` (if no other references).

Legacy photos get synthetic op backfill via migration v006: `foto.adicionar` + `foto.vincular` for each existing row in `fotos` + `foto_refs`, with `ator` = system node, `hlc` = `(criado_em, 0, node_id)`.

## Content-addressed storage

- `fotos` table already keys by filename; add `sha256` column (backfilled from current blob hashes).
- New photo uploads compute sha256; filename becomes `{sha256}.{ext}` internally.
- Resolver layer `{slug}-{N}.{ext}` → sha256 via `foto_refs` table (new: `{slug, indice, sha256}`).
- Legacy URLs continue to work via resolver lookup.

## Sync endpoints (both UAT and prod)

| Endpoint | Method | Notes |
|---|---|---|
| `GET /sync/api/manifesto` | GET | No auth |
| `GET /sync/api/ops?desde_hlc=X` | GET | Bearer token |
| `GET /sync/api/blob/:sha256` | GET | Bearer token |
| `POST /sync/api/proposta` | POST | Bearer; body = Proposta JSON; returns RelatorioMesclagem |
| `POST /sync/api/proposta/:id/blob/:sha256` | POST | Bearer; streaming bytes |
| `POST /sync/api/proposta/:id/resolver` | POST | Bearer; body = { resolucoes: [...] } |

All wrapped in SQLite transaction. `SYNC_TOKEN` env var on both apps.

## UI: `/admin/sync`

Feature-flagged by `SYNC_ENABLED=true`. On UAT always on; on prod optionally on (for receiving).

Three states:
1. **Sem mudanças** — base_hlc matches prod current; nothing to promote.
2. **Com mudanças pendentes** — N ops since base_hlc. Button "Abrir proposta de promoção".
3. **Proposta em revisão** — merge report loaded; per-conflict picker; "Enviar resolução" button.

Conflict picker UI per conflict:
- Split view: prod version vs UAT version (side by side with highlighted diff)
- Radio: `[ ] produção ganha  [ ] UAT ganha  [ ] criar cópia  [ ] manual...`
- Free-text comment (stored in resolver op's `detalhes.comentario`)

Bulk actions: "produção ganha todos", "UAT ganha todos" (toggles all radios).

## Rollback path

If a promoted op turns out wrong: admin emits a new `conflito.resolver` with opposite `ops_efetivas`/`ops_superadas`. Reducer re-evaluates; prior resolution is superseded. Audit trail preserved.

## Acceptance Criteria

### Functional — the 10 scenarios

- [ ] **01 clean add** — 20 photos on UAT, no prod conflict → promoted cleanly, visible on prod identical sha256s
- [ ] **02 prod advance** — UAT + prod add independent content → both land, UI shows "N novidades em prod"
- [ ] **03 prod wins default** — same-slug destaque conflict → default pick = prod, UAT op marked `superada_por`
- [ ] **04 UAT override** — admin picks UAT → resolver op records override, UAT version effective
- [ ] **05 copia** — admin picks "criar cópia" → new slug synthesized, both co-exist
- [ ] **06 idempotent retry** — POST same proposta twice → second returns `{ ja_aplicada: true }`
- [ ] **07 atomicity** — kill sync mid-transaction → prod state unchanged, proposta = cancelada
- [ ] **08 recursive resolution** — copia synthesizes slug collision → nested conflict opens → admin resolves → terminates
- [ ] **09 fresh UAT fork** — after merge + refork → UAT has ALL: previously-merged UAT changes + all prod concurrent changes (the trofeu-talentos event scenario)
- [ ] **10 reversibility** — admin regrets → new resolver op flips the override, state updates

### Testing procedure (executed on live UAT↔prod)

1. UAT at baseline (reforked from current prod — confirmed trofeu-talentos present)
2. Upload 5 photos to relato X on UAT
3. Set `SYNC_TOKEN` on prod (fresh secret)
4. Visit `/admin/sync` on UAT → "5 ops pendentes"
5. Click "Abrir proposta" → loads merge report
6. Expect `aplicadas: 5, conflitos: 0, novas_ops_remotas: 0`
7. Click "Promover" → blobs upload → success
8. Visit `https://quilomboaraucaria.org/blog/X` → 5 photos visible
9. Simulate conflict: on prod directly (via /admin/fotos) add a photo to same relato using slot that UAT also used
10. Re-open UAT /admin/sync → sees conflict → pick "produção ganha" → resolve
11. Verify prod photo wins; UAT op marked superseded; audit entry present
