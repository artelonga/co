## As

a user who already has a CO account (created via co.artelonga.com.br,
artelonga.com.br, or quilomboaraucaria.org)

## I Need

to navigate to yggdrasil-artelonga and be **already logged in** — no
email code, no separate yggdrasil account, no second JWT secret

## So That

"all universes feel like one CO" — the entire stack runs on one
identity authority. Yggdrasil stops minting its own JWTs with its own
secret and instead verifies CO's JWKS, the same pattern that worked
for quilombo (QB-12).

---

## Why this matters now

The yggdrasil-artelonga deploy notes say:

> "Same login as co" is implemented as the same UX (email-code → JWT),
> **not SSO**. Each app has its own JWT secret. If you want cross-app
> SSO later, we'd share the secret + align the sub claim format.

That "later" is now. Three pressures:

1. **The yggdrasil SMTP isn't configured** (only YGGDRASIL_JWT_SECRET is
   set on prod). Real fix isn't to wire SMTP — it's to remove the
   email-code flow on yggdrasil entirely.
2. **Two-way universe interop** (CO-207 — cross-universe tasks/messages)
   requires a single identity that flows between apps.
3. **Operational simplicity** — one secret to rotate, one user table,
   one recovery flow, one ban list.

The infrastructure for centralized auth is already 70% built:

| Piece | State |
|---|---|
| ES256 + JWKS at `/.well-known/jwks.json` | ✅ CO-186 |
| `/auth/co-handover` flow on receiving apps | ✅ quilombo via QB-12 |
| Cross-domain cookie on `.artelonga.com.br` | ✅ CO-184/205 |
| Bidirectional bridge (quilombo ↔ co) | ✅ CO-172/184 |
| **Yggdrasil verifies CO JWKS** | ❌ this ticket |

## Architecture

```
User on co.artelonga.com.br (already logged in)
         │
         │ clicks "Yggdrasil" or visits yggdrasil-artelonga.fly.dev
         │
         ▼
co.artelonga.com.br/auth/co-handover?return_to=https://yggdrasil-artelonga.fly.dev/auth/co-handover
         │
         │ CO checks: return_to host on safelist? YES (yggdrasil added in this ticket)
         │ CO signs short-lived (60s) ES256 JWT with the user's claims
         │ CO redirects → https://yggdrasil-artelonga.fly.dev/auth/co-handover?co_token=<jwt>
         │
         ▼
Yggdrasil /auth/co-handover handler:
   1. Reads co_token query param
   2. Fetches CO's JWKS at https://co.artelonga.com.br/.well-known/jwks.json
      (cached locally for 5 min)
   3. Verifies ES256 signature using the JWKS
   4. Extracts claims: sub (CO user_id), email, tier, usuario, exp, iat
   5. Provisions yggdrasil-local identity:
      - INSERT OR IGNORE INTO usuarios (email, user_id, co_user_id)
        VALUES (?, ?, ?) — links to the CO user_id
   6. Sets yggdrasil session cookie (yet to decide: own JWT signed by
      yggdrasil for in-app continuity, OR re-use the CO JWT directly)
   7. Redirects to the originally-requested path (lobby, /games/poker, etc.)
```

## CO-side changes

### 1. Add yggdrasil to `is_allowed_return_to`

`co-web/src/recovery_routes.rs` (the function is also re-used by
`/auth/co-handover` per CO-186) currently safelists:

```rust
host == "quilomboaraucaria.com.br"
    || host == "quilomboaraucaria.org"
    || host == "artelonga.com.br"
    || host.ends_with(".artelonga.com.br")
```

The fourth branch ALREADY covers `yggdrasil-artelonga.fly.dev` (it
ends with `.artelonga.com.br`)? No — `.fly.dev` ≠ `.artelonga.com.br`.
Add explicitly:

```rust
host == "yggdrasil-artelonga.fly.dev"
    || host == "yggdrasil.artelonga.com.br"   // future custom domain
```

### 2. `users.yggdrasil_user_id` column (optional, for bridging)

If we want yggdrasil-local user records to round-trip back to CO (so
"yuri on yggdrasil" is the same user as "yuri on co"), add a column on
the CO side:

```sql
ALTER TABLE users ADD COLUMN yggdrasil_user_id TEXT;
CREATE INDEX IF NOT EXISTS idx_users_yggdrasil
    ON users(yggdrasil_user_id);
```

Idempotent boot migration.

### 3. (Optional) `ensure_yggdrasil_user_for_co`

Storage helper mirroring `ensure_quilombo_user_for_co` (CO-184). Used
by CO-207 (cross-universe tasks) more than by this ticket — but file
the spec here so the implementer can decide whether to land it now or
defer.

```rust
pub fn ensure_yggdrasil_user_for_co(
    &self,
    co_user_id: &str,
) -> anyhow::Result<()> {
    // Yggdrasil-side: insert into yggdrasil/usuarios where co_user_id
    // matches; no-op if already exists. This runs CO-side via an HTTP
    // call to yggdrasil's bridge endpoint (since yggdrasil has its
    // own DB, we can't INSERT directly).
}
```

In v1, can be deferred — yggdrasil's `/auth/co-handover` handler
provisions the user lazily on first login.

## Yggdrasil-side changes (YG-N follow-up ticket)

Lives in the **yggdrasil repo** as a sibling ticket. Roughly:

1. Add `jsonwebtoken` + `reqwest` (already in tree)
2. New module `co_jwks.rs` — fetches + caches JWKS from
   `https://co.artelonga.com.br/.well-known/jwks.json` (5-min TTL)
3. New handler `auth::co_handover` mounted at `/auth/co-handover`:
   - Parses `co_token` query param
   - Validates ES256 via JWKS
   - Provisions local user (`co_user_id` column on `usuarios`)
   - Mints local session cookie OR returns the CO JWT directly
4. Update lobby/login UI:
   - Anonymous landing: instead of "Entrar com email →" link to
     `https://co.artelonga.com.br/login?return_to=https://yggdrasil-artelonga.fly.dev/auth/co-handover`
   - Logged-in: same as today (lobby visible)
5. Keep `POST /api/v1/auth/code` for backward compatibility for one
   release cycle; mark deprecated in CHANGELOG; remove in YG-N+1.
6. Cookie domain: set yggdrasil's session cookie on `.artelonga.com.br`
   once yggdrasil has a custom domain. For now (`*.fly.dev`), the
   cookie is third-party — CO's session won't leak; yggdrasil's own
   session is fine on the `fly.dev` apex.
