## As

A visitor or operator landing on co.artelonga.com.br for the first time (or the 100th)

## I Need

The relationship between **deployable platform units** (co, artelonga, quilombo, yggdrasil, rfq, comunicacao), **content universes**, and **sub-universes** (e.g. yggdrasil → shandara, tagmar, godot) to be **visually obvious** in the navigation, sidebar, and breadcrumbs — not inferred from URL structure or memorized.

Concretely:

- A user looking at the sidebar should immediately understand: *"these 5 things at the top are the platform's deployable units; these things below them are projects within the current universe; these things in the right pane are sub-universes nested inside the current one."*
- The `sidebar.co_dev_ship` button (currently confusing per user report) should either explain what it does or be removed/relocated.
- Visiting a sub-universe like `/yggdrasil/shandara` should make clear: *"you're inside the Shandara sub-universe, which is part of Yggdrasil, which is one of the platform's deployable units."*

## So That

- The information architecture stops being a leaky abstraction. Users currently see 5+ sister-deployable units in a sidebar without any signal that they're peers, not sub-items of `/co`. The user reports: *"Confusing that 5 sub universes are part of whole, clarify and review"*.
- New visitors stop bouncing because they can't tell what they're looking at.
- The operator stops second-guessing button placement (`co_dev_ship` weirdness is one symptom of a broader IA gap).

## Context

### The three layers, today

```
Layer 1 — Deployable units (Fly.io apps)
  co.artelonga.com.br        ← the platform itself
  artelonga.com.br           ← static site
  quilomboaraucaria.org      ← Fly app
  yggdrasil.artelonga.com.br ← Fly app
  rfq.fly.dev                ← Fly app
  (comunicacao — lives inside co)

Layer 2 — Content universes (folders served by any deployable)
  Each deployable can host multiple universes
  Each universe has: key, name, slug, members, entries
  Top-level: /co, /artelonga, /quilomboaraucaria, /yggdrasil, /rfq

Layer 3 — Sub-universes (folders nested inside a universe)
  Defined by `_universe.yaml` in a child folder
  Example targets (per CO-277 design):
    /yggdrasil/shandara
    /yggdrasil/tagmar
    /yggdrasil/godot
```

### What the user actually sees today

The sidebar mixes layers without visual distinction. The 5 deployables look identical to projects within the current universe. The `co_dev_ship` button (a dev-only shortcut?) sits in the user-visible sidebar with no explanation. Sub-universes (when they exist) aren't visually grouped under their parent.

### The confusion this causes

- A first-time visitor to `co.artelonga.com.br` clicks on `quilomboaraucaria` in the sidebar and is unclear whether they're entering a project, leaving the platform, or navigating a sub-universe.
- The operator looks at `co_dev_ship` and can't immediately remember what it does or which audience it's for.
- Yggdrasil's RPG sub-universes (Shandara, Tagmar, Godot) — once scaffolded per CO-277 — will need a visual home distinct from their parent's tasks.

## Decision

### Three IA primitives, three visual treatments

| Layer | Visual treatment | Example |
|---|---|---|
| **Deployable units** ("platforms") | Top-level nav bar across the header; subtle external-link icon when crossing deployables; each gets a brand color tied to its identity | A pill-style row at the top: `[CO] [ArteLonga] [Quilombo] [Yggdrasil] [RFQ]` |
| **Content universes** (current scope) | Left sidebar — only universes the current deployable serves; current universe highlighted; switcher dropdown for owned/subscribed | Sidebar header: "Universe: ArteLonga ▾" |
| **Sub-universes** (nested via `_universe.yaml`) | Indented under their parent in the sidebar; tree-style expansion; visual nesting depth indicator | Sidebar tree: `Yggdrasil > Shandara, > Tagmar, > Godot` (collapsible) |
| **Projects** (within a universe) | Left sidebar below universe header; click navigates to project board | "Projects in ArteLonga: [Default] [Marketing] [..]" |
| **Dev/operator tools** (`co_dev_ship`, admin links) | Separate "Tools" section at the bottom of the sidebar, gated by `if (isAdmin || isDevMode)`; clear labeling | "Tools: Ship task · Deploy dashboard · Logs" |

### `co_dev_ship` audit (sub-task)

Find the button, document what it does, decide:

- If it ships a task via `co-auto` HTTP (post-CO-278-D) → relabel "Ship via co-auto" + gate to admin
- If it's a now-stale dev shortcut → remove
- If it's a useful end-user action mislabeled → rename + describe with a tooltip

### Sub-universe sidebar pattern

When the current universe has children (per CO-277's `discover_subspaces`), render them as an indented section:

```
▼ Yggdrasil (you are here)
   ├── Shandara
   ├── Tagmar
   └── Godot
   ─────────
   Projects:
   ├── Default
   └── RPG bot
```

Click on a child → navigate to `/{parent}/{child}` → that becomes the active universe with breadcrumb `Yggdrasil › Shandara`.

### Breadcrumbs everywhere

Every page header gets a breadcrumb of the form:

```
Platform: CO  ›  Universe: Yggdrasil  ›  Sub-universe: Shandara  ›  Project: Default  ›  Entry: YG-64
```

Truncated gracefully when the trail is shorter (no project, no sub-universe, etc.). Each segment is clickable and navigates to the appropriate scope.

## Scope

### 1. Sidebar restructure

`co-web/static/variants/a/modules/sidebar.js` (or wherever it lives):

- Three labeled sections: **Platforms**, **This universe**, **Tools**
- Platforms section: hardcoded list of 5 deployables + external-link icon if URL differs from current origin
- This-universe section: universe switcher dropdown + project list + sub-universe tree (when present)
- Tools section: admin-gated, clearly labeled, `co_dev_ship` button moves here (with new label or removed)

### 2. Breadcrumbs component

New SPA component `breadcrumbs.js`:

- Renders the platform › universe › sub-universe › project › entry trail
- Each segment is a link
- Hides on screens narrower than 480px (collapses to back arrow)

### 3. `co_dev_ship` audit + decision

- Grep `co_dev_ship` across the SPA
- Document current behavior
- Apply one of: relabel, remove, or relocate based on findings
- If keeping: add a tooltip explaining what it does, who it's for, what happens after click

### 4. Sub-universe sidebar tree (depends on CO-277)

When CO-277's `/api/v1/universes/{slug}/subspaces` (TBD) returns children, render them as a tree. If CO-277 hasn't exposed an HTTP endpoint yet, derive from `entries` filtered to `entry_type: universe` or similar.

### 5. Visual differentiation

- Platforms: pill-style top nav, white-on-dark
- Universes: sidebar, current-state highlighting
- Sub-universes: indented under parent, lighter background
- Tools: bottom-of-sidebar, muted color, "Tools" header

### 6. Playwright spec

Assert:

- Sidebar has three labeled sections
- Clicking a sister deployable opens its URL (in new tab or current — TBD)
- Breadcrumbs render the correct trail on `/yggdrasil/shandara/SHN-1` (once sub-universe data exists)
- `co_dev_ship` is either gated to admin or removed

## Why now

User reported three distinct symptoms in one breath:

1. *"sidebar.co_dev_ship button is weird"* — one symptom
2. *"Confusing that 5 sub universes are part of whole, clarify and review"* — another symptom
3. (Implicit) the missing default-project + sub-universe seed → no obvious place to land

All three trace back to the same root: the IA layer hasn't been intentionally designed since CO-272 added the dev-tasks adapter and CO-277 added recursive subspaces. The platform now has 5 deployables × N universes each × M sub-universes — and the SPA's mental model is still "one universe = one board". Aligning the SPA to the actual architecture is overdue.

This also pairs naturally with CO-273 (deployment dashboard already understands the 5 platforms) and CO-278 (public API — needs stable, documented IA before sub-stories ship).
