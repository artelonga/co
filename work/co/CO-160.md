## As

a reader landing on `mbya/refs/GNDicLex.md` or any reference card with `type: reference` and `medium: pdf`

## I Need

the SPA to render the bound PDF **inline** in the entry view — pageable, searchable, zoomable — so I can read it without downloading. The download button stays as an explicit opt-in; the default is to read in place.

## To

match the pattern at <https://quilomboaraucaria.org/portfolio> (static Quartz site that embeds portfolio PDFs as readable previews) and turn the platform into a real reading surface, not a metadata listing.

---

## Implementation: PDF.js viewer

[PDF.js](https://mozilla.github.io/pdf.js/) is the Mozilla-maintained pure-JS PDF renderer; it's what most "PDF preview" features in browsers and tools (Firefox built-in, GitHub, GitLab, etc.) use. Self-hosted, no external dependency, works offline. ~2 MB for the viewer bundle.

### SPA detection

In the entry view (`co-web/static/variants/a/app.js`, the renderer that calls `md.renderMarkdown`):

```js
function shouldRenderInlinePdf(entry) {
  const fm = entry.frontmatter || {};
  return (
    fm.type === 'reference' &&
    fm.medium === 'pdf' &&
    fm.file &&
    fm.file.endsWith('.pdf')
  );
}

function pdfUrlFromCard(universe, entry) {
  // Reference card lives at e.g. mbya/refs/GNDicLex.md;
  // the bound PDF is at mbya/refs/GNDicLex (1).pdf as declared in `file:`.
  // It's served by the asset endpoint via its sha256 (CO-156 binds card → blob).
  // Fallback: assume the asset endpoint resolves the path-relative file.
  if (entry.frontmatter.blob_sha256) {
    return `/api/v1/universes/${universe}/assets/${entry.frontmatter.blob_sha256}`;
  }
  // Path-relative fallback (CO-156 backfill populates blob_sha256 eventually):
  const dir = entry.path.split('/').slice(0, -1).join('/');
  const filename = entry.frontmatter.file;
  return `/api/v1/universes/${universe}/vault/${dir}/${encodeURIComponent(filename)}`;
}
```

### Render

The `.md` body is rendered as usual *above* the inline viewer; the PDF appears below:

```html
<article class="entry">
  <h1>{{ frontmatter.title }}</h1>
  <div class="md-body">{{ rendered markdown body }}</div>

  <!-- inline PDF -->
  <div class="pdf-viewer">
    <iframe src="/static/pdfjs/web/viewer.html?file={{ pdf_url }}"
            width="100%"
            height="800"
            style="border: 0; border-radius: 8px;"></iframe>
    <div class="pdf-viewer-actions">
      <a href="{{ pdf_url }}" download class="pdf-download-btn">Baixar PDF</a>
      <button class="pdf-fullscreen-btn">Tela cheia</button>
    </div>
  </div>
</article>
```

The `<iframe>` to PDF.js's bundled viewer is the safest cross-browser path; the `?file=` parameter tells it where to fetch the PDF.

## Bundle hosting

`co-web/static/pdfjs/` ships the PDF.js dist bundle (versioned, downloaded once at build/deploy time). Same content-type / cache-control as other static assets. Adds ~2 MB to the docker image — acceptable.

Alternative: load PDF.js from a CDN (`cdn.jsdelivr.net/npm/pdfjs-dist`). Saves the image size but adds an external dep + offline failure mode. Vendoring is the better default for this platform's "you own your data" stance.

## Lazy load

PDF.js is heavy. Don't load the viewer JS unless the entry actually has an inline-PDF section. The asset already lazy-loads (CO-149 range support); the viewer JS is `<iframe>`-isolated so the SPA's main bundle stays small.

For very long PDFs (e.g. `Livro Guarani-digital.pdf` at 3.2 MB / ~150 pages), the iframe + range requests means only the visible pages are fetched — the user pays the network cost only for pages they scroll to.

## Other media — not in scope here

This ticket is **PDF only**. Patterns for other media:

- **Images** (jpg/png/webp) — already inline via `<img loading="lazy">` (CO-150).
- **Video** (mp4/webm) — already inline via `<video preload="none">` (CO-150).
- **Audio** (mp3/ogg) — `<audio preload="none">` follow-up.
- **YouTube** (URL refs) — embed via `<iframe src="https://www.youtube.com/embed/<id>">` when `medium: video` + `platform: youtube`. Separate ticket.
- **HTML/web archive** — not in scope yet; could open in iframe with sandboxing.

- [ ] Entry view detects `type: reference` + `medium: pdf` + valid `file:` and renders the inline viewer below the markdown body
- [ ] Bytes only fetched when iframe is visible (browser native; verify via dev tools network tab)
- [ ] `Baixar PDF` button explicitly downloads the file with the original filename
- [ ] `Tela cheia` button toggles the iframe to fullscreen via Fullscreen API
- [ ] On a private universe, the iframe URL resolves through the same auth as the entry view (cookie / bearer); no leakage to anonymous viewers
- [ ] Test: view `mbya/refs/GNDicLex.md` on prod and the dictionary renders inline, pageable

## Out of scope

- Annotation / highlighting (PDF.js supports it but persistence layer is separate work).
- OCR overlay for image-only PDFs (combine with CO-157 OCR follow-up).
- Server-side rendering of PDFs to images for thumbnails. Cards already get a generic "PDF" icon when no thumb is provided; thumb generation is CO-156-extension territory.
- E-book formats (epub, mobi). Different viewers; same pattern. File when needed.
