## As
A user adding a new repo (public or private) to a universe in CO

## I Need
The universe → local-repo binding to be runtime configuration (one API call or settings UI), not a hardcoded mapping in Rust source

## So That
Adding a new universe/repo pairing doesn't require a code change, rebuild, or deploy.

## Problem (current state)

`co-web/src/server/seed_orchestrator.rs` hardcodes:
```rust
let mappings: &[(&str, &str, &[&str])] = &[
    ("artelonga", "ArteLonga", &["docs", "content"]),
    ("yggdrasil", "yggdrasil", &["docs", "content"]),
    ...
];
```

Every new repo I want CO to ingest requires editing this file, rebuilding, redeploying. Content (the path) lives inside deployable code. That's wrong.

## Design

### Schema
Add two nullable columns to `universes`:
```sql
ALTER TABLE universes ADD COLUMN local_repo_path TEXT;
ALTER TABLE universes ADD COLUMN content_subdirs TEXT;  -- JSON array
```

- `local_repo_path`: absolute or `~`-relative path to the source repo (e.g., `~/projects/ArteLonga`)
- `content_subdirs`: JSON array of subdirs to walk (e.g., `["docs","content"]` or `[""]` for flat)
- Both NULL on existing universes → no auto-ingest, no behavior change

### API
- `GET /api/v1/universes/<key>/source` → returns current binding
- `PATCH /api/v1/universes/<key>/source` → owner-only, sets path + subdirs
  ```json
  {"local_repo_path": "~/projects/yuri", "content_subdirs": [""]}
  ```
- Validation: path must be readable, no symlink escape

### Seed orchestrator (refactor)
`run_sister_repo_seeds` becomes:
```rust
SELECT key, local_repo_path, content_subdirs FROM universes WHERE local_repo_path IS NOT NULL
```
Then for each row: expand `~`, walk subdirs, upsert entries. Hardcoded mapping array DELETED.

### One-time migration
Backfill the existing hardcoded mappings into the new columns so today's behavior is preserved:
```rust
UPDATE universes SET local_repo_path = '~/projects/ArteLonga', content_subdirs = '["docs","content"]' WHERE key = 'artelonga';
-- ... etc for each existing pair, including yuri ...
```
Runs once via migration version; idempotent (only sets when NULL).

### CLI integration
`co launch` (CO-322) already provisions a universe from CWD. Update it to also set `local_repo_path` to that path, so the new universe is automatically tied to the source.

### CO UI
Universe settings page gets a "Local source" panel: text field for path, multi-select for subdirs, save button → calls PATCH. Owner-only.

## Acceptance

- [ ] `universes` schema has `local_repo_path` + `content_subdirs` columns (nullable, default NULL)
- [ ] `PATCH /universes/<key>/source` sets them; auth = owner only
- [ ] Seed orchestrator reads from DB, no hardcoded mapping array
- [ ] One-time migration backfills the existing 7 mappings (artelonga, yggdrasil, etc.) + yuri
- [ ] `co launch` sets `local_repo_path` on the new universe automatically
- [ ] Settings UI shows + edits the binding
- [ ] Adding a brand-new universe pointed at a new repo works via API alone — no code change, no rebuild, no deploy

## Blast radius
- 1 schema migration (2 new columns + 1 backfill UPDATE)
- ~80 lines refactor in `seed_orchestrator.rs`
- 1 new route handler (~50 lines)
- ~30 lines SPA settings UI
- 1 small extension in `co launch`

## Why now
User feedback 2026-06-01 (rejected PR that added another hardcoded mapping): "any content from any repository [...] should be integrable (database only) without a deploy". This is the structural fix that makes that true.

This also unblocks the yuri.artelonga.com.br vision (CO-323..329) — once the binding is configurable, the yuri universe ingestion just needs a one-row UPDATE, not a PR.

## Not in scope
- Remote-repo polling (git pull from a URL on a cadence) — separate spec
- File-watcher live sync — separate spec
- Permissions on the *source* repo (read-only assumed)
