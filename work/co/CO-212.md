## As

a user who wants to read a CO universe with beautiful typography +
reactive UI without setting up Obsidian or installing anything

## I Need

a **Svelte + TypeScript** web app at `co.artelonga.com.br/viewer/{slug}`
that consumes the public Universe Content API (CO-211) and renders
markdown content beautifully — read-mostly experience, focused on
prolonged reading sessions

## So That

CO gets a "cloud reader" experience separate from the operational SPA
(co-web). Users have **choice**: vanilla SPA for ops/editing, Svelte
viewer for reading, Obsidian for serious editing. Same backend, three
frontends, no rewrite forced on existing surfaces.

---

## Why Svelte + TS for this specifically

Already established in [docs/markdown-renderers.md] and discussed
2026-05-13:

- **TypeScript**: small scoped app, types catch bugs at compile, refactors
  safer than ~6k lines of vanilla JS
- **Svelte**: reactive primitives ($state, $derived) instead of manual
  re-renders; less code; better animation patterns
- **Vite**: modern dev server, fast HMR
- **Scope is small**: read-mostly viewer, not full platform

Not chosen to replace co-web SPA — that's the operational/admin surface
and stays vanilla per the documented strategy.

## Features

### Read-focused

- Beautiful typography (max-width 65ch, font choice per universe theme)
- Dark / light / sepia / system themes
- Code block syntax highlighting (Prism or Highlight.js)
- Mermaid diagram support (lazy-loaded)
- Math via KaTeX
- Cross-link preview on hover (popover with first paragraph)
- Reading progress bar
- Table of contents for long entries
- Search within universe (client-side fuse.js initially; server-side later)

### Universe-aware

- Loads universe metadata from `GET /api/v1/universes/{slug}`
- Applies universe theme tokens (from manifest, CO-191 universe-info)
- Respects universe visibility (public-static, public-subscribable,
  private-with-token)
- Auth-aware: if user has session cookie for `.artelonga.com.br`,
  authenticated requests work transparently

### Performance

- SSR via SvelteKit (Vercel/Cloudflare Pages adapter) for first-paint
- Client-side navigation thereafter
- Image lazy-loading
- Critical CSS inlined
- Target: LCP < 1.5s, TTI < 2s on 3G

### Telemetry (per CO-210)

- Embedded `co_viewer_telemetry` JS module
- Page views, 404s, render times → `/api/v1/telemetry/events`
- Privacy respected: `localStorage` opt-out, no PII

## Deployment

Option A — same Fly app (subdomain or path):

- `co.artelonga.com.br/viewer/...` (path-based)
- Served by co-web alongside SPA

Option B — separate Cloudflare Pages / Vercel deploy:

- `view.artelonga.com.br` or `viewer.artelonga.com.br`
- Separate CI/CD
- Pro: zero impact on co-web; Con: yet another deploy target

**Recommendation: Option A initially.** Same app, same auth cookie,
easier debug. Move to B if performance justifies separate edge.
