GIVEN the platform target is thousands of universes per user (worst case ~10K × 1M users = 10B universes) and thousands of concurrent requests, and the current architecture (single SQLite file, single Fly machine, mutex-locked storage) caps writes around 1K/sec under no contention and far less under realistic load,
WHEN we land per-universe SQLite with global metadata + LiteFS replicas, a job queue, caching, rate limiting, and object storage,
THEN Co scales to platform-level traffic without rewriting application logic per feature.

## Sub-tasks (sequenced)

- CO-77 — Per-universe SQLite + global metadata DB + LiteFS read replicas
- CO-78 — Job queue + worker pool (doc gen, sync, indexing, changelog)
- CO-79 — Caching layer (manifest, theme, hot queries) + CDN strategy
- CO-80 — Per-tier rate limiting + quota
- CO-81 — Object storage for blobs + filesystem sharding

## Constraints driving the design

- Writes per universe are independent (no cross-universe transactions in normal flow) — sharding works
- Reads dominate writes (~10:1) — replication helps
- Manifest reads are hot — caching is critical
- Doc-gen and sync ops are non-real-time — queue them
- Most blobs are large + immutable (images, attachments, generated docs) — object storage is cheaper than block storage at TB scale

## Acceptance (epic-level)

- Sustained 10K req/sec across all universes without 99p latency degradation
- Single-universe writes of 100/sec sustained for 1 hour
- Read replicas serve > 80% of read traffic
- Backup of any single universe completes in < 30s
- Filesystem holds 10M universes without dirent-lookup degradation
