## Contexto
Vamos **vender storage as a service** a parceiros. Antes de implementar, precisamos do
**desenho** que amarra as peças que já existem/estão saindo: o `StorageBackend` (CO-458),
escopos de token (CO-448), envelope de API (CO-456), telemetria/usage (CO-453), quota
(CO-80). Esta tarefa produz **um design doc** (`docs/architecture/staas-partners.md`),
**sem código e sem migração** — o contrato que as tarefas de impl seguirão.

## Entregável: `docs/architecture/staas-partners.md`
Deve cobrir, concretamente e amarrado ao código atual:

1. **Modelo multi-tenant**: parceiro → **namespace** de storage isolado (prefixo de chave
   no `StorageBackend`); isolamento, nomeação, e como mapeia em `blob_refs` (CO-458).
2. **API de parceiro** (forma, usando o envelope CO-456): `PUT/GET/DELETE/LIST` escopados
   ao namespace do parceiro; versionada `/api/v1`; paginação; limites de tamanho.
3. **Auth & least-privilege**: tokens de parceiro via capacidades CO-448
   (`storage:read/write` por namespace); como emitir/revogar; isolamento entre parceiros.
4. **Metering & billing hooks**: usage = Σ(`blob_refs.size` × tempo) + operações; fonte
   na telemetria CO-453; como expor `/usage` por parceiro; ganchos de cobrança (sem
   gateway de pagamento aqui — só os pontos de medição).
5. **Quota & rate-limit**: enforcement via CO-80 (bytes armazenados + req/min por tier de parceiro).
6. **Backends de parceiro**: parceiro pode trazer o próprio backend (S3/compatível) como
   impl alternativa do `StorageBackend` (CO-458) — config por parceiro; trust boundary.
7. **Durabilidade & backup**: como o backup local (CO-459) / S3 (CO-81) se aplica por namespace.
8. **Roadmap de impl**: decompor em tarefas CO-N sequenciadas (namespaces → API → auth →
   metering → quota → partner-backend), com dependências e o que cada uma migra.

## So that
As tarefas de implementação do StaaS têm **um contrato escrito** — parceiros, namespaces,
auth, medição e cobrança — em vez de serem inventadas ad-hoc, e o dono pode aprovar a
arquitetura antes de gastar opus em impl.

## Não no escopo
- Implementar qualquer rota/handler (design only).
- Gateway de pagamento real (só os ganchos de medição).
- Mudar o `StorageBackend` (CO-458 define; aqui só consome no papel).
