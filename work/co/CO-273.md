## As

An operator (yuri) or curious visitor wanting one-glance view of every deployable unit's runtime state

## I Need

A single page at `/admin/deployments` (or `/deployments` for the public-friendly view) that shows for **each of the 5 deployable units** (artelonga, co, quilomboaraucaria, yggdrasil, rfq) **and the comunicacao content surface**:

| Column | Source |
|---|---|
| Unit | hardcoded list |
| URL | hardcoded list |
| Live version | `GET /api/health` on each unit |
| Fly app name | hardcoded mapping |
| Machine ID | `flyctl machine list -a <app>` |
| Region | same |
| VM size (CPU/RAM) | same |
| State (started / stopped / suspended) | same |
| Last deploy date | `flyctl status -a <app>` or fly API |
| Last deploy image | same |
| Tag matching live version | parse CHANGELOG / git tags |

## So That

Operator can answer at a glance:
- *"Which units are deployed and healthy right now?"*
- *"What VM size is each running on? Should I downsize/upsize?"*
- *"When was the last deploy of each unit?"*
- *"Is the live version matching the latest tag, or is something behind?"*

Today: this requires 5 separate `flyctl status` invocations + 5 separate `curl /api/health` + manual diff against CHANGELOG. Tedious.

## Context

### Data sources

1. **fly.io API** (`https://api.machines.dev/v1/apps/<app>/machines`) — needs a Fly API token in `CO_FLY_API_TOKEN` secret
2. **Each unit's `/api/health`** — publicly available, returns `{ status, version }`
3. **Local cache table** — `deployment_snapshots(unit TEXT, snapshot_at INT, machine_id, region, vm_size, state, image, version)` — populated by a periodic worker, surfaced read-only by the dashboard route
4. **CO's own CHANGELOG** — for matching live version to release notes (already in DB post-CO-261)

### Why "centralized"

User's exact words: *"a single centralized page for deployment apis statistics (eg what machine is it running, machine size, status etc)"*. The page is the **single pane of glass**.

### Public vs admin

Two options:
- **Admin only** (`/admin/deployments`) — gated by `require_admin` middleware. Shows machine IDs, sizes, internal details.
- **Public version** (`/deployments`) — strips internal IDs, shows: unit, URL, live version, healthy/down, last deploy date. Useful for users to know "is the platform up?".

v1 = admin only. v2 = sanitized public version.

## Scope

### Backend

- New table `deployment_snapshots` (migration v16 or whatever's next)
- New module `co-web/src/admin/deployment_dashboard.rs`:
  - `GET /api/v1/admin/deployments` → returns cached snapshots
  - `POST /api/v1/admin/deployments/refresh` → triggers a manual refresh (calls fly API for each app + curls each /api/health)
- New worker `co-web/src/platform/deployment_snapshot_worker.rs`:
  - Implements `Worker` trait (CO-223 pattern)
  - Tick interval: 5 minutes
  - For each unit in hardcoded list, calls fly API + /api/health, persists snapshot
- Config: `CO_FLY_API_TOKEN` env var (only set on co-artelonga, not on sister apps)

- Status dot color: green = healthy, yellow = stale snapshot (>1h since last refresh), red = unreachable
- Click a row → expands to show: full machine ID, image SHA, version vs latest tag (highlight if drifted), CHANGELOG link
- "Atualizar agora" button → POSTs to refresh endpoint, repolls every 10s until snapshot timestamp advances

### Worker reliability

The deployment_snapshot_worker MUST handle:
- Fly API rate limiting (back off on 429)
- Network failures (don't crash; mark snapshot as stale)
- One unit's failure shouldn't block others
- Use `tokio::join!` to fan out across all 6 units in parallel

## Acceptance

- `GET /api/v1/admin/deployments` (as admin) returns JSON for all 6 units with cached snapshot data
- `/admin/deployments` page renders the table above with live data
- Background worker refreshes every 5 min; manual refresh button works
- Snapshots persist across server restarts (deployment_snapshots table)
- Public deployment page (`/deployments` — v2) deferred to follow-up ticket if needed
- New Playwright spec asserts the admin page renders with at least one row visible

## Blast radius

- ~200 LOC Rust (worker + dashboard route + table migration)
- ~150 LOC SPA (new view module + CSS)
- 1 new env var (`CO_FLY_API_TOKEN`)
- 1 new fly secret to provision

## Why now

User asked for it directly. Plus the session has produced 20 tags across 6 deployable units — operationally this dashboard would have saved time during the deploy loops (manually flyctl status'ing 5 apps).
