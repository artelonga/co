## Purpose

Time-boxed spike to validate whether CO should adopt the layered architecture pattern from `alineaos/gerenciador-de-bibliotecas` (domain entities + DTO families + repository traits + service layer + thin controllers). Refactor ONE module (`entries`) as proof-of-concept; measure the cost/benefit; recommend full / partial / no adoption.

**This is NOT an implementation spec.** Output is a decision document + a branch with the refactored entries module. No merge to main without follow-up specs.

## Box

- **Duration**: 3 working days (24 person-hours)
- **Scope**: `entries` module only (one entity, one feature area)
- **Branch**: `spike/CO-390-layered-entries` — do NOT merge to main
- **Stop condition**: at hour 24, write the decision doc regardless of completion state

## Hypothesis (what we're testing)

> Adopting Spring Boot-style layering (domain / dto / repository / service / controller / mapper) for the `entries` module will:
> 1. Improve test coverage of business rules (target: 50% → 85% line coverage on service layer)
> 2. Make OpenAPI documentation richer (target: per-endpoint request + response schemas instead of free-form `Entry`)
> 3. Add < 60% LOC overhead per entity (boilerplate cost)
> 4. Not break wire compatibility (HTTP responses must be byte-identical for existing clients)

If 1+2+4 pass and 3 holds within budget → recommend full adoption (extend to other modules in v3.x).
If 3 fails OR 4 breaks → recommend partial adoption (DTOs + service layer only).
If 1+2 don't improve → recommend reject.

## Method

### Day 1 — read + plan

- Read `alineaos/gerenciador-de-bibliotecas` source (focus: `BookController`, `BookService`, `BookRepository`, `Book` entity, `BookCreateRequest/Response/Filter/...` DTOs, `BookMapper`)
- Inventory CO's current `entries` shape: which files, which lines, what mixes concerns
- Sketch the target Rust structure (see `docs/spikes/library-manager-case-study.md` "What CO-style adoption looks like" section)
- Output: `docs/spikes/library-manager-plan.md` (what files will be added/changed)

### Day 2 — refactor

- Create `co-web/src/domain/entity/entry.rs` (pure type, no rusqlite/axum deps)
- Create `co-web/src/dto/entries/` with 6 DTOs (create_request, create_response, update_request, filter, basic, info)
- Create `co-web/src/repository/entry_repository.rs` (trait + sqlite impl behind trait)
- Create `co-web/src/service/entry_service.rs` (business rules: anon-100-entry limit, type validation, visibility check)
- Create `co-web/src/mapper/entry_mapper.rs` (Domain ↔ DTO)
- Refactor `co-web/src/content/entry_routes.rs` to be a thin controller: 1 axum handler per route → `service.create_entry(req)` → `mapper::to_response(domain)`
- Keep all existing tests green — wire compatibility is non-negotiable

### Day 3 — measure + decide

- Run benchmarks:
  - LOC delta per file
  - Test coverage on service layer
  - `cargo build` time delta
  - Resulting `openapi.yaml` size + endpoint richness
- Run full Playwright suite + e2e against refactored module
- Verify wire compatibility: diff HTTP responses before/after using saved JSON fixtures
- Write `docs/spikes/library-manager-decision.md`:
  - Final metrics table
  - Hypothesis pass/fail per item
  - Recommendation: full / partial / reject
  - If full or partial: phased adoption plan (per-feature ordering)
  - If reject: explanation of why Rust ergonomics defeat the gains
- Push the spike branch (do not merge) for archival

## Not in scope

- **Refactoring other modules** (users, universes, etc.) — only entries
- **Database schema changes** — same SQLite tables, no migration
- **Cross-deployment effects** — single-process scope
- **Performance benchmarking beyond build time** — defer to follow-up if adopted
- **Library / dependency changes** — pure refactor with existing crates
- **Adoption decision for sister repos** (Yggdrasil, ArteLonga) — CO-only scope
- **Auto-derivation macros** — if the spike says "yes but boilerplate is painful", a follow-up spike can explore macros

## Why this is a spike, not a feature

Per CO-368 (scrum entry types), a `spike` is a time-boxed exploration to reduce uncertainty. It produces a decision, not a feature. Doing the full refactor without first knowing the cost would be a multi-month commitment based on a guess. 3 days to know is cheap.
