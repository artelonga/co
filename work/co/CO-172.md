## As

a Quilombo Araucária user who registers at `quilomboaraucaria.com.br`

## I Need

my account to also be a CO account so that:
- I can log in to other artelonga-family universes with the same credentials,
- "Esqueci minha senha" on quilomboaraucaria.com.br redirects me to `co.artelonga.com.br/recover` and the reset Just Works,
- one inbox / phone, one password, one set of recovery channels — never duplicated per deployment.

## So That

CO-166 (central auth) and CO-165 (recovery flow) actually deliver their stated value to the only deployment that has real signups today.

---

## Current state (1.88.4)

- `quilomboaraucaria.com.br` runs the same `co-web` binary as `co.artelonga.com.br` — same DB, same code, same registry. They're not separate deployments yet, but the user is treating them as such (and that's the planned direction).
- `quilombo_usuarios` table holds quilombo-specific signups with their own `senha_hash` (Argon2id), separate from `users.password_hash`.
- `quilombo_usuarios.linked_co_user_id` already exists (CO-167 prep) but is never populated — quilombo signups don't currently create a corresponding `users` row.
- `users.email` (CO-165) gets auto-promoted to a verified recovery channel on every boot via `backfill_email_recovery_channels()`. **`quilombo_usuarios.email` does not.**
- `POST /api/quilombo/auth/login` returns `missing_email: true` for users without an email — that signal is already in the API.

## Design

### Phase 1 — Mirror quilombo signup into `users`

Every successful signup at `POST /api/quilombo/auth/registrar` (and the email-set path `PUT /api/v1/quilombo/perfil`) makes a CO `users` row:

```rust
// in quilombo_routes::registrar (and atualizar_perfil when email is set)
let co_user_id = storage.ensure_co_user_for_quilombo(
    &quilombo_user.id,
    quilombo_user.email.as_deref(),    // may be None at signup time
    &quilombo_user.senha_hash,         // reuse the Argon2 hash — no plaintext exposure
)?;
storage.link_quilombo_to_co(&quilombo_user.id, &co_user_id)?;
```

`ensure_co_user_for_quilombo` is idempotent:
- If `linked_co_user_id` is already set → no-op, return it.
- Else if `email` is set and a `users` row with that email exists → link to it (return existing id).
- Else → INSERT new `users` row (`tier='player'`, `password_hash` = quilombo's `senha_hash` if argon2 OR re-hashed, `usuario` = quilombo's `usuario`, `email` = quilombo's `email` or NULL).

### Phase 2 — Recovery channel auto-promotion for quilombo users

Extend `backfill_email_recovery_channels` (or add a sibling) so that:
- For every `quilombo_usuarios` row with `email IS NOT NULL` and `linked_co_user_id IS NOT NULL`:
- Call `ensure_email_recovery_channel(linked_co_user_id, email)`.

Same idempotent path as the existing one. Runs on every boot.

After this lands, every quilombo user with an email on file can already type that email into `/forgot-password` on `co.artelonga.com.br` and get a code via Resend.

### Phase 3 — UI redirect from quilombo to CO

Two changes in the quilombo SPA:

1. **Login modal "Esqueci minha senha" link** — redirect to `https://co.artelonga.com.br/recover?return_to=https://quilomboaraucaria.com.br&identifier={prefilled-username-or-email}`. No quilombo-side handling; CO owns the flow end-to-end.

2. **Profile/security panel "Alterar senha"** — same redirect, but with `/recover?action=change_password&...`.

The `return_to` param is honored by `co.artelonga.com.br` — after a successful reset, redirect back to the originating domain. Restrict to `*.artelonga.com.br` and `quilomboaraucaria.com.br` allowlist (no open redirect).

CO must add `/recover` as a server-side route that serves the SPA login modal pre-pinned to the forgot-password step.

### Phase 4 — Make password changes propagate

When a CO user resets their password via `/api/v1/auth/reset-password`:
- After `users.password_hash` is updated, find every `quilombo_usuarios` row with `linked_co_user_id = <user_id>`.
- Mirror the new `password_hash` into `quilombo_usuarios.senha_hash`.

This way the user can keep logging into quilombo with the new password through the legacy quilombo login (until that login is deprecated in CO-166 Phase 3).

## Acceptance

- [ ] `quilombo_usuarios` registration creates a CO `users` row + sets `linked_co_user_id` (idempotent if linked or email matches existing CO user)
- [ ] Setting an email via `PUT /api/v1/quilombo/perfil` upgrades a previously-unlinked quilombo user to a CO user
- [ ] `backfill_email_recovery_channels` (or a new `backfill_quilombo_recovery_channels`) ensures every linked quilombo user has their email as a verified recovery channel on every boot
- [ ] `/recover?return_to=...` route exists on CO; safelist enforced (only `*.artelonga.com.br` and `quilomboaraucaria.com.br` accepted)
- [ ] Quilombo SPA "Esqueci minha senha" + "Alterar senha" redirect to that route with prefilled identifier
- [ ] `POST /api/v1/auth/reset-password` mirrors the new hash into `quilombo_usuarios.senha_hash` for all linked rows
- [ ] Tests: signup creates CO user, email-set links existing CO user, reset propagates to quilombo hash, redirect allowlist rejects evil hosts

## Out of scope

- OIDC / cross-apex SSO (CO-166 Phase 2) — that handles deployments on different domains. Phase 1 of THIS ticket is sufficient because quilomboaraucaria.com.br runs the same binary today; data sharing is the bottleneck, not domain.
- Quilombo legacy login deprecation (CO-166 Phase 3) — comes after every quilombo user is linked.
- Importing existing pre-CO-167 quilombo users without emails into `users` — they'll get the bridge created lazily on next email-set or password-reset.

## co-auto compatibility

This task is **co-auto compatible** — every change is local Rust + frontend JS that fits the existing autonomous-loop pattern:

- File-system writes only inside the repo.
- No infrastructure changes (same DB, same deployment).
- Idempotent migrations (the bridge can be re-run safely).
- All four phases land as separate small commits with their own changelog entry.
- No external service calls beyond Resend/SMTP, both already configured.

Suggested co-auto commit sequence:
1. `feat(auth): bridge quilombo signups into CO users`
2. `feat(auth): backfill recovery channels for linked quilombo users`
3. `feat(auth): /recover endpoint with safelisted return_to`
4. `feat(quilombo): redirect forgot-password and change-password to CO`
5. `feat(auth): propagate CO password resets to quilombo_usuarios.senha_hash`
6. Tests + changelog after each.
