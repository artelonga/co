## As
The platform operator running an end-to-end conversion funnel from discover → onboard

## I Need
The lead funnel documented in one place, and the capture paths (lead form + magic-code signup) unified so a signup automatically creates a lead and a lead form submission automatically creates a (pending) user — email is the join key.

## So That
- The funnel becomes one identity, attributable end-to-end (acquisition → engage → intent → capture → qualify → register → convert → onboard).
- Drop-off per step is measurable in a single report (CO-371 consumes this unification).
- A signed-up user has a lead record for triage (priority, source); a lead has a user shell ready to claim with magic-code login.
- The 3 review-flagged gaps shrink to 1 (payment, addressed in CO-366).

## Context

The funnel review (provided 2026-06-05) identified that today's lead capture (`POST /api/v1/leads` → `status: new`) and signup (`POST /api/v1/auth/onboard-with-email` → user row + verify code) live in separate tables, with no cross-link. So:
- A user who signs up via the magic-code flow is invisible to the `/admin/leads.html` queue.
- A lead form submitter who already has an account creates a duplicate identity.
- Conversion attribution breaks: `lead_form_submitter → paid_subscriber` is unjoinable today without manual SQL.

CO-183 shipped the lead pipeline. CO-190 shipped passwordless onboarding (`onboard-with-email`). This spec stitches them at the email join.

## Design

Content sourced from the funnel review provided 2026-06-05.

### Part B — Unification at the email join

Two write paths, one identity:

1. **`POST /api/v1/leads` extension**
   - Existing behavior: insert into `leads` with `status: new`, notify admin.
   - **New**: if `email` matches an existing user, link `leads.user_id = users.id`. If email is new, create a "shell user" row with `status: pre-registered` (no password, no verify needed) and link.
   - The lead's `status` continues as before. The user shell can be activated later by completing magic-code signup with the same email.

2. **`POST /api/v1/auth/onboard-with-email` extension**
   - Existing behavior: create user, send magic-code.
   - **New**: also insert/upsert into `leads` with `source: signup`, `status: new`, `email: <same>`, `user_id: <new>`. Skip if a lead already exists for this email (idempotent).
   - **Magic-code verify**: if `leads.status = new` for this email and `source = signup`, auto-advance to `status: in_progress` (the user qualified themselves).

### Schema

Migration v61 adds `leads.user_id` (nullable FK) + `leads.source`:

```sql
ALTER TABLE leads ADD COLUMN user_id TEXT;
ALTER TABLE leads ADD COLUMN source TEXT DEFAULT 'lead_form';  -- 'lead_form' | 'signup' | 'invitation' | 'manual'
CREATE INDEX IF NOT EXISTS idx_leads_email ON leads(email);
CREATE INDEX IF NOT EXISTS idx_leads_user_id ON leads(user_id);
```

Migration v62 adds `users.lead_id` for the reverse link (optional but useful for `/auth/me` to return lead state):

```sql
ALTER TABLE users ADD COLUMN lead_id INTEGER;
ALTER TABLE users ADD COLUMN status TEXT DEFAULT 'active';  -- 'active' | 'pre-registered' | 'suspended'
CREATE INDEX IF NOT EXISTS idx_users_lead_id ON users(lead_id);
```

Backfill in same migration: walk existing leads + users, match by lowercased email, populate the FKs.

### Endpoint additions / changes

- `POST /api/v1/leads` — extended (see above), backwards-compatible request shape
- `POST /api/v1/auth/onboard-with-email` — extended (see above), backwards-compatible
- `GET /api/v1/admin/leads` — extended response with `user_id`, `user_status`, `verified_at`
- `GET /api/v1/auth/me` — extended response with `lead_id`, `lead_status`, `lead_source`

### Race / idempotency

Both endpoints wrap their writes in a transaction. Email is lowercased + trimmed at the boundary. UPSERT pattern:

```sql
INSERT INTO leads (email, source, status, user_id, created_at)
VALUES (?, ?, 'new', ?, datetime('now'))
ON CONFLICT(email) DO UPDATE SET
  user_id = COALESCE(leads.user_id, excluded.user_id);
```

`leads.email` needs UNIQUE constraint — migration v61 adds it if absent.
