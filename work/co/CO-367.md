## As
A brain owner adding any content (note, article, poem, audio clip, screenshot) to their universe

## I Need
A unified ingestion pipeline — bake → cache-first render → consented async sync to the CO KB → downstream availability (search, agents, analytics) — that doesn't lock me into the analytics-only shape CO-340 shipped.

## So That
- The BaaS thesis's §6 promise "add anything → registered, synced, delivered" holds for all content, not just analytics rollups.
- A new entry is visible locally before sync (resilience: ingest break ≠ unavailable).
- The KB warehouse becomes a queryable substrate for cross-universe search, agent retrieval, and analytics — one pipeline, one tenancy model (`universe_key`).
- The CO-340 anomaly retroactively becomes "the analytics special case of the universal pattern."

## Context

CO-340 shipped per-universe analytics rollups with a precise architecture:
1. **Local write** = source of truth (the entry itself)
2. **Cache-first render** = the surface shows it before sync runs
3. **Consented async sync** = bearer-token gated POST to CO
4. **Idempotent upsert** = same payload twice = no double-count

That's exactly the right shape for ALL content, not just `DailyRollup`. This spec generalizes the pattern.

## Design

### The contract

Surface emits a `KbIngestEvent` per entry write:

```json
POST /api/v1/kb/ingest
Authorization: Bearer <CO_KB_TOKEN>
Content-Type: application/json

{
  "universe_key": "yuri",
  "entry_path": "notes/2026-06-05.md",
  "entry_type": "note",
  "body_hash": "sha256:abc...",
  "frontmatter_json": {...},
  "body_preview": "first 500 chars for search",
  "size_bytes": 2048,
  "updated_at": "2026-06-05T15:30:00Z",
  "asset_refs": ["sha256:def..."]
}
```

Server:
1. Validate token + universe_key tenancy
2. Idempotent upsert into `entry_kb_index` keyed by `(universe_key, entry_path, body_hash)`
3. If `entry_type` matches a known indexer, route to it (search index, embedding index, etc.)
4. Log success to atividades (CO-361)

### Schema

Migration v60 adds `entry_kb_index`:

```sql
CREATE TABLE entry_kb_index (
    universe_key TEXT NOT NULL,
    entry_path TEXT NOT NULL,
    body_hash TEXT NOT NULL,
    entry_type TEXT,
    frontmatter_json TEXT,
    body_preview TEXT,
    size_bytes INTEGER,
    updated_at TEXT NOT NULL,
    indexed_at TEXT NOT NULL,
    asset_refs TEXT,  -- JSON array
    PRIMARY KEY (universe_key, entry_path, body_hash)
);

CREATE INDEX idx_kb_universe_type ON entry_kb_index(universe_key, entry_type);
CREATE INDEX idx_kb_updated ON entry_kb_index(updated_at);
```

### Producer side

Two emitters:
1. **CO's own entry write path** — when an entry is created/updated in `entries`, fire `kb_ingest` async on the same node (tokio::spawn so it doesn't block the write response)
2. **External surfaces** — yuri.artelonga.com.br, future per-brain domains: send `KbIngestEvent` whenever they bake a new entry. Reuses the same endpoint.

### Bidirectional sync

- **Surface → CO**: this spec (push from edge to warehouse)
- **CO → Surface**: query endpoints `GET /api/v1/kb/search?q=...&universe_key=...` already shipped per CO-340 (`/api/v1/analytics/public/summary` pattern). Generalize to `/api/v1/kb/{query,search,recent}`

### Resilience

- Local entry is source of truth; ingest is non-blocking
- If `/api/v1/kb/ingest` returns 5xx or times out, surface queues for retry (exponential backoff: 1m, 5m, 30m, 2h)
- Queue is local (browser `IndexedDB` for web surfaces; SQLite for native surfaces)
- A cold start drains the queue
- Surface NEVER blocks user write on sync

### Search index

Phase 1: SQLite FTS5 over `body_preview` field. Wraps existing FTS5 schema used by entries.

Phase 2 (post-v3.0): vector embeddings via existing `co-embedding` Fly sidecar (CO-286). Embeddings flow through the same KB endpoint with an `embedding_vector` field.

### Asset ride-along

CO-146 binary assets (CAS-stored) reference by sha256. KB ingest includes `asset_refs: [sha256, ...]` — KB index records the binary linkage. Downstream agents can fetch the binary from `/api/v1/universes/{key}/assets/{sha256}`.

### Atividades

- `event_type = 'kb.ingested'` per upsert
- `event_type = 'kb.queried'` per query
- Surface in /gestao/resumo (CO-360) as "KB ingestion rate" + "Top queries"

## Not in scope

- **Vector embeddings** — Phase 2 (CO-367-B), uses existing co-embedding sidecar
- **Multi-modal indexing** (audio transcription, image OCR) — defer
- **Per-user search permissions** — KB queries respect universe visibility (public/private); finer-grained ACL is future
- **Real-time search-as-you-type** — UI sugar, post-v3.0
- **External KB connectors** (Notion, Obsidian sync, etc.) — separate epic
- **Cross-brain federated search** (search across N brain owners' KBs) — defer; raises privacy questions
- **Embedding-based deduplication** — defer
- **Stream-of-consciousness ingest** (every keystroke → KB) — pathological, defer
