GIVEN authoring content for Co today requires the round-trip "edit locally → `co sync push` → server stores → web reads it" — fine for batch authoring, but not for the case where the user wants to **see and edit their actual local filesystem from a Co web page** (e.g., a remote machine they don't have a desktop session on, a kiosk they can authorize for one task, an iPad with no native editor for a deeply-nested repo) — AND we want this **without trusting the Co server with the contents**, the architecture pivots from "server holds canonical state" to "server is a verified relay between browser and the user's own machine."
WHEN we add (a) a small `co-agent` daemon that runs on the user's PC and exposes a read/write filesystem surface over an encrypted WebSocket; (b) a Co server-side relay that lets a browser connect to a registered agent **only via specific pages with `mount: agent` capability**; and (c) end-to-end encryption with keys derived from a per-pairing secret never seen by the server,
THEN any allowed Co page can render a live, editable mirror of a remote PC's filesystem (or a slice of it), with the Co server serving only as an authenticated relay — operator cannot read or alter the bytes flowing through.

## Architecture (one diagram)

```
┌─────────────────┐    encrypted WS    ┌────────────────┐    encrypted WS    ┌────────────────┐
│   Browser       │ ◄────────────────► │  Co server     │ ◄────────────────► │  co-agent      │
│   (Co page)     │     (relay only)   │  /agent/relay  │                    │  on user PC    │
│                 │                    │                │                    │                │
│ E2E key pair    │                    │ Sees opaque    │                    │ E2E key pair   │
│ Renders FS UI   │                    │ ciphertext +   │                    │ Reads/writes   │
│                 │                    │ pairing IDs    │                    │ allowed paths  │
└─────────────────┘                    └────────────────┘                    └────────────────┘
       │                                                                              │
       └──────────────── shared X25519 ECDH key (never on server) ────────────────────┘
```

The Co server **multiplexes** WebSocket frames between paired (browser, agent) connections by their pairing ID. It cannot decrypt the payload. It enforces:
- The page making the connection has `mount: agent` capability in its manifest.
- The pairing ID is registered to the requesting user.
- Connection rate limits per user / per agent (CO-80 territory).

## Three new components

### 1. `co-agent` — daemon on user's PC

A new Rust crate at `dev/co-agent/` (or `co-agent/` once promoted out of dev). Runs as a long-lived process. Configuration at `~/.co/agent.toml`:

```toml
[identity]
public_key = "x25519:abc…"            # generated at first run
agent_id = "agent_<nanoid>"

[allowed_paths]
# Only paths under these roots are exposed to a successful pairing.
roots = [
    "/Users/yuri/projects/quilomboaraucaria",
    "/Users/yuri/projects/ArteLonga",
    "/Users/yuri/projects/rfq-gateway",
]

[pairings]
# A pairing is a (page_id, browser_pubkey, expires_at) triple. Created
# during a UI handshake (QR code + verify-on-agent confirmation).
prod_artelonga_review = { page = "co.artelonga.com.br/co/artelonga", browser_pubkey = "…", expires_at = "2026-05-30T00:00:00Z", scope = "read|write|read-write" }
```

Operations supported (over encrypted WS):

```
list <relative_path>           → JSON file tree slice
read <relative_path>           → bytes
write <relative_path> <bytes>  → ack + new mtime
delete <relative_path>         → ack
move <from> <to>               → ack
watch <relative_path>          → stream of fs change events
```

All paths are scoped to the configured `roots`. Path traversal (`../`) rejected at the agent.

### 2. Server relay — `/api/v1/agent/relay`

A WebSocket route in `co-web/src/agent_routes.rs`:

```
GET /api/v1/agent/relay?pairing_id=…&direction=browser|agent
Upgrade: websocket
```

Server validates:
- Caller is authenticated (JWT or API token).
- The pairing exists, is not expired, and belongs to the caller.
- The page (Referer) has `mount: agent` in its manifest.
- The corresponding peer endpoint is connected; if not, queue the frame for up to 60 seconds.

Frames are forwarded **as-is**. Server never inspects the body.

Connection registry:

```sql
CREATE TABLE agent_pairings (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    page_url TEXT NOT NULL,                   -- which page this is bound to
    agent_pubkey TEXT NOT NULL,               -- X25519 public key of the agent
    browser_pubkey TEXT NOT NULL,             -- X25519 public key of the browser session
    scope TEXT NOT NULL,                      -- 'read' | 'write' | 'read-write'
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,
    revoked_at TEXT
);
```

### 3. Browser-side library — `co-web/static/shared/agent-client.js`

JS module exporting:

```js
const session = await CoAgent.connect({
    pairingId: '…',
    serverPubkey: '…',                       // baked into the page (verified)
    onDisconnect: () => …,
});

await session.list('content/');               // → file tree
await session.read('content/sobre.md');       // → string
await session.write('content/sobre.md', body); // → ack
const events = session.watch('content/');     // → AsyncIterable of fs events
```

Implementation: WebSocket + libsodium-wrapper for X25519 ECDH + ChaCha20-Poly1305 frame encryption. Bundle size target: ≤ 80 KB gzipped.

## Pairing flow (the trust ceremony)

A pairing is established **once per (page, browser, agent)**, with explicit human consent on both sides:

1. Browser visits a page with `mount: agent`. Page renders a "Pair with my computer" button.
2. Click → browser generates an X25519 keypair, requests a pairing record from the Co server, gets back a pairing ID + a 6-word phrase.
3. User runs `co-agent pair <pairing_id>` on their PC. The agent fetches the same pairing from the server, displays the **same** 6-word phrase + the page URL, and asks: "Allow this page to mount your filesystem? Scope: read-write. Expires in 30 days."
4. User confirms in the terminal. Agent uploads its public key to the pairing record + signs a confirmation. Pairing becomes active.
5. The 6-word phrase appearing on **both** the page AND the terminal is the social proof that the pairing is correct (not a MITM). Both halves are derived from the X25519 ECDH shared secret.

This is the standard "QR code emoji verification" pattern from Signal / Wire, adapted to terminals.

## End-to-end encryption details

- **Key exchange:** X25519 ECDH between browser pubkey and agent pubkey. Server mediates exchange of pubkeys but never sees the shared secret.
- **Frame encryption:** ChaCha20-Poly1305 with a per-frame counter nonce. Same primitive as `.co` envelope (CO-86).
- **Message integrity:** authenticated via Poly1305; replay protected by counter nonce.
- **Forward secrecy:** ratchet keys per session (Double Ratchet, simplified — Signal-style). New session keys per connection.
- **Server compromise threat model:** server can drop frames, can deny service, can record ciphertext indefinitely. Cannot read content. Cannot inject content (any forgery fails Poly1305 check).

## Page capability — `mount: agent`

Pages that want to render an agent surface declare capability in their frontmatter:

```yaml
---
type: page
title: Editar repositório local
mount:
  type: agent
  scope: read-write
  default_root: /Users/yuri/projects/quilomboaraucaria
  pairing_required: true
---
```

The SPA reads this and shows the pairing UI + (post-pairing) the file tree + editor. Pages without `mount` capability cannot connect to any agent.

This composes naturally with CO-71 (per-universe schema validator): the `mount` block is part of the page schema and is verified server-side.

## Threat model summary

| Threat | Mitigation |
|---|---|
| Compromised Co server (operator turns evil) | E2E encryption — server sees only ciphertext + pairing IDs |
| MITM at TLS termination | Pairing 6-word phrase verifies the X25519 ECDH match |
| Compromised page (XSS in Co content) | Page capability requires explicit `mount: agent` declaration; CSP blocks inline scripts; agent-client.js shipped from the Co origin only |
| Compromised browser session | Pairings are per-session; close the tab, the symmetric key dies; ratchet prevents replay |
| Agent host compromise | Out of scope — full host compromise means anything is reachable. Mitigation via least-privilege agent process + path scoping |
| Server denial-of-service | Rate limits per pairing (CO-80); agent has its own pairing-rate limits |
| Cryptographic break of ChaCha20-Poly1305 / X25519 | Out of scope; primitives are best-of-class. Reassess if NIST guidance changes. |

## Out of scope

- Full LSP / language-server protocol bridging through the agent (huge; future ticket)
- Plugin extensibility for the agent (let custom code run on the host) — security minefield
- Federation between agents (peer A talks to peer B without server) — interesting; v3+
- Tail-end terminal access through the agent — hard no, would change the threat model fundamentally
