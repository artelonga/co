## As

an operator who wants to understand how the chat surface is actually used,
plus a user receiving a DM who wants context for "where did this message
come from"

## I Need

every `chat_messages` row stamped with an optional `origin_universe_key`
column — the universe context the sender was viewing when they hit Send.
Surface this in the DM thread UI ("via Quilombo Araucária") and in the
admin telemetry view.

## So That

- a DM from someone you met in a specific universe carries that breadcrumb
- product can answer "which universes are driving the most chat" and
  "are people DMing each other across universe boundaries?"
- privacy-respecting (it's the *sender's* current universe, not a
  cross-link to private content)

---

## Why this is distinct from `chat_rooms.universe_key`

`chat_rooms.universe_key` says where the **room** lives:
- `'quilomboaraucaria'` for a room in that universe
- `'dm'` (sentinel) for any DM

This ticket adds `chat_messages.origin_universe_key` — where the **author
was browsing** at the moment of sending. For universe rooms these are
usually the same. For DMs, the origin gives context that the room itself
lacks (since DM rooms have no universe).

## API

### Extend `POST /api/v1/universes/{slug}/chat/rooms/{room_slug}/messages`

Request gains optional field:
```jsonc
{
  "body": "Olá!",
  "reply_to_id": null,
  "origin_universe_key": "quilomboaraucaria"  // NEW
}
```

If omitted: the server falls back to `slug` (the room's universe — same
as today's behavior for universe rooms; NULL for DM rooms).

If present: validated against the caller's `universe_members` membership
or `subscriptions` row. If the caller is not in the claimed origin
universe, the field is **silently dropped** (no error — privacy-respecting:
"I'm in private universe X" shouldn't be leakable just by sending).

### Response includes `origin_universe_key`

`GET /messages` returns it on each row. UI consumers render the badge.

## UI — `modules/chat.js`

### When sending

```js
// In _sendMessage(), before POST:
const body = { body: text, reply_to_id: null };
if (state.currentUniverseSlug && state.currentUniverseSlug !== 'template') {
    body.origin_universe_key = state.currentUniverseSlug;
}
```

### When rendering DM messages

If `message.origin_universe_key` is set AND it differs from `state.currentUniverseSlug`:

```
Maria · há 2 min · via Quilombo Araucária
  Olá! Tudo bem?
```

The "via X" subtext is a small italic line below the timestamp.

### When rendering universe-room messages

Don't show the badge if `origin_universe_key === room.universe_key` (the
common case — redundant).

## Telemetry (admin-only)

`GET /api/v1/admin/chat/origin-breakdown` (admin gate) returns:

```jsonc
{
  "origins": [
    { "universe_key": "quilomboaraucaria", "message_count": 1234 },
    { "universe_key": "co", "message_count": 567 },
    { "universe_key": null, "message_count": 12 }  // unknown / pre-CO-204
  ],
  "total_messages": 1813
}
```

Used by an admin chart in a future dashboard ticket.

## Acceptance

- [ ] Migration adds `origin_universe_key` nullable column + index.
- [ ] POST message with explicit `origin_universe_key` writes it (when
      caller is member/subscriber of that universe).
- [ ] POST message with origin the caller doesn't belong to → field
      silently dropped, message persisted with NULL origin.
- [ ] POST message without origin → server defaults to room's
      universe_key for universe rooms, NULL for DM rooms.
- [ ] GET messages returns the field.
- [ ] DM UI shows "via {universe_name}" subtext for messages whose
      origin differs from the viewer's current universe.
- [ ] Admin breakdown endpoint returns aggregated counts.
- [ ] Tests: 6+ covering origin write/read, privacy drop, default
      behavior, admin gate.

## Out of scope

- **Re-tagging existing messages.** They stay NULL.
- **Per-message location/IP.** Origin is universe-level only.
- **Cross-tenant analytics.** Single instance only.
- **End-user-facing analytics.** Admin-only.
