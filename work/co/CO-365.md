## As
The platform operator opening CO to the public — wanting data durability without committing to a specific cloud provider yet

## I Need
A `BackupBackend` trait with a default local-filesystem implementation and stub implementations for S3, R2, Fly volume snapshots, and GCS — so the backend choice becomes a config flip, not a code change.

## So That
- The v3.0 public launch can ship with backup running (sovereignty signal at launch).
- The choice between S3 / R2 / Fly / GCS / something-else can be deferred until we know the cost + egress profile.
- The BaaS thesis's "no third-party lock-in" invariant holds — switching backends never requires a code change.
- CO-143 stops being a blocker for v3.0 (it required choosing AWS upfront).

## Context

CO-143 spec offered two paths: Fly cron app or GitHub Actions cron, both targeting S3. The user has been running `scripts/backup-prod-local.sh` ad-hoc (tarball → `~/co-backups/`) since 2026-05-02. Last snapshot: 6.9 MB, included all 3 production universes.

Per the BaaS thesis (`ArteLonga/docs/brain-as-a-service.md` §6 resilience + §8 review), backup must:
1. Run automatically (no human in the loop)
2. Not lock the platform to one vendor
3. Preserve sovereignty — the brain owner can re-host their own backup target

A trait-based scaffold satisfies all three.

## Design

### The trait

```rust
// co-web/src/storage/backup/mod.rs
#[async_trait]
pub trait BackupBackend: Send + Sync {
    /// Upload a snapshot. Returns a backend-specific identifier.
    async fn put(&self, snapshot: &Snapshot) -> Result<SnapshotId>;

    /// List snapshots, newest first.
    async fn list(&self) -> Result<Vec<SnapshotMeta>>;

    /// Download a snapshot to a local path.
    async fn fetch(&self, id: &SnapshotId, dest: &Path) -> Result<()>;

    /// Delete a snapshot (used by retention policy).
    async fn delete(&self, id: &SnapshotId) -> Result<()>;

    /// Backend name for telemetry/logs.
    fn name(&self) -> &'static str;
}

pub struct Snapshot {
    pub created_at: DateTime<Utc>,
    pub manifest_json: serde_json::Value,
    pub tarball_path: PathBuf,
    pub bytes: u64,
    pub sha256: String,
}

pub struct SnapshotMeta {
    pub id: SnapshotId,
    pub created_at: DateTime<Utc>,
    pub bytes: u64,
    pub sha256: String,
}
```

### Implementations

| Impl | Status | File |
|---|---|---|
| **`LocalFsBackend`** | full, default | `co-web/src/storage/backup/local_fs.rs` |
| **`S3Backend`** | stub returning `unimplemented` | `co-web/src/storage/backup/s3.rs` (`#[cfg(feature = "backup-s3")]`) |
| **`R2Backend`** | stub | `co-web/src/storage/backup/r2.rs` (`#[cfg(feature = "backup-r2")]`) |
| **`FlyVolumeBackend`** | stub — uses `flyctl volumes snapshots` shell call | `co-web/src/storage/backup/fly.rs` (`#[cfg(feature = "backup-fly")]`) |
| **`GcsBackend`** | stub | `co-web/src/storage/backup/gcs.rs` (`#[cfg(feature = "backup-gcs")]`) |

`LocalFsBackend` writes to `$CO_BACKUP_DIR` (default `/data/backups/`) — full implementation in v3.0. Inherits the existing `scripts/backup-prod-local.sh` tarball strategy.

### Snapshot format (backend-independent)

```
snapshot-<UTC-ISO8601>-<sha256-prefix>.tar.gz
  ├── manifest.json    { created_at, co_version, schema_version, universes: [...] }
  ├── meta.db          (SQLite, the platform metadata)
  └── universes/
      ├── <key>/
      │   ├── data.db
      │   ├── content/...
      │   └── blobs/...   (CO-146 CAS)
      └── ...
```

Format is identical across backends → restore-across-backends works trivially.

### Config

Env vars:
- `CO_BACKUP_BACKEND` = `local` (default) | `s3` | `r2` | `fly` | `gcs` | `disabled`
- `CO_BACKUP_DIR` (local) = `/data/backups/`
- `CO_BACKUP_BUCKET` (s3/r2/gcs) = e.g. `artelonga-co-backups`
- `CO_BACKUP_REGION` (s3/r2/gcs)
- `CO_BACKUP_RETENTION_DAYS` = `30` (default; LRU cleanup)

### Scheduler

New background tokio task in `co-web/src/platform/workers.rs`:
- Runs every 24h (configurable via `CO_BACKUP_INTERVAL_HOURS`)
- Calls `backend.put(snapshot)`
- Then `backend.list()` + delete snapshots older than `CO_BACKUP_RETENTION_DAYS`
- Logs success/failure to atividades (CO-361)

### Manual triggers

- `POST /api/v1/admin/backup/snapshot` — admin-only, fire one snapshot now
- `GET /api/v1/admin/backup/snapshots` — admin-only, list snapshots
- Both return backend-agnostic metadata

### Restore (post-v3.0; out of scope for this spec)

Restore is a CLI-driven flow `co restore --snapshot <id>` — built later. This spec only covers **put + list + retention**.

## Acceptance

- [ ] `BackupBackend` trait defined with 5 methods
- [ ] `LocalFsBackend` ships full (default backend, no feature flag needed)
- [ ] S3/R2/Fly/GCS impls are stubs (compile-tested) gated behind cargo features — no real network calls
- [ ] Snapshot format documented in `docs/backup-format.md`
- [ ] Background task runs every 24h on prod
- [ ] `CO_BACKUP_BACKEND=disabled` short-circuits the task (for dev)
- [ ] Atividades log shows snapshot put events (success + failure)
- [ ] `POST /api/v1/admin/backup/snapshot` works
- [ ] Retention prunes snapshots older than `CO_BACKUP_RETENTION_DAYS`
- [ ] Manifest includes the active backend name (so a restore tool knows where a snapshot came from)
- [ ] No regression in `scripts/backup-prod-local.sh` (keep it as a CLI fallback)

## Not in scope

- **Restore tooling** — separate CLI spec post-v3.0
- **Real S3/R2/GCS implementations** — fill the stubs when we pick a backend (v3.1+)
- **Cross-region replication** — too early
- **Encrypted snapshots** — covered by CO-145 epic; layer on top later
- **Cross-snapshot deduplication** — defer; tarballs are small (~7 MB today)
- **Subscriber-side backup** (each brain owner backing up their own universe) — different problem; CO-vault export endpoint handles ad-hoc
