## As

a CO operator standing up the lakehouse

## I Need

an Iceberg REST catalog (Lakekeeper as the v1 choice; Nessie as a 1-day spike candidate) deployed on Fly, configured to manage Iceberg tables backed by R2, and the first real table (`events`) wired up

## To

give every Iceberg-aware engine (Spark, Flink, Trino, ClickHouse, DuckDB, Pinot) **one** entrypoint for table discovery and metadata, with the option to add data branching later (Nessie) if the jujutsu mental model resonates with CO's UX

## Given / When / Then

GIVEN Iceberg supports many catalog backends but the REST spec is the only choice that's neutrally portable across all engines (`platform-evaluation.md` §13),
WHEN we deploy Lakekeeper on Fly with R2 as the warehouse and Redpanda Iceberg Topics writing into it,
THEN engines connect via a single `IcebergCatalog::REST` config and find a populated `events` table.

## Why Lakekeeper first, Nessie later

| | Lakekeeper | Nessie |
|---|------------|--------|
| Implementation | Rust | Java |
| Spec | REST catalog spec | REST catalog + git-like data branching |
| RBAC | Strong governance story | Weaker; designed for lineage, not auth |
| Branching | No | **Yes — branches/merges/diffs on table state** |
| CO fit | Easier first step; matches our Rust stack | Mirrors jujutsu UX once we want data branches |

**Phase 3 goal:** Lakekeeper for raw lake. **Phase 5 spike:** evaluate adding Nessie as a second catalog (or migrating) once jujutsu-shaped UX is real in the product.

## Acceptance

- [ ] Lakekeeper deployed on Fly with PostgreSQL backing (small managed Postgres or a Fly Postgres app)
- [ ] R2 bucket `co-iceberg-warehouse` created; Lakekeeper configured to use it
- [ ] First table `events` registered via REST API, schema matching the `events.exposure` topic
- [ ] Redpanda Iceberg Topics points its REST catalog config at Lakekeeper
- [ ] DuckDB query against the `events` table returns rows
- [ ] ClickHouse query against the same table returns identical rows
- [ ] `docs/OPERATIONS.md` updated with catalog management runbook

## Out of scope

- Nessie deployment — Phase 5 spike
- Cross-account / multi-tenant catalog isolation — single warehouse for now
- Polaris evaluation — deferred; vendor-neutrality is good but Lakekeeper's Rust fit wins for v1

## Risks

- **Catalog as SPOF.** Mitigation: Postgres backing is replicated; Lakekeeper itself is stateless and can run multiple replicas
- **REST spec drift.** Mitigation: pin Lakekeeper version; test catalog calls against the version's spec doc on every upgrade
