GIVEN prod's only auth path is the email-code flow which uses `LogMailProvider` (codes printed to stdout — no real email is sent), so logging in requires `flyctl logs | grep "Verification code"` and scripts can't run autonomously,
WHEN we extend the existing UAT password-login (Argon2id + JWT, already used by `seed_uat_user`) to work in prod for users with a `password_hash` column set, gated by an env-driven admin seed,
THEN any operational task that needs prod write access (CO-67 prod seed, CO-82 mirror token generation, future autonomous runs) works via `curl` with no log-fishing.

## Why this is strictly better than today

| Aspect | Email-code (today) | Password-login (after) |
|--------|-------------------|------------------------|
| Privacy | Email metadata leaks via mail provider | No third party sees credentials |
| Phishing surface | Email + code | Single password |
| Recovery | Re-request code | Standard password reset (defer until >1 user) |
| Works without internet/email | No | Yes |
| Scriptable | No (log-fishing) | Yes (curl + cookie jar) |
| Security primitive | Magic-link / one-time code | Argon2id (memory-hard KDF, OWASP-recommended) |

Same JWT + Set-Cookie response shape. Same backend migration table. Different front door.

## Architecture

- New endpoint: `POST /api/v1/auth/password-login`
  - Body: `{"email": "...", "password": "..."}`
  - Reads user by email; rejects if `password_hash IS NULL`
  - Verifies via `argon2::Argon2::default().verify_password(...)` (same code path as `uat_login_handler`)
  - On success: signs JWT, sets `session=<JWT>` cookie, returns `{user_id, email, display_name, expires_at}`
  - **No `is_uat()` gate** — works in any env when the user has a hash
- Existing `POST /api/v1/auth/uat-login` becomes a thin alias that delegates to the same handler (kept for compat with existing scripts/CLAUDE.md)
- Env-driven admin seed (idempotent):
  - On startup, if `CO_SEED_ADMIN_EMAIL` and `CO_SEED_ADMIN_PASSWORD_HASH` are set:
    - Look up user by email
    - If found: update `password_hash` and `tier='admin'` only if hash differs (prevents accidental clobber on every restart)
    - If missing: insert `(id=usr_admin_<rand>, email, display_name='admin', tier='admin', password_hash, created_at)`
  - Logs once per startup: "admin user seeded: <email>"

## Operational rollout

1. Generate Argon2id hash locally:
   ```bash
   # using `argon2` CLI or any equivalent (cost params match server's default)
   HASH=$(printf 'mySecretPassword' | argon2 "$(openssl rand -hex 16)" -id -t 3 -m 16 -p 1 -e)
   ```
2. Set Fly secrets:
   ```bash
   flyctl secrets set CO_SEED_ADMIN_EMAIL=yuri@artelonga.com.br \
                      CO_SEED_ADMIN_PASSWORD_HASH="$HASH" \
                      -a co-artelonga
   ```
3. Deploy 1.18.0 (the release that ships CO-85). Server seeds yuri on startup.
4. Verify:
   ```bash
   curl -sc cookies.txt -X POST https://co-artelonga.fly.dev/api/v1/auth/password-login \
        -H 'Content-Type: application/json' \
        -d '{"email":"yuri@artelonga.com.br","password":"mySecretPassword"}'
   # → 200, Set-Cookie: session=<JWT>
   ```
5. Generate prod API token (now runnable):
   ```bash
   curl -sb cookies.txt -X POST https://co-artelonga.fly.dev/api/v1/auth/token \
        -H 'Content-Type: application/json' \
        -d '{"name":"uat-mirror"}'
   # → { token: "..." }
   ```
6. That token unblocks CO-82 mirror operationalization + CO-67 prod seed.

## Security considerations

- Hash format = Argon2id with parameters compatible with the existing `seed_uat_user` (default: 19 MiB, 3 iterations, parallelism 1). Rotating params later requires re-hashing on next login.
- The Fly secret is a hash, not a plaintext password — secrets log accidentally (e.g., copy-pasted in chat) reveal at most the hash, which is computationally expensive to crack.
- Password complexity: leave to operator. Log a warning if hash format is recognized as something other than `$argon2id$v=19$m=...$...` (likely a misconfiguration).
- JWT lifetime: same 7 days as uat-login (configurable later).

## Out of scope (defer)

- Password reset flow (one user, low value)
- Rate limiting on login attempts (admin-only endpoint, low risk; CO-80 covers proper rate limiting later)
- 2FA / TOTP (defer to CO-80+ era)
- Per-user password change endpoint (admin re-seeds via env if needed)

## Acceptance

- `POST /api/v1/auth/password-login` on prod with valid creds → 200, sets session cookie, returns user JSON
- `POST /api/v1/auth/password-login` on prod with wrong password → 401
- `POST /api/v1/auth/password-login` on prod for user with no `password_hash` → 401 (same response as wrong password, no info leak)
- `CO_SEED_ADMIN_EMAIL` + `CO_SEED_ADMIN_PASSWORD_HASH` set → admin user exists in `meta.db` users table after restart
- Re-startup with same env vars → no spurious update (drift detection works)
- Existing `uat-login` flow on UAT continues to work
