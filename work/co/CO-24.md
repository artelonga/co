GIVEN every universe must separate content (what) from form (how it looks), and CO-36 defines the Entry abstraction (every entity is a .md file),
WHEN I wire universe config to drive presentation while entries drive content,
THEN:

## Form = universe config (NOT in entries)

- [ ] `universes` table extended with: `layout TEXT DEFAULT 'board'`, `font_headline TEXT`, `font_body TEXT`, `custom_tokens TEXT` (JSON, nullable)
- [ ] Serve universe config at `GET /api/v1/universes/:slug/config` returning: `{ theme_preset, layout, font_headline, font_body, custom_tokens }`
- [ ] `PUT /api/v1/universes/:slug/config` — owner can update form config
- [ ] On page load for `/co/:slug`, inject CSS from universe config:
  - Load preset CSS (scholarly, scholarly-dark, relic, relic-light) as base
  - Apply custom_tokens overrides as inline `:root` style
  - Load fonts if custom (Google Fonts link injection)
- [ ] Form config stored in `.universo.yaml` at vault root (synced with SQLite for API)
- [ ] Layout field: default view mode (board, table, timeline, calendar, dashboard)
- [ ] Settings panel in header (gear icon, owner only): theme, layout, fonts

## Content = entries (files with frontmatter)

- [ ] All content served via entry queries: `GET /api/v1/universes/:slug/entries?type=task`
- [ ] Board UI reads entries, NOT direct SQLite table queries
- [ ] Entry type determines rendering: `task` → kanban card, `event` → calendar item, `page` → wiki article, `clip` → link card
- [ ] Form never knows what content exists. Content never knows how it's displayed.
- [ ] Template universe uses Scholarly Light theme, board layout
- [ ] Cloned universes inherit form config at clone time

- [ ] Test: create universe → change theme → verify CSS → add entries → verify content unaffected by form change
- [ ] `cargo test` passes, `cargo clippy -- -D warnings` clean
