GIVEN the whatsapp bridge is currently the de-facto agent runtime (its
`lifecycle_brain.py` owns the tool-calling loop, backends, and per-user identity),
and once CO has a native runtime (CO-504) the bridge should hold **only transport** —
WhatsApp in, WhatsApp out — delegating all reasoning to CO,
WHEN we move the brain logic into CO and reduce the bridge to a transport adapter,
THEN WhatsApp is just **one client** of the general CO agent runtime, and the
co-web↔bridge wire contract is renamed to agent-named equivalents (with back-compat
aliases so live deploys don't break).

## Acceptance

- [ ] **Brain logic moved into CO** (the loop from `lifecycle_brain.py` now runs via
  the CO agent runtime, CO-504); the bridge no longer reasons, it transports.
- [ ] **Bridge = transport adapter**: receives inbound WhatsApp (Evolution `/webhook`
  / managed webhook), forwards to the CO agent runtime, returns the reply outbound.
- [ ] **Wire contract migrated to agent-named equivalents** with back-compat aliases:
  `CO_BOT_BRAIN_URL` → `CO_AGENT_URL` (or equivalent), `X-Bot-Secret` → `X-Agent-Secret`,
  `/bot/chat` → `/agent/chat`. Old names keep working (alias) so deploys don't break.
- [ ] **No regression**: an end-to-end WhatsApp exchange still works through the new
  thin client over the CO runtime.
- [ ] **Generalist**: nothing WhatsApp-specific leaks into the CO runtime; WhatsApp
  assumptions stay inside the adapter.
- [ ] Self-host/managed invariant preserved (CO-497): the thin client + local-model
  default still runs fully on one box.

## Notes
- Depends on CO-504 (runtime) and CO-503 (tools); coordinates terminology with CO-508
  (the full bot→agent rename) — this task does the **wire-contract** slice with aliases.
- Aliases are mandatory: the wire contract is live (`bot_proxy_routes.rs`,
  `CO_BOT_*` env, `X-Bot-Secret`), so renames ship with back-compat, never a hard cut.
- WhatsApp is **one client** of the agent runtime — the architecture's whole point.
