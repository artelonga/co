GIVEN blob storage (images, attachments, generated docs) doesn't scale on Fly volumes (~500 GB cost-effectively), and millions of small files in one directory degrade ext4 lookups,
WHEN we move blobs to S3-compatible object storage (Cloudflare R2 / Tigris / Fly Tigris) and shard the on-disk universe layout by hash,
THEN storage scales to PB without volume-size constraints, and filesystem operations stay fast.

## Architecture

- Blobs: content-addressed by SHA256, stored at `<bucket>/blobs/sha256/<aa>/<bb>/<full>`
- Universe DBs: `/data/universes/<aa>/<bb>/<universe_key>/data.db` (2-level fanout)
- Blob cache: per-universe LRU on local disk; cold blobs evicted to remote
- Vault PUT: small files (< 1 MB) inline in entry payload; large blob to S3 + reference

## Tasks

- [ ] Object storage adapter: S3 API (works with R2, Tigris, AWS S3)
- [ ] Content-addressed put: hash before upload, skip if blob already exists
- [ ] Blob cache at `/data/blob-cache/`, sized to volume capacity, LRU
- [ ] Migration: move existing blobs from filesystem to object storage
- [ ] Filesystem sharding: 2-level hex prefix on universe_key
- [ ] Garbage collection: blobs unreferenced for 30 days are deleted

## Scale notes

- S3 GET ~30ms; cache makes hot blobs ~1ms
- Content addressing dedupes across universes (same image used in many universes = stored once)
- 2-level fanout (256 × 256 = 65K dirs at level 2) keeps any directory under ~150 entries at 10M universes
- Egress cost: S3 → user direct via signed URL (no proxy through Fly) saves bandwidth
- Backup: object storage already redundant; per-universe DB still snapshotted via CO-77

## Acceptance

- 5 MB image upload completes in < 2s end-to-end
- Same image uploaded to N universes uses only 1 blob row
- 1M-universes filesystem has no directory with > 200 entries
- GC reclaims unreferenced blobs after 30-day grace period
