## As
A team member following CO's bi-weekly sprint cadence

## I Need
A sprint calendar that shows past sprints + the next 4 future ones, with Definition of Done per delivered PBI, exposed via JSON API + a SPA route + ICS export for Google Calendar.

## So That
- The cadence is visible to everyone without remembering "next sprint = next-but-one Thursday 15:00 BRT".
- DoD becomes inspectable per release — at a glance, did v2.41 hit all its acceptance criteria?
- ICS export means the sprint planning + review + retro events land in everyone's calendar automatically.
- New team members orient in under 30 seconds: "open `/scrum/calendar`, see what shipped, what's next".

## Context

CO-368 establishes the sprint data model (`entry_type: sprint`, computed current sprint from cadence + anchor). CO-369 retro-generates past sprints. This spec is the renderer + calendar surface.

Bi-weekly cadence anchor: **2026-06-11 15:00 BRT** (Sprint 1 start = first sprint after CO-372 ships).

PR cutoff: PRs merged ≤ Wednesday 23:59 BRT (the day before) ship in Thursday's release; merged later roll to the next sprint.

## Design

### Endpoint

`GET /api/v1/scrum/calendar?past=N&future=N`

Default `past=6`, `future=4` → 10 sprints. Max 24 each direction.

Response:

```json
{
  "anchor": "2026-06-11T15:00:00-03:00",
  "length_days": 14,
  "now": "2026-06-05T...",
  "current_sprint": { "number": 0, "start_at": "...", "end_at": "..." },
  "sprints": [
    {
      "number": -1,
      "start_at": "2026-05-22T15:00:00-03:00",
      "end_at": "2026-06-04T15:00:00-03:00",
      "release_tag": "v2.39.0",
      "goal": null,
      "pbis_delivered": 6,
      "pbis_carried_over": 0,
      "dod_complete_pct": 100.0,
      "events": [
        { "type": "planning", "at": "2026-05-22T10:00:00-03:00" },
        { "type": "review", "at": "2026-06-04T15:00:00-03:00" },
        { "type": "retro", "at": "2026-06-04T16:00:00-03:00" }
      ]
    },
    ...
  ]
}
```

### SPA route `/scrum/calendar`

Renders:
- Header with current sprint number + Sprint Goal + countdown to next release
- Past sprints as collapsed cards (click to expand → PBIs + DoD)
- Future sprints as empty cards (just dates + planned events)
- Per-PBI: title + acceptance checklist with green/red state
- Velocity sparkline (last 12 sprints)

Reuses existing SPA chrome from CO-360 (`/gestao/resumo`).

### ICS export

`GET /api/v1/scrum/calendar.ics`

Emits standard `BEGIN:VCALENDAR` with 3 events per sprint (planning, review, retro). 15-min reminders. UID pattern: `sprint-{n}-{event}@co.artelonga.com.br`.

Subscription URL: paste into Google Calendar / Apple Calendar → auto-updates.

### PR cutoff awareness

`scripts/release-commit.sh` extension: check `git log` for merges after Wednesday 23:59 BRT in the current sprint window; if any, refuse and print "Merged after cutoff; rolls to Sprint {n+1}." Override flag `--ignore-cutoff` for emergency hotfixes.

Implement in a new helper `scripts/scrum/cutoff-check.ts` called by `release-commit.sh`.

### Cron-driven release

Optional `.github/workflows/sprint-release.yml` that runs every other Thursday at 15:00 BRT (18:00 UTC) and executes `scripts/release-commit.sh` with the next version computed from sprint number. Defer the actual cron wiring to a follow-up (CO-372-B) — this spec ships the calendar; the user can still run release-commit manually.

### DoD checkbox aggregation

Per sprint: walk all PBIs in `pbis_delivered`, parse their spec file's `## Acceptance` section, count `[x]` vs `[ ]`, compute `dod_complete_pct`. Reuses CO-369's parsing logic.

### Telemetry

Per CO-361 atividades:
- `event_type = scrum.calendar.viewed`
- `event_type = scrum.ics.subscribed` (when ICS URL is fetched with a User-Agent matching common calendar apps)
