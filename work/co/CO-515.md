GIVEN a self-hoster may want co-web to serve HTTPS directly rather than standing up
a reverse proxy or tunnel just to terminate TLS — a single-binary HTTPS deployment
is simpler for a private box or small LAN,
WHEN they supply a certificate and key,
THEN co-web must support native TLS via rustls behind `--tls-cert`/`--tls-key`
flags, terminating TLS in-process as a first-class alternative to a reverse
proxy / Cloudflare Tunnel, so the operator can choose direct TLS without extra
infrastructure.

## Acceptance checklist

- [ ] `--tls-cert <path>` and `--tls-key <path>` flags make co-web listen over HTTPS via rustls.
- [ ] Absent both flags, co-web serves plain HTTP as today (no behaviour change to the default path).
- [ ] Supplying only one of the pair fails loudly with a clear error (no half-configured TLS).
- [ ] Invalid/unreadable cert or key fails at boot with an actionable message, not a panic.
- [ ] `docs/SELF-HOST.md` documents native TLS vs reverse-proxy/tunnel, with the trade-offs.

## Notes
- An alternative to the reverse-proxy / Cloudflare Tunnel path documented for
  operators who want a public domain; native TLS suits a private box or LAN where
  running a separate proxy is overhead.
- rustls keeps it pure-Rust (no OpenSSL system dep), consistent with the thin-binary
  distribution (CO-513).
