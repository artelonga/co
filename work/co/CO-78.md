GIVEN doc generators (CO-72), changelog regeneration (CO-75), search index updates, and full-universe re-syncs are CPU-heavy non-real-time tasks that must NOT block request threads at scale,
WHEN we add a job queue + worker pool with retry, idempotency, and per-universe rate limiting,
THEN long-running tasks scale horizontally on dedicated machines without degrading API latency.

## Architecture

> **Migration PINNED 2026-06-14: v088** (`co-web/src/storage/migrations/v088.rs`).
> Train tip is v085; CO-458 claims v086, CO-449 claims v087, so this `jobs` table
> takes **v088**. Re-confirm max+1 vs open migration PRs before writing. Keep ALL
> job-queue schema in v088 (one migration file) — do not spill into v089.

- Queue: SQLite-backed initially (`jobs(id, universe_key, kind, payload, status, attempts, run_at, …)`); migrate to Redis Streams or NATS once SQLite contention shows
- Workers: separate Fly machines with toolchains pre-installed (Scala, Python, Node, Rust)
- Job kinds: `doc_gen`, `index_rebuild`, `changelog_regen`, `sync_pull`, `webhook_dispatch`, `cleanup`
- Idempotency: jobs have a content-derived dedupe key; submitting the same job twice = no-op
- Retry: exponential backoff, max 5 attempts, dead-letter queue for inspection
- Per-universe rate limit (CO-80): N jobs per hour per universe per kind

## Tasks

- [ ] `jobs` table with indexes on `(status, run_at, universe_key)`
- [ ] Submit API (internal): `enqueue_job(universe_key, kind, payload, dedupe_key)`
- [ ] Worker process: polls oldest pending job, claims with `UPDATE … SET status='running' WHERE id = … AND status='pending' RETURNING *`
- [ ] Worker pool: 4-16 Fly machines; autoscale on queue depth
- [ ] Dead-letter queue: jobs failing 5 times move to `dead_letter` for human review
- [ ] Per-job timeout (default 5 min, configurable per kind)
- [ ] Metrics: queue depth, p99 latency, success rate per kind

## Scale notes

- SQLite-backed queue handles 1K jobs/sec for v1; migrate to Redis once sustained > 5K/sec
- Worker autoscale: scale up on queue depth > 100, down when idle 5 min
- Doc-gen jobs ~30s each → 4 workers handle 480 jobs/hour; scale to 32 workers for 4K/hour
- Heavy jobs (full-universe re-index, changelog regen) get their own kind with stricter rate limits
- Idempotency prevents double-charging users on retry

## Acceptance

- Job submitted via API surfaces in queue immediately
- Workers claim and process in FIFO order with starvation protection (oldest pending always wins)
- Failed job retries with exponential backoff
- Dead-letter has at most 100 entries during normal operation
- Queue depth metric exposed via `/metrics` endpoint
