GIVEN typical bilingual dictionaries collapse meaning into translation pairs (mãe → mother), losing the cultural and metaphysical resonances that make a word meaningful inside its own world (in Mbyá, ancestral/maternal figures sit on a continuum with Earth and divinity; the *same* relation lives in Yoruba `ìyá` and many West African Bantu languages), AND existing embedding-based meaning models derive their topology from a single language's corpus first and then bolt translations on top, AND CO already has the right primitives (universe = bounded semantic space, entry = unit of meaning, CO-74 typed FK relations) to express a multi-plane meaning graph natively, AND `~/projects/mbya/` (Arandu) already provides a deep Mbyá lexicon with primary-source data — meaning the right design is for the cross-language topology to be a **layer above** Arandu, not a parallel word list,
WHEN we author a `concepts` universe (language-agnostic meaning anchors) plus three language universes (`guarani-mbya`, `portuguese`, `yoruba`) as a standalone content tree at `~/projects/topologia/`, with every term carrying typed references back to its concept anchor, to other terms within its own language (compounds, etymons, related forms), and to external sources (citation URLs + quoted content with embedded wikilinks),
THEN a learner or researcher can land on a single concept (e.g. `mother`) and see, side by side, how three traditions name and inflect it — including within-language structure (`pyau` lives inside `jaxy pyau` and `ara pyau`), cross-language sibling terms, and the source texts that ground each entry — making CO the first version of "embedding from relations across languages" rather than "translation pairs decorated with metadata."

## Vision

Each language is a graph plane. The `concepts` universe is the high-level low-dimension topology where most cultures share anchors (kinship, nature elements, spirituality, time, language, body, kosmos). Language universes are denser planes whose terms project onto concept anchors. The same concept may attract very different *clouds* of terms in different languages — and that asymmetry is the data, not noise.

Long-term: we want users to assemble particles → words → sentences as composable entries linked by morphology and meaning, not just look-up. Definitions are optional; the primary signal is the relation graph.

**Out of scope** (each becomes a separate CO-1XX follow-up):

- **Cross-universe typed relations** — today `entry_relations(universe_key, from_path, to_path, relation_type)` is per-universe. Cross-plane links need either `to_universe TEXT` added to the schema, or a path convention (`co://...`) the extractor recognizes.
- **References as a first-class content type** — currently stored as a frontmatter array + body excerpt. Promote to `references` rows in their own table so they're searchable, dedupable across terms, and retrievable as a citation index.

- **Display-layer i18n** — chrome labels (Concept, Parts, References, Sources) need translation in the Co UI. Term content itself stays in each term's native language; this is a UI concern, not a content concern.
- **Lexicon imports (Wiktionary, Yoruba reference dictionaries)** — downstream tickets can parametrize the structure to ingest external corpora.

## Schema design

### `concepts` universe

```yaml
# _universe.yaml
name: concepts
version: 1
content_types:
  - concept
properties:
  domain:
    kind: enum
    values: [kinship, nature, spirituality, time, language, body, kosmos]
    required: true
  realized_in:
    kind: ref_list   # term entries across language universes (cross-universe; see "Out of scope")
```

### Language universes (`guarani-mbya`, `portuguese`, `yoruba`)

```yaml
# _universe.yaml
name: guarani-mbya
language_code: gn-mbya
version: 1
content_types:
  - term
properties:
  word:
    kind: text
    required: true
  pronunciation:
    kind: text
  concept:
    kind: ref       # cross-universe → concepts/<name>.md
  parts:
    kind: ref_list  # within-language morphological breakdown
  appears_in:
    kind: ref_list  # compounds that use this term
  related:
    kind: ref_list  # within-language meaning siblings
  references:
    kind: list      # array of {url, source, retrieved} citation objects
  seed_status:
    kind: enum
    values: [draft, reviewed, native-confirmed]
```

### References + linked content

Each term may carry an array of external citations:

```yaml
references:
  - url: https://meuorixa.wordpress.com/2013/05/02/yemanja-ogunte/
    source: "meuorixa.wordpress.com — Yemanjá Ogunté"
    retrieved: 2026-05-01
```

The actual quoted content lives in the body under a `## Referência:` heading, with `[[wikilinks]]` inserted for every term we have an entry for and TODO markers for terms we don't yet have. This makes the dictionary self-extending: each new reference's content becomes a list of candidate term entries to author.

### Cross-universe linking convention (interim)

Until typed relations cross universe boundaries, store cross-plane refs as path strings with a `co://` prefix in frontmatter, e.g.:

```yaml
concept: "co://concepts/mother.md"
```

The relation extractor will treat these as untyped string fields for now (no graph row written). The follow-up ticket defines the schema migration.
