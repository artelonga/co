GIVEN the entire user-content surface lives on a single Fly volume (`/data` on machine 1850920b111d38), AND volume snapshots provided by Fly are operator-managed but not user-driven nor cross-region, AND we cannot honestly invite real users to upload content with no documented recovery story,
WHEN we add a daily cron snapshot of `/data/co.db` and `/data/universes/` to an S3-compatible bucket plus a tested `restore.sh` that can pull a named backup into a target Fly app,
THEN any disk corruption, accidental wipe, or single-region Fly outage costs at most ≈24 hours of data and 5 minutes of restore time, instead of being catastrophic.

## Scripts

### `scripts/backup-prod.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
APP=${APP:-co-artelonga}
BUCKET=${BUCKET:-artelonga-co-backups}
DATE=$(date -u +%Y%m%d-%H%M%S)
WORK=$(mktemp -d)
trap "rm -rf $WORK" EXIT

# 1. Snapshot SQLite via the official .backup command (atomic, no lock).
flyctl ssh console -a "$APP" -C "sqlite3 /data/co.db '.backup /tmp/co.db.bak'"
flyctl ssh sftp get -a "$APP" /tmp/co.db.bak "$WORK/co-$DATE.db"
flyctl ssh console -a "$APP" -C "rm /tmp/co.db.bak"

# 2. Tar the universes directory.
flyctl ssh console -a "$APP" -C "tar czf /tmp/universes.tar.gz -C /data universes"
flyctl ssh sftp get -a "$APP" /tmp/universes.tar.gz "$WORK/universes-$DATE.tar.gz"
flyctl ssh console -a "$APP" -C "rm /tmp/universes.tar.gz"

# 3. Upload both artifacts.
aws s3 cp "$WORK/co-$DATE.db" "s3://$BUCKET/co.db/$DATE.db"
aws s3 cp "$WORK/universes-$DATE.tar.gz" "s3://$BUCKET/universes/$DATE.tar.gz"

# 4. Retention: 30 daily, 12 monthly.
# (deferred — first ship the daily upload; retention via lifecycle policy is
# easier than scripting and survives script bugs)

echo "Backup ${DATE} uploaded."
```

### `scripts/restore.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
DATE=${1:?Usage: restore.sh <YYYYMMDD-HHMMSS> [target-app]}
TARGET=${2:-co-artelonga-uat}
BUCKET=${BUCKET:-artelonga-co-backups}
WORK=$(mktemp -d)
trap "rm -rf $WORK" EXIT

aws s3 cp "s3://$BUCKET/co.db/$DATE.db" "$WORK/co.db"
aws s3 cp "s3://$BUCKET/universes/$DATE.tar.gz" "$WORK/universes.tar.gz"

# Stop the target app, replace files, restart.
flyctl ssh console -a "$TARGET" -C "sqlite3 /data/co.db 'PRAGMA wal_checkpoint(TRUNCATE);' || true"
flyctl ssh sftp put -a "$TARGET" "$WORK/co.db" /data/co.db
flyctl ssh sftp put -a "$TARGET" "$WORK/universes.tar.gz" /tmp/universes.tar.gz
flyctl ssh console -a "$TARGET" -C "rm -rf /data/universes && tar xzf /tmp/universes.tar.gz -C /data && rm /tmp/universes.tar.gz"
flyctl machine restart -a "$TARGET"

echo "Restored $DATE into $TARGET."
```

## Cron strategy

**Option A — separate Fly app `co-backup-cron`** (recommended)
- Tiny `alpine + flyctl + awscli` image
- Runs `scripts/backup-prod.sh` daily at 03:17 UTC (off-minute, see CronCreate convention)
- Logs to its own app's stream
- Failure mode is independent of prod

**Option B — GitHub Actions cron**
- `.github/workflows/backup.yml` schedules daily
- Needs Fly token + AWS creds in repo secrets
- Lighter to set up but couples to GitHub (we are deprecating GitHub for work tracking — but CI/cron may stick around longer)

**Decision:** start with Option A. Document Option B in the spec as a fallback if/when we pull off Fly.

## Bucket setup

- Bucket: `artelonga-co-backups` (or whatever yuri picks)
- Region: `us-east-1` (Cloudflare R2 / Backblaze B2 also acceptable, S3-compatible)
- Lifecycle: transition to IA after 30 days, delete after 365 days
- Encryption at rest: SSE-S3 (provider-managed). User-managed key is overkill for backups when the live DB is plaintext.
- Access: dedicated IAM user with PutObject/GetObject on this bucket only

## First-run checklist

1. Create the bucket; configure lifecycle.
2. Generate IAM credentials; store in `~/.aws/credentials` locally and in `co-backup-cron` secrets.
3. Run `scripts/backup-prod.sh` manually; verify both artifacts in bucket.
4. **Restore test against UAT.** Pick yesterday's prod backup; run `scripts/restore.sh <date> co-artelonga-uat`; verify yuri can log in to UAT and see same universes.
5. Set up cron app; let one full daily cycle run; confirm second snapshot lands.

## Constraints

- No interactive prompts in either script — they must run in cron.
- Scripts are idempotent: re-running the same date overwrites (S3 PUT, no conflict).
- Total backup time should be ≤ 5 min for our current data (~MB scale). Re-evaluate when DB hits 1 GB.
- `restore.sh` must NOT default to prod target — fail loud if target=`co-artelonga` without an explicit `--yes-i-want-to-overwrite-prod` flag.

## Out of scope

- Cross-region replication of the bucket.
- Point-in-time recovery (PITR) — would need WAL streaming, big jump.
- Backup of the Fly machine config / secrets (separate concern; `flyctl config save` works for that).
- Encrypted-at-rest backups of an encrypted DB (CO-86 territory).
