## As

a CO operator wanting to know what happened, when, and which migration version is live

## I Need

a typed `atividades` audit log writing every meaningful action with a before/after diff, plus a `schema_versoes` table that records every migration with the app version that applied it — both surfaced in the `/gestao` admin SPA.

## So That

- "Who deleted that entry?" is answerable in 5 seconds, not "let me check Fly logs".
- After every deploy I can verify at a glance: DB schema v56 / app v2.39.0 → matches expected, container is up to date.
- The audit log is fast: deferred-write via `tokio::spawn`, never adds TTFB to the originating request.
- Sensitive fields (passwords, tokens) are redacted in the diff JSON before write — never logged in plaintext.
- IP addresses are SHA256→16-char-hashed; we keep enough signal for "same visitor" without storing the raw IP.

## Context

### Reference — Quilombo

- `/Users/artelonga/projects/quilomboaraucaria/web/src/lib/server/atividade.ts` — `logAtividade()` helper, SENSITIVE_KEYS redactor, deferred write via `setImmediate`. CO's equivalent is `tokio::spawn`.
- `/Users/artelonga/projects/quilomboaraucaria/web/src/lib/server/db/index.ts:823` — `schema_versoes` table pattern: `(versao INTEGER PRIMARY KEY, descricao TEXT, versao_app TEXT, applied_at TEXT)` with one INSERT per migration on success.

### CO today

- `core/src/telemetry.rs` (via CO-291) emits CRUD events into `telemetry_events`, but it's a flat event stream — no before/after, no typed action enum, no redaction, no error/success distinction.
- `co-web/src/storage/migrations.rs` writes only `(version INTEGER)` into `schema_version` — no description, no app version, no timestamp.
- After every deploy I can't tell, by looking at the DB, which migration the running container last applied without grepping the migration source.

## Design

### Part A — `atividades` audit log

#### A.1 Schema (new migration v18)

Add `/Users/artelonga/projects/co/co-web/src/storage/migrations.rs` step v18:

```sql
CREATE TABLE atividades (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  acao TEXT NOT NULL CHECK (acao IN ('criar','ler','atualizar','excluir','login','logout')),
  entidade TEXT NOT NULL,           -- 'task' | 'universe' | 'user' | 'session' | ...
  entidade_id TEXT,                 -- string PK of the affected row (nullable for 'login')
  conteudo TEXT,                    -- JSON: { before: {...}, after: {...} } with sensitive keys redacted
  tipo TEXT NOT NULL CHECK (tipo IN ('sucesso','erro','navegacao','sistema')),
  user_id TEXT,                     -- nullable for anonymous
  ip_hash TEXT,                     -- SHA256(ip)[:16]
  user_agent TEXT,
  versao_app TEXT,                  -- e.g. '2.40.0' — captured at write time
  criado_em TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_atividades_criado ON atividades(criado_em DESC);
CREATE INDEX idx_atividades_user   ON atividades(user_id, criado_em DESC);
CREATE INDEX idx_atividades_acao   ON atividades(acao, entidade, criado_em DESC);
```

#### A.2 Helper

New file `/Users/artelonga/projects/co/co-web/src/platform/atividade.rs`:

```rust
pub enum Acao { Criar, Ler, Atualizar, Excluir, Login, Logout }
pub enum Tipo { Sucesso, Erro, Navegacao, Sistema }

pub struct Atividade {
    pub acao: Acao,
    pub entidade: String,
    pub entidade_id: Option<String>,
    pub before: Option<serde_json::Value>,
    pub after: Option<serde_json::Value>,
    pub tipo: Tipo,
    pub user_id: Option<String>,
    pub ip: Option<String>,
    pub user_agent: Option<String>,
}

const SENSITIVE_KEYS: &[&str] = &[
    "password", "password_hash", "token", "api_token", "jwt",
    "secret", "private_key", "ssh_key", "session_token",
];

pub fn log_atividade(state: AppState, atividade: Atividade) {
    tokio::spawn(async move {
        let conteudo = redact(json!({"before": atividade.before, "after": atividade.after}));
        let ip_hash = atividade.ip.map(|ip| sha256_short(&ip));
        let versao = env!("CARGO_PKG_VERSION");
        // INSERT INTO atividades (...) VALUES (...)
        // Best-effort; log warn on failure, never bubble.
    });
}
```

`redact()` walks the JSON tree; any key in `SENSITIVE_KEYS` (case-insensitive) gets `"[REDACTED]"` regardless of depth.

`sha256_short(ip)` = `format!("{:x}", Sha256::digest(ip.as_bytes()))[..16].to_string()`.

#### A.3 Wiring

Add `log_atividade()` calls at meaningful sites:

| Site | Acao | Entidade |
|---|---|---|
| `co-web/src/routes/tasks_routes.rs::create_task` | Criar | task |
| `co-web/src/routes/tasks_routes.rs::update_task` | Atualizar | task |
| `co-web/src/routes/tasks_routes.rs::delete_task` | Excluir | task |
| `co-web/src/routes/universe_routes.rs::create_universe` | Criar | universe |
| `co-web/src/routes/universe_routes.rs::delete_universe` | Excluir | universe |
| `co-web/src/auth/login_routes.rs::login` | Login | user |
| `co-web/src/auth/login_routes.rs::logout` | Logout | user |
| Anything else that mutates and matters — let it be a follow-up; ship the helper + the obvious sites |

All call sites use the deferred-write helper — never blocking the response.

#### A.4 Surface

Powers the **Atividades** tab in the `/gestao` SPA (CO-360 §4):

- `GET /api/v1/gestao/atividades?limit=50&since=<iso>&acao=excluir` — paginated, filterable
- Renders as a feed: `[icon by acao] <user> <acao> <entidade> <entidade_id> · <relative time> · [diff]` where `[diff]` opens a side panel with the JSON before/after.

### Part B — `schema_versoes`

#### B.1 Schema (same migration v18)

```sql
CREATE TABLE schema_versoes (
  versao INTEGER PRIMARY KEY,
  descricao TEXT NOT NULL,
  versao_app TEXT NOT NULL,        -- e.g. '2.40.0'
  applied_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- Backfill rows for migrations 1..17 with descricao='(backfilled)' and versao_app='unknown'
INSERT OR IGNORE INTO schema_versoes (versao, descricao, versao_app)
  SELECT version, '(backfilled)', 'unknown' FROM schema_version;
```

#### B.2 Migration step pattern

Modify `co-web/src/storage/migrations.rs`: every existing `INSERT INTO schema_version (version) VALUES (N);` step is followed by:

```rust
self.conn.execute(
    "INSERT OR IGNORE INTO schema_versoes (versao, descricao, versao_app) VALUES (?1, ?2, ?3)",
    params![N, "<short description of what this migration does>", env!("CARGO_PKG_VERSION")],
).expect("Failed to record schema version");
```

Going forward (v19+), every new migration must include both inserts.

Helper macro to avoid drift:

```rust
macro_rules! record_migration {
    ($self:ident, $version:expr, $desc:expr) => {
        $self.conn.execute("INSERT INTO schema_version (version) VALUES (?1)", params![$version]).expect(...);
        $self.conn.execute(
            "INSERT OR IGNORE INTO schema_versoes (versao, descricao, versao_app) VALUES (?1, ?2, ?3)",
            params![$version, $desc, env!("CARGO_PKG_VERSION")],
        ).expect(...);
    };
}
```

#### B.3 Surface

Two things:

1. **Header strip on `/gestao`**: "DB schema v56 / app v2.40.0" — green if matches the migration list compiled in, red badge if drift (e.g. schema older than expected for this app version).
2. Feed in the `resumo` endpoint payload (CO-360 §1) — `schema_versao` + `app_versao` fields already specified.

### Privacy

- Sensitive keys redacted before insert (never plaintext at rest).
- IPs hashed SHA256 → first 16 hex chars (sufficient for "same visitor" cohorting, not reversible).
- `atividades` retention: keep 180 days, then nightly job deletes older (`tokio::spawn` background worker, runs once at boot + daily).
- User-agent kept verbatim (already public client info).
