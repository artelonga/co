GIVEN CO's only WhatsApp channel was the unofficial `EvolutionApiProvider`
(Baileys / WhatsApp-Web), which violates WhatsApp's ToS and is not
enterprise-compliant (no SLA, no DPA, ban risk),
WHEN we add a provider for Meta's **official WhatsApp Cloud API** (Graph API)
plus the inbound webhook Meta calls, behind the existing `ChannelProvider`
trait and the same HMAC-verified-in-handler posture as the billing webhook,
THEN CO can send and receive WhatsApp over a compliant, verifiable transport
the moment a verified WhatsApp Business Account + number exist — a drop-in swap,
not a rewrite — while the local Evolution bot stays as the dev/personal channel.

## Acceptance

- [x] `CloudApiProvider` implements `ChannelProvider` (channel `"whatsapp"`),
  `from_env()` reads `WHATSAPP_CLOUD_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID`
  (+ optional `WHATSAPP_GRAPH_VERSION`, default `v21.0`); `send()` POSTs a text
  message to `graph.facebook.com/{ver}/{phone_number_id}/messages` with a
  `Bearer` token. Unit-tested (`messages_url`, channel name).
- [x] Inbound webhook `GET/POST /api/v1/whatsapp/webhook`
  (`integrations/whatsapp_cloud_routes.rs`), no auth gate, registered in the
  router next to the billing webhook. GET echoes `hub.challenge` when
  `hub.verify_token` == `WHATSAPP_VERIFY_TOKEN`; POST verifies
  `X-Hub-Signature-256: sha256=<hmac>` against `WHATSAPP_APP_SECRET` (reusing
  `billing::hmac_sha256_hex` + `constant_time_eq`) and parses inbound text.
- [x] Signature + parse are pure, unit-tested (valid/forged/missing-prefix/
  wrong-secret; message extraction; status-only callbacks → empty).
- [x] `recovery_routes::deliver_whatsapp_code` prefers `CloudApiProvider`
  (compliant) and falls back to `EvolutionApiProvider` — demonstrating the
  provider swap with no behavioural change when Cloud is unconfigured.
- [x] `cargo test` (new tests) + `cargo clippy -- -D warnings` + `cargo fmt` clean.
- [x] Onboarding runbook `docs/integrations/whatsapp-cloud-api.md`: Meta steps
  (Business verification, WABA, number, tokens), env vars, public-webhook
  hosting (Fly / tunnel), template + opt-in (LGPD) notes.

## Out of scope / follow-ups

- **CO-480**: wire the inbound webhook to the bot brain + auto-reply via
  `CloudApiProvider` (the brain currently lives in the `whatsapp-bot` bridge).
- Message **template** registry for business-initiated messages outside the 24h
  customer-service window (Meta-approved templates).
- Per-recipient **opt-in/consent** record (LGPD) before any business-initiated send.
- BSP variant (Take Blip / Zenvia / 360dialog) — same trait, different base URL/auth.
