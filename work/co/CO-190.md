## As

a person arriving at `co.artelonga.com.br` (or `quilomboaraucaria.org`) who
just wants to get in with their email — they may or may not already have
an account, they don't want to choose a username, set a password, or pick
between "Sign in" and "Sign up"

## I Need

a single "Continuar com email" entry point that takes only an email,
emails me a 6-digit code, and on verify either logs me in (if I already
have a CO account) or creates one (auto-deriving a usuario from the
email's local-part) and logs me in

## So That

I never see a "no account exists" dead-end. The flow is identical for
new users and returning users from the user's perspective — Slack /
Notion / Linear-style passwordless onboarding.

---

## Why this is distinct from `/forgot-password`

Today (1.96.2) `/forgot-password` is a **recovery** endpoint — it requires
an existing CO or quilombo identity to recover from. Per the
no-enumeration policy it returns 202 with `sent_to: []` for unknown
identifiers, never sending mail. Surfaced repeatedly when testing with
fresh emails like `retrocore@artelonga.com.br`: the system silently does
nothing because there's nothing to recover.

This ticket adds a separate flow that is **explicitly an onboarding
endpoint**. It can send mail to a previously-unknown email because the
verify step provisions an account as a side effect. The two flows live
side-by-side; `/forgot-password` keeps its no-enumeration semantics.

## Endpoints

### `POST /api/v1/auth/onboard-with-email` (no auth)

Request:
```jsonc
{
  "email": "guest@example.com",
  "preferred_usuario": "guest",      // optional; if absent, derived from email local-part
  "return_to": "/some-universe"      // optional; for post-login redirect
}
```

Logic:
1. Validate email format (basic: contains `@`, length ≤ 254).
2. Rate-limit by email AND by IP — 5 codes per email per hour, 20 per IP
   per hour. (Reuses CO-165's rate-limit infra; new keys
   `onboard:email:<hash>` and `onboard:ip:<ip>`.)
3. Lookup `users.email` — if found, this becomes a **login flow**. If
   not, this becomes a **create flow**. Both paths converge on:
4. Mint a 6-digit code, hash with Argon2id, store in
   `onboarding_codes` table (new — see schema below) keyed by
   `email_lookup_hash`. Persist `intent: 'login'|'create'`.
5. Send the code to the email via the existing Resend cascade. Subject:
   `Seu código de acesso ao CO`. Body PT:
   ```
   Olá,

   Seu código de acesso é {code}.

   Se você ainda não tem conta, ela será criada automaticamente quando
   você confirmar este código.

   O código expira em 10 minutos.
   ```
6. Return 202 `{sent: true, expires_at}`. **Crucially — return non-empty
   `sent: true` even for unknown emails**, since this is an onboarding
   endpoint and that's the intended behavior. (Distinct from forgot-password,
   which returns `sent_to: []` for unknown emails to avoid enumeration.)

### `POST /api/v1/auth/onboard-with-email/verify` (no auth)

Request:
```jsonc
{
  "email": "guest@example.com",
  "code": "123456"
}
```

Logic:
1. Look up `onboarding_codes` by `email_lookup_hash`.
2. 410 if not found, expired, or already consumed.
3. Verify code (Argon2id). On wrong code, increment `attempts`; lock the
   row at `attempts >= 5` (same lockout pattern as `forgot-password/verify`).
4. Branch on `intent`:
   - **`login`**: load existing user → mint session JWT → set cookie.
   - **`create`**:
     - Pick a usuario: prefer `preferred_usuario` if available and unique;
       else derive from email local-part with the existing dedupe-suffix
       chain (`yuri-2`, `yuri-3` etc per migration v37 logic).
     - INSERT into `users` (no `password_hash` yet — user can set one later
       via change-password).
     - Run CO-184 reverse bridge to create `quilombo_usuarios` row.
     - Run `ensure_email_recovery_channel` so future `/forgot-password`
       works.
     - Mint session JWT → set cookie.
5. Mark `onboarding_codes` row consumed.
6. Return 200 `{user_id, email, display_name, expires_at, return_to}`.

### Schema — migration v41

```sql
CREATE TABLE IF NOT EXISTS onboarding_codes (
    id                  TEXT PRIMARY KEY,
    email_lookup_hash   TEXT NOT NULL,        -- compute_lookup_hash(normalize_channel_value("email", email))
    intent              TEXT NOT NULL,        -- 'login' | 'create'
    code_hash           TEXT NOT NULL,        -- argon2id of the 6-digit code
    preferred_usuario   TEXT,                 -- nullable; only meaningful when intent='create'
    return_to           TEXT,                 -- nullable; for post-verify redirect
    expires_at          TEXT NOT NULL,        -- created_at + 10 minutes
    consumed_at         TEXT,                 -- single-use
    attempts            INTEGER NOT NULL DEFAULT 0,
    created_at          TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_onboarding_codes_lookup
    ON onboarding_codes(email_lookup_hash, consumed_at);
INSERT OR IGNORE INTO schema_version (version) VALUES (41);
```

`email_lookup_hash` is hashed (not the raw email) so the table is safe
to dump for debugging. Plaintext only ever lives in the email body.

## Storage helpers

In `co-web/src/storage/onboarding.rs` (new):

```rust
impl Storage {
    pub fn create_onboarding_code(
        &self,
        email_lookup_hash: &str,
        intent: &str,                 // "login" | "create"
        code_hash: &str,
        preferred_usuario: Option<&str>,
        return_to: Option<&str>,
        expires_at: &str,
    ) -> anyhow::Result<()>;

    pub fn get_onboarding_code(&self, email_lookup_hash: &str) -> Option<OnboardingCode>;
    pub fn consume_onboarding_code(&self, id: &str) -> anyhow::Result<()>;
    pub fn increment_onboarding_attempts(&self, id: &str) -> anyhow::Result<i64>;
    pub fn cleanup_expired_onboarding_codes(&self) -> usize;  // run on boot
}
```

Plus a `derive_usuario_from_email(email, storage) -> String` helper that
strips the local-part, lowercases, replaces non-alphanumeric with `-`,
then dedupes via the existing `usuario UNIQUE` collision-suffix chain
(`yuri`, `yuri-2`, `yuri-3` ...).

## UI

### Login modal — new primary entry point

Promote "Continuar com email" to the **first** option above the existing
username/password tabs and Google button:

```
┌────────────────────────────────────┐
│  Entrar no CO                       │
│                                     │
│  ┌──────────────────────────────┐ │
│  │ email@exemplo.com           │ │
│  └──────────────────────────────┘ │
│  [ Continuar com email ]            │
│                                     │
│  ───────  ou  ────────              │
│                                     │
│  [ G  Continuar com Google ]        │
│                                     │
│  Já tem usuário e senha? ▼          │
│  (collapsible: classic login form)  │
└────────────────────────────────────┘
```

On submit → POST `/onboard-with-email` → switch to code-entry view:

```
┌────────────────────────────────────┐
│  Verifique seu email                │
│                                     │
│  Enviamos um código para            │
│  guest@example.com                  │
│                                     │
│  ┌──────────────┐                   │
│  │ 6 dígitos    │                   │
│  └──────────────┘                   │
│  [ Confirmar ]                      │
│                                     │
│  Não recebeu? [Reenviar] · [Editar] │
└────────────────────────────────────┘
```

On verify success → set cookie → redirect to `return_to` or `/`.

Identity-mismatch / abuse handling on the form:
- "Reenviar" disabled for 60s after each send.
- "Editar email" goes back to the previous step.
- After 5 failed code attempts: card flips to "Código bloqueado.
  Solicite um novo código."

### "Esqueci minha senha" stays as-is

Still routes through `/forgot-password` for users who *know* they have
an account but lost the password. The new flow is for users who don't
know whether they have an account.

## Email template

PT default; EN translation key. Subject line + body localized via the
existing email-localization plumbing CO-165 introduced.

## Rate-limit / abuse considerations

| Limit | Scope | Window | Existing infra reused |
|---|---|---|---|
| 5 codes per email | by `email_lookup_hash` | 1 hour | rate_limit module (CO-165) |
| 20 codes per IP | by client IP | 1 hour | rate_limit module |
| 100 new accounts per day | global signup | 24 hours | `count_users_created_since` (CO-175) |
| 5 wrong code attempts | per onboarding row | per row | new `attempts` column |

## Acceptance

- [ ] Migration v41 creates `onboarding_codes` table + index.
- [ ] `POST /api/v1/auth/onboard-with-email` works for unknown email,
      sends code via Resend, stores `intent='create'`, returns 202.
- [ ] `POST /api/v1/auth/onboard-with-email` works for known email,
      stores `intent='login'`, sends code, returns 202.
- [ ] `POST /api/v1/auth/onboard-with-email/verify` with correct code
      and `intent='login'` mints a session for the existing user.
- [ ] `POST /api/v1/auth/onboard-with-email/verify` with correct code
      and `intent='create'` creates a `users` row with derived usuario,
      creates the quilombo bridge, sets the email recovery channel,
      mints a session.
- [ ] Wrong code 5 times → 410, code locked.
- [ ] Re-using a consumed code → 410.
- [ ] Expired code (>10min) → 410.
- [ ] Tests: 8+ covering happy login, happy create, unknown email rate-
      limit, wrong-code lockout, consumed-code reuse, identity bridge
      side effects, deriving usuario from local-part, collision suffix.
- [ ] UI: "Continuar com email" is the primary login affordance.
      Code-entry view appears, "Reenviar" disabled 60s.
- [ ] After verify with `intent='create'`, the user can immediately set
      a password via the existing change-password modal (already a
      no-current-password edge: extend it to skip the verify step when
      `users.password_hash IS NULL`, or require email-channel-code
      instead — small follow-up).
- [ ] No-enumeration semantics of `/forgot-password` are unchanged.

## Out of scope (defer or split)

- **Magic-link variant** (clickable URL instead of typing a code).
  Code-only is simpler and enough for v1.
- **Display-name selection on first verify**. Use email local-part as
  display_name initially; user can edit later in profile.
- **TOS / privacy acceptance UI flow**. Add as a separate ticket if
  legal requires it.
- **WebAuthn / passkeys**. Different endpoint family entirely.
- **Onboarding analytics events** (CO-177..182 workstream).
- **First-time onboarding wizard inside the universe view** (which
  template to clone, which preset, etc). Just gets the user logged in;
  what they see after is governed by the existing landing flow.
