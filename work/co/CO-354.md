## As

a universe owner curating user-contributed content (mbya term suggestions, comunicacao source submissions, event proposals from visitors) — and as a visitor who wants to *contribute* a correction or a new entry without commit access — I need a moderated path between "suggestion from anyone" and "published in the universe."

## I Need

a generalized suggest/review pipeline as a CO primitive: a `review_status` lifecycle on every entry, an anon-friendly `POST /api/v1/universes/{key}/suggest` endpoint, an owner-facing review queue at `/u/{key}/review`, and approve/edit/reject actions.

## So That

- Yggdrasil's `seed_status: draft|reviewed|native-confirmed` pattern (currently bespoke to mbya/yoruba lexicon) becomes universal.
- The `btn-sugerir` from CO-352's Sala has a real backend — clicking it actually drafts a reviewable entry.
- Universes can open up to community contribution without granting write access.
- The "anon can suggest" half + "owner reviews" half compose cleanly with everything else (notifications, atividades log, surface keys).

## Context

### Today

- Yggdrasil has `seed_status` on mbya/yoruba term frontmatter — bespoke, hand-curated, no review UI.
- CO has no concept of draft entries: every entry an author creates is immediately published/visible.
- CO-329 ships notifications (email + in-app); we tap it for "you got a new suggestion."
- CO-351 (in flight) is an atividades log — every review action emits one.

## Design

### Frontmatter / schema

New optional field on every entry:

```yaml
review_status: draft       # draft | reviewed | published (default: published)
submitted_by: anon:abc123  # user_id or anon:<session> (set only when not the universe owner)
submitted_at: 2026-06-05T12:00:00Z
reviewed_by: <user_id>     # nullable
reviewed_at: <iso>         # nullable
```

`review_status` defaults to `published` so existing entries are unaffected — this is purely additive.

### Schema (additive migration)

```sql
ALTER TABLE entries ADD COLUMN review_status TEXT NOT NULL DEFAULT 'published';
ALTER TABLE entries ADD COLUMN submitted_by TEXT;
ALTER TABLE entries ADD COLUMN submitted_at TEXT;
ALTER TABLE entries ADD COLUMN reviewed_by TEXT;
ALTER TABLE entries ADD COLUMN reviewed_at TEXT;
CREATE INDEX idx_entries_review_status ON entries (universe_key, review_status)
  WHERE review_status != 'published';
```

The partial index keeps reads cheap — only draft/reviewed rows are indexed.

### Endpoints

| Method | Route | Auth | Notes |
|---|---|---|---|
| `POST` | `/api/v1/universes/{key}/suggest` | optional | Body: `{entry_type, path?, title, body, frontmatter?}`. Creates entry with `review_status: draft`. |
| `GET` | `/api/v1/universes/{key}/review` | owner/admin | Lists draft + reviewed entries (newest first) |
| `POST` | `/api/v1/universes/{key}/review/{entry_id}/approve` | owner | Sets `review_status: reviewed` then `published` (one-step or two-step configurable) |
| `POST` | `/api/v1/universes/{key}/review/{entry_id}/reject` | owner | Deletes (or moves to `rejected/` archive — TBD) |
| `PATCH` | `/api/v1/universes/{key}/entries/{path}` | owner | Edit-then-approve in one shot |

### Rate-limiting & anti-spam

- Anon `POST /suggest`: 5/hour per IP, 20/day per IP (existing rate limiter from CO-329 family — reuse).
- Honeypot field on the public suggest form.
- Optional: require email for anon submissions (kept private; never displayed).

### Review queue UI

- New page at `/u/{key}/review` (rendered by `co-web/static/variants/a/pages/review.js` — new module).
- Or per-owner global queue at `/gestao/review` aggregating across owned universes.
- Each row: type, title preview, submitted_by (anon name or @handle), submitted_at, body excerpt, [Approve] [Edit & Approve] [Reject] buttons.
- Filter by universe, type, status. Sort by date.

### Suggest form

- Reachable from:
  - `btn-sugerir` in Sala (CO-352)
  - Standalone public form at `/u/{key}/suggest` (linked from universe footer or a "contribute" button)
- Anon: optional name + email + body. Login CTA: "Want attribution? Sign in."
- Authenticated: name pre-filled, email hidden.

### Notifications

- On `POST /suggest`: enqueue notification to owner (uses CO-329 notif system). Email + in-app.
- On approve/reject: notify submitter if they provided an email (or via in-app if logged in).

### Atividades log (CO-351 tie-in)

Each lifecycle transition emits an atividade:

```
{
  kind: "entry.suggest" | "entry.review.approve" | "entry.review.reject" | "entry.review.edit",
  universe_key, entry_id, actor (user or anon), from_status, to_status
}
```

### Read filtering

- Public list endpoints (`GET /entries`) return only `review_status = published` by default.
- `?include_drafts=1` requires owner/admin.
- Drafts visible to their submitter even when anon (via session cookie).

## Acceptance

- [ ] Migration adds 5 columns + partial index (idempotent)
- [ ] `POST /suggest` accepts anon submissions, rate-limited
- [ ] Submitted entries land with `review_status: draft`, hidden from public listings
- [ ] Submitter can see their own draft via session (anon) or login (authenticated)
- [ ] Owner sees review queue at `/u/{key}/review` with pending items
- [ ] Approve → entry becomes `published`, appears in public listings
- [ ] Reject → entry removed (or archived; pick one and document)
- [ ] Edit-then-approve mutates body/frontmatter then publishes
- [ ] Owner notified on new suggestion (email + in-app via CO-329)
- [ ] Submitter notified on approve/reject (if email/login provided)
- [ ] Atividades log records every lifecycle transition (if CO-351 shipped)
- [ ] `btn-sugerir` in Sala (CO-352) wired to this endpoint
- [ ] E2E test: anon submits → owner approves → entry visible in public listing

- 1 migration (5 columns + 1 partial index)
- ~200 lines new `review_routes.rs`
- ~150 lines `suggest_routes.rs`

- ~80 lines suggest form (frontend)

## Dependencies

- **CO-329** (notifications) — required for owner/submitter alerts
- **CO-352** (workspace primitive) — `btn-sugerir` endpoint consumer
- **CO-351** (atividades log) — soft dep; emit if available, no-op otherwise

## Not in scope

- Multi-reviewer / quorum / N-eyes approval — single-owner approval only
- Diff view between draft and current published version — Phase 2
- Public "see what's pending" page — review queue is owner-only
- Git PR-style branching of suggestions — out of scope; suggest is flat
- Spam ML classifier — rate limit + honeypot is enough for v1
- Versioned history of edits during review — relies on entry history (separate concern)
