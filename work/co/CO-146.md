## As

an admin trying to migrate 506 MB of quilomboaraucaria content (markdown + images) into a CO universe today

## I Need

a `POST /api/v1/universes/{u}/assets` endpoint that accepts arbitrary bytes, content-addresses them by sha256, stores them at `data/universes/<aa>/<bb>/<key>/blobs/<aa>/<bb>/<sha256>`, indexes a row in the per-universe `assets` table, and returns `{sha256, mime, size, url}`

## To

unblock binary content the Vault API rejects today (it only accepts `String` markdown bodies), without prematurely shipping encryption (CO-148) before the basic upload path works

---

## Implementation

### Migration (per-universe data.db)

```sql
CREATE TABLE IF NOT EXISTS assets (
    sha256          TEXT PRIMARY KEY,
    blob_path       TEXT NOT NULL,
    mime            TEXT NOT NULL,
    size_bytes      INTEGER NOT NULL,
    filename        TEXT,
    created_at_ns   INTEGER NOT NULL,
    created_by      TEXT,
    refcount        INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_assets_mime ON assets(mime);
CREATE INDEX IF NOT EXISTS idx_assets_created_at ON assets(created_at_ns);
```

Per-universe migration adds this table (use `ensure_table` helper from CO-137 to be drift-safe).

### Endpoints

```
POST   /api/v1/universes/{u}/assets
       Content-Type: <whatever>
       Body: raw bytes
       Optional query: ?filename=foo.png
       → 200 { sha256, mime, size, url }
       → 401 if not owner of universe
       → 413 if body > MAX_ASSET_BYTES (50 MB Phase 1)

GET    /api/v1/universes/{u}/assets/{sha256}
       → 200 bytes
         Content-Type: <mime from index>
         Cache-Control: private, max-age=31536000, immutable
         ETag: "<sha256>"
       → 304 if If-None-Match matches
       → 404 if not in index
       → 401 if private universe and caller not authorized

DELETE /api/v1/universes/{u}/assets/{sha256}
       → 204 if refcount == 0 (file unlinked, row deleted)
       → 409 if refcount > 0 (returns referrers)
       → 404 if not found
```

### Storage layout

```
data/universes/<aa>/<bb>/<universe-key>/
  data.db                  (existing)
  blobs/
    <aa>/<bb>/<sha256>     (new)
```

Where `<aa>` = first two hex chars of sha256, `<bb>` = next two. Two-level fan-out.

### Limits

- `MAX_ASSET_BYTES = 50 * 1024 * 1024` (50 MB) Phase 1; raised in CO-149 with streaming.
- MIME sniffed via `infer` crate (sane default; falls back to `application/octet-stream`).

## Acceptance

- [ ] `POST /api/v1/universes/{u}/assets` accepts raw bytes and returns `{sha256, mime, size}`
- [ ] Same content uploaded twice produces same sha256 and one filesystem blob (idempotent)
- [ ] `GET /api/v1/universes/{u}/assets/{sha256}` returns bytes with correct Content-Type
- [ ] `If-None-Match: "<sha256>"` returns 304
- [ ] DELETE with refcount=0 unlinks the file; refcount>0 returns 409
- [ ] Anonymous request to public universe asset succeeds; to private universe returns 401
- [ ] Upload of 5 MB image completes in < 2 s on UAT (matches CO-81 acceptance)
- [ ] Storage path is sharded `<aa>/<bb>/<sha256>` (no flat dir)
- [ ] `assets` table created via `ensure_table` (drift-safe per CO-137)
- [ ] Tests cover: round-trip, dedup, 304, delete-refcount, oversize-rejection
- [ ] CHANGELOG entry under `### Added` for the version bump

## Out of scope (deferred phases)

- Encryption (CO-148 Phase 3)
- Indexable list endpoint with filters (CO-147 Phase 2)
- HTTP range support (CO-149 Phase 4)
- SPA lazy-load integration (CO-150 Phase 5)

## Notes

- Phase 1 plaintext is acceptable because the existing markdown content in `entries.content` is also plaintext. We aren't widening the privacy gap.
- Refcount maintenance is best-effort Phase 1: `upsert_entry_row` does not yet scan markdown bodies for `![]()` references. CO-147 will add that pass.
