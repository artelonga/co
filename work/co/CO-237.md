## As

The operator of CO, and every user with an active API token

## I Need

API tokens to be stored as **hashes** in the `api_tokens` table, not as raw strings

## So That

A database compromise (stolen backup, SSH escalation, accidental log dump) doesn't immediately expose every active token in plaintext, allowing the attacker to impersonate every user with CLI/agent integrations.

## Context

Today, `co-web/src/storage/api_tokens.rs:54-62` stores the token in plain text:

```rust
let token = format!("co_{}", nanoid::nanoid!(40));
// ...
conn.execute(
    "INSERT INTO api_tokens (id, user_id, name, token, created_at, expires_at) \
     VALUES (?1, ?2, ?3, ?4, ?5, ?6)",
    params![id, user_id, name, token, now_str, exp_str],
)?;
```

The `token` column holds the raw `co_<40chars>` value. On lookup (`get_api_token_by_value`), the server compares the incoming Bearer token directly against the stored string. Functional, but breaks the standard "hash secrets at rest" practice.

This is a known gap, documented in `co-web/seed/co/public/seguranca-criptografia.md` ("Tokens de API"). Filed as a separate ticket so it's tracked and reviewable independently of the larger CO-236 CLI work.

## Scope

1. Hash the token before insert. Two options, both acceptable:
   - **SHA-256** (fast, deterministic, the standard for opaque API tokens). Comparison is constant-time via `subtle::ConstantTimeEq` or `ring::constant_time::verify_slices_are_equal`.
   - **Argon2id** (matches the password-hashing style; overkill for high-entropy tokens but consistent with the rest of the codebase).
2. Add a `token_hash` column to `api_tokens`. Keep the existing `token` column during migration. Optional: keep the first 8 chars (`token_prefix`) in a separate column for display ("show me a token that starts with `co_abc12345`").
3. Migration plan:
   - **Phase 1** (this PR): add the new column. On each successful lookup of a plain-text token, write back the hash + flip a `migrated` flag. Background migrator hashes existing tokens (each token can be hashed without knowing the original — but we KEEP the original for that one migration moment, then null it). Or simpler: invalidate all existing tokens at migration time and force re-create (acceptable since CO is pre-1.0; document in CHANGELOG.md as a breaking change for token holders).
   - **Phase 2** (follow-up PR): drop the `token` column entirely.
4. Update `get_api_token_by_value` to hash the incoming value and look up by hash.
5. List API (`GET /api/v1/auth/tokens`) returns only `token_prefix` + `name` + dates, never the full token (already the case in practice).

## Acceptance

- New `api_tokens.token_hash` column populated for every existing + future token.
- `token` column either null after migration or removed (Phase 2).
- `get_api_token_by_value` runs `hash(input) == row.token_hash` in constant time.
- A DB dump shows no plaintext `co_<value>` strings.
- Existing CLI/agent users hit a single re-create-token cycle (documented as a breaking change in CHANGELOG.md if Phase 1 invalidates old tokens; otherwise transparent).
- Unit test: insert via old code path, look up via new code path (verifies the migration shim).
- Updated `seguranca-criptografia.md` removes this from the "lacunas conhecidas" table.

## Blast radius

Medium. Touches `api_tokens.rs` (storage), one migration, one route handler comparison. No public API change unless we go with the "invalidate all" path (which surfaces as: users must re-create their CLI tokens after this ships).

## Related

- **CO-236** — `co auth` CLI command suite; will start producing a stream of new tokens. Best if CO-237 ships first so they're hashed from day one.
- **seguranca-criptografia.md** — documents this gap as a known limitation.
