## As

a maintainer who's been shipping rapidly into a few god-files for months and is paying the cognitive tax every time a small change requires scrolling 5,000 lines

## I Need

these monoliths split into composable, single-responsibility modules — each with a clear public API, a focused test surface, and a changelog entry that documents what moved where

## So That

(a) compile times improve when iterating on a single concern,
(b) future contributors (human or agent) can find the right file in seconds,
(c) merge conflicts shrink because changes touch leaf modules instead of the trunk,
(d) the test surface gets to live next to the code rather than in a global mod tests {} at the bottom of every file.

## Proposed module split (Rust side)

### `storage.rs` → `storage/` directory module

```
co-web/src/storage/
├── mod.rs              # pub use ... (re-export the Storage struct + key types)
├── core.rs             # Storage struct, new(), conn(), pool, helpers
├── schema.rs           # CREATE TABLE statements + ensure_table / ensure_column
├── migrations/
│   ├── mod.rs          # run_meta_migrations() dispatch
│   ├── v01_to_v10.rs   # historical, frozen
│   ├── v11_to_v20.rs
│   ├── v21_to_v30.rs
│   ├── v31_to_v37.rs
│   └── v38.rs          # CO-170 hidden flag
├── seed/
│   ├── mod.rs
│   ├── template.rs     # seed_template_universe, reseed_template_content_pages
│   ├── quilombo.rs     # seed_quilombo_universe
│   ├── yggdrasil.rs
│   ├── timelines.rs    # tempo, humanity, universo
│   └── admin.rs        # seed_admin_user_from_env, ensure_admin_universe_memberships
├── universe.rs         # get_universe, list_universes_*, hide_*, delete_*
├── project.rs          # list_projects_*, get_project, create_project, project_universe_index
├── task.rs             # list_tasks_paginated, get_task, archive, etc.
├── recovery.rs         # recovery channel CRUD (already partially separate)
├── cleanup_co170.rs    # cleanup_empty_projects, migrate_co170_phase_b
└── recompute.rs        # recompute_content_counts, rebuild_*
```

Each submodule exposes `impl Storage { ... }` blocks via `pub(super)`. The trait-on-struct pattern is what Rust idiomatically calls "split impls" — same struct, methods organized by file. No public API change.

### `recovery_routes.rs` → `recovery/` module

```
co-web/src/recovery/
├── mod.rs              # router builders
├── channels.rs         # add/verify/list/delete handlers
├── reset.rs            # forgot/reset password handlers
├── change.rs           # change-password (logged-in)
├── delivery.rs         # send_verification_code + cascade
└── tests.rs            # the 19 existing tests, organized by handler
```

### `server.rs` → keep as router orchestrator

Already mostly reasonable; just lift the inline handlers (`login_handler`, `verify_handler`, `password_login_handler`, `uat_login_handler`) into `co-web/src/auth/handlers.rs`. server.rs becomes a router-build file under 1k LOC.

## Proposed module split (frontend)

### `app.js` → ES modules under `co-web/static/variants/a/modules/`

```
co-web/static/variants/a/
├── index.html
├── app.js                 # boot — imports the modules, wires init()
└── modules/
    ├── state.js            # the global state object
    ├── api.js              # apiFetch + thin API wrappers
    ├── i18n.js             # translation helpers (already partially separate)
    ├── login-modal.js      # setupLoginModal + helpers
    ├── recovery-flow.js    # forgot/reset UI handlers
    ├── settings-panel.js   # universe theme/layout config
    ├── sidebar.js          # universe + project sidebar render
    ├── views/
    │   ├── kanban.js
    │   ├── calendar.js
    │   ├── conteudo.js
    │   ├── table.js
    │   ├── timeline.js
    │   └── dashboard.js
    ├── editor.js           # CoEditor lazy bundle integration
    ├── yggdrasil.js        # game-hub view
    ├── theme.js            # dark/light, custom tokens
    └── onboarding.js       # CO-99 anonymous first-visitor coach mark
```

Use native ES module imports (`<script type="module">`) — no bundler. Browsers handle it natively, dev iteration stays fast.

## Migration approach (changelog-oriented)

**One PR per file extraction.** Each PR:
1. Creates the new module/file with code lifted verbatim.
2. Re-exports from the old file via `pub use` so existing import sites don't break.
3. Updates the CHANGELOG with a `### Refactored` entry naming exactly which functions/types moved where.
4. Ships independently — no big-bang "and the codebase looked completely different" PR.

After all extraction PRs land, a final cleanup PR removes the re-exports and updates import sites.

## Acceptance

- [ ] `storage.rs` reduced to < 500 LOC (the `Storage` struct definition + `new()` + a `pub use`)
- [ ] No file in `co-web/src/` exceeds 1,500 LOC
- [ ] `app.js` reduced to < 500 LOC (boot + module imports)
- [ ] No file in `co-web/static/variants/a/` exceeds 1,500 LOC
- [ ] All existing tests still pass without modification
- [ ] CHANGELOG has a `### Refactored` entry per extraction PR naming the moves
- [ ] No public API change (HTTP endpoints, JS globals, `pub fn` signatures)

## Out of scope

- Behavioral changes — pure refactor, no feature work
- Test reorganization beyond moving with their code
- TypeScript / build-system changes
- Renaming modules to fit some other taxonomy than the one above
