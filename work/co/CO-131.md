## As

a CO operator running aggregation jobs inside the privileged zone

## I Need

a registered allow-list of aggregation jobs (each is named, code-signed, peer-reviewed) plus a k-anonymity filter at egress that rejects any output row containing a count below the threshold (default `k = 5`)

## To

guarantee that **no individual user's behavior** can be reconstructed from privileged-zone outputs, even by the operators of the zone, and that arbitrary SQL is structurally not allowed inside the zone

## Given / When / Then

GIVEN the privileged zone (CO-130) has key-unwrap capability,
WHEN we add (a) a registry of approved jobs with code hashes + reviewers, (b) a sidecar that intercepts all topic writes from the zone and applies a k-anonymity filter,
THEN any job not in the registry refuses to start, and any output row with `count < k` is rejected (logged + dropped) before reaching the aggregated topic.

## Job registry shape

```yaml
# privileged-zone/jobs/registry.yaml
- name: sessions_aggregated
  code_hash: blake3:b1c2...
  reviewers: [yuri, sr-engineer]
  output_topic: events.aggregated.sessions
  output_schema: schemas/sessions_aggregated.avsc
  k_threshold: 5
  approved_at: 2026-05-15T00:00:00Z

- name: ab_results_v1
  code_hash: blake3:7f3a...
  reviewers: [yuri, sr-engineer]
  output_topic: events.aggregated.ab_results
  output_schema: schemas/ab_results.avsc
  k_threshold: 10  # higher for behavioral data
  approved_at: 2026-05-22T00:00:00Z
```

Jobs not in the registry don't run. Code hash mismatches → refuse to start. Reviewer list is informational + audit-relevant.

## DLP filter

```rust
fn dlp_filter(row: &OutputRow, threshold: u32) -> Decision {
    if row.count < threshold {
        Decision::Reject { reason: "k-anonymity below threshold" }
    } else if row.has_pii_pattern() {
        Decision::Reject { reason: "PII pattern detected" }
    } else {
        Decision::Accept
    }
}
```

Where `has_pii_pattern` checks for things like email-shaped strings, UUIDs that look like user-ids, etc.

## Acceptance

- [ ] Job registry file format + validation in `co-core`
- [ ] Aggregation jobs cannot start without a matching registry entry
- [ ] DLP filter implemented as a Flink sink wrapper or a dedicated Worker on the egress path
- [ ] Synthetic test: submit a job that emits a row with `count = 1` → rejected with audit row
- [ ] Synthetic test: submit a job that emits a row containing an email → rejected with audit row
- [ ] Runbook for adding a new approved job (review process, code-hash update, deploy)
- [ ] Tested k=5 default; adjustable per job up to k=100

## Out of scope

- Differential privacy noise (Laplace/Gaussian mechanisms) — Phase 5+ if regulatory requirements emerge
- Homomorphic encryption alternatives — see HE+FP review
- ε-delta budgeting — same

## Risks

- **k=5 is too aggressive for low-traffic flags.** Mitigation: per-job threshold lets owners trade off privacy vs. statistical power explicitly
- **PII detection false positives.** Mitigation: opt-in pattern list; document edges
