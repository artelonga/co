## As

A reader of the `co-web/src/` tree (contributor, agent, or future maintainer)

## I Need

Universe-specific Rust modules (`quilombo/`, `game/`) extracted from the same top-level alongside `auth/`, `content/`, `social/`, `admin/`, `integrations/`, `platform/` — so the directory structure mirrors the conceptual separation:

- **Co (platform)** = `auth/` + `content/` + `social/` + `admin/` + `integrations/` + `platform/`
- **Universes (extensions)** = `universes/quilombo/` + `universes/game/` + future per-universe modules

## So That

The split between "**form** (the platform shell)" and "**content** (universe-specific data + code)" — and between "**co** (the platform)" and "**universes** (specific instances)" — is visible at directory level. New contributors instantly understand what's reusable platform code vs. one-off universe extensions.

## Why CO-224 didn't go far enough

CO-224's 8 context folders put `quilombo/` and `game/` at the same depth as `auth/`/`content/`/`platform/`. But:

- `quilombo/` is **one universe's** custom backend (quilomboaraucaria.org integration: processos, relations to events/fotos/publicacoes specific to that universe)
- `game/` is the leaderboard backend for yggdrasil's games — **another universe-specific**
- `auth/`, `content/`, `platform/` are **all universes** (the core CO substrate)

Mixing them at the same level says they're peers. They're not.

## Decision — v1 = in-tree `universes/` subtree

Two approaches considered:

### A. In-tree (`co-web/src/universes/`) — picked for v1

```
co-web/src/
├── auth/             ← co platform
├── content/          ← co platform
├── social/           ← co platform
├── admin/            ← co platform
├── integrations/     ← co platform (external services)
├── platform/         ← co cross-cutting infra
├── universes/        ← universe-specific extensions
│   ├── quilombo/     ← was quilombo/
│   └── game/         ← was game/
├── server/
├── lib.rs            ← re-exports adjusted
└── main.rs
```

Pros: same crate, same build, minimal blast radius.
Cons: still in `co-web`, not truly decoupled.

### B. Separate crates (`co-universes-quilombo`, `co-universes-yggdrasil-game`) — deferred

```
crates/
├── co-web/                ← platform-only
├── co-universes-quilombo/ ← own Cargo.toml, depends on co-web
└── co-universes-game/     ← same
```

Pros: true plugin model, each universe is its own crate, can be open-sourced separately.
Cons: ~2 days of work, requires plugin registration pattern (we have `plugin_loader.rs` but it's WASM-oriented).

**v1 = A. v2 = B as future ticket.**

## Scope

### Move operations

```bash
git mv co-web/src/quilombo co-web/src/universes/quilombo
git mv co-web/src/game co-web/src/universes/game
```

### Update lib.rs re-exports

```rust
// Before:
pub mod quilombo;
pub mod game;

// After:
pub mod universes;
// In universes/mod.rs:
pub mod quilombo;
pub mod game;
```

### Update consumer imports

Any `use crate::quilombo::...` becomes `use crate::universes::quilombo::...`. Mostly internal to `routes/`/`server.rs`.

If keeping the public-API contract via `pub use` aliases in `lib.rs`:

```rust
// In lib.rs:
pub use universes::quilombo;
pub use universes::game;
```

Existing external consumers (tests, binaries) keep `crate::quilombo` working. Best of both worlds.

### MODULES.md update

Document the new layout + the principle ("universes/ holds per-universe Rust extensions; the rest of co-web/src/ is platform").

## Acceptance

- `co-web/src/quilombo/` and `co-web/src/game/` no longer exist
- `co-web/src/universes/quilombo/` and `co-web/src/universes/game/` exist with all original sources
- `co-web/src/universes/mod.rs` declares the two sub-modules
- `cargo check --workspace` clean
- `cargo test -p co-web` no new failures
- Existing imports `use crate::quilombo::...` either still work (via `pub use` alias) OR are updated everywhere
- MODULES.md §6 (architecture map) explains the universes/ rule
- New entry in `co-universes.yaml` if needed to declare which Rust modules each universe activates (future-proofing for plugin path)

## Blast radius

- `git mv` × 12 files (quilombo's 6 + game's 2 + new mod.rs's)
- ~20 LOC re-export adjustments in `lib.rs` (or 30 LOC if updating all import paths)
- ~30 LOC MODULES.md update
- Build: must be green
- No behavior change

## Why now

Your direct feedback on CO-224: *"THERE ARE universe stuff (eg quilombo) that is present here, wrong. separate form from content, co from universes, platform."*

CO-224 made the platform-internal split (auth/content/social/admin/integrations/platform) crisp. CO-265 makes the platform-vs-universes split equally crisp. The two together give the file tree a self-documenting architecture.
