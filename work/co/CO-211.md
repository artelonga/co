## As

a developer building a markdown renderer, Obsidian plugin, or mobile
client

## I Need

a formal v1 OpenAPI 3.1 spec for the Universe Content API that
documents every public endpoint, request/response shape, auth
requirements, and error codes — published at `/api/openapi.json` and
human-rendered at `/api/docs`

## So That

any frontend (the existing CO SPA, the new Svelte viewer CO-212,
Obsidian plugin CO-213, future mobile app, third-party tools) can
consume universe content uniformly without reading source code.

---

## Why now

CO ships a working REST API today, but the contract is implicit:

- Some endpoints are documented in `docs/analytics-api.md`
- Most are only discoverable via grep in `co-web/src/`
- No machine-readable spec — clients can't generate stubs
- No versioning — breaking changes only caught by manual testing

For the "all universes feel like one CO" vision to scale beyond the
current SPA, the contract has to be **the source of truth**, not the
Rust handler code.

## Scope

### Endpoints to document (Universe Content focus)

#### Public (no auth required for public universes)

```
GET  /api/v1/universes
GET  /api/v1/universes/{slug}
GET  /api/v1/universes/{slug}/entries                ?type=&limit=&offset=
GET  /api/v1/universes/{slug}/entries/{path}
GET  /api/v1/universes/{slug}/entries/tags
GET  /api/v1/universes/{slug}/entries/tree
GET  /api/v1/universes/{slug}/manifest
GET  /api/v1/universes/public                         (public catalog)
```

#### Authenticated (Vault API for private universes)

```
GET  /api/v1/universes/{slug}/vault/notes
GET  /api/v1/universes/{slug}/vault/note/{path}
PUT  /api/v1/universes/{slug}/vault/note/{path}
DELETE /api/v1/universes/{slug}/vault/note/{path}
GET  /api/v1/universes/{slug}/vault/tags
```

#### Auth-only

```
GET  /api/v1/auth/me
POST /api/v1/auth/login
POST /api/v1/auth/logout
POST /api/v1/auth/token            (generate API token)
```

#### NOT in v1 scope (separate spec)

- Chat endpoints (CO-193 family) — own spec when stable
- Notifications (CO-199 family) — own spec
- Admin endpoints — internal, not for third-party

### Versioning policy

- `v1` is locked: no breaking changes
- `v2` will be a new path prefix (`/api/v2/...`) parallel to v1
- v1 stays supported for at least 12 months after v2 launches
- Additive changes (new optional fields, new endpoints) don't need
  version bump

### Format

- **OpenAPI 3.1** YAML in `docs/api/openapi.yaml`
- Generated artifacts:
  - `docs/api/openapi.json` — machine-readable
  - `/api/docs` — Swagger UI rendering
  - `/api/openapi.json` — same file served at well-known location

### Auth schemes documented

- `BearerAuth` — JWT in `Authorization: Bearer <token>`
- `SessionAuth` — session cookie (set by login flow)
- Public — no auth

### Common responses documented

- 200 OK
- 400 Bad Request (validation errors)
- 401 Unauthorized
- 403 Forbidden (permission denied)
- 404 Not Found
- 409 Conflict (e.g., universe slug taken)
- 429 Too Many Requests (rate limited)
- 500 Internal Server Error

## Acceptance

- [ ] `docs/api/openapi.yaml` exists, valid OpenAPI 3.1
- [ ] All listed endpoints documented with request schema + response
      schema
- [ ] Schemas use shared components for `Universe`, `Entry`, `Project`,
      `User`, etc.
- [ ] `/api/openapi.json` serves the spec
- [ ] `/api/docs` renders Swagger UI (or alternative like Redoc)
- [ ] CO-N test suite: parse the spec and validate at least one
      example request/response for each endpoint matches the actual
      server behavior
- [ ] CI gates: spec must be valid YAML + valid OpenAPI 3.1

## Out of scope

- Generation of client SDKs (separate ticket; can be done by anyone
  consuming the spec via `openapi-generator`)
- Backward compatibility shims for v0 (informal pre-spec endpoints
  remain as-is; deprecation later)
- Auto-sync from Rust types via macros — possible, defer to follow-up

## Co-auto
