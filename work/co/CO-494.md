GIVEN the target user speaks more than they type, and voice is the single biggest
accessibility unlock — and transcribing locally keeps their voice on the operator's
machine (privacy),
WHEN a user sends a WhatsApp voice note,
THEN it is transcribed by a **local** model (e.g. whisper.cpp) into the same brain
path, and replies may be returned as voice — no audio leaves the box to a third
party by default.

## Acceptance

- [ ] Inbound WhatsApp audio (Cloud API media) is fetched and transcribed **locally**
  (local model, default no third party — mirrors the local-LLM privacy posture).
- [ ] Transcript flows into the existing brain path (per-sender identity, capability
  packs) unchanged.
- [ ] Optional local text→speech for replies (off by default; configurable).
- [ ] No audio/transcript sent to any external service in the default path; if an
  operator enables a remote ASR, it requires a consent-version bump (CO-491).
- [ ] Patience/repair: unclear audio → a gentle "me conta de outro jeito?" (no blame).
- [ ] Memory note: local ASR fits the 36 GB envelope alongside the chat model
  (size the models; never co-resident a 30B + ASR + apps).

## Notes
- Belongs to the "everyday" stage of the UX north star. Latency/concurrency interact
  with the model ceiling (CO-496) — count ASR as part of the per-message cost.
