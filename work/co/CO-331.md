## As
A CO user wanting to add an open-source tool (like Claude Code, a custom agent, a co-compatible plugin) to my CO setup

## I Need
The ability to install any open-source repo as a CO tool — declare it, version-pin it, run it from local source — without going through a separate package manager

## So That
Tools are first-class to CO (same model as universes/content via CO-330), versions are user-controlled (pin a tag, follow main, or use a local checkout), and the whole flow extends git natively while staying jujutsu-compatible.

## Background

The user's framing: "ensure any open source repo can be cloned as a tool (e.g. claude code), this will allow for easy, npm-like version and conflict handling and we can just deploy these from the local source, up to user to choose version. in the future we can just opt to always follow main for example. this extends git to our native, jujutsu-compatible logic."

This is conceptually parallel to **CO-330** (universes bound to local repos for content):
- CO-330: `universe.local_repo_path` → source of *entries* (data)
- CO-331: `tool.local_repo_path` → source of *executable* (code that does things)

Both treat git repos as the unit of integration. CO is the orchestrator.

## Design

### Tool registry (new table)

```sql
CREATE TABLE tools (
    key TEXT PRIMARY KEY,                  -- e.g. "claude-code", "co-auto"
    name TEXT NOT NULL,                    -- display name
    description TEXT,
    remote_url TEXT,                       -- git URL to clone from (https or ssh)
    local_path TEXT,                       -- local checkout location (override)
    version_pin TEXT,                      -- "v1.2.3" | "main" | "follow-main" | "<sha>"
    entry_command TEXT,                    -- what to run (e.g. "claude" or "node bin/cli.js")
    installed_at TEXT,
    last_updated TEXT,
    follow_main INTEGER DEFAULT 0          -- auto-update on each `co update`
);
```

### Resolution order

When `co run <tool>` (or any CO subsystem invokes a tool):
1. If `local_path` is set + exists → use that checkout (dev override)
2. Else: ensure cloned at `<data-dir>/tools/<key>/`, checkout `version_pin`
3. Run `entry_command` from that dir

### CLI surface

```bash
co tool add claude-code --from https://github.com/anthropics/claude-code --pin v2.0.0
co tool add co-auto --from ~/projects/co-auto                    # local-only, no remote
co tool list                                                       # show all + version/state
co tool update claude-code --pin v2.1.0                            # bump version
co tool update claude-code --follow-main                           # always main
co tool update --all                                               # refresh follow-main tools
co tool remove claude-code
```

### npm-like version + conflict handling

- Per-tool `lockfile` snapshot (commit SHA at install time)
- `co tool verify` → checks each tool's checkout matches its lockfile
- `co tool update` rewrites the lockfile
- Conflict detection (initial scope): when two tools declare incompatible peer-tools, surface a warning. Full SAT-style resolution is out of scope for v1.

### Jujutsu compatibility

- Use git as the *protocol* (clone URLs, fetch, checkout SHA) — works with both git and jj-backed repos
- Don't assume `.git/` directory structure — invoke through `jj` if `.jj/` exists, else `git`
- Internal helper `vcs::fetch(remote, dest)` / `vcs::checkout(dest, ref)` chooses backend
- Repo's own VCS choice doesn't affect users of the tool

### Local-source deploy

- `co tool add <key> --local <path>` installs without remote URL (purely local)
- `co tool update <key> --from-local` re-syncs from local checkout
- Useful when iterating on a tool you maintain

### "Always follow main" (future toggle)

- `follow_main: 1` → on each `co update` or `co serve` boot, the tool's checkout is `git pull` + `checkout origin/main`
- Trade-off: bleeding-edge vs stability. User-chosen per tool.

### Future: tools-as-runners

A tool could declare itself as a runner for a content type (CO-325). E.g., a `markdown-tutor` tool could declare `accepts: { type: notas }` and become an option in the entry view. Out of scope for v1 but the registry should make this expressible.

## Acceptance

- [ ] `tools` table exists with schema above
- [ ] `co tool add` clones (or registers a local path) + sets version pin
- [ ] `co tool list` shows status (installed, pinned version, follows-main)
- [ ] `co tool update <key>` re-fetches and checks out the new ref
- [ ] `co tool update --all` refreshes all `follow_main=1` tools
- [ ] `co tool remove` deletes the checkout + DB row
- [ ] jj-backed repos work end-to-end (detected via `.jj/`)
- [ ] Conflict warning surfaces when two tools both define competing entries (initial: name collisions, expand later)

## Blast radius

- 1 schema migration (tools table)
- New module `co-cli/src/commands/tool.rs` (~250 lines)
- New `vcs::` abstraction in `co-cli/src/vcs/` (~100 lines, dispatch git vs jj)
- ~50 lines of integration with co serve (load tool list at startup)
- 0 SPA changes for v1; settings UI can come later

## Dependencies

- **CO-330** ships first — both proposals share the "git repo as integration unit" model and CO-330 lays groundwork (universes bound to repos). CO-331 is parallel, but if CO-330 ships first, CO-331 can reuse the `vcs::` helpers.

## Why now

The user wants CO to be the canonical integration surface for both content and code. NPM does this for JS, cargo for Rust — CO does it for "anything git-backed." This unblocks:
- Self-hostable Claude Code (and other AI tools)
- Version-pinned co-auto deployments
- User-shared content/tool bundles (e.g., yuri publishes a "notas" tool other CO users install)
- The full yuri.artelonga.com.br vision (a tool can present a UI that complements published entries)

## Not in scope

- Remote tool publishing/discovery (a "tools index" that lists what's available — could come in a v2)
- Sandboxed execution (tools run with user's permissions)
- Cross-platform binary distribution (out of scope; tools must build from source or ship platform-aware install scripts)
