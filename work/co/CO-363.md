## As
A content author writing markdown in CO

## I Need
Wikilinks of the form `[[key::path]]` (and `[[key::path|label]]`) to be extracted as edges in `entry_relations` with `to_universe` populated, the same way same-universe `[[path]]` links already do.

## So That
- CO-345's cross-universe graph view has real edges to render.
- The platform-canonical `key::path` syntax (decided in CO-338) is usable in markdown bodies, not just frontmatter.
- Content gets future-proof — referencing a sibling universe by key never breaks if the source folder moves.

## Context

Today's relations extractor (`extract_relations` in `core/` per CO-74 memory) walks markdown bodies + frontmatter and writes typed edges into `entry_relations`. It handles:
- Frontmatter refs like `concept: co://concepts/mother.md`
- Same-universe wikilinks `[[terms/iemanja]]`

It does **NOT** handle:
- `[[key::path]]` cross-universe wikilinks (decided syntax in CO-338)
- `[[../sibling-universe/path]]` relative paths (deprecated per project_cross_universe_link_syntax memory)

The schema field `entry_relations.to_universe` (text, nullable) already exists per CO-74. It's just never populated by the extractor for cross-universe wikilinks.

CO-345's graph_routes.rs hard-filters `WHERE to_universe IS NULL` (line 154) — this filter relaxes in CO-345, but only matters if `to_universe` is populated, which is what THIS spec fixes.

## Design

### Parser change

Locate the wikilink regex in `core/src/extract_relations.rs` (or wherever it lives — search for `\[\[` patterns). Extend to:

```rust
// Match [[key::path]] or [[key::path|label]]
let cross_universe_re = Regex::new(r"\[\[([a-z][a-z0-9_-]*?)::([^\|\]]+?)(?:\|([^\]]+))?\]\]").unwrap();
```

Emit a row per match:
- `from_universe`: current entry's universe_key
- `from_entry`: current entry's path
- `to_universe`: captured key (group 1)
- `to_entry`: captured path (group 2)
- `relation_type`: `"wikilink"` (matches existing same-universe wikilink rows)
- `link_text`: optional label (group 3) or None

### Same-universe wikilinks (unchanged behavior)

`[[terms/iemanja]]` without `::` → `to_universe = from_universe` (same as today).

### Relative path rewrite (deprecation handler)

If we see `[[../sibling/path]]` in the body, emit a *deprecation warning* in the extractor log + emit a relation row with `to_universe = NULL` and `relation_type = "wikilink_relative_deprecated"`. This makes them discoverable for a one-shot migration script (CO-340+1).

### Frontmatter `key::path` (extend CO-74 frontmatter walker)

Frontmatter refs like `concept: yoruba::terms/iemanja.md` already work in the CO-338 spec? Verify the frontmatter walker accepts both `co://` and `key::` shapes; if not, add. (Look at `extract_relations` frontmatter handling; should be parallel.)

### Idempotency

Extractor is already called on every entry write per CO-74. Re-runs upsert by `(from_universe, from_entry, to_universe, to_entry, relation_type)` — confirm this is the unique key; if not, add it as a migration.

### Backfill

One-shot migration that re-runs `extract_relations` against every existing entry to populate cross-universe rows. Approx: 11,500 entries × ~5ms each = ~60s startup overhead one time.

```rust
// In a new migration vNN
if !flag_exists("co-340-backfill-done") {
    for entry in storage.all_entries()? {
        let _ = extract_relations(&entry, &storage);
    }
    set_flag("co-340-backfill-done");
}
```

## Acceptance

- [ ] `extract_relations` parses `[[mbya::terms/jaxy-jatere]]` and writes a row with `to_universe="mbya"`, `to_entry="terms/jaxy-jatere"`.
- [ ] `extract_relations` parses `[[concepts::mother.md|mãe]]` and stores label `"mãe"` in `link_text`.
- [ ] Same-universe `[[terms/x]]` still resolves to `to_universe = from_universe` (no regression).
- [ ] `[[../sibling/x]]` emits a deprecation log line + row with `relation_type="wikilink_relative_deprecated"`.
- [ ] Frontmatter `concept: yoruba::terms/ogunte` populates `to_universe="yoruba"`.
- [ ] Migration backfills cross-universe relations for the existing 11,500 entries.
- [ ] Unit tests cover all 5 forms.
- [ ] `GET /api/v1/universes/mbya/graph?universes=mbya,yoruba` (after CO-345 ships) returns edges connecting the two.

## Blast radius

- ~80 lines in `core/src/extract_relations.rs` (or wherever the regex lives)
- ~30 lines new migration (vNN+1)
- ~120 lines unit tests
- 1 startup backfill (one-time ~60s)
- No schema changes — `to_universe` column already exists

## Dependencies

- CO-74 ✓ shipped — `entry_relations` table + `extract_relations` framework
- CO-338 (todo, related) — the `key::path` canonical syntax — but this spec implements ONE side of CO-338 (the wikilink form); CO-338's frontmatter validation + UI hints are independent

## Not in scope

- CO-345 graph_routes filter change (separate spec)
- Migration of existing `[[../sibling/x]]` content to `[[key::path]]` (separate migration — track with the deprecation-tagged rows)
- `co://` URI deprecation (still accepted, just normalized to `key::path` internally)
- Validation that `to_universe` key actually exists (no FK constraint — link to non-existent universe is allowed, renders as orphan)
