GIVEN the platform has never been tested above 1 concurrent user, AND we cannot honestly say "ready for public test" without measured p95/p99 figures at meaningful concurrency, AND debugging a production stampede after launch is dramatically more expensive than discovering a known-bad endpoint now,
WHEN we add k6 scripts for the eight hottest endpoints and capture a baseline run against UAT at 50 / 100 / 500 virtual users,
THEN we have a documented expected-throughput envelope, an alarm threshold ("if p95 > X at N users, something regressed"), and a clear "what hardware do we need before launch" answer based on real numbers.

## Scenarios

Each scenario is a separate k6 script under `tests/load/`. All read `BASE_URL` env var (default `https://co-artelonga-uat.fly.dev`).

### `01-anon-browse.js` — anonymous landing flow

Simulates a first-time visitor. Each VU loops:
1. `GET /` (or `/co`) — index.html
2. `GET /app.js`
3. `GET /style.css`
4. `GET /api/v1/universes/template` — universe info
5. `GET /api/v1/universes/template/config`
6. `GET /api/v1/universes/template/theme.css`
7. `GET /api/v1/universes/template/projects`
8. `GET /api/projects/CO/tasks?u=template`
9. think 3-7s
10. `GET /shared/timeline.html?u=tempo`
11. `GET /api/v1/universes/tempo/entries?type=event`
12. `GET /api/v1/universes/universo/entries?type=event`
13. `GET /api/v1/universes/humanity/entries?type=event`
14. think 5-10s
15. repeat

### `02-logged-in-board.js` — power user (yuri-style)

Setup: log in as `yuri@uat.local` once per VU, store cookie. Each VU loops:
1. `GET /api/v1/auth/me`
2. `GET /api/v1/universes`
3. Switch through 3 universes (info, config, projects, tasks for each)
4. `POST /api/projects/<key>/tasks` — create a task (with content)
5. `PUT /api/projects/<key>/tasks/<id>` — update status
6. think 4-8s
7. repeat

### `03-vault-write.js` — API token holder

Setup: provision an API token via login + `/api/v1/auth/token`. Each VU loops:
1. `GET /api/v1/universes/template/vault/notes`
2. `PUT /api/v1/universes/template/vault/load-test-<vu>-<iter>.md`
3. `DELETE /api/v1/universes/template/vault/load-test-<vu>-<iter>.md`
4. think 2-5s

(Use a non-template universe for write scenarios in real runs — template should stay clean.)

## Baseline runs

Against UAT (`co-artelonga-uat`, default Fly machine size), run each scenario at:

| VUs | Duration |
|-----|----------|
| 50  | 1 min    |
| 100 | 1 min    |
| 500 | 30 sec   |

Capture for each combination: p50, p95, p99 latency; error rate; iteration rate.

Commit results to `tests/load/baselines/2026-04-29-uat.md` as a markdown table:

```
## Scenario: 01-anon-browse
| VUs | Duration | p50 | p95 | p99 | Errors | Iters/s |
|-----|----------|-----|-----|-----|--------|---------|
| 50  | 1m       | 42  | 180 | 350 | 0%     | 124     |
| 100 | 1m       | 89  | 420 | 920 | 0.2%   | 215     |
| 500 | 30s      | 510 | 2.1k| 4.8k| 4.1%   | 480     |
```

For the 500-VU run, **document the exact failure mode** (which endpoint started timing out / 5xx-ing, what the SQLite contention looked like, did the machine OOM). This is the most important artifact.

## Constraints

- **Do NOT run against prod.** UAT only. Add a guard in each script that aborts if `BASE_URL` includes `co-artelonga.fly.dev` or `co.artelonga.com.br` (and not `-uat`).
- Use `--quiet` and `--summary-export` in CI runs; full output for local exploration.
- Keep total run time per scenario under 5 min — these are integration-grade, not soak tests.
- Don't pollute the UAT data — write scenarios use temp paths and clean up.

## Acceptance

- [ ] Three k6 scripts under `tests/load/`.
- [ ] Each script aborts when `BASE_URL` looks like prod.
- [ ] `tests/load/README.md` explains how to install k6 (`brew install k6`), run a scenario, read the output, and update the baseline.
- [ ] Baseline file committed with results from at least 50-VU runs of each scenario.
- [ ] Documented the failure mode at 500 VUs (where it broke, exact symptom).
- [ ] One section in baseline file recommends what we need to test against before opening v1.0 to the public — concrete number (e.g. "200 VUs sustainable on the current Fly machine; recommend bumping to shared-cpu-2x before public launch").

## Out of scope

- Continuous load testing in CI (defer until baseline is stable).
- Distributed load (multi-region k6 cloud). Single runner is fine for UAT.
- Stress / soak tests (1+ hour). Tier 3 work.
