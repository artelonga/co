GIVEN the codebase has accumulated 1.20.0 → 1.21.x worth of architectural decisions (CO-49 access model, CO-50 universe-as-repo, modern theme override, atomic switching, timeline trio, network-first SW) but the only durable docs are `CLAUDE.md` (instructions for me, not for humans) and per-feature CHANGELOG entries, AND we cannot launch publicly with onboarding instructions that point at superseded behavior,
WHEN we write three honest documents — ARCHITECTURE (what is it), OPERATIONS (how to run it), ONBOARDING (how to set it up locally) — describing 1.21.x reality, not aspirations,
THEN a new contributor or operator can be productive within an hour without pinging yuri, and the public README link target is non-embarrassing.

## Files

### `docs/ARCHITECTURE.md`

Sections:

1. **At a glance** (3 paragraphs + Mermaid C4-style component diagram)
   - SPA → axum → SQLite + filesystem
   - Single deployment unit (Fly.io machine, GRU region)
   - Custom domain `co.artelonga.com.br` + automatic Let's Encrypt
2. **Data flows** — anonymous visitor, logged-in (cookie JWT), API token (keychain via `co-token`)
3. **Universe storage**
   - SQL row in `universes` (key, name, owner_id, visibility, theme_preset, layout, parent_key)
   - Filesystem at `/data/universes/<key>/` with markdown files
   - `entries` table is a search index over the filesystem
4. **Theme system**
   - `ThemePreset::by_name` returns compiled-in CSS tokens
   - `/api/v1/themes/<name>` returns the preset directly (overrides win)
   - `/api/v1/universes/:slug/theme.css` returns universe-stored preset + custom_tokens overlay
5. **Access model (CO-49)**
   - Six visibility states: template, public-static, public-subscribable, requires_login, private, anon-owned
   - Six access outcomes: ReadWrite, ReadOnly, MetadataOnly, LoginRequired, Denied
   - Owner ↔ member ↔ subscriber distinction
6. **Service worker** (network-first for HTML/JS/CSS, cache-first for assets, auto-reload on SW update)

Embed Mermaid diagrams where they aid comprehension. Reference: `docs/diagrams/`.

### `docs/OPERATIONS.md`

Runbook style. Each section is a numbered procedure, not prose.

1. **Deploy to UAT**
2. **Deploy to prod** (UAT must pass first)
3. **Tail logs** (`flyctl logs -a co-artelonga --no-tail`)
4. **SSH into a machine**
5. **Backup** (link to `scripts/backup-prod.sh`, see CO-104)
6. **Restore from backup** (link to `scripts/restore.sh`)
7. **UAT data reset** (touch `/data/uat-reset.flag` + restart machine)
8. **Rotate `JWT_SECRET`** (with the side-effect note: invalidates all sessions)
9. **Add a custom domain** (DNS + `flyctl certs add`)
10. **Health checks** — `/api/health` (shallow) and `/api/health/deep` (DB + disk probe, see CO-103)
11. **Smoke test post-deploy** — `bash scripts/smoke-prod.sh`
12. **Recover from a stuck deploy** — Fly machine status + manual `flyctl machine restart`

Each section is ≤ 10 lines and contains the exact commands.

### `docs/ONBOARDING.md`

5-minute "set up Co locally" guide.

1. Prerequisites (Rust toolchain, sqlite3, optional: jj for delta uploads)
2. `git clone && cd co`
3. `cargo build -p co-web --release`
4. Set env: `JWT_SECRET`, `CO_SEED_ADMIN_EMAIL`, `CO_SEED_ADMIN_PASSWORD_HASH` (use `cargo run -p co-pwhash`)
5. Run: `cargo run -p co-web`
6. Open `http://localhost:3000`
7. Log in with the seeded admin credentials
8. Create your first universe
9. Where things live (1-line per directory)
