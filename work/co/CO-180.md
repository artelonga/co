## As

visitante chegando em `artelonga.com.br`

## I Need

o grid de serviços no home ordenado pelo que outros visitantes realmente exploram, não pela ordem de declaração em `data.js`

## So That

ofertas mais procuradas (sinal empírico de "isso é o que importa") apareçam acima da dobra em vez de soterradas alfabeticamente.

---

## Estado atual

`renderHome` em `assets/renderer.js:454` no repo artelonga renderiza serviços de `AL.publicServices()` filtrado a `!s.parent`. Ordem é a sequência declarativa em `data.js` — função de quando cada serviço foi adicionado, não de sinal.

Sem dados de popularidade hoje. Após CO-177 + analytics.js wired, eventos começam a fluir; esse ticket constrói a agregação que vira ranking.

User escolheu **bake-via-GH-Action** (não CLI no `co`): site estático fica sem dependência runtime do API. JSON commitado em `assets/popularity.json`, renderer consome.

## Shape

`GET /api/v1/analytics/public/popularity?prefix=/servicos/&days=30`:

```jsonc
{
  "as_of": "2026-05-09T00:00:00Z",
  "window_days": 30,
  "prefix": "/servicos/",
  "items": [
    { "path": "/servicos/desenvolvimento-web/", "slug": "desenvolvimento-web", "views": 1240, "visitors": 412 },
    { "path": "/servicos/grafite/",            "slug": "grafite",             "views": 880,  "visitors": 301 },
    ...
  ]
}
```

Order: `views DESC`, tie-break `slug ASC`. Limit 200 (>> ~50 serviços hoje).

`slug` derivado: strip `prefix` + trailing `/`.

## Validação de parâmetros

- `prefix`: required, começa com `/`, sem `..`, max 64 chars.
- `days`: optional, clamp `[1, 365]`, default 30.

## Agregação

```sql
SELECT path, COUNT(*) AS views, COUNT(DISTINCT visitor_token) AS visitors
FROM telemetry_events
WHERE universe_key = 'artelonga'
  AND event_name = 'page_view'
  AND path LIKE ?1 || '%'
  AND timestamp >= datetime('now', ?2 || ' days')
GROUP BY path
ORDER BY views DESC, path ASC
LIMIT 200
```

Bot filter já é upstream (CO-46). Não dedupe within session — usuário curioso recarregando 3× sinaliza interesse.

## Cache

5 min in-memory por (prefix, days). Mesmo padrão de CO-179.

## CORS

Mesmo allowlist (CO-177).

## Distribution (não nesse ticket)

GH Action em `artelonga/ArteLonga`:

```yaml
name: bake-popularity
on:
  schedule: [{ cron: '0 4 * * *' }]
  workflow_dispatch: {}
permissions: { contents: write }
jobs:
  bake:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          curl -fsSL "https://co.artelonga.com.br/api/v1/analytics/public/popularity?prefix=/servicos/&days=30" \
            | jq -S '.' > assets/popularity.json
      - uses: stefanzweifel/git-auto-commit-action@v5
        with:
          commit_message: "chore: bake popularity.json"
          file_pattern: assets/popularity.json
```

Workflow vive no repo artelonga — `co` não precisa ter token de write em outro repo. Renderer também é trabalho do repo artelonga.

## Implementação no co

1. Handler em `co-web/src/analytics_public.rs` (mesmo módulo de CO-179).
2. Helper de query em `telemetry.rs` retornando `Vec<{path, views, visitors}>`.
3. Validação do prefix (path traversal etc).
4. Tests cobrindo query + endpoint.
5. CORS herda layer de CO-177.

## Tests

- 0 events no window → `items: []`, `as_of` populado.
- Paths mistos (alguns com prefix, outros não) → só os que casam.
- Order por views DESC, tie-break slug ASC.
- Limit clamp 200.
- `prefix=/../etc` → 400.
- Cache hit retorna bytes idênticos.

## Out of scope

- Mudança no renderer da artelonga consumindo `popularity.json` (PR separado lá).

- Métricas além de views (dwell, bounce) — view count é o sinal load-bearing pra v1.
