## As

a CO user who registered with username + password (per `feedback_auth_email.md` — email is not mandatory at signup) and has now forgotten their password

## I Need

a forgot-password / change-password flow that requires verification through a recovery channel (email · WhatsApp · SMS) the user proves ownership of, with all channel values stored encrypted at rest just like content

## So That

(a) I can recover my account without contacting an admin,
(b) the system never holds my email/phone in plaintext (parity with content encryption-at-rest, CO-148),
(c) recovery channels remain optional — only required when the user opts in, never harvested at signup

---

## Current state (1.76.1)

- Users have `id, email, display_name, tier, password_hash` in the `users` table.
- `email` is `UNIQUE NOT NULL` today — but the user's stated direction is username-primary, email-optional. **This issue blocks CO-165** and is part of its scope.
- `POST /api/v1/auth/login` sends a 6-digit code to email (printed to server logs in dev).
- `POST /api/v1/auth/password-login` accepts `{email, password}` and returns a JWT.
- No password change. No forgot-password. No verified recovery channels.

## Design

### Schema

New table `user_recovery_channels` (in meta DB, server's main `co.db`):

```sql
CREATE TABLE user_recovery_channels (
    id              TEXT PRIMARY KEY,
    user_id         TEXT NOT NULL,
    channel_type    TEXT NOT NULL CHECK (channel_type IN ('email','whatsapp','sms')),
    -- Encrypted-at-rest envelope (CO-148 pattern: ChaCha20-Poly1305).
    value_ciphertext BLOB NOT NULL,
    value_nonce      BLOB NOT NULL,        -- 12 bytes per row
    -- BLAKE3 keyed hash for lookup ("does anyone have this email/phone?")
    value_lookup_hash TEXT NOT NULL,        -- 32 hex chars, deterministic for lookup
    verified_at     TEXT,                   -- NULL = pending verification
    created_at      TEXT NOT NULL,
    last_used_at   TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX idx_urc_user      ON user_recovery_channels(user_id);
CREATE UNIQUE INDEX idx_urc_lookup ON user_recovery_channels(channel_type, value_lookup_hash)
    WHERE verified_at IS NOT NULL;
```

Plus a short-lived verification table:

```sql
CREATE TABLE recovery_verifications (
    id            TEXT PRIMARY KEY,
    channel_id    TEXT NOT NULL,             -- target channel (may be unverified)
    user_id       TEXT NOT NULL,
    purpose       TEXT NOT NULL CHECK (purpose IN ('add_channel','reset_password','change_email')),
    code_hash     TEXT NOT NULL,             -- argon2id(code)
    expires_at    TEXT NOT NULL,             -- now + 10 min
    consumed_at  TEXT,
    attempts      INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL
);
CREATE INDEX idx_rv_user_purpose ON recovery_verifications(user_id, purpose, consumed_at);
```

Reset tokens (longer-lived than verification codes):

```sql
CREATE TABLE password_reset_tokens (
    token_hash    TEXT PRIMARY KEY,           -- sha256(token)
    user_id       TEXT NOT NULL,
    channel_id    TEXT NOT NULL,              -- which channel proved ownership
    expires_at    TEXT NOT NULL,              -- now + 30 min
    consumed_at  TEXT,
    created_at    TEXT NOT NULL
);
```

### Encryption-at-rest

Reuse the CO-148 envelope (ChaCha20-Poly1305, server-held master key). Per-row 12-byte nonce. Master key from env `CO_RECOVERY_KEY` (32 bytes base64); generated once and stored in fly secrets. Same key bytes can derive separate sub-keys via BLAKE3 keyed-hash for: (1) field encryption, (2) the lookup-hash keyed digest.

The lookup hash uses `BLAKE3::keyed_hash(lookup_key, normalized_value)` — deterministic so we can find "does this email exist", but cannot be inverted.

### Endpoints

```
POST   /api/v1/auth/recovery/channels           # add (sends code)
       body: { channel_type, value }
       → { channel_id, expires_at }              # value normalized + stored ciphertext

POST   /api/v1/auth/recovery/channels/verify    # verify the code
       body: { channel_id, code }
       → 200 { verified: true }

GET    /api/v1/auth/recovery/channels           # list (no values, only redacted hint)
       → [{ id, channel_type, masked_value, verified_at, created_at }]

DELETE /api/v1/auth/recovery/channels/:id       # remove (requires fresh password)

POST   /api/v1/auth/forgot-password             # start reset
       body: { username_or_channel_value }
       → 202 { sent_to: [masked_value, ...] }    # always 202; doesn't leak existence

POST   /api/v1/auth/forgot-password/verify      # exchange code for reset token
       body: { username_or_channel_value, code }
       → { reset_token, expires_at }

POST   /api/v1/auth/reset-password              # set new password
       body: { reset_token, new_password }
       → { ok: true } + new session cookie

POST   /api/v1/auth/change-password             # logged-in only
       body: { current_password, new_password }
       → { ok: true } + new session cookie
```

`masked_value` examples: `j***@artelonga.com.br`, `+55 11 ****-9876`, `wa: ****1234`.

### Verification code delivery

- **Email:** SMTP. Phase 1 supports either dev (printed to logs, like the existing `/auth/login` flow) or production (env vars `CO_SMTP_HOST`, `CO_SMTP_USER`, `CO_SMTP_PASS`, `CO_SMTP_FROM`). lettre crate.
- **WhatsApp:** WhatsApp Business Cloud API. Env: `CO_WHATSAPP_ACCESS_TOKEN`, `CO_WHATSAPP_PHONE_ID`. Phase 1 can stub with dev-mode-logs.
- **SMS:** Twilio. Env: `CO_TWILIO_SID`, `CO_TWILIO_TOKEN`, `CO_TWILIO_FROM`. Phase 1 can stub with dev-mode-logs.

Codes are 6 digits, 10-min TTL, max 5 attempts per code, rate-limited per channel (5/hour).

### Username + email decoupling (prerequisite work)

- Add `usuario TEXT UNIQUE` to `users`. Backfill from email's local-part for existing rows; NULL until then.
- Drop `email NOT NULL` constraint (recreate table or `ALTER TABLE` with `IF NOT EXISTS` pattern). Migration carefully — `email UNIQUE` becomes `email UNIQUE` (still unique when present, but nullable).
- Update signup paths to accept `usuario + password` only. Email becomes a recovery channel, not a primary identifier.
- Existing `password-login` accepts both `{usuario, password}` and `{email, password}` — back-compat.

### UI changes (`app.js`)

- Login modal gains a "Esqueci minha senha" link → opens recovery flow.
- Settings panel gains a "Recovery channels" section: add/verify/list/remove, plus a "Change password" subsection.
- Toast feedback per stage.
