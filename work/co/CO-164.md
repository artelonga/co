## As

a user with thousands of entries across universes (CO at 5k+, comunicacao at 4.7k, time at 700+) who keeps reaching for `q=` keyword search and missing semantically-similar content under different vocabulary

## I Need

a vector index keyed on entry body text with `?semantic=…&k=…` query support, automatically maintained on entry write

## So That

(a) `q=` upgrades from substring/FTS to semantic similarity for users who opt in,
(b) the mempalace shim (CO-163) gets a real `query` implementation backing it,
(c) cross-universe similarity ("find entries like this one across all my universes") becomes possible

---

## Current state (1.76.0)

CO indexes entries via SQLite FTS5 (substring/keyword). No embedding storage, no vector similarity. The blob CAS (1.75.0) can store embedding bytes content-addressed, but there's no index over them.

## Tech choice

Three options, ranked by likely fit:

1. **`sqlite-vss`** (or its successor `sqlite-vec`). In-process, single dependency, embeds in the same SQLite file. Ships with CO's existing storage layer. **Preferred** unless brute-force perf becomes a wall (>50k entries per universe).

2. **`hnswlib`-rs** with on-disk persistence. Faster recall@k at million-scale, but a separate index file per universe to manage and rebuild on schema changes.

3. **External Qdrant** (Docker sidecar). Most flexible, worst operational story for a single-binary deploy.

Default to (1). If `sqlite-vec` is too immature on the Rust side, fall back to brute-force cosine via SQL (`SELECT … ORDER BY embedding_distance(...)` with a custom function) — works fine up to ~10k entries per universe.

## Embedding model

Default to **`all-MiniLM-L6-v2`** (384-dim, 80MB, no GPU needed) via the `fastembed` Rust crate (or ONNX runtime if needed). Local inference only — no external API calls, fits CO's offline-first ethos. Configurable via env var `CO_EMBEDDING_MODEL`.

## Storage

Per-universe SQLite gains:

```sql
CREATE TABLE entry_embeddings (
    universe_key TEXT NOT NULL,
    path         TEXT NOT NULL,
    body_hash    TEXT NOT NULL,    -- so we know the embedding is fresh
    embedding    BLOB NOT NULL,    -- 384 × f32 = 1536 bytes
    model        TEXT NOT NULL,    -- e.g. "all-MiniLM-L6-v2"
    indexed_at   TEXT NOT NULL,
    PRIMARY KEY (universe_key, path)
);
CREATE INDEX idx_emb_body_hash ON entry_embeddings(body_hash);
```

Plus the `sqlite-vec` virtual table over `entry_embeddings.embedding`.

## Index lifecycle

- **On entry write** (vault PUT, entry create, entry update): enqueue an embedding job. Jobs run on a background worker (single thread, batch up to 32 entries per call to amortize model load).
- **On entry delete**: remove from index.
- **On model change**: re-index everything (rare, manual `co reindex --embeddings`).
- **On boot**: scan `entries.body_hash` against `entry_embeddings.body_hash`, queue mismatches.

## API

```
GET /api/v1/universes/:slug/entries?semantic=<query>&k=10
   → returns top-K entries by cosine similarity, includes a `_score` field

GET /api/v1/universes/:slug/entries/:path/similar?k=10
   → entries similar to the given one (skips self)

GET /api/v1/search?semantic=<query>&k=10
   → cross-universe similarity, scoped to universes the user can read
```

The `?semantic=` parameter is independent of `?q=` — they can be combined; if both are present, results are ranked by the harmonic mean of FTS rank and cosine similarity (hybrid search).

## Acceptance

- [ ] `entry_embeddings` table created via migration v10
- [ ] `fastembed` (or equivalent) integrated, model auto-downloaded on first use to `~/.co/models/`
- [ ] Background worker indexes new entries within 1s for batches up to 32
- [ ] `?semantic=…&k=10` returns top-K with `_score` ∈ [0, 1]
- [ ] `/api/v1/search?semantic=…` aggregates across visible universes
- [ ] Hybrid search (q + semantic) outperforms either alone on a benchmark set
- [ ] Re-index on `body_hash` change (boot scan), not on every write of a same-content entry
- [ ] No regression on 329 lib tests

## Out of scope

- Multi-modal (image / audio) embeddings — separate ticket
- User-trained / fine-tuned models — out of scope; default model only
- Federation across CO instances — out of scope

## Estimate

~2 days end-to-end if `sqlite-vec` works first try; ~3 days if we fall back to brute-force or need ONNX runtime plumbing. Sequence: storage + migration (½d), embedding pipeline (½d), background worker (½d), API endpoints (½d), tests (½d).
