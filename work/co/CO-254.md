## As

A first-visit anonymous user landing on the template universe

## I Need

The tutorial onboarding to clearly distinguish itself from the **actual** CO development project, so I can tell which `CO-1`, `CO-2`, etc. is real and which is pretend.

## So That

When I see "CO-1: Mova este cartão para Concluído" in the kanban, I understand it's a tutorial task — not the same as the real `CO-1: Initial CLI` work item in the dev universe. The universe tree (template → its tutorial project + sub-universe `co`) becomes the **pedagogy** for understanding what universes are.

## Context

### Current naming collision

| Layer | Identifier | Content |
|---|---|---|
| Universe | `co` | Real dev project — CO-1..CO-253+ task entries |
| Universe | `template` | Onboarding — wiki + tutorial project (child of `co` via `parent_key`) |
| Project (inside template) | `CO` / "Bem-vindo ao Co" | 9 *tutorial* tasks with keys `CO-1`..`CO-9` that overlap with real dev task IDs |

Both layers use `CO-N` as the task key. A user looking at `/template` sees 9 fake "CO-1..9" tasks. A user looking at `/co` sees the real CO-1..CO-253. Without context, the first looks like a buggy/stub version of the second.

### Decision — Option B from review

Keep the `co` (parent) ← `template` (child) DB relationship. **Rename only the tutorial project + its tasks inside template.** No migration of universe parent_key needed.

## Scope

- **`co-web/seed/template/projects/CO/_project.md`** — rename:
  - `key: CO` → `key: tutorial`
  - `name: "Bem-vindo ao Co"` → `name: "Tutorial — comece por aqui"`
  - Directory rename: `seed/template/projects/CO/` → `seed/template/projects/tutorial/`
- **`co-web/seed/template/projects/tutorial/{1..9}.md`** — rename task keys:
  - Old: `key: CO-1` through `CO-9`
  - New: `key: tut-1` through `tut-9` (or `tarefa-1` through `tarefa-9` if Portuguese feels better)
- **Seed migration on boot** — `seed.rs reseed_template_content_pages` should detect the old `CO` project + tasks and either rename in place (preserving timestamps + history) or drop+re-seed if no user data was added (anonymous template should always be pristine).
- **Sidebar surfacing of the `co` sub-universe** — already shipped in CO-252. Verify the sub-universe relationship is visible from `template` so anonymous users see: *"This universe (template) has a sub-universe (co) where the real development happens"*.
- **Wiki text in `index.md`** — add a short paragraph explaining: *"O painel de tarefas abaixo é um tutorial. Para ver o desenvolvimento real do Co, abra o sub-universo [Co](/co)."*

## Acceptance

- Visit `/template` (or `/`) anonymously → kanban shows project "Tutorial — comece por aqui" with 9 tasks keyed `tut-1`..`tut-9` (or chosen Portuguese variant).
- Visit `/co` → real dev tasks `CO-1`..`CO-253` (no overlap).
- index.md wiki explicitly tells the user: tutorial = practice, sub-universe `co` = the real thing.
- Seed boot migration: existing prod data with the old `CO` project gets renamed (or replaced if no edits — template is meant to be ephemeral per CO-49).
- E2E spec `seed-links.spec.ts` updated to check the new project key.

## Blast radius

- ~30 LOC seed YAML/markdown renames (`projects/CO/` → `projects/tutorial/`)
- ~20 LOC `seed.rs` migration step (handle old `CO` project entries on boot)
- ~5 LOC index.md text update
- 1 SQL migration if we want to rename in-place rather than re-seed
