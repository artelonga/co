## As

a user with one CO account who wants to log in once and have access to every universe deployment in the artelonga family — `quilomboaraucaria.com.br`, `artelonga.com.br`, `co.artelonga.com.br`, future deployments — without juggling separate accounts per site

## I Need

`co.artelonga.com.br` to be the de facto auth backend for any universe deployment, and a deployment-side mechanism that defers signup, login, and session validation to that central server

## So That

(a) one signup gives access to every universe in the family,
(b) password reset (CO-165) and recovery channels live in one place rather than being duplicated per deployment,
(c) Quilombo (today only deployment with login) and ArteLonga (planned login) authenticate against the same source of truth,
(d) future deployments inherit the same auth without rebuilding it.

---

## Current state (1.76.1)

- `co.artelonga.com.br` is the canonical CO server — has `users`, `password_login`, JWT cookies.
- `quilomboaraucaria.com.br` runs its own deployment; has `quilombo_usuarios` table and its own login flow (separate user space — see `quilombo_routes.rs`).
- `artelonga.com.br` (the public content site) does not yet have login.
- No federation — a yuri@artelonga account on co does not exist on the quilombo deployment.

## Design

### Mechanism A — Shared cookie domain (preferred for in-family deployments)

All artelonga-family sites share the parent domain `artelonga.com.br`. JWT session cookie can be issued with `Domain=.artelonga.com.br`, making it readable from every subdomain — no OAuth dance required.

```
co.artelonga.com.br/api/v1/auth/password-login
   Set-Cookie: session=<JWT>; Domain=.artelonga.com.br;
              Secure; HttpOnly; SameSite=Lax; Path=/

quilombo.artelonga.com.br → reads session cookie → validates JWT signature
                            → hits co.artelonga.com.br/api/v1/auth/me to enrich
```

Each deployment caches the user lookup. JWT `iss=co.artelonga.com.br`, `aud=*` (or per-deployment audiences if we want to scope).

**Constraint:** All deployments must be subdomains of `artelonga.com.br`. `quilomboaraucaria.com.br` (different apex) cannot share cookies — would need Mechanism B.

### Mechanism B — OAuth-like delegation (for cross-apex deployments)

`co.artelonga.com.br` becomes an OAuth 2 / OIDC provider:

```
1. User on quilomboaraucaria.com.br clicks "Entrar com CO"
2. Redirect to co.artelonga.com.br/oauth/authorize?client_id=quilombo&redirect_uri=...&state=...
3. User authenticates (or already has session)
4. Redirect back: quilomboaraucaria.com.br/oauth/callback?code=...&state=...
5. Quilombo backend exchanges code for token: POST co.../oauth/token
6. Quilombo gets { access_token, id_token, refresh_token } and creates a local session
```

Plain OIDC code flow. CO needs `/oauth/authorize`, `/oauth/token`, `/oauth/userinfo`, `/.well-known/openid-configuration`. Per-client config in env or a `oauth_clients` table.

### Recommended split

- ArteLonga + future artelonga-subdomain deployments: **Mechanism A** (cookie share). Trivial — already same JWT signing key.
- Quilombo + any cross-apex deployment: **Mechanism B** (OIDC). More work but standard.

Phase 1 ships A only; Phase 2 adds OIDC for B.

### User model migration

Quilombo today has `quilombo_usuarios` (separate table, separate password). To unify:

1. Phase 1 of this ticket: dual-mode — Quilombo accepts both legacy `quilombo_usuarios` login AND CO session cookies (when present, treats them as authoritative).
2. Add a `linked_user_id` column on `quilombo_usuarios` so a quilombo profile can be associated with a CO user.
3. UI nudge: "vincule sua conta quilombo a uma conta CO" → redirect to login → on return, link.
4. Phase 3 (deprecation): once all quilombo users are linked, drop `quilombo_usuarios` password support entirely; password lives only in CO.

### Deployment integration kit

Each deployment ships with:

- A small `co_auth.{ts,py,rs}` module that:
  - reads `session` cookie from request
  - validates JWT against CO's public key (fetched from `co.artelonga.com.br/.well-known/jwks.json`)
  - exposes a middleware: `requireUser(req) → user | 401`
- A login button that either (A) drops a cookie via cross-subdomain auth, or (B) starts the OIDC flow.

For artelonga (planned login, A): just import the module and add the button.
For quilombo (B): drop the local `verifyPassword` path in favor of the OIDC bouncer.

### Scoping & permissions

A CO user accessing quilombo gets a quilombo-side authorization decision based on:
- universe membership table (already exists in CO)
- quilombo's own per-event/post permissions (stays in quilombo)

The CO user's tier (admin / user) is propagated via the JWT's `tier` claim.

### Crypto

JWT signing key rotation: introduce a `kid` claim and a JWKS endpoint. Today's single `JWT_SECRET` becomes the current key; new keys can be added without invalidating active sessions.

## Acceptance

### Phase 1 — Cookie-share for `.artelonga.com.br` subdomains

- [ ] CO sets session cookie with `Domain=.artelonga.com.br` (env-flagged, default off in dev so localhost still works)
- [ ] CO publishes `/.well-known/jwks.json` so deployments can verify without sharing secrets
- [ ] Sample integration kit at `scripts/co_auth_kit/` with TS + Python adapters
- [ ] ArteLonga deployment uses kit and authenticates through CO; "Entrar" button works
- [ ] Test: log in on `co.artelonga.com.br`, navigate to `artelonga.com.br`, see logged-in state without re-entering creds

### Phase 2 — OIDC for cross-apex deployments

- [ ] `oauth_clients` table + admin UI to register a client
- [ ] `/oauth/authorize`, `/oauth/token`, `/oauth/userinfo`, `/.well-known/openid-configuration` endpoints
- [ ] Standard OIDC code flow with PKCE
- [ ] Quilombo deployment integrates: "Entrar com CO" works, dual-mode with legacy login during transition
- [ ] Per-client `redirect_uri` allowlist; per-client scopes

### Phase 3 — Deprecation

- [ ] All quilombo users linked
- [ ] Quilombo legacy login removed; users authenticate solely via CO

## Out of scope

- Federated graph queries (one search returns results from all universes via SSO) — separate ticket
- B2B / external clients (third parties consuming CO auth) — separate ticket
- Social login (Google, GitHub) — separate ticket; the user has stated git OAuth is planned but distinct

## Estimate

- Phase 1 (cookie share): ~1-2 days. Mostly config + JWKS endpoint + a sample TS adapter.
- Phase 2 (OIDC): ~3-5 days. Real protocol implementation, client registration UI, dual-mode flow.
- Phase 3 (deprecation): ~1 day plus a coordination window.

Total: ~1-2 weeks across phases.
