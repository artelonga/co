GIVEN a security-compliance review of auth/login (`infra/e2e/SECURITY-REVIEW.md`)
found that `build_session_cookie` emitted the JWT-bearing session cookie as
`HttpOnly; SameSite=Lax` **without `Secure`** — while the logout clear-cookie
*did* set `Secure` — so the cookie carrying the session token could be sent over
plain HTTP on a downgrade/mixed-content request (session-token theft; OWASP
A05/A07),
WHEN we add `Secure` to the session cookie in every TLS environment, omitting it
only for the plain-HTTP local envs (`local`/`dev`/`test`) where browsers would
otherwise drop the cookie and break local login,
THEN the session token is transport-protected in prod/staging/uat (and on an
unset/empty `CO_ENV`, which fails closed to `Secure`), with no impact on local dev.

## Acceptance

- [x] `cookie_secure_for_env(co_env)` — pure helper: `false` for
  `local`/`dev`/`test`; `true` otherwise (incl. empty → fail closed).
- [x] `build_session_cookie` appends `; Secure` when `cookie_secure_for_env` is
  true (reads `CO_ENV` via `secrets::global()`); local HTTP login unaffected.
- [x] Unit test covers local/dev/test (no Secure) + prod/staging/uat/empty (Secure).
- [x] `cargo test` + `cargo clippy -- -D warnings` + `cargo fmt` clean.

## Notes / scope

- **SameSite (F3)** left as `Lax` on the login cookie — intentional: `Strict`
  blocks the cookie on cross-site top-level navigation (e.g., following an email
  link), logging users out. The logout clear-cookie's `Strict` is fine.
- **CSP (F2)** is a separate hardening task (edge/middleware `Content-Security-Policy`).
- Found by the auth-security probe suite `infra/e2e/auth-sec.sh`.
