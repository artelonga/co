## As

a logged-in member of a universe with the chat surface open

## I Need

a WebSocket that pushes new messages, edits, deletes, and presence
events to every connected client of a given room, so I see other
people's messages appear without polling and I can see who's currently
in the room

## So That

chat actually feels like chat. CO-193 produces a refresh-driven
experience; this slice makes it live.

---

## Precondition

CO-193 (chat schema + REST) must be live. This ticket consumes the
same `chat_rooms` and `chat_messages` tables, adds no new schema.

## Connection model

### Endpoint

```
GET /api/v1/universes/:slug/chat/rooms/:room_slug/ws
```

WebSocket upgrade. Auth via the existing session cookie (JWT) — the
upgrade handler reuses `require_auth_with_token` so the WS shares the
same gate as REST.

### Authorization (re-check on connect)

Same as CO-193 read-message gate:

- Anonymous → 401 close (code 4401)
- Non-member → 403 close (code 4403)
- Room archived → 410 close (code 4410)
- Member or above → connection accepted

Role is captured at connect time and stamped on each outgoing event so
the client can render correct affordances (e.g., delete buttons only
for own messages + admin/owner).

### Subscription scope

One WS connection = one room. Switching rooms in the UI closes and
re-opens. Simpler than multiplexing; aligns with the typical "one
room visible at a time" sidebar UI pattern.

## Wire format

JSON Lines over WS. Server → client events:

```jsonc
// On connect — initial state digest
{ "type": "ready", "room_id": "room_abc", "your_role": "member",
  "presence": [{ "user_id": "usr_a", "display_name": "Yuri", "usuario": "yuri" }] }

// Live message events (push only — POST still happens via REST)
{ "type": "message.created", "message": { /* same shape as REST GET messages */ } }
{ "type": "message.edited",  "message": { /* with edited_at populated */ } }
{ "type": "message.deleted", "message_id": "msg_xyz", "deleted_at": "..." }

// Presence
{ "type": "presence.join",  "user": { "user_id": "usr_b", "display_name": "...", "usuario": "..." } }
{ "type": "presence.leave", "user_id": "usr_b" }

// Typing indicators (optional polish; if cut, leave for v2.2)
{ "type": "typing.start", "user_id": "usr_c" }
{ "type": "typing.stop",  "user_id": "usr_c" }

// Server-initiated close on error
{ "type": "error", "code": "rate_limited" | "kicked" | "internal", "message": "..." }
```

Client → server events:

```jsonc
{ "type": "ping" }                              // keep-alive
{ "type": "typing.start" }                       // optional
{ "type": "typing.stop" }
```

**Messages are NOT posted over WS.** POST still goes through the existing
CO-193 REST endpoint. Rationale: keeps the write path single-source-of-
truth (rate limit, validation, persistence in one place), and the WS is
purely a push channel. The REST handler, after successful insert, fans
out a `message.created` event to all connected clients of that room.

## Server architecture

### Fan-out

In-process broadcast — no external pubsub. A `tokio::sync::broadcast`
channel per `room_id` lives in `AppState.chat_rooms_broadcast`
(`HashMap<RoomId, broadcast::Sender<ChatEvent>>`). Created on first
connection to a room, dropped when subscriber count returns to 0.

After every successful `POST /messages` (or edit/delete from CO-196),
the REST handler does:

```rust
if let Some(tx) = state.chat_rooms_broadcast.lock().unwrap().get(&room_id) {
    let _ = tx.send(ChatEvent::MessageCreated(msg.clone()));
}
```

Best-effort. If no subscribers, the send is a no-op.

This means we're **single-machine**. Fine for current Fly deploy (single
machine app). A future "scale-out" ticket adds Redis pubsub between
instances. Don't pre-build that.

### Presence

`AppState.chat_presence` (`HashMap<RoomId, HashMap<UserId, JoinedAt>>`).
Updated when a connection opens or closes. Initial roster shipped in
the `ready` event. Join/leave events broadcast to the room.

A user with multiple concurrent connections (browser + mobile) is
present-once; presence reference-counted per user_id.

### Keep-alive

Server sends a ping frame every 30s. Client must respond within 10s
or connection drops. Standard tungstenite/axum-ws pattern.

### Rate limiting

- Connect rate-limit: 5 connects per user per minute (prevents reconnect
  storms).
- Typing-event rate-limit: 1 typing.start per 2s per user.

Both reuse the existing `rate_limit` module with keys
`chat:ws:connect:<user_id>` and `chat:typing:<user_id>:<room_id>`.

### Tasks per connection

Each WS spawns two tokio tasks:
- Reader: deserializes client → server events, updates typing state.
- Writer: subscribes to the broadcast channel + sends pings, serializes
  events as text frames.

On any side completing (client close, broadcast lag, server shutdown),
the other is aborted.

## Tests

Pure-Rust integration tests using axum's test client. The hard part is
deterministic WS testing — accept that the assertions are about
broadcast behavior, not socket-level framing.

- [ ] `test_ws_unauthenticated_4401` — connect without cookie closes 4401.
- [ ] `test_ws_non_member_4403` — connect to a room in a universe the
      caller isn't in.
- [ ] `test_ws_archived_room_4410` — connect to archived room.
- [ ] `test_ws_ready_event_includes_presence` — first frame is `ready`.
- [ ] `test_ws_broadcast_to_all_subscribers` — open 2 connections, POST
      via REST, both receive `message.created`.
- [ ] `test_ws_no_broadcast_to_other_rooms` — events stay scoped to
      `room_id`.
- [ ] `test_ws_presence_join_leave_events` — second connection triggers
      `presence.join` for the first; closing triggers `presence.leave`.
- [ ] `test_ws_same_user_multiple_connections_dedup` — opening 2 tabs
      as the same user emits only one `presence.join` (refcount).
- [ ] `test_ws_connect_rate_limit_6th_in_minute_fails` — uses the
      `rate_limit` module's test clock.
- [ ] `test_ws_typing_rate_limit_2s` — second typing.start within 2s is
      silently dropped (no broadcast).
- [ ] `test_ws_keepalive_drops_silent_client` — fast-forward simulated
      time past keep-alive threshold.

## Acceptance

- [ ] WS endpoint mounted + reachable under correct universe slug
      + room slug.
- [ ] Auth gates match REST (anonymous = 4401, non-member = 4403,
      archived = 4410).
- [ ] After CO-193 REST POST, all WS subscribers of that room receive
      `message.created` within ~50ms.
- [ ] `presence.join` / `presence.leave` fired correctly with
      multi-connection refcounting.
- [ ] Keep-alive ping every 30s; silent client dropped at 40s.
- [ ] Connect rate-limit: 6th connect/min returns 4429 close.
- [ ] No regression on CO-193 REST behavior.

## Out of scope

- **Cross-instance fan-out** (Redis pubsub). Single-machine for v2.1.
- **Message history via WS.** Initial history still fetched via the
  REST `GET /messages` endpoint; WS only pushes new events from
  connect-time forward.
- **Reactions, read receipts, message search.** Separate tickets.
- **UI consumer.** CO-195.
