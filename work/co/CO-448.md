## As
A token issuer (operator, staging CI, future public-API consumer), QUERO emitir
um api-token com **exatamente** as capacidades que ele precisa — nem mais — PARA
que um vazamento de secret não conceda admin pleno, e PARA que a API pública
(CO-278) tenha autorização granular desde o dia 1.

## Contexto
Hoje `api_tokens` **não tem coluna de escopo** — um token herda a *tier* do dono
(all-or-nothing). É por isso que o token de staging do CO-401 teve que ser
**admin pleno**. O dono decidiu (2026-06-14): **least-privilege obrigatório**,
modelo **híbrido** (capacidades `recurso:ação` + *bundles* nomeados), cobrindo o
**release atual** (suíte de staging CO-374) **e** os **requisitos futuros do
roadmap** (API pública CO-278). Esta task é o **CO-278-B** puxado pra frente
porque o CO-401 depende dele.

## Design — híbrido (capacidades + bundles)

> **Pin de migração (pré-flight 2026-06-14):** main em **v80** (CO-204). CO-401
> #246 está **em draft/held** reivindicando v81 mas **será reworkeado**; esta task
> **merge antes** do CO-401, então claim **v81** aqui (`v081.rs`,
> `migrate_v081`, `if current_version < 81`, `mod v081;`). O CO-401 rebaseado
> passa a usar **v82**. NUNCA referenciar `scopes` no batch base.

### Coluna
- Migração v81: `ALTER TABLE api_tokens ADD COLUMN scopes TEXT` (JSON array de
  strings de capacidade; `NULL` = sem escopo declarado → ver compat abaixo).

### Capacidades (`recurso:ação`) — vocabulário inicial (extensível)
Cobrir o que a suíte CO-374 exercita **e** o que a API pública CO-278 precisará:
- Leitura: `entries:read`, `universes:read`, `telemetry:read`, `gestao:read`,
  `funnel:read`, `chat:read`, `deployments:read`
- Escrita: `entries:write`, `universes:write`, `chat:write`
- Agente: `agent:dispatch`
- (novas capacidades entram aditivamente quando o roadmap adiciona superfícies —
  ex.: CO-288 cost panel já mapeia em `deployments:read`)

### Bundles nomeados (presets = conjuntos de capacidades)
- `read`  → `{entries:read, universes:read, telemetry:read}`
- `write` → `read ∪ {entries:write, universes:write}`
- `admin` → `write ∪ {gestao:read, funnel:read, chat:read, chat:write, deployments:read}`
- `agent` → `write ∪ {agent:dispatch}`
Um token guarda **capacidades expandidas** (resolver bundle → set na emissão), ou
guarda o nome do bundle e expande na checagem — escolha do implementador, mas
deve ser **auditável** (dá pra ver o que o token pode).

### Enforcement
- Cada endpoint protegido declara a **capacidade exigida** (ex.: o handler de
  `/admin/chat/origin-breakdown` exige `chat:read`; `PUT entries` exige
  `entries:write`). O gate em `co-web/src/auth/mod.rs` resolve o token, expande
  seus escopos, e **nega (403)** se a capacidade exigida não estiver presente.
- Sem escalonamento: um token nunca obtém uma capacidade fora do seu set.

### Compatibilidade (crítico — não quebrar nada)
- Tokens existentes têm `scopes = NULL`. Tratar `NULL` como **"herda a tier do
  dono"** (comportamento atual) para não quebrar os tokens já emitidos (vault,
  co-auto reporting, etc.). Só tokens **com** `scopes` são restringidos por
  capacidade. Teste: token antigo (NULL) continua acessando o que acessava.

## Acceptance
- [ ] Migração **v81** adiciona `api_tokens.scopes` (idempotente, `ensure_column`).
- [ ] Modelo híbrido: capacidades `recurso:ação` + 4 bundles (`read/write/admin/
      agent`) que expandem para conjuntos de capacidades. Vocabulário inicial acima.
- [ ] Emissão de token aceita `scopes` (lista de capacidades **ou** nome de bundle)
      e persiste o set resolvido (auditável).
- [ ] Gate de auth **nega 403** quando a capacidade exigida pelo endpoint falta no
      token; **permite** quando presente. Pelo menos os endpoints admin que a suíte
      CO-374 toca declaram sua capacidade.
- [ ] **Backward-compat:** token com `scopes = NULL` mantém o comportamento de hoje
      (herda tier do dono). Teste explícito.
- [ ] Testes: (a) token `read` não escreve (403) mas lê (200); (b) token `admin`
      bundle acessa as superfícies admin da suíte; (c) capacidade ausente → 403;
      (d) bundle expande corretamente; (e) compat NULL.
- [ ] `docs/cross-env-auth.md` + `api-catalog.md`/openapi documentam o modelo de
      escopo e as capacidades por endpoint (sem drift).
- [ ] Sem MCP; sem quebrar tokens existentes.

## So that
O token de staging do **CO-401** vira **least-privilege** (só as capacidades que a
suíte CO-374 exercita, não admin pleno), e a **API pública CO-278** ganha
autorização granular nativa. Um vazamento de secret concede só o escopo do token.
