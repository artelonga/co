GIVEN current relationships are ad-hoc (parent_id on tasks, project_key, Obsidian `[[wikilinks]]` parsed but untyped), and the manifest epic requires arbitrary typed relationships (event → place, task → person, comment → entry),
WHEN we add an `entry_relations` table and a query DSL exposing relationships as joinable, indexable graph edges,
THEN queries like "events at place X with attendee Y" become declarative, and the board can render relationship-aware views.

## Architecture

- Manifest declares `relationships: [{ from: <type>.<field>, to: <type>, cardinality }]`
- Storage: `entry_relations(universe_key, from_path, to_path, relation_type, created_at)` indexed in both directions
- Wikilinks `[[target]]` resolve at write to entry paths; if manifest declares the field as typed `ref`, the resolution stores a relation row
- Untyped wikilinks remain as text (no graph storage)
- Query DSL: SQL-like surface compiling to SQLite joins; returns entries with hydrated relations

## Tasks

- [ ] Migration: create `entry_relations` table with indexes on both directions
- [ ] Wikilink parser upgrade: resolve `[[target]]` against entries in the same universe at write
- [ ] Manifest-driven typing: when `tarefa.assignee = ref(pessoa)`, wikilinks in `assignee` create relations of type `assignee`
- [ ] Query DSL: parsed to AST, lowered to SQLite joins
- [ ] API: `GET /api/v1/universes/:slug/query` accepts DSL string, returns matching entries
- [ ] Board UI: relation-aware views (mention this in entry detail)
- [ ] Backfill: on manifest update, re-resolve wikilinks for affected content types

## Scale notes

- `entry_relations` indexed on `(universe_key, from_path, relation_type)` and `(universe_key, to_path, relation_type)` — both directions, reverse lookups O(log N)
- At 10M entries × 5 relations avg = 50M rows — within SQLite's range with per-universe DBs (CO-77)
- Cross-universe relations forbidden by manifest validation; graph queries scope to a universe
- Query DSL must be sandboxed — no recursive infinite descent without explicit `LIMIT N`
- Result size cap: 1000 rows per query (paginate beyond that)

## Acceptance

- Manifest declaring `evento.attendees: ref_list(pessoa)` creates relation rows on entry write
- Query "events with attendee yuri" returns correct results in < 50ms at 100K entries
- Wikilink in non-ref field stays as plain text (no relation row)
- Manifest update that promotes a field to ref backfills relations correctly
