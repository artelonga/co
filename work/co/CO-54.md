GIVEN multiple clients can edit the same universe (web UI, CLI sync, co auto, Obsidian plugin), and two users might edit the same file simultaneously,
WHEN I formalize idempotency guarantees and conflict resolution fallbacks,
THEN:

## Scenarios

### Scenario 1: Two web users edit the same task
- User A opens task modal, edits description
- User B opens same task modal, edits title
- Both save at similar times

**Current:** Last write wins (PUT replaces entire task). B's save overwrites A's description change.
**Fix:** Field-level merge. PUT only updates fields that changed. Server merges non-overlapping field changes.

### Scenario 2: Web user + CLI sync edit same file
- Alice edits `content/sobre.md` on web → saves → server has version 2
- Bob edits `content/sobre.md` locally → `co sync push` → server has version 2, Bob's push has base version 1

**Resolution:** Sync protocol detects conflict (both hashes differ from base). Applies configured strategy (default: last-write-wins by timestamp).

### Scenario 3: co auto + web user edit same task
- co auto picks task CO-42, starts implementation
- Yuri manually changes CO-42 status to "done" on web
- co auto finishes, tries to update CO-42 status to "done"

**Resolution:** Idempotent. Setting `status: done` when already `done` is a no-op. No conflict.

### Scenario 4: Two co auto agents on same task
- Agent A (worktree 1) picks CO-42
- Agent B (worktree 2) also picks CO-42 (race condition)

**Resolution:** co auto uses a lockfile per task. Second agent skips locked tasks. Lock expires after 30 minutes (crash recovery).

## Idempotency Rules

| Operation | Idempotent? | Guarantee |
|-----------|------------|-----------|
| Create entry (POST) | No — returns 409 if path exists | Use PUT for upsert |
| Update entry (PUT) | Yes — same content = no version bump | Hash comparison |
| Delete entry (DELETE) | Yes — deleting non-existent = 204 | No error on missing |
| Change task status | Yes — setting same status = no-op | Field comparison |
| Sync pull | Yes — downloading same content = no change | Hash comparison |
| Sync push | Yes — uploading same content = no change | Hash comparison |

## Conflict Resolution Matrix

| Client A | Client B | Detection | Resolution |
|----------|----------|-----------|------------|
| Web (field edit) | Web (field edit) | Different fields → no conflict | Auto-merge fields |
| Web (field edit) | Web (same field) | Same field, different values | Last-write-wins (timestamp) |
| CLI sync | Web | Hash mismatch on both sides | Configured strategy |
| CLI sync | CLI sync | Lockfile prevents | Second sync waits |
| co auto | Web | Status convergence | Idempotent (no conflict if same target state) |
| co auto | co auto | Task lockfile | Second agent skips |
| Obsidian | Web | Same as CLI sync | Same conflict strategies |

## Worst-Case Fallbacks

1. **Data loss prevention:** Before any destructive operation, save the previous version to `_versions/{path}/{timestamp}.md`
2. **Conflict marker files:** When auto-merge fails, create `{path}.conflict` with both versions embedded (Git-style `<<<<<<<` markers)
3. **Audit trail:** Every write operation logged with `actor`, `timestamp`, `before_hash`, `after_hash` in `entry_versions` table
4. **Manual recovery:** `GET /api/v1/universes/:slug/entries/:path/versions` returns version history
5. **Nuclear option:** `co sync reset <universe>` → re-clone from repo, discard all local changes
