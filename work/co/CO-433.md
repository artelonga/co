## As
O operador do co em produção, QUERO que escritas em universos diferentes não
serializem num único mutex global e que nenhum handler fale SQL cru, PARA
escalar com mais universos/usuários e manter o acesso a dados auditável e
trocável de backend (SQLite hoje, S3/Postgres no roadmap).

## Contexto técnico (do audit 2026-06-12)
- **Gargalo:** `Arc<parking_lot::Mutex<Storage>>` global (`server/state.rs`);
  264+ `.lock()` em 47 arquivos. Universos distintos serializam à toa, embora o
  `UniversePool` (CO-77) já dê conexões por-universo.
- **Vazamento de camada:** `security/routes.rs`, `auth/onboarding_routes.rs`,
  `auth/recovery_routes.rs`, `eda/mod.rs` chamam `storage.conn().prepare/execute/
  query_row` direto — SQL cru fora da camada de storage.
- **Lock-over-await:** alguns handlers seguram `universe_conn().lock()` perto de
  fronteiras async (já é regra proibida; o audit achou padrões frágeis).

## Acceptance
- [ ] Estado por-universo: trabalho de escrita/leitura de conteúdo de um universo
      passa a usar o lock do `UniversePool` (por-universo) em vez do
      `Mutex<Storage>` global. O mutex global fica restrito ao meta-DB (users,
      universes, tokens). Provar com um teste de contenção: escritas em dois
      universos não bloqueiam uma à outra.
- [ ] `trait EntryStore` (get/upsert/delete/list por universo) extraído; o
      `UniversePool` vira fábrica sobre o backend — SQLite é a impl default
      atrás do trait. (Não implementar S3 aqui; só deixar o seam.)
- [ ] **Zero SQL cru em handlers**: os acessos diretos em security/auth/eda
      movidos para métodos tipados de Storage (impl-blocks dedicados:
      `storage::security`, `storage::auth`). `grep` de `conn().prepare\|
      conn().execute` em `*_routes.rs`/subscribers = vazio.
- [ ] Nenhum `Mutex<Storage>` mantido através de `.await`; nenhum panic sob o
      lock (regra do incidente 2026-05-12).
- [ ] **Zero mudança de comportamento**: `cargo test -p co-web` verde; clippy
      limpo; rotas idênticas.
