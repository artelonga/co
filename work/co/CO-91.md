GIVEN today's content-author workflow is a 250-line `scripts/seed-prod-universes.sh` that handles login, universe creation, jj-based delta detection, changelog generation, and bulk upload — and the platform has decided this is the canonical authoring loop (not a one-off script),
WHEN we promote that workflow into a proper `co sync` subcommand of the user-facing `co` CLI, with the same composability primitives (`co-token` for auth, `jj` for delta, `~/.co/seed-runs/` for changelog history) but a clean argument shape and proper error handling,
THEN authors edit markdown locally, run `co sync push`, and changes flow to the configured remote with a paper trail — without touching curl, scripts, or the underlying API surface. The same command works against any universe on any deployment (UAT, prod, self-hosted), gated by a per-deployment auth token in the OS keychain.

## What this consolidates

This task formalizes patterns invented across CO-65/82/85/co-token/seed-prod-universes.sh:

- **Auth via OS keychain** — `co-token` (CO already shipped) stores per-deployment API tokens encrypted at rest. `co sync` reads them on demand.
- **Delta upload via jj** — local source repo wrapped with `jj git init --colocate`; per-universe baseline (jj commit ID) stored at `~/.co/sync-state/<deployment>/<universe>.commit`; only files changed since the baseline are pushed.
- **Automated changelog** — between baseline and `@`, `jj log -r '<baseline>..@'` produces a per-run changelog snippet, saved to `~/.co/sync-runs/<deployment>/<universe>-<ts>.md`. Optionally pushed to the universe as `event` entries (CO-89).
- **Vault REST API as transport** — vault routes accept API tokens; no JWT acrobatics. The `.co` protobuf format (CO-86) is content-negotiated when both sides support it; markdown over HTTP is the v1 wire format.
- **Per-deployment isolation** — auth tokens, baselines, and changelog snippets are namespaced by deployment URL hash. `co sync push --to prod` and `co sync push --to uat` are independent operations against independent baselines.

## Command surface

```
co sync push [--to <deployment>] [--full] [--dry-run] [--no-changelog]
co sync pull [--from <deployment>] [--into <local-path>]
co sync status [--to <deployment>]    # show diff between local and remote without uploading
co sync watch [--to <deployment>]     # fsnotify; auto-push on save (debounced)
co sync changelog [--for <universe>]  # print accumulated changelog snippets
```

`<deployment>` is a key into `~/.co/deployments.toml`:

```toml
[prod]
url = "https://co-artelonga.fly.dev"
token_name = "prod"               # co-token get prod
default = true

[uat]
url = "https://co-artelonga-uat.fly.dev"
token_name = "uat"
```

Per-universe configuration lives in the source repo as `.co/sync.toml`:

```toml
universe = "artelonga"
include = ["**/*.md"]
exclude = ["node_modules/**", "build/**"]
```

(or omit `.co/sync.toml` and pass `--universe artelonga --root .`)

## Workflow comparison

### Today (script)

```bash
bash scripts/seed-prod-universes.sh --bootstrap   # password, full seed, token gen, keychain
```

### After CO-91 (`co sync`)

```bash
co sync push --to prod --bootstrap                # password once, then never
co sync push                                      # uses default deployment (prod), delta upload
co sync push --to uat                             # same, against UAT
co sync watch                                     # auto-push as you edit

```

The script becomes a fossil. The same workflow becomes a first-class CLI surface that any author (not just yuri) can adopt.

## Tasks

### Phase 1 — port the script to a Rust binary (no behavior change)

- [ ] Move script logic into `co-cli/src/commands/sync.rs` (lives in the user-facing `co` binary, NOT in `dev/`)
- [ ] `co sync push` mirrors the script's behavior 1:1
- [ ] `co sync push --bootstrap` does the same login+create+upload+token-gen+store flow
- [ ] Tests: dry-run produces the same diff as `jj diff --name-only`
- [ ] Cargo deps: add `keyring` to co-cli for token reading (already a workspace member via `dev/co-token`)
- [ ] Documentation: `co sync --help` covers the workflow with examples

### Phase 2 — clean argument shape + multi-deployment support

- [ ] `~/.co/deployments.toml` parsing (default = `prod`)
- [ ] `--to <deployment>` flag; defaults to the deployment marked `default = true`
- [ ] Per-deployment baseline namespacing (`~/.co/sync-state/<deployment>/...`)
- [ ] `co sync status` — diff-only, no upload
- [ ] `co sync changelog` — print accumulated snippets

### Phase 3 — `co sync watch` and content-negotiated `.co` format

- [ ] `co sync watch` via `notify` crate; debounced (default 1s)
- [ ] If server `OPTIONS /api/v1/universes/:slug/vault/` advertises `co/protobuf` support, send `.co` bytes; else markdown
- [ ] Bench: throughput vs the script

### Phase 4 — optional changelog push (CO-89 integration)

- [ ] `--push-changelog` flag: after upload, POST a synthesized `event` entry to the universe with the jj-log snippet as body
- [ ] Server adds it as `entry_type: event`, `kind: sync`, `summary: <commit count>` — visible in CO-89's calendar view

## Acceptance

### Phase 1
- `co sync push --bootstrap` exhibits identical behavior to today's script
- `co sync push` delta-uploads only changed files; baseline persists across runs
- A changelog snippet is generated and saved
- `cargo install --path co-cli` produces a `co` binary that has the new `sync` subcommand
- All existing co-cli tests pass

### Phase 2
- `co sync push --to uat` and `co sync push --to prod` are independent operations
- `co sync status` prints the changed-files list without uploading
- `~/.co/deployments.toml` schema is documented in `co/docs/`

### Phase 3
- `co sync watch` auto-pushes within 1.5s of a file save
- When server advertises `.co` support, `Accept`-negotiated content type is `application/vnd.co+protobuf`
- Throughput >= 2× the bash script for the same workload (Rust + bounded concurrency wins)

### Phase 4
- `co sync push --push-changelog` produces a visible event entry on the universe
- The event's body matches the local `~/.co/sync-runs/<deployment>/<universe>-<ts>.md`

## Tradeoffs

- **`jj` becomes a soft dependency** — the script auto-`jj git init`s on first use, so the user doesn't install jj manually. But `jj` IS required at runtime. Acceptable: it's a first-class part of the post-pivot direction (per memory note about jujutsu being the optional local VCS). Document as a prerequisite.
- **Watch mode is opinionated** — fsnotify is fine for desktop; mobile will need a different mechanism. Defer mobile.
- **Per-deployment auth feels like a step away from "one universe, many homes"** — but it's the correct abstraction for the multi-environment reality (UAT vs prod isolation matters; can't share a token).

## Out of scope (deferred to follow-ups)

- Cross-deployment sync (`co sync push --from prod --to uat` to migrate content) — interesting but not the primary author UX
- Encrypted blobs + recipient sets (CO-86 privacy layer) — adds key management; defer until multi-user
- Hooks / pre-push validators — defer until there's a real use case
