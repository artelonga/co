## As
Um dev que abre PRs, QUERO que o gate `security-audit` (pr-route.yml) só acuse SQL
de verdade, PARA não gastar ciclos de CI reescrevendo strings inofensivas.

## Contexto
Na wave CO-445, o heurístico CWE-89 `format!\("(SELECT|INSERT|UPDATE|DELETE)`
deu **falso-positivo** em strings que não são SQL: `format!("DELETE vault/{path}")`
(contexto de erro de um HTTP DELETE, CO-51) e similares em logs. É a metade "A"
da decisão do dono no CO-433 (refinar o scanner E reestruturar). O CWE-79
(`.innerHTML =`) também acusa innerHTML já escapado — mas ali a reescrita p/ DOM
é defesa-em-profundidade legítima, então o foco desta task é o CWE-89.

## Acceptance
- [ ] **CWE-89 exige contexto SQL.** O regex no job `security-audit` de
      `.github/workflows/pr-route.yml` só dispara quando o keyword é seguido (na
      mesma string) por token SQL real: `FROM` / `INTO` / `SET` / `WHERE` /
      `VALUES`. `format!("DELETE vault/{path}")` e `format!("UPDATE failed for {id}")`
      → **não** acusam; `format!("SELECT {C} FROM t WHERE x=?")` → acusa.
- [ ] **O gate passa em si mesmo** (regra hard-won): rodar o scanner refinado
      contra o próprio diff + contra `main` atual; nenhum falso-positivo novo, e os
      verdadeiros-positivos históricos continuam pegos (manter os excludes de
      `storage/*`, `repository/*`, `security/audit/*`).
- [ ] **Teste do scanner.** Fixtures em `co-web/src/security/audit/` (ou onde os
      testes do grep vivem) cobrindo: HTTP-verb string (deve passar), log string
      (passar), SQL real com `format!` (deve falhar), SQL com colunas const +
      bind params (já é o padrão seguro — confirmar comportamento).
- [ ] Documentar a heurística no comentário do job (o que dispara e por quê).

## Não no escopo
- Mudar o CWE-79/innerHTML (a reescrita p/ DOM é a postura correta; `.html` já não
  é escaneado).
- Trocar o grep por uma ferramenta SAST completa — isto é só um aperto do heurístico.
