## As

a developer running `co-auto --task CO-N` repeatedly across a series
of related tickets

## I Need

co-auto to either (a) fast-forward `main` to the feature-branch tip
after each successful task completion, or (b) branch the next task
off the previous task's feat-branch tip instead of off `main` —
whichever is the project convention

## So That

the second and subsequent ticket runs don't silently regress the
working tree to a stale `main` tip, dropping every previous ticket's
work.

---

## Concrete incident (2026-05-11)

After committing 8 stacked feature branches (CO-188, 189, 190, 187,
192, 183, 193, plus a sweep commit) that piled linearly via co-auto's
classic mode, none of those branches were ever merged back to `main`.
`main` stayed at `35694da` (pre-CO-188).

Running `co-auto --task CO-194` then triggered:

```
auto.rs:1092-1095 (classic mode, !use_worktree)
    git checkout main         # main = 35694da, stale
    git checkout -b feat/CO-194-...
```

…which silently reset the working tree to `35694da`, losing:

- `Cargo.toml` version: 2.0.0 → 1.83.0
- `work/co/project.yaml` next_id: 197 → 170
- All `work/co/CO-1{83,87,88,89,90,91,92,93,94,95,96}.md` files
  vanished (they only existed on the unmerged feat-branch chain)

Co-auto then crashed with `error: No such file or directory (os error 2)`
when trying to read `work/co/CO-194.md` — because that file didn't
exist on `main` and the new feat-branch was created from main.

Recovery required:
```bash
git checkout main
git merge --ff-only feat/CO-193-chat-schema-rest-endpoints-phase-4-first
# then delete 8 dangling feat/CO-* branches with `git branch -d`
```

## Fix — recommended approach: merge feat-branch on success

In `dev/co-auto/src/auto.rs`, after the task is committed and tests/
clippy pass (the point where co-auto would normally exit cleanly),
add a step:

```rust
// After commit succeeds and CI checks pass
if !use_worktree && task_succeeded {
    // Fast-forward main to the feat-branch tip so the next task
    // starts from current state.
    let merge_result = Command::new("git")
        .args(["checkout", "main"])
        .current_dir(workdir)
        .output()?;
    if !merge_result.status.success() {
        eprintln!("WARNING: failed to switch to main after task: {}",
                  String::from_utf8_lossy(&merge_result.stderr));
    }
    let ff_result = Command::new("git")
        .args(["merge", "--ff-only", &branch_name])
        .current_dir(workdir)
        .output()?;
    if !ff_result.status.success() {
        // Not a clean FF — there are commits on main not on the
        // feat-branch. Refuse to merge; leave user on feat-branch
        // with a clear message.
        eprintln!(
            "Cannot fast-forward main to {} — main has diverged. \
             Resolve manually before next task.",
            branch_name
        );
        // Switch back to feat-branch so state isn't surprising
        let _ = Command::new("git")
            .args(["checkout", &branch_name])
            .current_dir(workdir)
            .output();
        return Ok(()); // task itself succeeded; just couldn't FF
    }
    // Optionally delete the feat-branch now that it's merged
    let _ = Command::new("git")
        .args(["branch", "-d", &branch_name])
        .current_dir(workdir)
        .output();
}
```

Worktree mode (`--cycle` / `--teams`) is a separate question — those
runs typically merge via PR / external process, not local FF. The fix
above is scoped to classic mode only.

## Alternative fix — branch from previous tip

Less invasive but more confusing for users (`git log` on main wouldn't
reflect progress): change `create_task_branch` at `auto.rs:1092` to
`git checkout HEAD` instead of `git checkout main`, so the new branch
descends from wherever HEAD currently is (which after a successful
prior task is the feat-branch tip).

Cons: user-confusing because branches stack without main ever
advancing. Pros: zero loss-of-work risk regardless of merge state.

**Recommended path: option 1 (FF main on success).** Matches user
expectation that main is the canonical progress trunk.

## Edge cases

| Scenario | Expected behavior |
|---|---|
| Task succeeds, FF clean | Merge to main, delete feat-branch, next task starts from current main |
| Task succeeds, FF blocked (main diverged) | Stay on feat-branch; print warning; user resolves |
| Task fails (tests/clippy fail) | No FF attempt; leave feat-branch alone for user to fix |
| User runs co-auto on a branch that isn't `main` (e.g. trunk-based with `develop`) | Honor `--base-branch` flag if present; otherwise check `git config init.defaultBranch` |
| Pre-commit hook on the FF merge | Should not run hooks for FF (no new commits created) |

## Acceptance

- [ ] After `co-auto --task CO-N` completes a task successfully in
      classic mode, `git log -1 main` shows the task's commit as the
      tip of main.
- [ ] Running `co-auto --task CO-(N+1)` immediately after picks up
      CO-N's work and does not regress.
- [ ] If FF fails (main diverged), the user sees a clear warning and
      stays on the feat-branch — no silent regression.
- [ ] If the task itself fails (cargo test / clippy / build), no FF
      is attempted and the feat-branch is preserved for debugging.
- [ ] Existing worktree mode (`--cycle`, `--teams`) behavior is
      unchanged.
- [ ] Add an integration test or scripted scenario that runs two
      synthetic tasks back-to-back and asserts main advances.

## Out of scope

- Auto-deleting feat-branches after merge (nice-to-have; the snippet
  above includes it but it's optional and easy to disable via flag).
- Rebasing main onto an upstream remote.
- Multi-branch trunk policies (release / develop / main).
- Worktree mode behavior — separate ticket if needed.
