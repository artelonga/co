## As

Anyone running CI (every commit author) and anyone wanting to verify changes locally before pushing

## I Need

A **right-sized, parallelizable, locally-runnable** test pyramid replacing today's 301-e2e-serial monolith. Specifically:

1. **Parallel by default**: Playwright workers=4 (or auto), with sharding hooks ready for when the suite grows
2. **Extendable structure**: clear conventions so adding tests at the right layer is obvious; new tests don't accidentally re-bloat e2e
3. **Local-first runner**: `co-test` command that runs the full suite (or any layer) against `co serve` localhost — same code paths CI runs, observable on your machine in &lt; 15 min
4. **Aggressive redundancy cut**: 301 → ~80 e2e tests by moving component-detail coverage to a new Vitest layer + archiving shipped per-CO-N acceptance tests
5. **Review tooling**: `co-test review` surfaces what's covered, what's redundant, what's slow

## So That

- Every PR's CI wall-clock drops from ~48 min → ~13 min in Phase 1 (parallelization alone)
- Subsequent waves can keep adding features without re-inflating CI to 1+ hour
- The "ship it" loop becomes runnable locally — debug a failing test on your laptop in 30s instead of waiting 50 min for CI to re-run
- The test pyramid is **principled** — each layer answers a different question, no overlap

## Context

### Current state (2026-05-26)

- **301 e2e tests in 29 files**, running serially on Playwright workers=1
- Wall-clock: **45-50 min** per CI run
- **686 Rust lib tests** (fast, parallel) — fine, no changes needed
- **0 component tests** — UI logic only verified through full-browser e2e

### Tests-per-file breakdown (top offenders)

| File | Tests | Suspected layer |
|---|---|---|
| board-ux.spec.ts | 49 | 80% component-level (sidebar render, view toggle, kbd shortcuts) |
| integration.spec.ts | 36 | overlaps with pipeline-workflow + auth-crdt |
| pipeline-workflow.spec.ts | 27 | combinatorial: auth × create × edit × status × view × bulk |
| subtask-tree.spec.ts | 22 | same logic tested 3x across kanban/table/timeline |
| auth-crdt.spec.ts | 19 | auth covered again elsewhere (107+ total tests touch auth) |
| Per-CO-N acceptance | ~50 | proved the feature shipped, now re-running forever |

### Why this happened

- Project started with ~50 e2e tests when Playwright workers=1 was fine
- Each new feature added an acceptance spec ("did CO-N ship correctly?")
- Acceptance specs became permanent fixtures
- No component-test infrastructure → all UI verification fell to e2e
- No "cut after merge" policy for acceptance tests

### The shape we want

| Layer | Count target | Wall-clock | Tool | Question it answers |
|---|---|---|---|---|
| **Smoke e2e** | 5-10 | ~3 min | Playwright | "Does the full stack work?" |
| **Per-feature e2e** | 30-40 | ~8 min | Playwright | "Does this user-facing flow work end-to-end?" |
| **Component tests** | 100+ | ~30s | Vitest + happy-dom | "Does this widget render correctly given inputs?" |
| **Lib tests (existing)** | 686 | ~10 min | cargo test | "Does this Rust module behave correctly in isolation?" |
| **Visual regression** | 5-10 snapshots | ~1 min | Playwright + golden images | "Has the visual layout regressed?" |

Total: ~150-200 tests across all layers, ~25 min wall-clock if run serially. **With parallelization, ~10-12 min.**

## Decision — three phases, each independently shippable

### Phase 1 — parallelize what exists (~2h)

**Goal**: cut CI wall-clock from 48 min → ~13 min without touching test content.

- [ ] Edit `co-web/playwright.config.ts` — set `workers: process.env.CI ? 4 : undefined`
- [ ] Audit any test that relies on shared global state (DB, ports, env vars) — those break under parallel execution
  - Common pattern: tests that POST to the same `/api/projects/test-project` and assume isolation → use per-test unique keys
  - The JWT_SECRET race we keep fighting (CO-295 will fix structurally) — for now, ensure tests don't mutate env vars during execution
- [ ] Verify locally with `npx playwright test --workers=4` — fix any newly-flaky tests
- [ ] Add CI matrix sharding scaffold (commented out, ready to enable if needed):
  ```yaml
  # Future: shard across 4 runners for ~3 min wall-clock
  # strategy:
  #   matrix:
  #     shard: [1/4, 2/4, 3/4, 4/4]
  ```

**Acceptance**: PR CI completes in &lt; 15 min wall-clock.

### Phase 2 — local-first runner + review tooling (~3h)

**Goal**: same suite runs against `co serve` localhost; review tool surfaces redundancy.

- [ ] New `scripts/co-test` (bash or python wrapper) exposing:
  ```bash
  co-test                      # full suite locally (lib + e2e + components after Phase 3)
  co-test smoke                # just smoke (3 min)
  co-test e2e                  # just e2e
  co-test e2e --grep auth      # filter
  co-test components           # just component layer (after Phase 3)
  co-test lib                  # just cargo test
  co-test review               # inventory: tests per file, slowest 10, redundancy candidates
  co-test review --since main  # only tests touching files changed since main
  ```
- [ ] `co-test e2e` auto-starts a local `co serve` instance (from CO-282), runs tests against `BASE_URL=http://localhost:54321`, tears down on exit
- [ ] `co-test review` outputs:
  - Test count per file, sorted by slowest
  - "Suspected redundancy": files with similar names (e.g. `theme.spec.ts` + `theme-coverage.spec.ts`), tests with similar names across files
  - "Per-CO-N acceptance tests" (filename matches `co-NNN-*.spec.ts`) — candidates for archiving
- [ ] Documentation: `co-web/e2e/README.md` explaining the layer convention + when to use each

**Acceptance**: `co-test smoke` runs in &lt; 3 min against local server; `co-test review` lists redundancy candidates.

### Phase 3 — audit + cut + add component layer (~5h)

**Goal**: 301 e2e → ~80 e2e + 100+ component tests; archive shipped acceptance.

- [ ] Set up Vitest + happy-dom in `co-web/`:
  ```bash
  pnpm add -D vitest happy-dom @testing-library/dom @testing-library/user-event
  ```
- [ ] New `co-web/components/__tests__/` directory with conventions
- [ ] Migrate from board-ux.spec.ts:
  - "Sidebar renders project list" → component test
  - "View tabs render and toggle" → component test
  - "Keyboard shortcut 1-6 switches view" → component test (no real backend needed)
  - Keep only the e2e for "navigate to board, see tasks, click one" (the smoke version)
- [ ] Migrate from subtask-tree.spec.ts:
  - Tree-rendering logic per-view → 3 component tests
  - Keep 1 e2e: "create parent + subtask, see indented in kanban"
- [ ] Consolidate auth coverage:
  - Merge auth-crdt + integration's auth section + usage-gate + unsubscribed-access → `auth.spec.ts` (~20 tests)
  - Delete redundant duplicates
- [ ] Archive per-CO-N acceptance specs:
  - Move `co-270`, `co-272`, `co-275`, `co-280`, `co-27`, `co-260` etc. to `co-web/e2e/archived/`
  - Excluded from CI by `testMatch` config
  - Restorable if behavior regresses

**Acceptance**: e2e suite ≤ 80 tests, runs in ~10 min wall-clock locally with workers=4.

### Phase 4 — guard rails to prevent regression (~1h, ships with Phase 3)

- [ ] Pre-commit hook (or CI check) that fails if a new `*.spec.ts` is added without a matching entry in a `tests/manifest.yaml` (forces conscious decision about which layer)
- [ ] CI prints "Tests per file" after each run — visible signal if any file balloons past 30 tests
- [ ] `co-test review --fail-on-bloat` exits non-zero if any spec file has > 30 tests

## What this enables for scalability

Each layer scales differently:

| Layer | Scaling story |
|---|---|
| **Lib tests** | Cargo runs in parallel by core count. 686 tests in ~10 min today; adding 100 more → ~11 min |
| **Component tests** | Vitest workers parallelize by file. 100 tests → ~30s; 500 tests → ~2 min |
| **E2e** | Playwright workers=4 = 4x throughput. 80 tests → 10 min; 200 tests → 25 min; **shard across CI runners** if needed |
| **Visual regression** | Effectively constant: snapshot N pages = N×~1s |

The structure means you can ADD tests without compounding CI cost — each layer absorbs growth at its own rate. Today's 48-min wall-clock comes from having all tests in the slowest layer.

## Scope summary

- **Phase 1**: ~50 LOC playwright config + audit + verify → 48 min → 13 min
- **Phase 2**: ~300 LOC new tooling script + e2e README → local-first runner exists
- **Phase 3**: ~500 LOC component-test setup + ~50 migrations + ~10 archive moves → 80 e2e + 100+ component tests
- **Phase 4**: ~80 LOC guard-rail tooling → no regression

Total: 8-10 hours of agent time spread across phases. Each phase ships independently with measurable improvement.

## Out of scope

- Cypress, Selenium, or other test framework swaps (Playwright is fine)
- Visual regression overhaul (mentioned as a layer; full snapshot system is a separate ticket)
- Performance/load testing (different concern — k6/Vegeta territory)
- The JWT_SECRET race (CO-295 — structural fix via SecretsProvider trait)

## Why now

User's exact ask: *"these tests can't be all necessary sufficient and non redundant... keep parallelizable and extendable for scalability, we also want to review these tests and run results locally on localhost"*.

Three converging pressures:

1. **CO-290's CI cycle was 48 min × 4 attempts = 3+ hours of waiting** for one ticket. Every future PR pays the same tax.
2. **The localhost direction (CO-282 + CO-300)** demands the same suite runs locally. Today's 48-min serial e2e isn't usable on a laptop.
3. **The test pyramid is upside-down**: 301 e2e + 0 component tests. Should be ~80 e2e + 100+ component. The current shape is brittle (every UI tweak breaks dozens of e2e) and slow (every CI run pays 50 min).

This is foundational tooling — every subsequent CO-N ticket benefits.
