## As

an operator of CO and quilombo deployments who wants notifications delivered to users via WhatsApp and email without running a separate n8n instance

## I Need

first-class `ChannelProvider` adapters for Resend (email) and Evolution API (WhatsApp) built into the CO webhook worker

## So That

(a) small deployments can send notifications without operating n8n infrastructure,
(b) the n8n path from CO-168 keeps working for complex routing — these adapters are additive, not a replacement,
(c) the `ChannelProvider` trait gives a stable extension point for future adapters (Twilio SMS, FCM push, etc.)

---

## Current state (1.77.0)

CO-168 ships: `webhooks` + `notifications` tables, outbound webhook worker, HMAC-signed delivery, retry state machine. The worker delivers to any URL — including an n8n instance. This ticket adds built-in provider adapters that bypass the n8n hop for the two highest-priority channels.

## Design

### Trait

```rust
// co-web/src/notification_providers.rs
#[async_trait]
pub trait ChannelProvider: Send + Sync {
    /// Provider name for logging (e.g. "resend", "evolution_api").
    fn name(&self) -> &str;
    /// Send one notification. `recipient` semantics are provider-specific
    /// (email address for Resend, phone number or JID for Evolution API).
    async fn send(&self, recipient: &str, subject: &str, body: &str) -> anyhow::Result<()>;
}
```

### Resend email adapter

Config (env vars):
- `RESEND_API_KEY` — Resend API key
- `RESEND_FROM` — sender address (e.g. `CO <noreply@co.artelonga.com.br>`)

Implementation: `POST https://api.resend.com/emails` with JSON body. Single `reqwest` call (already a dep).

Recipient: email address from `quilombo_usuarios.email` or `users.email`.

### Evolution API WhatsApp adapter

Config (env vars):
- `EVOLUTION_API_URL` — base URL of self-hosted Evolution API instance
- `EVOLUTION_API_KEY` — API key
- `EVOLUTION_INSTANCE` — instance name (e.g. `quilombo`)

Implementation: `POST {EVOLUTION_API_URL}/message/sendText/{EVOLUTION_INSTANCE}` with `{ number, text }`.

Recipient: phone number in E.164 format (`+5541999...`). Stored in a new `telefone` column on `quilombo_usuarios` (migration v36 — nullable).

### Routing

The webhook worker checks, per notification row, whether a built-in adapter is configured for the event's target channel. The notification row gains two new columns:

```sql
ALTER TABLE notifications ADD COLUMN channel TEXT;      -- 'email' | 'whatsapp' | 'webhook' (default)
ALTER TABLE notifications ADD COLUMN recipient TEXT;    -- channel-specific address
```

Routing decision (in `emit_event`):
1. If `RESEND_API_KEY` set and event has a user with email → also enqueue a `channel='email'` notification
2. If `EVOLUTION_API_KEY` set and event has a user with `telefone` → also enqueue `channel='whatsapp'`
3. Always enqueue `channel='webhook'` for registered webhooks (existing CO-168 behaviour)

Worker dispatches by channel:
```rust
match notification.channel.as_deref() {
    Some("email")     => email_provider.send(...).await,
    Some("whatsapp")  => whatsapp_provider.send(...).await,
    _                 => deliver_webhook(...).await,   // CO-168 path
}
```

### Message templates

Simple mustache-style template strings stored as env vars or a `notification_templates` table (v1: env vars only):

```
CO_TPL_QUILOMBO_EVENTO_EMAIL_SUBJECT="Novo evento no Quilombo: {{titulo}}"
CO_TPL_QUILOMBO_EVENTO_EMAIL_BODY="Olá {{nome}},\n\nHá um novo evento: {{titulo}} em {{data}} às {{hora}} em {{local}}.\n\nVeja em https://quilomboaraucaria.com.br"
CO_TPL_QUILOMBO_EVENTO_WHATSAPP="🌿 Novo evento no Quilombo!\n*{{titulo}}*\n📅 {{data}} às {{hora}}\n📍 {{local}}"
```

Template rendering: regex `{{key}}` replacement — no new dependencies.

## Acceptance

- [ ] `ChannelProvider` trait in `notification_providers.rs` with `name()` + `send()` methods
- [ ] `ResendProvider` implements trait; sends email via `POST api.resend.com/emails`; requires `RESEND_API_KEY` + `RESEND_FROM`
- [ ] `EvolutionApiProvider` implements trait; sends WhatsApp text via Evolution API; requires `EVOLUTION_API_URL` + `EVOLUTION_API_KEY` + `EVOLUTION_INSTANCE`
- [ ] Migration v36 adds `telefone TEXT` (nullable) to `quilombo_usuarios` and `channel` + `recipient` columns to `notifications`
- [ ] `emit_event` enqueues channel-specific rows when env vars are set and recipient is known
- [ ] Worker dispatches by `notifications.channel`; existing webhook path unchanged
- [ ] Template rendering via `{{key}}` substitution; at least 3 templates for `quilombo.evento.criado` (email subject, email body, WhatsApp text)
- [ ] Tests: ResendProvider and EvolutionApiProvider both use mock HTTP (no real API calls); template rendering tests
- [ ] When `RESEND_API_KEY` absent: email rows are never enqueued (no silent failures)
- [ ] When `EVOLUTION_API_KEY` absent: whatsapp rows are never enqueued

- Template UI (admin page to edit templates) — CO-171
- Delivery receipts / read receipts from WhatsApp — Evolution API can push these; deferred
