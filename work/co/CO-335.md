## As
A platform user with two existing graph implementations (ArteLonga's neuro/portfolio network + Yggdrasil's comunicacao lexicon)

## I Need
A **single canonical graph-rendering primitive** maintained in CO, consumed by every sister site, with content (nodes + edges + metadata) stored in CO universes and the visual form decoupled from the data so UI variations can come later

## So That
- Two iterations don't drift further (artelonga's neuro and yggdrasil's comunicacao both implement graphs separately right now)
- The graph data is queryable + composable via CO's universe API (already typed via CO-325's reference/relation system)
- Each sister site customizes visuals without re-implementing the layout/physics
- Future iterations (yuri portfolio, music-graph from CO-325 categories, etc.) reuse the same library

## Centralization design

### Where the canonical lives
- New crate `co-graph/` in the co workspace OR a new top-level module `co-web/static/variants/a/modules/graph/`
- Source-of-truth = CO. Sister sites pull via:
  - Option A: JS module imported from `https://co.artelonga.com.br/lib/co-graph.js` (CDN-style; CSP-friendly)
  - Option B: vendored copy in each sister's static assets (more isolated, easier to bisect regressions)
- Recommend **A**: single source, deploy = update everywhere

### Content layer (already exists)
CO-325 + CO-330 already give us:
- Entries with `type` + frontmatter (nodes)
- `references: { ... }` recursive composition (edges from CO-74 typed FK graph)
- `tags`, `author`, `caderno_id`, etc. → metadata
- Query DSL → filtered graph subset

The graph data API:
```
GET /api/v1/universes/<u>/graph
   ?include_types=song,poem,nota
   ?relation=references,tags
   ?root=<entry-path>            (start from one node, walk N hops)
   ?max_depth=3
   ?published_only=true          (CO-330 published filter)
→
{
  "nodes": [{ "id": "...", "type": "...", "title": "...", "frontmatter": {...} }, ...],
  "edges": [{ "source": "...", "target": "...", "kind": "references|tag|author|..." }, ...]
}
```

Already mostly there — formalize the response shape + expose as a documented endpoint.

### Rendering primitive (the centralized library)
A small JS module exposing one function:
```javascript
co_graph.render(container, {
    data: { nodes, edges },        // shape above
    layout: 'force' | 'fractal' | 'radial' | 'timeline',
    onNodeClick: (node) => {},
    theme: { ... },                // CSS variables, optional
});
```

- Uses canvas or SVG (decide on benchmark; canvas wins for >500 nodes)
- Layout: force-directed by default; fractal/radial available
- Physics + interactivity: built-in pan, zoom, hover, click
- Theme: CSS variables only — no built-in colors. Each sister styles via `:root { --co-graph-node-color: ... }`

### Form/UI customization (deferred — explicit non-goal in v1)
The library exposes the rendering primitive. Wrapper UIs (neuro's curated gallery, comunicacao's lexicon filters, yuri's portfolio chips) stay in the sister sites and call into `co_graph.render(...)` with their own surrounding layout.

**This is the key separation:** the graph engine is universal; the framing UI varies per site.

- Build `co-graph` module from the best-of-both: ArteLonga's animation polish + Yggdrasil's data composition
- Publish at `https://co.artelonga.com.br/lib/co-graph.js`

### Phase 2: rewire sister sites (1 day each)
- ArteLonga neuro pages → load co-graph, pass their existing data, keep their visual chrome
- Yggdrasil comunicacao → same

- `/universe/<key>/graph` page renders the graph for that universe's entries
- yuri.artelonga.com.br shows yuri's published entries as a graph (CO-323 + CO-324 published filter)

### Phase 4 (out of scope here): UI variants
Theming + per-universe layout preferences. Comes after Phase 1-3 prove the primitive works.

## Not in scope

- Per-universe layout persistence — out of scope for v1
- Editing graph topology inline (drag-to-create-edge) — read-only first
- Server-side layout pre-computation (offload force-directed iterations) — could come if perf demands
- Graph search / find-by-text — `q` filter on the API but no inline search UI in v1
- Cross-universe graphs (combining entries from multiple universes into one view) — flag for v2 once single-universe is solid

- Two iterations exist; if a third (yuri portfolio) is added without consolidation it becomes three diverging codebases

- Yuri's vision for yuri.artelonga.com.br includes a graph view of his references/notes — natural to use the same primitive
