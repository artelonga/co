## As
O operador do co, QUERO toda configuração e segredo passarem por um
`SecretsProvider`/`CoServerConfig` em vez de `std::env::var` espalhado, PARA
trocar o backend de segredos (env, static, Vault, AWS SM, S3-roadmap) e tunar o
servidor sem editar 50 arquivos.

## Contexto técnico (do audit 2026-06-12)
`infra/secrets.rs` define um `SecretsProvider` limpo, mas há **124 leituras
diretas de `std::env::var` em 52 arquivos** que o ignoram (`CO_EDA_BACKEND`,
`CO_BLOB_BACKEND`, `R2_*`, `RESEND_API_KEY`, `OPENAI_API_KEY`, `CO_CHAT_MODEL`,
`CO_USAGE_SOFT_LIMIT_*`, `CO_BRIDGE_*`, `CO_TELEMETRY_*`, `CO_ALERT_*`…). A
abstração existe mas não é imposta.

## Acceptance
- [ ] Inventário das 124 leituras (lista no PR) classificado em: **segredo**
      (via `SecretsProvider`) vs **config** (via `CoServerConfig`).
- [ ] Novo `CoServerConfig` (struct com defaults sensatos) populado uma vez no
      boot a partir do provider; subsistemas recebem a config/segredo por
      parâmetro/estado, não por `env::var` no ponto de uso.
- [ ] Leituras diretas de `std::env::var` eliminadas do código de runtime
      (permitido só no boot/CLI parse e em testes). `grep -rn "std::env::var"
      co-web/src | grep -v test` ≤ um punhado justificado e documentado.
- [ ] Um teste prova a troca: um `StaticSecretsProvider`/config de teste muda o
      comportamento (ex.: `CO_EDA_BACKEND`) sem env global — já é o padrão dos
      testes; estender para os pontos hoje hardcoded.
- [ ] **Zero mudança de comportamento** em produção (mesmos defaults); `cargo
      test -p co-web` verde; clippy limpo.

## Notas
Desbloqueia o roadmap S3 (config de backend trocável) e deixa o servidor
embutível com config injetada. Fazer por subsistema (telemetry, eda, blob, ai,
alert) para PRs revisáveis — mas entregar como um story só.
