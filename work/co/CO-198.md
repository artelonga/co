## As

a signed-in user

## I Need

a way to send private messages to another signed-in user, see all my
DM threads in an inbox with unread counts and last-message previews,
and control who can DM me (everyone / only people I share a universe
with / nobody)

## So That

chat completes the loop — universe rooms (CO-193 → CO-196, shipped in
2.1.0) handle group conversations; this slice handles private 1:1
threads. Both reuse the same schema, WebSocket, and UI surfaces.

---

## Precondition

CO-193 (REST), CO-194 (WS), CO-196 (moderation) live in 2.1.0. This
ticket extends the same `chat_rooms` + `chat_messages` tables — no new
parallel schema.

## Schema — single migration

**One column add + one table add + one column add.** All idempotent
`ALTER TABLE` / `CREATE TABLE IF NOT EXISTS` — no schema version slot,
runs every boot.

```sql
-- 1. chat_rooms: nullable universe_key + kind + dm-pair canonical pair
ALTER TABLE chat_rooms ADD COLUMN kind TEXT NOT NULL DEFAULT 'universe';
-- kind ∈ {'universe', 'dm'}

-- For dm rooms: universe_key IS NULL, slug = canonical pair id.
-- (SQLite ALTER TABLE doesn't allow dropping NOT NULL once set, so the
-- universe_key column stays NOT NULL in the schema; for DM rows we
-- insert the literal string 'dm' as a sentinel — see "DM row shape"
-- below for the workaround.)

-- 2. Generic membership table that subsumes universe + dm
CREATE TABLE IF NOT EXISTS chat_room_members (
    room_id     TEXT NOT NULL,
    user_id     TEXT NOT NULL,
    last_read_at TEXT,         -- for unread counts; nullable until first read
    muted_until TEXT,          -- nullable, future-dated to mute
    joined_at   TEXT NOT NULL,
    PRIMARY KEY (room_id, user_id),
    FOREIGN KEY (room_id) REFERENCES chat_rooms(id)
);
CREATE INDEX IF NOT EXISTS idx_chat_room_members_user
    ON chat_room_members(user_id);

-- 3. users.dm_policy — who can DM me?
ALTER TABLE users ADD COLUMN dm_policy TEXT NOT NULL DEFAULT 'shared-universe';
-- dm_policy ∈ {'everyone', 'shared-universe', 'nobody'}

-- 4. user_blocks — bidirectional block list
CREATE TABLE IF NOT EXISTS user_blocks (
    blocker_id  TEXT NOT NULL,
    blocked_id  TEXT NOT NULL,
    created_at  TEXT NOT NULL,
    reason      TEXT,
    PRIMARY KEY (blocker_id, blocked_id)
);
CREATE INDEX IF NOT EXISTS idx_user_blocks_blocked
    ON user_blocks(blocked_id);
```

### DM row shape

```jsonc
chat_rooms row for a DM between users A and B:
{
    "id":           "room_dm_{nanoid}",
    "universe_key": "dm",                 // sentinel — not a real universe
    "name":         "",                   // unused for DMs
    "slug":         "dm-{userA}-{userB}", // canonical: user_a < user_b lex order
    "kind":         "dm",
    "is_default":   false,
    "created_by":   "{whoever opened it}"
}
```

Canonical pair ordering: `min(user_a, user_b) || '-' || max(user_a, user_b)`.
Ensures `POST /dms/with/userB` and `POST /dms/with/userA` (called by
B reciprocally) both resolve to the same `slug` → idempotent.

### Backfill — for existing universe rooms

A boot-time backfill inserts a `chat_room_members` row for every
existing `universe_members` row (so existing universe rooms stay
accessible after this migration). Idempotent via `INSERT OR IGNORE`.

## Endpoints

### `POST /api/v1/dms/with/:user_id` (auth required)

Idempotent open-DM endpoint.

Logic:
1. Resolve canonical pair (`min(me, other) || '-' || max`).
2. Check authorization:
   - If `other_user.dm_policy = 'nobody'` → 403.
   - If `'shared-universe'` → check whether me + other share any
     `universe_members` row. If no → 403.
   - If `'everyone'` → allow.
   - In all cases: 403 if `user_blocks(blocker_id=other, blocked_id=me)`
     exists (target blocked me).
3. Look up `chat_rooms WHERE kind='dm' AND slug = ?`. If exists, return it.
4. Otherwise, INSERT the room + 2 rows in `chat_room_members`. Return it.

Response:
```jsonc
{
  "room_id": "room_dm_xyz",
  "slug": "dm-userA-userB",
  "other_user": { "user_id": "...", "display_name": "...", "usuario": "..." },
  "created": true | false
}
```

### `GET /api/v1/me/dms` (auth)

Inbox. Returns my DM threads with last-message preview + unread count.

```jsonc
{
  "threads": [
    {
      "room_id": "room_dm_xyz",
      "slug": "dm-userA-userB",
      "other_user": { "user_id": "...", "display_name": "...", "usuario": "..." },
      "last_message": {
        "id": "msg_abc",
        "author_id": "usr_...",
        "body_preview": "Olá, tudo bem?",  // first 80 chars
        "created_at": "..."
      },
      "unread_count": 3,         // messages with created_at > my last_read_at
      "last_read_at": "..."
    }
  ],
  "total_unread": 7
}
```

Ordered by `last_message.created_at DESC`.

### `POST /api/v1/dms/:room_id/read` (auth)

Mark thread as read up to current time. Updates
`chat_room_members.last_read_at = now()` for the caller.

```jsonc
// Response
{ "last_read_at": "..." }
```

### `POST /api/v1/dms/:room_id/mute` (auth)

Body:
```jsonc
{ "until": "2026-05-18T00:00:00Z" }  // or null to unmute
```

Updates `chat_room_members.muted_until`. Muted threads still receive
messages but don't bump the unread count display in the UI (just a
visual flag).

### `PUT /api/v1/me/dm-policy` (auth)

```jsonc
// Request
{ "policy": "everyone" | "shared-universe" | "nobody" }
```

Updates `users.dm_policy`. Returns 200.

### `POST /api/v1/users/:user_id/block` (auth)

Creates `user_blocks` row. Also, as a side effect, **disables existing
DM threads between the two users** — neither side can send new
messages (room becomes read-only for both).

### `DELETE /api/v1/users/:user_id/block` (auth)

Removes the block. Existing DM thread becomes usable again.

## Messages flow through existing endpoints

Posting / editing / deleting / WebSocket subscribing — **all use the
existing CO-193/194/196 endpoints unchanged**:

```
POST   /api/v1/universes/{slug}/chat/rooms/{room_slug}/messages
GET    /api/v1/universes/{slug}/chat/rooms/{room_slug}/messages
GET    /api/v1/universes/{slug}/chat/rooms/{room_slug}/ws
PATCH  /api/v1/universes/{slug}/chat/rooms/{room_slug}/messages/{msg_id}
DELETE /api/v1/universes/{slug}/chat/rooms/{room_slug}/messages/{msg_id}
```

For DMs, the route uses `{slug}="dm"` (the sentinel) and `{room_slug}=
"dm-userA-userB"`. Route handler resolves `chat_rooms WHERE kind='dm'
AND slug=?` — same query path as universe rooms, just with `kind='dm'`.

Authorization for DM messages: caller must be in `chat_room_members`
for that room AND not be blocked by the other party. No
viewer/subscriber roles in DMs — both members can read and post equally.

WebSocket events identical: `message.created`, `message.edited`,
`message.deleted`, `presence.join`, `presence.leave`. Presence in DMs
is just "is the other person currently looking at this thread."

```rust
impl Storage {
    pub fn open_dm(&self, caller_id: &str, other_user_id: &str)
        -> Result<DmRoom, DmError>;

    pub fn list_my_dms(&self, user_id: &str)
        -> Vec<DmThreadPreview>;

    pub fn mark_dm_read(&self, room_id: &str, user_id: &str)
        -> anyhow::Result<()>;

    pub fn set_dm_policy(&self, user_id: &str, policy: &str)
        -> anyhow::Result<()>;

    pub fn block_user(&self, blocker_id: &str, blocked_id: &str, reason: Option<&str>)
        -> anyhow::Result<()>;

    pub fn unblock_user(&self, blocker_id: &str, blocked_id: &str)
        -> anyhow::Result<()>;

    pub fn is_blocked_either_way(&self, user_a: &str, user_b: &str) -> bool;

    pub fn can_dm(&self, sender_id: &str, target_id: &str) -> bool;
    // Combines: target's policy + block check + (if 'shared-universe') membership overlap.

    pub fn backfill_chat_room_members_from_universe_members(&self) -> usize;
}

pub enum DmError {
    Blocked,           // target blocked the caller
    PolicyDenied,      // target's dm_policy doesn't allow
    SelfDm,            // caller_id == other_user_id
    UserNotFound,
    Db(rusqlite::Error),
}
```

## Out of scope

- **Group DMs (3+ people)** — universe rooms already serve this use
  case. If we ever want "ad-hoc small groups," that's a separate
  ticket (CO-199+).
- **Voice / video calls.** Different feature family.
- **End-to-end encryption.** Future ticket.
- **Message reactions.** Phase 4 v2 ticket.
- **Replying-to + threading in DMs.** The `reply_to_id` column exists
  in schema but UI for threads is a separate ticket.
- **Push notifications** for offline DMs (web push, native push). Big
  ticket on its own.
- **Search across DMs.** Future ticket.
