## As

a CO operator and a user collaborating across devices

## I Need

a Redpanda streaming bus with Iceberg Topics writing to R2 through a REST catalog (Lakekeeper or Nessie), a first Flink job (session stitching), an Apple-style 4-way conflict modal (`Ignore / Replace / Keep both / Apply to all`), and a jujutsu-shaped changelog renderer

## To

unlock real-time analytics joins, give the lakehouse a populated `events` table for cheap multi-engine reads, and ship the **two missing user-named v1 features** (4-way conflict UX + jj-shaped changelog) that the SR plan omitted

## Stories

- CO-125 — Redpanda cluster on Fly + Iceberg Topics (Parquet) + Schema Registry
- CO-126 — REST catalog (Lakekeeper) deploy + Iceberg-on-R2 first table
- CO-127 — First Flink job: session stitching → ClickHouse `sessions_aggregated`
- CO-128 — Apple-style 4-way conflict UI with Apply-to-all
- CO-129 — Jujutsu-shaped changelog renderer (read op log → render commit DAG)

## Acceptance gates

- [ ] 1k events produced to a Redpanda topic land in Iceberg-on-R2 within 30s, queryable from DuckDB and ClickHouse
- [ ] 5 events sharing a `session_id` produce 1 row in `sessions_aggregated` within 30s
- [ ] Concurrent edit on same entry from 2 sessions surfaces the 4-way modal; "Apply to all" persists choice for batched conflicts
- [ ] A 3-commit branch + merge renders as a 5-node DAG (3 commits + branch point + merge node)
- [ ] Two-device sync converges within 5s of last edit (existing Tier 3 exit criterion)

## Out of scope

- Privileged compute zone (encrypted analytics) — Phase 4
- Pinot — Phase 5
- Multi-target deployer adapters — Phase 5

## Why now

This phase unlocks the jujutsu-shaped collaboration UX that the user explicitly named as a v1 requirement. Streaming bus + lake are necessary for richer analytics; built once, reused by all later phases. Lakekeeper as starting catalog because it's REST-spec-conformant and Rust-implemented; Nessie revisited if jujutsu-on-data resonates.
