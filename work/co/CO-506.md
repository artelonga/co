GIVEN CO has tools (CO-503) and an agent runtime (CO-504) but **no native workflow
concept** — there is no declarative way to chain agents and tools, so any
multi-step orchestration lives ad-hoc in a client,
WHEN we add **workflows**: a declarative way to compose agents and tools into a
pipeline (or to drop an LLM-agent stage into the existing Engine pipeline),
THEN multi-step agent work (e.g. ingest → synthesize → classify → write) is
expressed as data CO can run, version, and inspect — not hand-rolled per client.

## Acceptance

- [ ] A **workflow** is a declarative definition that chains stages, where a stage is
  a tool call or an agent invocation (CO-503 / CO-504).
- [ ] Stages pass typed results forward (output of one stage feeds the next); failures
  are surfaced, not swallowed.
- [ ] **LLM-agent stage in the Engine pipeline**: an agent can be a step in CO's
  existing processing pipeline (the synthesis/organize loop), not a separate system.
- [ ] Workflows are **versioned and inspectable** (what ran, with which tools/agents,
  on whose behalf), reusing CO's op_log/identity where applicable.
- [ ] At least one end-to-end workflow runs through the native runtime.
- [ ] **Generalist**: workflows carry no tenant names; any tenant-specific chain is a
  data definition, not platform code.

## Notes
- Caps the agents-not-bot runtime: CO-503 (tools) → CO-504 (agents) → **CO-506
  (compose them)**; CO-505 scopes what's available.
- A workflow is the native answer to "do these N agent/tool steps in order" that the
  bridge currently improvises.
- Term is **workflow/fluxo** + **agent/agente**, never "bot".
