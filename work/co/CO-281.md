## As

The operator (yuri) paying the Fly.io bill, plus future contributors who'll inherit the deploy footprint

## I Need

A one-week pass over all 5 Fly deployments that:

1. **Right-sizes** each machine to its actual workload (no blanket 1GB)
2. **Enables auto-suspend** on low/medium-traffic apps so idle minutes cost ~$0
3. **Extracts the embedding worker** out of `co-artelonga` into a dedicated `co-embedding` sidecar that runs on-demand only
4. **Documents the new sizing** in a place we can re-check (the CO-273 deployment dashboard + a runbook entry)

Target: cut the monthly Fly bill **50-65%** with zero user-visible latency regression and zero migration risk.

## So That

- The bill stops being a quarterly surprise. Right now one oversized machine drags the whole footprint.
- The "machines need extra RAM" symptom that triggered this work goes away — the embedding model is the actual reason RAM creeps up, and isolating it means the rest of the platform can shrink back to its true footprint.
- Cloud-migration discussions (Hetzner / AWS / CF Workers per the platform review) are deferred to a future where they actually pay off. After this ticket, Fly is right-sized — no point switching for marginal savings.

### Why an embedding sidecar specifically

The embedding worker loads a vector model + tokenizer into RAM at boot:

- Model footprint: 400-1500MB depending on which model is selected
- Lives in the same machine as the HTTP server + WebSockets + chat
- Forces the whole `co-artelonga` machine to a 1-2GB tier just to hold the model
- Most CO-N tasks never embed anything — the model sits idle 95%+ of the time

Extracting to `co-embedding` (a sibling Fly app):

- Listens on an internal `.flycast` URL only — no public exposure
- `min_machines_running = 0` — suspends after 5min idle (Fly's default)
- Cold start ~30-60s (model load) — acceptable for an async background worker
- `co-artelonga` calls `co-embedding/embed` over private network when needed
- Both machines independently right-sized: co-artelonga back to 512MB, co-embedding gets the 1GB

Net: pay for the embedding model **only when actively embedding**.

### Auto-suspend semantics (Fly)

`fly.toml`:

```toml
[[services]]
  auto_stop_machines = "suspend"   # was "off" or "stop"
  auto_start_machines = true
  min_machines_running = 0         # was 1
```

- **"suspend"** (not "stop") preserves RAM state on disk; restart is ~250ms vs cold-boot ~5-10s
- `min_machines_running = 0` means after 5min of no requests, machine suspends; first request triggers wake
- WebSocket apps need careful handling — long-lived connections prevent suspend. Co-artelonga keeps `min_machines_running = 1` for that reason.

### Latency budget for cold-starts

| App | Acceptable cold-start | Rationale |
|---|---|---|
| co-artelonga | Must stay always-on (WebSockets) | User-facing chat/sync |
| co-embedding | 30-60s OK | Background worker, async caller |
| quilomboaraucaria | 250ms OK | Public content site, suspend acceptable |
| yggdrasil | 250ms OK | Game catalog, suspend acceptable |
| rfq | 250ms OK | Internal-ish, suspend acceptable |

## Decision

### Phase order (each is one safe step)

1. **Phase 0 — Baseline measurement.** Before any change, capture current machine sizes, current monthly spend, current RAM/CPU peaks per app via the CO-273 deployment dashboard (post-deploy of v2.30.x). Snapshot to `docs/infra/fly-baseline-2026-05.md`.
2. **Phase 1 — Auto-suspend the four low-traffic apps** (quilomboaraucaria, yggdrasil, rfq). One PR per app, deploy, verify cold-start works, monitor for 48h. Co-artelonga stays unchanged in this phase.
3. **Phase 2 — Extract co-embedding sidecar.** Create new Fly app, move embedding code into a thin `co-embedding-server` binary that exposes `POST /embed`, switch `co-artelonga`'s embedding worker to HTTP calls instead of in-process. Deploy `co-embedding` first, then `co-artelonga` pointing at it.
4. **Phase 3 — Right-size co-artelonga down to 512MB.** Only after co-embedding has been stable in production for 1 week. Verify p95 latency unchanged, no OOM events.
5. **Phase 4 — Document + dashboard.** Update CO-273's deployment dashboard with the new baseline, add a "cost panel" showing estimated monthly spend per app based on machine size + uptime. Update `CLAUDE.md` deployment section with new sizing.

Each phase is independently reversible — if Phase 1 breaks anything for a specific app, revert *that* `fly.toml`, leave others alone.

### What NOT to do in this ticket

- Migration to Hetzner / AWS / Cloudflare — explicitly out of scope (deferred until post-Phase 4 data shows Fly is still expensive).
- Touching the static `artelonga` site (it's on GH Pages, not Fly; no Fly cost).
- Bundling apps onto shared machines — increases coupling, hurts independent deploy.

## Scope

### 1. Phase 0 — baseline (1-2h)

- `flyctl status -a <app>` for each of 5 apps; record machine size, region, uptime
- Pull deployment-dashboard JSON from `/api/v1/admin/deployments` (post v2.30.x deploy) for current sizing
- Estimate current monthly bill from Fly billing portal
- Write `docs/infra/fly-baseline-2026-05.md` with the snapshot

### 2. Phase 1 — auto-suspend low-traffic apps (3-4h, one app per PR)

For each of {quilomboaraucaria, yggdrasil, rfq}:
- Edit that app's `fly.toml` to add `auto_stop_machines = "suspend"`, `min_machines_running = 0`
- `flyctl deploy --config fly.<app>.toml`
- Verify: stop sending traffic for 10 min, confirm machine suspends via `flyctl status`; then curl `/api/health`, confirm 250ms wake-up
- Monitor for 48h — any user reports of slow first-request → bump `min_machines_running = 1`

### 3. Phase 2 — extract co-embedding sidecar (1-2 days)

New crate `co-embedding-server`:
- Single binary: axum + the embedding worker code (move from `co-web/src/platform/embedding.rs`)
- One endpoint: `POST /embed` body `{texts: [String]}` → `{vectors: [[f32]]}`
- Auth: shared secret in env var `CO_EMBEDDING_TOKEN`

New Fly app `co-embedding`:
- `fly.embedding.toml` at repo root
- shared-1x 1GB, `min_machines_running = 0`, `auto_stop_machines = "suspend"`
- Internal-only — bind to `[::]:8080`, no public IP

Refactor `co-artelonga`:
- Replace in-process embedding worker with HTTP client to `co-embedding.flycast`
- Fall back to "embedding skipped" (no panic) when sidecar is unreachable
- New env var `CO_EMBEDDING_URL` (defaults to `http://co-embedding.flycast`)

Deploy order: `co-embedding` first, verify health, then `co-artelonga` pointing at it.

### 4. Phase 3 — right-size co-artelonga (1-2h, +1 week observation)

After 1 week of co-embedding running fine:
- `flyctl scale memory 512 -a co-artelonga`
- Watch `/admin/deployments` + `flyctl logs` for 48h
- If OOM or p95 latency regression → scale back to 1GB and investigate

### 5. Phase 4 — dashboard + runbook (3-4h)

- Extend CO-273's deployment dashboard with a "cost" column: `(machine_size_factor × uptime_ratio × hourly_rate)` per app
- Sum row at bottom: "Estimated monthly spend: $X.YY"
- Update `CLAUDE.md` deployment section with the new sizing rationale
- Add `docs/infra/fly-runbook.md` with: how to suspend an app, how to scale memory, when to consider extracting another sidecar
