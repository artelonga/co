GIVEN a single shared SQLite serializes all writes via a global mutex (~1K writes/sec on best hardware, far less under contention), and Co targets thousands of concurrent writes,
WHEN we shard storage to one SQLite file per universe + a global metadata DB + LiteFS for read replication,
THEN writes parallelize naturally (different universe = different lock), reads serve from replicas, and backup/migration scopes to one universe at a time.

## Architecture

```
/data/
├── meta.db                                # users, universes (metadata), subs, sessions
└── universes/
    └── ab/cd/abcd1234-universe-key/       # 2-level fanout (256×256 = 65K dirs at level 2)
        ├── data.db                        # entries, projects, tasks, ops, manifests
        └── blobs/                         # local blob cache (CO-81 stores remote)
```

- `meta.db`: tier-zero state — small, fits in memory, replicated via LiteFS
- Per-universe `data.db`: opened on-demand, evicted from connection pool when cold
- LiteFS replicates each DB to read replicas; primary handles writes
- Connection pool: max N concurrent open per-universe DBs (LRU evict cold ones)
- Filesystem fanout: hash universe_key, take first 4 hex chars as 2-level prefix

## Tasks

- [ ] Migration tool: split current `co.db` into `meta.db` + per-universe DBs
- [ ] Connection pool with LRU eviction (default N=1000)
- [ ] LiteFS configuration on Fly (primary in gru, replicas in other regions)
- [ ] Read query routing: nearest replica when possible; primary on staleness > threshold
- [ ] Backup-per-universe: `sqlite3 /data/.../data.db ".backup …"`
- [ ] Storage quota per universe (CO-80)
- [ ] Cross-universe queries (rare): aggregator that fans out to relevant DBs

## Scale notes

- Per-universe DB ceiling: ~10 GB before SQLite slows; manifest can declare archive policy
- Open-FD budget: connection pool LRU caps it at N
- LiteFS lag: typically < 1s; reads requiring strong consistency route to primary
- 10M universes × 1 GB avg = 10 PB — far beyond Fly volumes; CO-81 moves blobs to object storage to fit within budget
- Each per-universe DB has its own indexes (CO-71), naturally scaling

## Acceptance

- Single-universe writes sustained at 100/sec for 1 hour without lock contention
- Read replicas serve 80%+ of read traffic in benchmark
- Migration from monolithic `co.db` to sharded layout is online (no downtime)
- Backup of one universe completes in < 30s
- Filesystem holds 10M empty universes without `ls` taking > 1s on any directory
