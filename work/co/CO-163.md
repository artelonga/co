## As

a user running mempalace locally for daily memory work who also runs CO as the durable content store for everything else

## I Need

a Python `MempalaceCoBackend` implementation of mempalace's `BaseBackend` ABC that talks to CO's HTTP API instead of mempalace's bundled SQLite/ChromaDB

## So That

mempalace drawers (chunks) live in CO's CAS + entry graph — getting versioning, sync across devices, and a unified search surface for free, while keeping mempalace's mining + interactive UX

---

## Current state (1.76.0)

CO ships:

- `POST /api/v1/blobs` / `GET /api/v1/blobs/:hash` / `HEAD /api/v1/blobs/:hash` (1.75.0) — content-addressed byte storage
- Vault PUT/GET on `/api/v1/universes/:slug/vault/...` — markdown with frontmatter, indexed
- Entry tags + relations + frontmatter index
- Auth via `Authorization: Bearer <token>` (long-lived API token)

Mempalace's `BaseBackend` (Python) requires:

- `upsert(ids, documents, embeddings, metadatas)` — write chunks
- `get(ids, where=…)` — fetch by id or filter
- `query(query_texts, n_results, where=…)` — semantic search
- `delete(ids, where=…)` — remove

The byte storage maps cleanly to CO's blob CAS. The metadata + tag filter maps cleanly to CO entries with frontmatter. The semantic search half does **not** map to current CO — there's no vector index yet (see CO-164).

## Design

### Hybrid storage strategy

- **Chunk content (bytes)** → `POST /api/v1/blobs`, returns sha256.
- **Chunk metadata + embedding pointer** → vault PUT under `mempalace/<wing>/<room>/<chunk_id>.md` in a dedicated CO universe (default slug `mempalace`). Frontmatter:
  ```yaml
  ---
  type: mempalace-chunk
  chunk_id: <id>
  blob_hash: <sha256>
  wing: <wing-name>
  room: <room-name>
  metadata: { …arbitrary mempalace metadata… }
  embedding_dim: 384
  embedding_blob: <sha256-of-embedding-bytes>
  ---
  ```
  The embedding itself is also stored as a CAS blob (raw f32 bytes), keyed by its own hash. This lets two chunks with identical embeddings share storage.

- **Vector index (semantic search)** → blocked on CO-164. Until then, `query(...)` falls back to keyword search via CO's existing `/api/v1/universes/:slug/entries?q=…`. Acceptable degradation; mempalace works keyword-only out of the box.

### Filter mapping

mempalace's `where` clause uses Chroma-style operators (`$eq`, `$in`, `$gt`, `$and`). Map to CO's entry frontmatter index via existing `?filter=…` query syntax. Out of band: `$ne`, `$nin` not supported by CO's filter — emulate client-side after fetching candidate set.

### File layout

```
scripts/mempalace_co_backend.py     # the shim (single file, no install)
scripts/mempalace_co_README.md      # how to plug into mempalace's config
scripts/test_mempalace_co.py        # offline tests against a local CO server
```

The shim depends only on `requests` (or `httpx`) — no mempalace import in the file itself, just type-stubs in docstrings. Mempalace registers it via:

```python
# in mempalace's config
backend: scripts.mempalace_co_backend.MempalaceCoBackend
backend_args:
  server: https://co.artelonga.com.br
  universe: mempalace
  token_env: CO_API_TOKEN
```

## Acceptance

- [ ] `MempalaceCoBackend` class exposes `upsert`, `get`, `query`, `delete` matching mempalace's `BaseBackend` ABC signatures
- [ ] `upsert` writes content blob via `/api/v1/blobs`, embedding blob via `/api/v1/blobs`, metadata entry via vault PUT — three calls, parallelizable
- [ ] `get(ids=[...])` reads vault entries by path; resolves `blob_hash` → bytes via `/api/v1/blobs/:hash`
- [ ] `query` returns keyword-search results today; design has a hook (`self._vector_search` no-op) for swapping in CO-164's vector endpoint when it ships
- [ ] `delete` removes vault entries (CAS blobs are content-addressed and shared — never deleted by the shim)
- [ ] Offline tests in `test_mempalace_co.py` pass against a local CO server (`co serve` in a temp universe)
- [ ] `mempalace_co_README.md` documents config + the keyword-only caveat for `query`

## Out of scope

- Vector index (CO-164) — `query` fallback is keyword search only
- Multi-universe routing (one mempalace wing per CO universe) — single universe for v1, split later if useful
- Concurrent client conflict handling — mempalace is single-user; rely on CO's last-write-wins
