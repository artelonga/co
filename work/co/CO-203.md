## As

an operator who just spent the morning recovering from two
back-to-back storage-lock-poisoning incidents

## I Need

`std::sync::Mutex<Storage>` swapped for `parking_lot::Mutex<Storage>`
across the codebase, so a panic inside a storage method doesn't
poison the global lock and take the whole app down

## So That

the ~30 remaining `.expect()` calls in storage methods stop being
site-wide landmines. A future panic still kills that ONE request,
but the next request gets a fresh lock and the app keeps running.

---

## Context — incidents 2026-05-12

| Time | Trigger | Recovery |
|---|---|---|
| ~09:05 UTC | `notification_email_worker` (CO-200) panicked inside `Storage::list_users_with_pending_email_notifications` (`.prepare(…).expect()`) while holding the lock. Poisoned site-wide. | Restart + hotfix 2.3.1 |
| ~09:23 UTC | `me_universes_handler` (CO-191) panicked inside `Storage::list_subscribed_universes` (`.expect("list_subscribed_universes")` on `query_map`) while holding the lock. Same poison cascade. | Restart + hotfix 2.3.2 |

Both fixes were surgical (replace `.expect()` with match-and-log).
But `grep -nE '\.expect\("(prepare|query|list_|fetch_|select_)' co-web/src/storage/*.rs` shows ~30 more identical landmines across chat, invitations, notifications, push, and universe modules.

## Why `parking_lot::Mutex`

| Property | `std::sync::Mutex` | `parking_lot::Mutex` |
|---|---|---|
| Returns Result from `lock()` | Yes (`PoisonError`) | **No (direct guard)** |
| Poison on panic | Yes (cascades) | **No** |
| Fairness | Poor | Better |
| Smaller code | — | One fewer `.unwrap()` per call site |
| Already in tree? | Yes (used by tokio) | **No — needs adding** |

Switching means: a panic during one request kills that ONE request
(the lock guard drops as the stack unwinds, releasing the lock),
and the next request acquires a fresh lock. No cascade.

## Scope

Replace `Mutex<Storage>` in `co-web/src/server.rs` (`AppStateInner`)
and update every call site. The mechanical edit is small:

```rust
// Before
pub storage: std::sync::Mutex<crate::storage::Storage>,

// After
pub storage: parking_lot::Mutex<crate::storage::Storage>,
```

Then at each call site:

```rust
// Before — poison-aware:
let storage = state.storage.lock().unwrap();
let storage = state.storage.lock().unwrap_or_else(|p| p.into_inner());
let storage = state.storage.lock().map_err(|_| AppError::Internal("Storage lock failed".into()))?;

// After — direct:
let storage = state.storage.lock();
```

## Cargo.toml addition

```toml
parking_lot = "0.12"
```

## Audit grep + replace

The mechanical changes:

```bash
# 1. Find all current storage.lock() sites
rg 'state\.storage\.lock\(\)' co-web/src

# 2. Replace patterns (5 variations expected):
#    .lock().unwrap()                                              → .lock()
#    .lock().unwrap_or_else(|p| p.into_inner())                    → .lock()
#    .lock().map_err(|_| AppError::Internal("Storage lock failed".into()))?
#                                                                   → .lock()
#    .lock().ok()?                                                 → Some(.lock())
#    .lock()                                                       → .lock() (no change for parking_lot variant)
```

Estimate: ~60-80 call sites across the codebase. Most are mechanical;
a few may need re-thinking (places that used the `Result` for fall-back
logic — convert to optional/early-return).

## Acceptance

- [ ] `parking_lot = "0.12"` added to `co-web/Cargo.toml`.
- [ ] `AppStateInner.storage` is `parking_lot::Mutex<Storage>`.
- [ ] All `state.storage.lock().unwrap()` / `.unwrap_or_else()` /
      `.map_err()` sites collapse to plain `.lock()`.
- [ ] `cargo build -p co-web` passes.
- [ ] `cargo clippy -p co-web -- -D warnings` clean.
- [ ] `cargo test -p co-web --lib -- --test-threads=1` shows no
      regression vs current pass count (526 + new tests from
      CO-198/199/200/201/202).
- [ ] Deliberate panic test: temporarily insert `panic!("test")` in
      one storage method, hit the endpoint that triggers it from a
      browser, verify (a) that one request 500s, and (b) the very
      next request succeeds (no cascading "storage lock" errors).
      Then remove the panic.
- [ ] Smoke test on prod after deploy: log in via Google, view a
      board, send a chat message, open DMs inbox — none should 500.

## Same time, don't fix

This ticket explicitly DOES NOT remove the existing `.expect()` calls
in storage methods. They become merely "kills one request" instead of
"kills the whole app." A separate ticket can audit them later for
better error handling, but it's no longer urgent.

## Out of scope

- **`Mutex<AuthStore>`, `Mutex<RateLimiter>`, etc.** — also use
  `std::sync::Mutex` but lower blast radius. Worth a follow-up but
  not in this ticket.
- **Async `tokio::sync::Mutex`** — different concurrency model.
- **Removing all `.expect()` from storage** — separate cleanup ticket.
