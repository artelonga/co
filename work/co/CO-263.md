## As

A developer building CO

## I Need

CO-134's `StaticOnR2Adapter` (and the AWS SDK dependency it brings) gated behind a Cargo feature flag, off by default.

## So That

The default release binary doesn't carry ~3MB of unused AWS SDK code, and the Dockerfile's rust 1.94 requirement (driven by `aws-sdk-s3 → wasmtime-internal-*` deps) reverts to whatever the rest of the workspace actually needs. The R2 adapter is dormant infrastructure for the "revert to UAT" feature (post-CO-134) — until it's actually used, it shouldn't drag deps along.

## Context

CO-134 shipped `core/src/deploy/r2.rs` with a `StaticOnR2Adapter` that uses `aws-sdk-s3` to push static-site builds to Cloudflare R2. The adapter is wired into the `DeployerAdapter` trait registry but no production code calls it yet — it's groundwork for the future deploy.yaml-driven UAT revert flow (CO-N+).

Today (v2.23.0): every release build compiles + links the entire AWS SDK chain. Forced the Dockerfile to bump rust 1.90 → 1.94. Adds binary size and CI compile time for zero current benefit.

## Scope

### `core/Cargo.toml`

```toml
[features]
default = []
deploy-r2 = ["dep:aws-sdk-s3", "dep:aws-config"]

[dependencies]
aws-sdk-s3 = { version = "...", optional = true }
aws-config = { version = "...", optional = true }
```

### `core/src/deploy/mod.rs`

```rust
#[cfg(feature = "deploy-r2")]
pub mod r2;

// Optional: when feature is OFF, register a no-op stub
#[cfg(not(feature = "deploy-r2"))]
pub mod r2 {
    pub struct StaticOnR2Adapter;
    impl crate::deploy::DeployerAdapter for StaticOnR2Adapter {
        fn name(&self) -> &'static str { "static-on-r2 (disabled — build with --features deploy-r2)" }
        // ... stubs that return "feature disabled" errors
    }
}
```

### `co-web/Cargo.toml`

Stay unaffected (it doesn't depend on R2 today). Confirmed by `cargo tree -p co-web | grep aws` returning nothing once the gate is in place.

### Optional: Dockerfile

If the feature is OFF and there's no other rust ≥1.91 dep, revert Dockerfile to `rust:1.90-slim-trixie` (smaller image, faster build). If there ARE other ≥1.91 deps, leave as-is — we already paid the cost.

## Acceptance

- `cargo build` (no features) succeeds with no AWS SDK in `target/release/deps/`
- `cargo build --features deploy-r2` succeeds and includes AWS SDK
- `cargo tree -p core -e features` shows AWS SDK only when feature is enabled
- `co-web` still builds and runs without the feature
- Production Dockerfile uses default features → no AWS SDK in deployed binary
- New entry in MODULES.md documenting how to enable R2 deployer for a future deployment

## Blast radius

- ~30 LOC across `core/Cargo.toml` + `core/src/deploy/mod.rs` + `core/src/deploy/r2.rs` (the cfg attributes)
- 1 line in MODULES.md
- Zero behavior change in current default-features build

## Why now

CO-134's R2 adapter is dormant infrastructure. Until the deploy.yaml → R2 push pipeline (CO-N+) is actually being used in CI/CD, the AWS SDK is dead weight. Feature gates it cleanly so we can keep iterating on the deploy story without forcing the toolchain bump on everyone.
