## Failure Mode at 500 VUs

At 500 concurrent virtual users, the `/api/v1/universes/mbya/entries?type=lexeme` endpoint
degrades catastrophically:

- p50 entry-list latency: **30 seconds**
- p95 entry-list latency: **50 seconds** (k6 scenario timeout = 60s)
- 89% of entry-list requests failed (HTTP 503 / k6 timeout)
- Tags endpoint similarly degraded (p50: 20s at 500 VU vs 84ms at 50 VU)

**Root cause:** `entries` table filter on `entry_type = 'lexeme'` (or equivalent
frontmatter-derived column) performs a full table scan over 4,608 rows at each request.
Under 500 concurrent readers hitting SQLite on a shared-cpu-1x machine, the read
path serializes and each scan takes O(N × lock-wait).

**Specific regression confirmed:**

> Without an index on `entries.entry_type`, listing entries by type is O(N) per query.
> At 50 VUs the single-machine SQLite WAL mode can service concurrent reads; at 500 VUs
> the read queue depth exceeds WAL concurrency limits and p95 explodes from 608 ms → 50 s.
>
> Adding `CREATE INDEX idx_entries_type ON entries(universe_key, entry_type);` would
> collapse the scan to a B-tree seek and is expected to keep p95 < 500 ms at 500 VU.

---

## Recommended Actions Before v1.0 Public Launch

1. **Add `entries.entry_type` index** — expected to fix the 500-VU collapse.
2. **Add `entries.frontmatter_json` GIN-equivalent index** (SQLite JSON extract index)
   for `lema`, `classe`, and `glosa_pt` lookups — needed before any dictionary search feature.
3. **Bump UAT to `shared-cpu-2x` (512 MB)** before the next 500-VU run — the current
   machine is too small to distinguish "needs index" from "needs hardware."
4. **200 VUs is sustainable on `shared-cpu-1x`** with the entry_type index applied;
   recommend `shared-cpu-2x` for public launch to headroom.
