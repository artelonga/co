## Scenario: 01-anon-browse

Anonymous visitor flow — 12 HTTP requests per iteration (static assets + board API + timeline).

| VUs | Duration | p50   | p95    | p99    | Errors | Req/s  |
|-----|----------|-------|--------|--------|--------|--------|
| 50  | 1m       | 97ms  | 618ms  | 1.12s  | 0.0%   | 36.2   |
| 100 | 1m       | 111ms | 932ms  | 9.51s  | 1.0%   | 62.6   |
| 500 | 30s      | 173ms | 2.59s  | 5.95s  | 0.0%   | 251.8  |

**Notes:**
- 50 VUs: clean baseline. Static assets fast (20-50ms). Board API (universe, projects, tasks) avg 160ms. Timeline API avg 425ms.
- 100 VUs: 1% error rate appears on board API endpoints (`/api/v1/universes/template`, `/config`, `/theme.css`, `/projects`, tasks). Root cause: SQLite read contention returning 500s transiently.
- 500 VUs: 0% errors but p95 rises to 2.6s. Board API avg load climbs to 5.7s per iteration. The server queues requests (no drops) but p99=5.95s makes the board feel stuck. Timeline API remains fast (avg 746ms, likely cached by CDN).

**Notes:**
- 50 VUs: excellent. Board reads fast (30ms median). Write cycle (create→update→delete) p95=295ms.

- 500 VUs: 0% errors, p95=1.57s. SQLite write serialisation holds — LiteFS queues writes rather than rejecting them. Board read path (universes, projects) handles 500 VUs acceptably.

## Scenario: 03-vault-write

API token vault writes — list + PUT + DELETE per iteration.

| VUs | Duration | p50  | p95   | p99   | Errors | Req/s  |
|-----|----------|------|-------|-------|--------|--------|
| 50  | 1m       | 31ms | 155ms | 182ms | 97.5%  | 38.5   |
| 100 | 1m       | 33ms | 160ms | ~185ms| 97.6%  | 59.8   |
| 500 | 30s      | 56ms | 966ms | ~1.1s | 99.5%  | 330.8  |

**Notes:**
- All VU levels: vault write path is rate-limited by the server. Requests exceeding ~15 concurrent writes receive `HTTP 429 Too Many Requests` ("Muitas requisições"). The latency figures above represent mainly 429 responses, not actual writes. Only ~15 VUs complete a successful write in the first burst; subsequent iterations are rate-limited.
- The rate limiter appears to allow bursts of ~15 concurrent writes before enforcing back-pressure.
- List (`GET /vault/`) succeeds at low concurrency but is also affected by the rate limiter at 50+ VUs.
- Delete (`DELETE /vault/*path`) is covered by the same rate limit.

## Failure Mode at 500 VUs — Detailed Analysis

### anon-browse (500 VUs, 30s)

**What failed:** Latency, not availability. Board API endpoints queued behind SQLite reads.  
**Symptom:** p95=2.6s (vs. 618ms at 50 VUs). Board iteration avg load time: 5.7s (vs. 1.6s at 50 VUs). Timeline API remained fast.  
**Exact bottleneck:** `/api/v1/universes/template` and `/api/projects/CO/tasks` endpoints are SQLite reads with no caching. At 500 VUs they saturate the single SQLite connection pool.  
**No errors, no OOM.** Fly machine did not restart. LiteFS held its lease.

### board (during pure write-only stress test, pre-baseline)

**What failed:** SQLite entered read-only mode.  
**Symptom:** All write operations returned `HTTP 500 — "attempt to write a readonly database"`. Reads still worked.  
**Root cause:** Under sustained write-only load at 50 VUs (no reads mixed in), the LiteFS Consul lease was not renewed fast enough. LiteFS dropped the primary role, making the database read-only. A machine restart recovered it.  
**Important:** This did NOT reproduce during the mixed read+write baseline (02-board at 500 VUs). It only triggered during the write-only stress test.  
**Health check blind spot:** `GET /api/health/deep` returned `{"status":"ok","db":"ok"}` even while writes were failing — false positive.

### vault-write (50+ VUs)

**What failed:** Server-side rate limiter.  
**Symptom:** `HTTP 429 Too Many Requests` on vault PUT and DELETE immediately. Error rate 97-99%.  
**Rate limit:** ~15 concurrent vault writes allowed. Additional requests return 429 instantly (25ms).  
**Impact:** The vault API is not suitable for high-concurrency write workloads without client-side throttling. Single-user or low-concurrency use (Obsidian plugin, CLI sync) is unaffected.

## Recommendation Before Public v1.0 Launch

### Hardware

The current `shared-cpu-1x:256MB` machine can sustain approximately **50 concurrent anonymous users** without errors. At 100 VUs, transient SQLite read errors appear (1%). At 500 VUs, board API latency becomes unacceptable (p95=2.6s) for a responsive board UX.

**Recommendation:** Upgrade to `shared-cpu-2x:512MB` before opening to the public. This doubles the CPU time share and reduces SQLite contention from concurrent reads.

**Estimated capacity after upgrade:** ~150-200 concurrent anonymous users with p95 < 1s. Validate with a post-upgrade re-run of `01-anon-browse` at 150 VUs.

### Rate Limiter Tuning

The vault write rate limiter (429 at 15 concurrent) is correct behavior for the write path. Before publishing Vault API docs, document the rate limit and advise clients to use exponential backoff. Add a `Retry-After` header to 429 responses.

### LiteFS Lease Renewal

The write-only stress test revealed that LiteFS can lose its primary lease under sustained write-only load. Ensure `lease.ttl` in the Consul config is tuned to tolerate burst write scenarios. Consider adding a write-path health check that performs a test write (not just a `PRAGMA integrity_check`).

### Alarm Thresholds (suggested for CI/monitoring)

| Metric | Alarm at |
|--------|----------|
| `http_req_duration p(95)` | > 1500ms at ≤ 100 VUs |
| `http_req_failed rate` | > 1% at ≤ 100 VUs |
| Board write latency p95 | > 2000ms at ≤ 100 VUs |
| LiteFS primary role lost | Any 500 on write path |
